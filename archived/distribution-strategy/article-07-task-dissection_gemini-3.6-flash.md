# 一个 Agent 任务的完整解剖——从第一轮到最终交付

> **TL;DR**：一个复杂的 Coding Agent 任务从发起请求到最终交付代码，中间到底经历了什么？本文将使用 VMR（Virtual Model Router）的 `vmr story` 功能，像外科手术一样，纵向解剖一次包含 **初始任务理解、工具链调用、中途上下文压缩（Compaction）、故障 Failover 以及最终代码交付** 在内的完整 Agent 执行全流程。

---

## 0. 为什么我们需要对 Agent 任务做“解剖”？

大语言模型的推理过程是非线性的。一个由自然语言驱动的 Agent 任务，其执行轨迹通常比传统的软件程序更加不可预测：

```
[用户初始 Prompt] ➔ [理解任务] ➔ [搜索代码] ➔ [创建文件] ➔ [触发 Compaction 压缩] ➔ [编译报错] ➔ [重试修 Bug] ➔ [交付]
```

在普通的控制台界面里，这只是成千上万行滚动的文本。

但如果我们要优化 Agent 的 Prompt、评估工具链的效率，或者诊断中途出现的逻辑偏差，我们就必须像解剖医学标本一样，把任务在时间轴上切开，去观察**每一次状态演进（Step）的微观细节**。

VMR 的 `vmr story` 子命令就是专门为此而生的。它消费本地的审计 JSONL 文件，将死板的 API 调用重构成一份包含完整因果链条的**任务叙事（Task Story）**。

---

## 1. 第一阶段：初始任务理解与动作规划 (Step 1 - 3)

我们以一个真实的工程任务为例：“为项目增加 Prometheus 指标暴露接口 `/metrics`，并为 API 耗时打上直方图（Histogram）统计”。

使用 `vmr story` 展开最初的 3 轮交互：

```markdown
================================================================================
Step 1/18 | [任务发起] 客户端: OpenClaw ➔ 上游: DeepSeek-V3
================================================================================
[User Prompt]: "为项目增加 /metrics 端点，支持 API 耗时直方图..."
[模型推理 (Thinking)]:
  > 1. 需要先检查项目当前使用的 HTTP 路由库 (Gin / Chi / Standard log)；
  > 2. 检查现有的中间件结构；
  > 3. 寻找依赖管理文件 `go.mod` 确认是否已引入 prometheus/client_golang。
[工具调用声明 (Tool Calls)]:
  └─ ToolCall #1: fs_read(path: "go.mod")
  └─ ToolCall #2: directory_list(path: "internal/server")

--------------------------------------------------------------------------------
Step 2/18 | [工具回执与分析] 耗时: 1,120ms | Tokens: 4,120 ➔ 5,800
--------------------------------------------------------------------------------
[Tool Result #1]: `go.mod` 中未找到 prometheus 依赖。
[Tool Result #2]: 发现 `internal/server/server.go` 与 `internal/server/middleware.go`。
[模型决策]: 决定先修改 `go.mod` 引入依赖，然后在 `middleware.go` 中植入耗时拦截器。
```

### 💡 专家视角解析：
在前两轮中，`vmr story` 清晰展示了 **Prompt ➔ Thinking ➔ Tool Call ➔ Tool Result ➔ 次轮决策** 的完整闭环。
这种闭环断言（F9 不变量）确保了工具调用的入参和返回值在视觉上高度绑定，省去了手动核对 JSON `call_id` 的痛苦。

## 2. 第二阶段：上下文压缩与实体丢失危机 (Step 8)

随着任务推进到第 8 轮，Agent 已经连续读取了 5 个源文件，累积的上下文达到了 85,000 Tokens。

此时，系统触发了长会话中不可避免的操作——**上下文压缩（Compaction）**。

在 `vmr story` 的解剖下，我们可以清晰看到这一关键时刻：

```markdown
================================================================================
Step 8/18 | [历史压缩 Compaction 触发 ⚠️]
================================================================================
[上下文变化]: 消息数 32 ➔ 8 | Token 占用: 85,000 ➔ 14,200 (压缩率 83.3%)
[前缀保留 (LeadSys)]: 保留了初始系统 Prompt 与全局工具 Schema 定义
[衍生摘要 (Derived Summary)]:
  > "用户要求增加 /metrics。之前已在 go.mod 中添加依赖，并创建了 metrics.go..."

⚠️ [VMR 实体损失摘要 (Entity Loss Detection)]:
  - 丢失路径实体: `internal/server/middleware.go` (未在摘要中提及)
  - 丢失变量实体: `MetricsRegistry` (全局注册表指针)
```

### 💡 专家视角解析：
**这是整个任务最危险的时刻！**
VMR 的 `ctxgraph` 算法通过对比压缩前后的消息哈希向量，自动识别出了这次编辑属于 `Contract`（历史截断）。

更重要的是，VMR 的实体提取器在解剖视图中发出了**警告**：摘要虽然总结了主要进度，但丢掉了 `MetricsRegistry` 这个全局变量名！

在接下来的第 9 轮中，Agent果然因为“失忆”，在新建的 Handler 中重新声明了一个同名的 `MetricsRegistry`，引发了后续的编译冲突。

## 3. 第三阶段：错误处理与故障自愈 (Step 12)

在第 12 轮，Agent 尝试使用 `go test` 工具运行单元测试。

此时发生了突发的上游 API 故障：

```markdown
================================================================================
Step 12/18 | [供应商 Failover] 耗时: 2,450ms
================================================================================
[Attempt 1]: upstream `deepseek-v3` ➔ HTTP 429 Too Many Requests (限流)
             └─ VMR 判定: ErrRateLimit (尊重 Retry-After: 15s)
             └─ 动作: 自动将该端点隔离，零失败暴露给客户端

[Attempt 2]: upstream `minimax-m2` ➔ HTTP 200 OK (转发成功)
             └─ 响应头注入: X-VMR-Failover: deepseek-v3:429
             └─ 归一化处理: 自动清洗 MiniMax 输出前缀中的 `<think>` 草稿块
```

### 💡 专家视角解析：
对于客户端 Agent 来说，它完全不知道第 12 轮背后发生了一次跨供应商的级联拯救。在解剖视图中，我们可以清晰看到 VMR 如何在底层默默挡下了 429 报错，并安全清洗了 MiniMax 的思考草稿，保证了上层 Agent 的正常运行。

## 4. 第四阶段：收敛与最终交付 (Step 18)

到了第 18 轮，Agent 完成了测试修复并提交了最终成果：

```markdown
================================================================================
Step 18/18 | [任务交付完成] 结果: 成功 | 累计耗时: 2分15秒 | 累计成本: $0.14
================================================================================
[交付物检查]:
  1. `go.mod`: 已新增 `github.com/prometheus/client_golang` 依赖
  2. `internal/server/metrics.go`: 新增了 /metrics 路由 Handler
  3. `internal/server/middleware_test.go`: 单元测试 100% 通过

[全任务统计]:
  - 交互轮次: 18 轮
  - 工具调用总数: 14 次 (成功率 100%)
  - 重复动作率: 5.5% (仅在第 9 轮因失忆重复读取了 1 次文件)
```

## 5. 总结：解剖带来的改进启发

通过对这次 Agent 任务的完整解剖，我们不仅看清了任务的全貌，更获得了可落地的优化指导：

1. **改进 Compaction 提示词**：要求 Agent 在做历史总结时，必须强制保留带全路径的文件名和全局变量名，防止第 8 轮的“失忆”再次发生；
2. **验证路由健壮性**：证实了 VMR 的分级 Failover 在应对夜间 429 限流时的关键保护作用；
3. **建立工程自信**：从盲目的“祈祷 Agent 能跑对”，变成了有数据、有图谱的工程化掌控。
