# VMR 渠道与分发战略详细方案

> 本文档是 `vmr_future_strategy_v2_sonnet-5.md` §5.3 的完整展开，覆盖渠道分析、内容策略、执行节奏、参考案例、风险与度量。
> 基线：VMR 当前 2 star，0 issue，0 外部贡献者。产品侧已过关，瓶颈 100% 在分发侧。

---

## 0. 执行摘要

**一句话**：VMR 的目标用户高度集中在中文开发者社区，但旧的分发策略只有 HN 和 Reddit——这是错配。本文档定义一套以中文社区为第一优先级的渠道与内容策略，目标是在 D1（预编译二进制发布）完成后 3 个月内，从 2 star 走到 50+ star 和第一个真实外部 issue。

**核心原则**：
- 中文优先，英文跟进——受众密度决定顺序
- 产品叙事从"路由器"转向"黑匣子"——差异化必须落在对手结构性做不到的地方
- 内容驱动分发——技术文章比功能公告传播力强一个数量级
- 分发动作顺序不能乱——D1（二进制）必须先完成，否则流量窗口浪费

## 1. 为什么中文市场是最高优先级

### 1.1 产品基因的天然匹配

VMR 不是"一个通用 LLM 网关"。它的每一项设计选择都在指向一个非常具体的用户画像：

| VMR 的设计选择 | 对应的用户场景 |
|---|---|
| 配置样例里 MiniMax / DeepSeek 排最前面 | 中国用户用量产模型做日常 Coding |
| 专门为 MiniMax 写了 `<think>` 标签剥离 | 只有中国用户会遇到这个 quirk——海外模型没这东西 |
| `soft_block_detected` 检测（2xx 但内容为空） | 国产厂商特有的软屏蔽——OpenAI/Anthropic 没有这种行为 |
| `role_map: {developer: system}` | DashScope/千问拒绝 `developer` role——又是国产网关特有的 |
| 国内 provider 默认 `proxy: false`，海外 provider `proxy: true` | 中国用户国内直连、海外走代理的默认网络拓扑 |
| 审计报告里 `vmr-report.zh.md` 的输出 | 报告面向中文用户可读 |
| 167KB 设计文档为中文 | 架构决策面向中文读者 |
| README.zh.md / UserGuide.zh.md 为完整翻译 | 中英双语一等公民 |

这些不是巧合，是 VMR **实际在使用场景里长出来的**。作者本人就在用国产模型跑 Claude Code/OpenClaw，所以才会有 MiniMax 的 thinking 剥离、才会有软屏蔽检测。VMR 最独特的 5 项护城河能力里，至少有 2 项（quirk 修复、软屏蔽检测）是完全为中国模型生态量身定做的。

### 1.2 受众密度对比

同一篇"Claude Code 接国产模型"场景的内容：

| 渠道 | 潜在受众密度 | 说明 |
|---|---|---|
| linux.do | 极高 | 整个站就是一个巨大的"Claude Code + 国产中转"讨论区 |
| V2EX / 程序员 | 高 | 凡是"Claude Code 替代方案"相关帖子，回复数和收藏数都远高于均值 |
| Reddit r/LocalLLaMA | 中低 | 有相关讨论，但以英文生态为主（OpenRouter + Ollama + vLLM） |
| Hacker News | 低 | "Claude Code 接 DeepSeek"这个场景对 HN 读者太 niche |
| 掘金 | 高 | 长文形式，适合深度技术内容 |
| GitHub Trending | 中 | 需要前面几项先做起来——它是结果不是手段 |

**结论**：同样的时间投入，发一篇中文文章到 linux.do/V2EX 的触达效率，是发一篇英文文章到 HN/Reddit 的 5–10 倍。这不是"中文社区比英文社区好"，是"VMR 的目标用户在中文社区的密度远高于英文社区"。

### 1.3 参考案例：类似项目在中文社区的传播路径

以下是几个与 VMR 形态/受众相似的项目在中文社区的传播案例：

**gpt-load（6.3k star, Go, 单二进制）**
- 首发 V2EX → 被转到 linux.do → GitHub Trending 中文圈上榜
- 关键内容：一篇"我用 Go 写了个多 Key 轮询代理"的帖子，附带配置截图
- 启示：单二进制 Go 工具在 V2EX 有固定的欣赏人群，"零依赖"是加分项

**new-api（43.6k star, TS）**
- 在 one-api 停更后接手社区，首发 linux.do
- 关键内容：教程式文章——"三步搭建你自己的 API 中转站"
- 启示：linux.do 的用户对"中转/代理/路由"类工具的接受度和理解力极高

**claude-code-router（36.2k star, JS）**
- 最早在 V2EX 和 linux.do 被自然讨论——不是作者主动发的
- 传播动力来自"终于能用 DeepSeek 跑 Claude Code 了"这个痛点
- 启示：痛点叙事比功能列表传播力强得多

**CLIProxyAPI（45.2k star, Go）**
- Go 语言、单二进制——证明了这种形态在中文社区完全跑得通
- 启示：VMR 的技术选型本身就是传播资产（"一个文件搞定"在中文社区是有效的卖点）

## 2. 渠道详细画像与发布策略

### 2.1 中文渠道

#### linux.do（优先级：最高 ⭐⭐⭐）

**用户画像**：深度 AI 工具用户，大量 Claude Code / Cursor / Windsurf 用户，对中转/代理/路由非常熟悉。技术讨论质量高，用户之间互相推荐工具的习惯很强。

**内容偏好**：
- 实操教程类（"一步步教你 X"）反响最好
- 对比评测类（"X vs Y 实测"）其次
- 纯功能介绍类效果最差

**发布策略**：
- 第一帖应该是**实操教程**，不是功能公告
- 标题格式：`[项目分享]` 或 `[工具推荐]` 前缀
- 正文必须有：配置截图、跑起来的终端录屏或截图、和竞品的对比表
- 在评论区主动回答问题——linux.do 的帖子生命周期约 2–3 天，头 24 小时的互动密度决定能不能上首页

**注意**：linux.do 用户对"自卖自夸"敏感。写"我做了个工具"没问题，写"最好的 XX 解决方案"会触发反弹。正确姿态是"我在用这个解决自己的问题，觉得可能对你们也有用"。

**参考成功帖子模式**：
- "Claude Code 用 DeepSeek 跑了三天，我总结了这 5 个坑"（痛点 → 方案）
- "给 Claude Code 装了个黑匣子，意外发现代理商偷偷换了我的模型"（故事 → 工具）

---

#### V2EX（优先级：高 ⭐⭐⭐）

**用户画像**：全栈程序员为主，Go 语言有固定粉丝群。对"单二进制""零依赖""自建工具"有天然好感。技术审美偏实用主义——不喜欢过度包装，但尊重工程深度。

**内容偏好**：
- 技术实现细节类（"我是怎么做 X 的"）反响好
- 开源项目首发帖有固定的关注度（尤其是带 Go 标签的）
- 对比帖（"为什么我不用 LiteLLM 而自己写了一个"）容易引发讨论

**发布策略**：
- 发在**程序员**节点，标签选 `Go` 和 `OpenAI`
- 标题直接、不标题党：如"VMR：一个为 AI Agent 设计的透明 LLM 路由器（Go，单二进制）"
- 正文突出技术选型理由和工程数据（压测结果、测试覆盖率、架构图）
- V2EX 帖子生命周期约 1–2 天，上首页的关键是前 2 小时的回复数

**注意**：V2EX 对"这是我的 GitHub 项目"有固定的友善度，但前提是内容有技术深度。如果正文只是一个 README 链接 + 一句话，会被点踩。至少要在帖子里放：架构图、为什么做的动机、和现有方案的区别。

---

#### 掘金（优先级：中高 ⭐⭐½）

**用户画像**：前端/全栈开发者为主，也有一定比例的后端和 AI 方向。内容消费习惯偏向长文深度阅读。掘金的推荐算法会给深度技术文章更多曝光。

**内容偏好**：
- 深度技术长文（>3000 字）在掘金表现好
- "源码解析""架构设计""性能优化"类文章天然高分
- 叙事型技术文章（"我是怎么一步步解决 XX 问题的"）比教程型更受欢迎

**发布策略**：
- 适合发的是"给 Claude Code 装个黑匣子"这篇文章——它既有故事性又有技术深度
- 标签：`Go` `AI` `开源` `架构`
- 掘金的文章生命周期长（7–14 天），不急于短期互动数据

---

#### 少数派（优先级：中 ⭐⭐）

**用户画像**：数字工具深度用户，覆盖面比纯程序员社区广（产品经理、设计师、独立开发者都会看）。付费意愿强，但必须是"这个工具真的能省我的时间"。

**内容偏好**：
- "效率提升"叙事——"我用这个工具每周省了 X 小时"
- 软件评测/工具推荐类文章在少数派有固定读者群
- 文章质量要求高（少数派有编辑审核），不适合轻量内容

**发布策略**：
- 适合发的内容：VMR 的"agent 无人值守"叙事——"我的 Agent 在凌晨 3 点挂了，VMR 帮它切到了备用供应商"
- 形式：不是功能介绍，是**使用体验 + 效率提升**
- 建议在 V2EX/linux.do 获得一定反馈后再投少数派——有外部证据支撑的文章通过概率更高

---

#### 知乎 / 微信公众号（优先级：中 ⭐⭐）

**用户画像**：覆盖面广但密度低。知乎的 AI 话题下有一定数量的从业者，微信公号需要已有粉丝基础。

**发布策略**：
- 作为二次分发渠道——把已经在 linux.do/V2EX/掘金 验证过的内容搬过去
- 知乎回答"Claude Code 有哪些好用的配套工具？""如何在国内稳定使用 Claude Code？"之类的问题，在回答中自然引入 VMR
- 微信公号如果没有已有粉丝，纯新号发一篇文章的效果有限

---

#### GitHub Trending 中文圈（优先级：中 ⭐⭐）

**用户画像**：GitHub 中文用户，通过 Trending 页面发现项目。**这不是一个可以直接操作的渠道**——它是前面所有渠道做起来后的自然结果。

**触发条件**：
- 单日 star 增量 >20–30 时开始出现在 Trending
- 需要项目有中文 README（已有 ✓）
- 需要项目有明确的描述（已有 ✓）
- 发布 Release 带二进制会提升被发现的概率（尚未完成，属 D1）

---

### 2.2 英文渠道

#### Hacker News — Show HN（优先级：中 ⭐⭐）

**用户画像**：全球技术创业者/工程师，对"这个工具解决了什么真实问题"最敏感。Show HN 规则要求项目必须是可以试用/体验的——**必须在 D1 完成后才能发**。

**内容偏好**：
- "我遇到了 X 问题，现有工具解决不了，所以我做了 Y"——这个叙事在 Show HN 表现最好
- 不要列功能列表——讲一个具体的使用场景
- 在第一条评论里补充技术细节和设计决策

**标题建议**："Show HN: VMR — a flight recorder for AI agents (single Go binary, no translation)"

**风险**：
- Show HN 运气成分大，可能在 10 分钟内上首页也可能沉掉
- 如果 D1 的二进制发布没做好（让读者必须装 Go 才能跑），负面评论会集中在"你管这叫 Show HN？"上
- 同一个项目不要发两次 Show HN——一次没上就等几个月后有了重大更新再说

---

#### Reddit r/LocalLLaMA（优先级：中低 ⭐½）

**用户画像**：本地模型部署 + 代理/路由工具的硬核用户。对"不翻译""字节级透传"这个概念比中文社区接受度高得多。

**发布策略**：
- 不直接发"这是我的项目"——发一篇技术深度帖，比如"为什么翻译型网关对你的 Agent 请求有潜在风险"
- 在讨论中自然引出 VMR 作为替代方案
- r/LocalLLaMA 用户对 Go 单二进制的偏好不如中文社区明显

---

#### Reddit r/ClaudeAI（优先级：中低 ⭐½）

**用户画像**：Claude Code 用户，其中相当一部分在寻找"怎么用别的模型跑 Claude Code"的方案。

**发布策略**：
- 回答"Can I use Claude Code with DeepSeek?"之类的问题
- 在回复中自然提到 VMR 作为方案之一
- 不要只发链接——Reddit 会把纯链接帖压低

---

#### Lobsters（优先级：低 ⭐）

**用户画像**：硬核程序员社区，对 Go 工具和系统工具有天然好感。

**发布策略**：和 HN 类似——一个"我做了什么以及为什么"的帖子。Lobsters 流量远小于 HN，但用户质量高（能给出有深度的技术反馈）。

## 3. 内容策略

### 3.1 核心叙事

**旧叙事（不可用）**："VMR 是一个字节级透传的 LLM 路由器，支持自动故障切换和成本核算。"

为什么不可用：
- "字节级透传"是实现属性，不是用户收益
- "自动故障切换"已被 claude-code-router 追平（§3.2）
- "成本核算"已被 claude-code-router 追平（§3.2）
- 这个叙事让 VMR 在 2 star 的身份下和 36k star 的对手正面比功能列表——必输

**新叙事**："VMR 是你 Agent 运行的黑匣子——那次凌晨 3 点的失败，你能翻出上游到底收发了什么原始字节，还能把那一刻原样重放一遍。"

为什么有效：
- 落在对手结构性做不到的地方（两层完整字节记录 + agent 语义分组 + 可回放）
- 讲的是具体场景而非抽象能力
- "黑匣子"的类比一讲就懂，不需要解释"字节保真"是什么意思

### 3.2 文章选题矩阵

按"传播力 × 技术深度"两个维度组织所有选题：

```
          传播力
            ▲
            │  ② 国产模型软屏蔽       ① 给 Claude Code 装个黑匣子
            │  （高传播，中技术）       （高传播，高技术）
            │
            │  ④ Claude Code 半夜挂了    ③ byte-faithful 深度解析
            │  （中传播，低技术）         （低传播，高技术）
            └──────────────────────────▶ 技术深度
```

**① 给 Claude Code 装个黑匣子（首发文章——最高优先级）**

- 平台：linux.do + V2EX 首发，掘金/少数派后续
- 叙事：一个 agent 跑了一夜的故事 → 翻日志发现某个请求上游返回了空内容 → vmr report 帮定位 → 用 vmr replay 复现
- 配图：`vmr report` 的会话分组视图 + 单次请求的两层记录展开
- 差异化卖点：别人只能告诉你"这次请求失败了"，VMR 能告诉你"上游到底收到了什么、返回了什么"

**② 国产模型返回 2xx 但内容是空的（第二篇）**

- 平台：linux.do 首发
- 叙事：这是国产厂商特有的"软屏蔽"行为——HTTP 200、但 body 被替换或清空 → 为什么危险（agent 不会报错，基于空回复继续跑）→ VMR 怎么检测和打标
- 配图：一次软屏蔽的审计记录截图，标注 `soft_block_detected` 标记
- 差异化卖点：没有任何其他工具（包括 claude-code-router）能检测这个，因为它们都在忙着翻译请求，根本注意不到响应内容被替换了

**③ byte-faithful 深度解析（英文圈首发备选）**

- 平台：HN / Lobsters / Reddit
- 叙事：翻译型网关到底丢掉了什么——从一次真实的新参数上线案例说起 → 为什么"先翻译再还原"会静默丢失字段 → byte-faithful 的正确性论证
- 差异化卖点：这不是"VMR 更快更小"，是"VMR 从根本上避免了翻译型网关无法避免的一整类问题"

**④ Claude Code 半夜挂了怎么办（轻量入门帖）**

- 平台：V2EX / 掘金
- 叙事：Claude Code 跑长任务时供应商挂了 → 手动重跑的代价 → VMR 的按错误类分级的自动 failover
- 差异化卖点：这个不是独有的（CCR 也有），但可以作为一个低门槛的入门帖吸引初始用户

### 3.3 内容发布节奏

```
Week 1 (D1 完成后): ① 中文版 → linux.do + V2EX
Week 1–2:          ② 中文版 → linux.do
Week 2:            ① 英文版 → HN Show HN（如果 D1 完成）
Week 2–3:          ③ 英文版 → Reddit（如果 Show HN 效果不佳）
Week 3–4:          ① 修改版 → 掘金（根据 V2EX/linux.do 的反馈迭代后重发）
```

**不要在 D1 完成前发帖**——每个帖子带来的流量窗口只有几小时到几天，如果落地页要求读者先装 Go 再编译，这个窗口就浪费了。

## 4. 渠道以外：被低估的分发手段

### 4.1 进入 Agent 工具的 Setup 文档（D8）

这是获客效率最高的单一路径——一个 Claude Code 用户在配置其他模型时，在文档里看到"你也可以用 VMR 做透明路由"，点进来就是一个高度匹配的用户。

具体操作：
1. 在 Claude Code 的社区 wiki / awesome-claude-code 列表里加上 VMR
2. 在 OpenClaw 的文档里提"可与 VMR 配合做透明 failover"
3. 在 Cline / Roo Code 的 Reddit/Discord 里自然提及（不是刷屏，是回答相关问题）

**这一项 VMR 单方面完不成**——它需要外部项目愿意收录。但它应该作为一个持续的背景任务来推进。

### 4.2 GitHub 搜索优化

目标：当用户搜索 `claude code router` `llm failover` `claude code deepseek proxy` 等关键词时，VMR 出现在搜索结果里。

当前状态：
- 仓库 description 只有 "The transparent LLM router for AI agents"（已设置 ✓）
- README 有 keyword 注释（已设置 ✓）
- Topics 未设置（需添加）

建议添加的 GitHub Topics：`llm-router` `ai-agent` `failover` `claude-code` `openai-proxy` `anthropic` `go` `single-binary` `deepseek` `minimax`

### 4.3 在竞品 Issue 区自然出现

不在对手仓库里恶意推广，而是**当用户在对手 Issue 区问"VMR 和 X 有什么区别"或"X 能帮我记录完整请求 body 吗"时**，有一个客观的技术解释回复。

这个操作需要：
1. 监控相关 Issue（可以靠 GitHub 通知）
2. 回复必须是技术实质内容，不能是广告
3. 建议使用比较中立的语气："我是 VMR 的作者，这两个工具的设计哲学不同——X 做的是翻译，VMR 做的是透传加两层审计。如果你需要的是什么什么，X 更合适；如果你需要的是什么什么，VMR 可以试试"

## 5. 分发的先行条件

以下条件必须在任何分发动作之前完成（即 §5.2 的 D1–D4）：

## 7. 中文渠道特有注意事项

### 7.1 不要做的事

- **不要在帖子标题或开篇写"我们"**——VMR 是个人项目，用"我们"会让人觉得在假装有团队。用"我"
- **不要吹牛**——中文技术社区对过度营销极度敏感。"最好的""最强的""唯一"在英文社区可能被容忍，在中文社区会触发直接反弹
- **不要只发链接不带内容**——纯链接帖在任何社区都不受欢迎，在中文社区尤甚。至少要在帖子里放完整的背景、截图、使用说明
- **不要刷帖**——同一个内容发 linux.do 和 V2EX 是可以的（用户重叠度不高），但在同一个站内重复发或多账号操作会被封

### 7.2 建议做的事

- **在 README 里放中文用户的使用案例**——哪怕只有一个（作者自己的），也能让中文读者觉得"这个工具和我的场景一样"
- **配置样例里的模型名用中文用户熟悉的**——目前已经有 MiniMax/DeepSeek/GLM（✓），可以再加 Kimi、Qwen、火山引擎
- **回复每一条评论**——在 star 数还没过百的阶段，每一条来自外部的评论都是珍贵的。认真回复本身就是传播（linux.do 帖子被回复会 bump 到首页）
- **如果有人在社区里问了关于 VMR 的问题但你不知道——去回答**。用 GitHub 的 mention 搜索或 Google `site:linux.do vmr` 定期检索

### 7.3 中文社区对"国产 AI 工具"的特殊心态

需要意识到的一个微妙点：VMR 本身是 MIT 开源、单机部署，与任何厂商没有商业绑定。但由于它专门修复国产厂商 quirk、配置样例以国产模型为主，可能会被部分读者误读为"为某个国产厂商站台"。

对策：在文章中自然提及"支持的厂商"时，保持品类覆盖（OpenRouter、DeepSeek、MiniMax、GLM 都列），避免只提某一家。强调"vmr 是个人工具，和任何厂商没有关系"。
