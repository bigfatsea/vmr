# Changelog

All notable changes to this project are documented here, in
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. This project
tags releases `vX.Y` rather than strict semver (see `internal/buildinfo`'s
doc comment for why there is no other version file to keep in sync) — the
version headers below match the tag with the leading `v` dropped.

`release.yml`'s release job extracts the section matching the pushed tag and
uses it verbatim as the GitHub Release body — GitHub's own auto-generated
notes (bare PR titles) are unreadable on this repo's mostly direct-to-main
workflow, so every tag needs a matching section here before it's pushed, or
the release job fails on purpose rather than publishing something empty.
See this file's row in `CLAUDE.md`'s Conventions section for the write-time
process (write into `[Unreleased]` as you go, retitle it when cutting a tag).

## [Unreleased]
### Added
- `vmr analyze [audit.jsonl]` — the single analysis entry point: one flag set (the union of `vmr report`'s and `vmr story`'s own), three mutually exclusive zoom selectors (`-journey`/`-compare`/`-corpus`, each routing into exactly that one story-side view — no macro report half runs alongside a selector). With no selector, the default suite runs the story half first (so `vmr-report.md` can link `stories/vmr-stories.md` on the very first call) then the macro report half, sharing one `-o`: `vmr-report.md` + `vmr-requests.md` + `stories/vmr-stories.md` + every rendered `category=task` journey, cross-linked — `cron`/`heartbeat`/`subagent` candidates still appear in the index but aren't pre-rendered by default (real full-corpus long-running conversations dominate rendering cost regardless of category, so this default keeps the common case fast without the "render literally everything" cost); `-render-all` widens it to every non-partial candidate
- Six new navigation edges close the loop between the three report tiers: `vmr-report.md` now links `stories/vmr-stories.md` (when present) and, in §8, shows an example `vmr replay -print -req` coordinate instead of a bare "see details/" note on a default (no-`-details`) run; each session card in `vmr-requests-<tag>.md` links its journey when one was rendered for it; `journey-<id>.md`'s header links back to `vmr-stories.md` and, when it exists, `vmr-report.md`; every `details/<req>.md` page links back to `vmr-requests.md`
- `vmr-stories.md` splits candidates by category (`vmr story`'s title-marker classifier: `cron`/`heartbeat`/`subagent`/plain `task`) — real tasks and cron jobs stay expanded, heartbeat/subagent noise (over half of a typical candidate list) collapses into a `<details>` block by default. `vmr-stories.json` still lists every candidate with no such split
- Self-traffic exclusion: `vmr story -llm-addr`'s own interpretation calls route back through the same VMR instance and land in the audit log like any other request — `vmr report`'s cost/usage totals and `vmr story`'s candidate journey list now exclude them by default (the tag is derived from `report.yaml`'s `llm_key`, the same transform `api_keys` auth already applies; `self_traffic_client_tags` covers a rotated-credential edge case). `-include-self-traffic` on either command disables it for that run; `vmr-report.json`'s `meta.self_traffic_excluded` reports how many records were skipped
- `vmr replay -req COORD` no longer requires the audit file positional argument — omit it to search the current directory and `config.yaml`'s `log_dir` for the coordinate's basename, or pass a directory to search instead; an exact file path still gets the existing strict basename check
- `vmr story`: the decision spine's every Step now carries a "→ detail" link to that record's own rendered detail page (`details/<coordinate-hash>.md`), materialized on demand as the Journey renders (no need to separately run `vmr report -details` first) — the same `internal/reqdetail` renderer `vmr report` uses, so the page is byte-identical regardless of which command wrote it. A per-Step materialization failure (rare: a malformed body, a transient disk error) is reported as a warning and does not abort the report — the other Steps still render
- `internal/reqdetail`: exported `SysPromptEvidenceFileName(sysHash)` — the deterministic evidence filename for a given `Manifest.SysHash`, letting a caller that only has the hash (not the full record) compute the same name `EnsureSysPromptEvidence` would write, without re-deriving the private naming convention
- `vmr story`: `journey-<id>.json` gained a `structure` field — the complete Task/Step/Event/ToolCall skeleton: each Step's `req` coordinate, per-step timing/cost (endpoint, duration, TTFT, token usage), the same graph-level analysis fact-layer shows today (edit classification, stitch evidence, compaction token/entity counts — none of which are recoverable from a single audit record, so they're inlined rather than referenced), a bounded excerpt of the Step's own response/reasoning/tool-call arguments, and whether each tool call found a paired result (`matched`/`result_error`, via the same precise ID matching the decision spine trusts). Conversation-history messages (`new_events`) are references only (content hash, role, first-appearance step) — never inlined text, and neither is a tool call's result text (it already exists as the *next* Step's own referenced message); a reader follows the owning Step's `req` back to the audit record or its rendered detail page for the actual content. This is the machine-readable counterpart to the human-readable decision spine/fact-layer, sized to the Journey's step count rather than its conversation length
- `internal/story`: `ToolIndexEntry` (the LLM interpretation layer's per-step summary) gained a `req` field, so an LLM-cited step ("at step 7 it looked up...") has a coordinate a reader can follow back to the source record
- `vmr replay -req basename:line` — locate the record to replay by its `req` coordinate (as published in `vmr-requests.json`'s `req` field or a `ctxgraph.Manifest`'s `Req`), sibling to the existing `-line`/`-ts`; the audit file argument's own canonical basename must match, or it errors rather than guessing. `vmr replay -print` prints the resolved record's raw JSON to stdout and exits — no `-provider`, no request building, no network — the direct replacement for reading a `details/*.json` copy now that copy no longer exists (see Removed)
- `internal/audit.LineAt(path, line)` — fetch one audit line's raw bytes by 1-based line number, the primitive `vmr replay -print` (and any future coordinate-addressed reader) builds on
- Shared evidence blobs: a session's system prompt and a request's declared tool set, previously repeated in full inside every `vmr report` detail page that used them, are now written once as content-addressed `evidence/sysprompt-<h8>.md` / `evidence/tools-<h8>.md` (`internal/reqdetail`'s `EnsureSysPromptEvidence`/`EnsureToolsEvidence`), with detail pages linking to them instead of inlining them. On one real Journey's worth of traffic (322 records), this collapsed 322 potential system-prompt copies down to 6 actual files
- `vmr report`/`vmr story`'s shared parse cache moved out of `vmr-requests.json`/`vmr-stories.json`'s embedded `files` section into its own directory, `{outDir}/.parse-cache/<filehash>.json` — one compact-encoded shard per input file, named by its own content hash (`ctxgraph.LoadCacheDir`/`SaveCacheDir`), so both index files stay human-scale and a rerun only ever writes the shards that actually changed
- The parse cache's payload now also covers `vmr report`'s own per-record aggregation facts (`internal/report/factscache.go`), not just `ctxgraph.Manifest`s — a file whose cache entry is still valid lets `vmr report`'s second scanning pass skip reopening/re-decoding it entirely when `-details` is off. See Changed below for the measured effect
- Parse cache entries carry a schema version stamp (`ctxgraph.CacheSchemaVersion`) alongside their content hash — a version bump (whenever the extraction logic itself changes) invalidates an entry exactly like a content-hash mismatch does, so a code change can never be silently served from a cache built by the logic it replaced
- `vmr report`: `vmr-requests.json` rows carry a `req` field — a stable cross-command coordinate (`<audit-file-basename>:<line>`, compression suffix stripped) identifying the exact audit record regardless of which command produced the row or how its input paths were spelled (absolute vs. relative). `internal/ctxgraph.Manifest` gained the same coordinate (`Req`), so `vmr-stories.json`'s per-file manifest list is independently joinable against `vmr-requests.json` on it — a script can now correlate "this report row" and "this story record" without either command depending on the other
- Config: `endpoints[].providers` — one or more accounts as one try-order entry, expanding into `providers` × `models` independent endpoints (outer loop over `models`, inner over `providers`). `providers:` is a list even for the single-account case (`providers: [p1]`) — there is no separate singular `provider:` field. Cuts the "same models/priority/role_map repeated once per account" duplication multi-account setups previously needed
- Config: top-level `fallback_endpoints:` — a list of endpoint-group entries appended to the tail of every virtual model's own try-order that already has an entry point on the fallback's `protocol` (never opens a new ingress a model didn't declare); `fallback: false` on a `models.<name>` entry opts that model out. A fallback's `priority` is required and must be > 0 (unlike an ordinary endpoint-group, where it's optional). `vmr check` shows a `=== Fallback Endpoints ===` preview, annotates injected endpoints with `fallback`, and flags a fallback that would duplicate an endpoint a model already declares for itself
- `vmr story`: Phase 1b LLM semantic detectors pipeline (`ComputeLLMFindings`) with 6 high-level behavioral defect detectors — tool result misinterpretation (`tool_result_misinterpretation`), semantic oscillation (`semantic_oscillation`), long-term goal drift (`goal_drift`), unverified completion claim (`unverified_completion_claim`), compaction constraint loss (`constraint_text_dropped_at_compaction`), and plan-execution misalignment (`plan_execution_misalignment`). Gated behind discrete HIGH/MEDIUM/LOW confidence and verbatim transcript `EvidenceAnchor` verification, with fail-open fallback; `journey-<id>.json` exposes structured `llm_findings` when `-llm-addr` is provided
- `vmr story -corpus`: Context Rot analysis (`Context Rot Analysis` / `上下文退化分析`) and Tool Sequence Patterns mining (`Tool Sequence Patterns` / `工具调用序列模式`) sections, supporting 2-gram/3-gram sequence frequency distributions and tail-step error rate attribution across token context buckets
- `vmr story`: Output repetition rate (`output_repetition_rate`, `Metrics.OutputRepetitionRate`) added as the 14th behavior-profile metric across single-journey profiles, comparison diffs, and corpus analytics
- `vmr story`: Multi-format plan parser (`ExtractActionablePlan`) supporting markdown checklists (`- [ ]`/`- [x]`), Chinese step prefixes (`步骤一：`), and parenthesized numbers (`(1)`/`1)`)
- `vmr story`: Shell verification command candidate extraction (`ExtractShellVerificationCandidate`) with a whitelist of 17 CLI test and validation command patterns
- `vmr story -compare`: Automatic generation of missing individual journey reports (`ensureJourneyFile`) during comparison and cross-linking in comparison markdown reports
- `vmr story`: Blue diamond prefix (`🔷`) for step role tags in the decision spine for consistent visual hierarchy
- `GET /health` — an unauthenticated liveness endpoint, reachable from any address. `/admin/status` stays loopback-only and answers the operational questions; this one answers only "is this process serving HTTP", so a container probe, reverse proxy or external monitor no longer needs a credential or a 127.0.0.1 source address (and no longer has to pay for an `exec: vmr status` subprocess per probe). The JSON body is `{status, time, uptime_seconds}` plus `Cache-Control: no-store`: a constant `"ok"` body is indistinguishable from a cached one, so an intermediary could keep answering 200 long after the process died — both fields move on every request and uptime moves monotonically. Deliberately liveness, never readiness: gating 200 on endpoint health would have an orchestrator kill a working router during an upstream outage a restart cannot fix. Nothing about the instance appears in the response, and a test asserts the field set is exactly those three so it stays that way
- `cmd/vmr/quota_parity_test.go`: `TestQuotaParity_TokensMetric_NonIntegerMultiplier` — the `tokens` metric's differential test only ever ran at an implicit 1.0x, while `requests` had float-multiplier coverage. `tokens` is the stricter case: `quota.ApplyModelMultiplier` scales the sniffed and the degraded halves in separate statements, and the router multiplies per response while the report multiplies one summed window, so a float factor has two independent places to diverge. The multiplier reaches the report side through the real `config.yaml` pipeline, so the wiring is asserted alongside the arithmetic

Two such drifts (`docs/VirtualModelRouter_Design_v4_Strategy.md` and `fmtutil.FmtTokens`, both cited by CLAUDE.md long before they existed) had only ever been caught by hand. The checking logic is a plain function the accompanying negative test drives over synthetic broken references, so the guard's own failure path is exercised rather than assumed
- `docs/VirtualModelRouter_Design_v4_Strategy.md` — the fourth design doc, and the only one answering "why" rather than "how": positioning, the multi-token-plan procurement pain points, a competitor matrix, and what is deliberately out of scope. Referenced by CLAUDE.md and the three sibling design docs but missing until now

### Changed
- **Breaking**: `vmr report`/`vmr story` are now deprecated aliases for `vmr analyze` — each prints a one-line stderr migration hint on every call, but keeps its own independent flag set, defaults, and output exactly as before (`vmr story -render-all`, in particular, still renders every candidate with no category filtering; the `category=task` default is `vmr analyze`-only). Neither alias is scheduled for removal; when to actually remove them is a separate future decision
- `vmr story`/`vmr analyze`: rendering a large batch of candidates (`-render-all`, a multi-match `-journey`, or the default suite) now builds them in bounded chunks of 20 instead of one unbounded batch — real full-corpus testing (34 files, ~9GB decompressed) found the previous single-batch `ctxgraph.FetchRecords` call scaled with total candidate *volume*, not just candidate *count*: a handful of long real task conversations already drove peak memory to tens of GB and the process was killed before writing anything. Chunking bounds peak memory to one chunk's worth regardless of total candidate count or size; small batches (the common case) are unaffected
- **`-lang zh`'s effect on JSON output widened**: `compare-*.json`'s `rows[].label` and `vmr-report.json`'s `efficiency[].{finding,implicated,action}` now follow `-lang` the same way the accompanying Markdown does — previously they stayed fixed English regardless of the report's display language (`journey-<id>.json`'s narrative fields already followed `-lang`; this change brings the other two JSON outputs in line with it). `FindingCode`/`MetricCode`/`EvidenceAnchor` are unaffected and remain the stable, language-independent fields a script should key off of — same values, same meaning, in either language
- **Breaking**: `vmr-report.json`'s `sessions[].id` (and the matching Markdown session headings) changed from a run-scoped `s01`/`s02` position label to the underlying `ctxgraph.Lineage`'s content-addressed identity (`l-<hash8>`) — the same identity `vmr story`'s Journey ids already build on. A session's id no longer depends on which other files were scanned in the same run, and is directly joinable against `vmr-stories.json`'s new `journeys[].lineages` field (no more hash-and-compare between the two commands). The old positional label is still shown alongside it (`SessionRow.alias`) for at-a-glance reference within one report, but no longer carries identity — code that parsed `sessions[].id` as `s\d\d` must switch to the new format
- `vmr story`: `journey-<id>.md` no longer duplicates the decision spine with a separate per-Task/per-Step "fact layer" (the old `## t01 · ...` / `### Step N ...` sections walking the full event stream with folded message bodies and LLM response blocks) — the decision spine is now the report's only per-Step content layer. Every Step's own reasoning/reply/tool-call content was already fully shown there (P1.2); conversation-history message bodies are reachable one click away via the new per-Step detail link instead of inlined; the cross-record analysis facts the fact layer used to carry (edit classification, stitch evidence, system-prompt-changed marker, compaction token/entity summary, no-reply marker) moved into the spine itself, since a per-record detail page cannot reconstruct them (they compare two or more records) — nothing that was previously visible in the human-readable report is now unreachable. A routine `Append` edit (the overwhelming majority of turns) is no longer flagged at all — it's the default, uninteresting case; `journey-<id>.json`'s `structure` field still records every Step's edit classification for a reader who wants it. On one real Journey (22 steps/33 tool calls), the rendered `.md` shrank from ~312KB to ~107KB
- `vmr story`: the system-prompt header no longer inlines the full prompt text — each distinct version ("era") now shows its effective Step range, a character-count summary, and a link to a shared `evidence/sysprompt-<hash>.md` blob (the same one `vmr report`'s detail pages already link to). Era detection also stopped relying on scanning each Step's newly-introduced messages, which structurally could only ever detect a version change at a Journey's first Step or a stitch boundary — a system-prompt change occurring mid-conversation (e.g. a model or tool-set switch within the same session) went completely undetected. Era grouping is now driven directly by each Step's own `Manifest.HasSys`/`SysHash`, the same fields the decision spine's own "system prompt changed" marker already uses, so the two can no longer disagree
- `vmr report -details` default flipped from `true` to `false` — a plain run now only writes the index (`vmr-requests.json`/`.md`), not a Markdown file per record; every row still carries its computable detail filename regardless of whether the file exists on disk. Pass `-details` to render them all up front; rendering is now idempotent — a rerun skips any file it already wrote instead of re-rendering it
- `vmr report`'s warm-cache full-corpus rerun dropped from ~71.8s to ~16.2s on a real 34-file/177MB-compressed corpus (cold: ~83.8s, unchanged) — the cache benefit rose from ~1.17× to ~5.2×, closing most of the gap to `vmr story`'s own ~5× warm-cache benefit on the same corpus (see Known Issues in `docs/KNOWN_ISSUES_sonnet-5.md` for the remaining uncached pass)
- `vmr report`'s per-request detail page rendering (`details/*.md`) moved out of `internal/report` into a new shared leaf package, `internal/reqdetail` — the same code `vmr story` will render its own detail links through once it starts generating them (a later phase). Detail filenames are now derived purely from the record's own coordinate (a short content hash of `req`), not a run-scoped batch counter or the rendering machine's local timezone: two runs of the same record — full corpus vs. a narrower subset, or on two machines in different timezones — now produce byte-identical filenames and content, verified against real audit logs. The filename's decorative prefix (`{ts}_{model}_{upstream-model}_{outcome}`) no longer appends the structured error-class suffix errored requests used to carry (e.g. `error-network`) — that detail remains visible one click into the page itself; only the coordinate hash, not the prefix, ever guaranteed uniqueness. `-N` collision suffixes are gone; they can't occur, the coordinate is already unique
- `vmr report`'s detail pages no longer show a "Session sNN · Task tNN" position line or a compaction cross-reference (which session a compaction call summarized/continued into) — both were run-scoped facts computed during report's own session/task aggregation, not facts of the record itself, and made a detail page's content depend on which other files happened to be in the same scan. That context still exists; it now belongs to whatever links to the page (a requests-index row, a future spine step), not to the page. The previous-turn link and the 🆕 delta highlight are unaffected — both are recomputed per-page from the record's own lineage predecessor (`ctxgraph.Classify`), not carried over from report's aggregation pass
- `internal/chatmsg`: Entity extraction (`ExtractEntities`) refactored into a multi-pattern classifier (URLs, explicit paths, files with extensions, two-segment directory paths, camelCase/snake_case symbols, and CLI command whitelist), with trailing punctuation stripping and spatial span overlap suppression (capped at 30 entities per step)
- `internal/story`: Tool call argument canonicalization (`canonicalizeToolArgs`) with JSON key sorting and `UseNumber` 64-bit integer precision preservation for duplicate call detection
- `internal/story`: Plan step tag (`StepTagPlan`) in decision spine tightened to require extracting at least 2 actionable plan items
- Documented the per-request memory peak an inline-image request adds on top of the three buffer caps (`docs/UserGuide.md` + `.zh`'s "Per-request memory budget", `config.example.yaml` + `.zh`'s `image_downscale`). Downscaling decodes each image to a bitmap sized by its **pixel count**, not its byte size — a 4K screenshot arriving as 1.5MB of base64 decodes to ~33MB, which `max_request_body_mb` cannot see because it caps bytes. Two existing bounds already contain it and are now stated rather than implied: images decode one at a time (ten screenshots peak at one screenshot's worth), and anything over ~64MP passes through undecoded. Documentation only, no behavior change
- `internal/archtest`'s file-line guard is now a global default (700) with an exemption table, mirroring the inversion `TestArchitecture_FuncSizes` already applied to function length — and for the reason that test's own comment gives: "a whitelist only ever constrains what someone remembered to register". Under the old 32-entry whitelist, 11 production files at 400+ lines had no budget at all (`diagnose.go` 660, `report/requests.go` 637, `audit/audit.go` 593, …) while an already-registered file went red for a single added line — the guard was penalizing the places already cleaned up and waving through the ones that weren't. 700 was picked so that every file already over it was one the table had registered anyway, so the inversion needed zero new first-time budgets. Exemptions override in both directions: most existing entries are tighter than 700 and stay that way
- Quota accounting for an account with `model_multipliers` now charges the exact configured multiplier instead of rounding each charge up to the next integer — a fractional multiplier like `2.5` used to be silently charged as `3` (a systematic overcharge of up to ~+100% per charge, magnitude unrelated to the configured value, e.g. `2.5`→+20%, `2.9`→+3.4%). `internal/quota.Counters`'s five raw components (and the matching `estimated`/`Estimated` fields) are now `float64`, so `vmr-quota.json`'s `requests`/`fresh`/`out`/etc. fields may now hold a fractional value for such an account — this is a one-directional upgrade: an older `vmr` binary cannot read a `vmr-quota.json` written by this version if any configured account has a non-integer effective multiplier (it falls back to an empty counter for that file, same as any other corrupt-file recovery, and self-heals at the next period boundary). An account with no `model_multipliers` configured is bit-for-bit unaffected.
- `vmr report` §2.5: the declared `quota:` reference moved out of the main table entirely — it now appears only in the "Quota vs. Consumption" sub-table below, instead of being duplicated in both places through two different number formatters
- `vmr report`: a `config.yaml` read failure now prints one unified warning instead of two near-identical ones (pricing and §2.5 quota references used to each print their own)
- Live router log line redesigned for density: `»` replaces `-> ... (stream)` for a streaming request; the pre-call `req=xxxKB/xxxESTKT` column is replaced by actual token usage (`in`/`ch` cache-hit%/`cw`/`out`) once a response reports it, falling back to `in xxxKT(est)` when it doesn't; capabilities are now pipe-joined and omitted entirely for a pure-text request instead of printing `cap=-`; and the trailing `attempt=N, status=X, dur=Ys` triplet collapses into `STATUS(Ys, Nx)`
- Live router log line's client-tag column widened from 8 to 9 chars — an 8-char client tag used to run straight into the next field with no separating space (e.g. `openclawopenai:agent`); non-streaming requests now use `>` instead of `->`; token counts always render as `X.XXKT`/`X.XMT` (2 decimals below 1000, 1 above) instead of a bare token count below 1000, so a value like `6` tokens no longer prints unit-less next to a `35.4KT` on the line above it; the background probe's log line (`probe    ...`) now shares the same comma-separated `key=value` punctuation as every other live-log line instead of its own space-separated one; a returned-as-is client error (4xx, no cooldown) now reads `status/class=400(...)` instead of a bare `400(...)`
- Startup/hot-reload config summary in the server log now shares `vmr check`'s exact section renderers (`=== Global Settings ===`/`=== Providers ===`/`=== Models ===`, same column widths, same ⚠️ warning markers) instead of a separately-maintained, less detailed format — the two can no longer drift out of sync
- `internal/router`'s response-normalization state machine (`response.go`/`responsefix.go` — event splitting, model-field rewrite, `[DONE]` policy, the buffered/passthrough decision, and the two MiniMax-specific thinking-mode repairs) moved into its own package, `internal/respnorm`, exposing only `Wrap(io.Reader, Options) NormalizerStream` — `router`/`quota.go` now depend on that interface instead of reaching into a router-private type. Both sides' full instruction now renders as a folded block under the existing summary (bounded to 2000 characters), dialect-aware (`taskseg.Profile.RealUserText`, the same filter Journey titles already use, so an agent-injected scaffold/heartbeat message can't get shown as if it were the real instruction), and flows into the `-llm-addr` evidence pack automatically since it lives on the already-embedded `ComparisonExtras`
- `vmr story`'s LLM interpretation section rendered the model's returned Markdown verbatim; a model that didn't follow the prompt's "use level-3 headings for your own subsections" instruction could emit a `##` that collided with the document's own outline. Now a deterministic render-layer pass shifts every heading level 2-through-5 the model actually used down by one (preserving whatever internal parent/child structure the model built, not just rewriting `##` in isolation), skipping both ``` and ~~~ fenced code blocks
- `vmr report`'s default (no `-details`) request index tables (`vmr-requests.md`, its per-client/per-scheduled-class siblings, `vmr-requests-failed.md`) rendered a "文件"/"File" column link to `details/*.md` unconditionally, even though `-details` defaults to off and writes no such files — every one of those links was dead. The column now renders the record's already-published `req` coordinate (`` `basename:line` ``) as inline code when details weren't generated this run, and the usual Markdown link when they were
- `internal/taskseg`'s OpenClaw dialect only stripped a leading `[timestamp]`/`[message_id: ...]` scaffolding bracket pair inside its `(untrusted metadata)` envelope-handling branch; a "bare" message (no envelope, just the two brackets glued onto the front) passed both straight through into task titles and, via `vmr story`'s mid-task instruction line, into the decision spine. Both brackets are now stripped from bare messages too, in a loop (order-independent), via a narrow `timestampBracketRe` (OpenClaw's specific day-name-prefixed shape) rather than a generic "any leading bracket" rule — the latter would also strip (and, for a bracket-only message, wrongly reject as pure scaffolding) a real message that happens to legitimately open with one, e.g. `[Bug] fix the crash`. The spine's instruction line also now reads the same filtered-and-preview-truncated text `buildFrom` already computes for the task title (`Step.Instruction`), instead of re-deriving it unfiltered from raw event text, and — a gap in the original P1.2/P6 spine-completion work, not new in this change — now renders on a tool-calling Step too, not only a non-tool-calling one; a mid-task instruction very often triggers an immediate tool call, so the previous non-tool-calling-only rendering made most real instructions invisible in the spine
- `vmr story -llm-addr ''` (explicitly passed as an empty string, e.g. to force off LLM interpretation for a quick verification run) silently fell back to `report.yaml`'s configured default address instead of disabling the LLM call — `resolveString` couldn't distinguish an explicitly empty flag from one never passed at all. A new `resolveStringExplicit` (using the existing `flagPassed` idiom `resolveBool` already relies on for the same distinction) fixes the one call site that needs it (`-llm-addr`); every other `resolveString` use is unaffected
- `vmr-stories.json`'s `journeys[].category` used the empty string as `CategoryTask`'s zero value with `omitempty`, so the most common candidate class (real tasks) never appeared in the field at all — a JSON consumer had to know that field absence meant "task". `CategoryTask` is now the explicit string `"task"`, serialized like the other three categories. `journeys[].files` also switched from the manifest's raw input path (absolute or relative depending on how the file was passed) to the same `CanonicalPath` coordinate spelling `vmr-requests.json`'s `req` field already uses, so the two can be joined without re-normalizing one of them first
- `internal/story`'s tool-result truncation notice (`capFull`) pointed every truncated value — both a tool call's own arguments and its paired result — at "this Step's detail link", but a paired result's full text actually lives in the *next* Step's request record, not this one. Split into `capFull` (arguments, unchanged text) and a shared `capFullWith` used by `toolResultLine` with a new, distinct `SpineResultValueTruncated` text pointing at the next Step's link instead
