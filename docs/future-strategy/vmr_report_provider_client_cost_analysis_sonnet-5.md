# 成本/用量分析增强：Client / Provider / Story 三维度设计

**状态**：分析与方案设计，尚未实现。本文只做问题分析、方案比较与最终建议，不改动任何代码。
配套的落地步骤见 `docs/future-strategy/vmr_report_story_cost_dimensions_devplan_opus-5.md`。

**范围**：Client 与 Provider 两个维度落在 `vmr report`（横向聚合报表）；Story 维度落在
`vmr story`（单个 Journey 的纵向叙事），见 §5.2 对为什么这样划分的说明。

**动机**：这次会话前几轮深入核实了火山方舟 AFP（Agent Fuel Point）计费逻辑与 `config.mba.yaml`
里 `volcengine2` 账户配置的对应关系，过程中发现 `vmr report` 现在的成本分析对 Token Plan/AFP 这类
按额度而非按 $ 计费的账户几乎不产生有效信号——报表回答不了"我们几个 Token Plan/Coding Plan 账户
之间是不是平衡"这个问题。

**本版是第三稿，基于一次逐文件的源码核对重写。** 前两稿有两处**事实错误**，都会直接把工程量估反：
第二稿认为"按 Client 的统计数据从来没被画成表格，第一批纯渲染零风险"——**错的**，`vmr report` 的
§5 负载分布早就有一张 8 列的按客户端表；第二稿还认为 Story 维度可以直接读 `Manifest.Model` 拿到
"这一步用了哪个模型"——**也是错的**，那个字段是**虚拟模型名**，一个 Journey 里它几乎永远不变，
照着实现出来的功能会是一张永远显示"没换过模型"的空表。核对结论见 §3.1、§5.5。

## 1. 判断标准：一个指标该不该进产物

在列具体指标之前，先定一把尺子，后面每一项都要经得起这三个问题：

1. **它直接服务"评估账户间是否平衡"这个目标吗？** 一个指标如果只是"知道了也不错"，但既不影响
   "该不该多导流量给这个账户"的判断，也不解释"为什么这个账户消耗异常"，就不该占篇幅。
2. **数据已经在算，只是没被用起来吗？** 如果是，这类改动应该优先做。**但"已经在算"必须逐文件
   核实到渲染层，不能停在"结构体里有这个字段"** ——前两稿正是在这一步栽了跟头（§3.1）。
3. **加了它之后，真的会有人打开这张表看吗？** 一张没人会点开的表，维护成本不会消失，只会累积成
   以后没人敢删的技术债。

## 2. 三个维度回答的是三个不同的问题

| 维度 | 分组单位 | 输出落在哪个产物里 | 回答的问题 | 是否要算成本/花费 |
|---|---|---|---|---|
| **Client（Agent）** | `client_key_tag` | 聚合报表 `vmr-report.md`/`.json` | 这个 Agent 烧了多少、都烧在哪些上游端点上——是"谁在花钱"的视角 | 要 |
| **Provider** | provider（= 一个 Token Plan/Coding Plan 账户） | 同上，聚合报表 | 这个账户整体消耗多少、可靠性如何、离它自己配置的额度上限还有多远——是"账户是否吃紧"的视角 | 要，这是"评估平衡"最终要看的那张表 |
| **Story（一次任务）** | 一个 Journey | **`vmr story` 的单个 `journey-<id>.md`/`.json`——不进 `vmr-report.md`**，见 §5.2 | 这一次任务用了哪些上游模型、什么时候切换的 | **不要**——只看 token 消耗，也不再按 Provider/Client 二次拆分 |

三者互不替代，且**输出载体本身就是分开的**：Client/Provider 属于横向聚合（`vmr report`），
Story 属于纵向还原（`vmr story`）。`vmr report` 不该因为这次任务反过来长出一块本属于 `vmr story`
的单任务叙事能力。

## 3. 维度一：Client（Agent）

### 3.1 现状核对（推翻前两稿的结论）

逐文件核对 `internal/report` 的渲染层后，实际情况是：**按 Client 的统计早就被渲染出来了，而且相当
完整**，前两稿"从没画成表格"的判断是错的。已经存在的三处：

| 已有位置 | 内容 |
|---|---|
| **§5 负载分布**（`section_workload.go`，8 列表） | client_key、请求数、成功率、token 三分（fresh/cached/out 含 reasoning）、缓存效率、耗时 P50/P95、**每请求输入 token P50/P95**、**每请求输出 token P50/P95** |
| **§2 成本估算**（`section_cost.go`，4 列表） | client_key、fresh、out、估算成本——**但仅在该 client 解析出定价时才渲染** |
| **§6 会话与任务**（`section_sessions.go`） | 会话本来就**按 client 分组**展示，每行是该会话的请求数/任务数/token/结果 |

`docs/UserGuide.zh.md` 也早就写明了 §5 "按客户端（后两张表还带每请求输入/输出 token 分位数）"。

于是这个维度**用户提出的四项指标里，三项已经有了**：$ 成本（§2）、缓存命中率（§5 的缓存效率）、
平均每请求 token（§5 的 P50/P95 真分位数）。**只剩一项是真缺口**：

| 指标 | 结论 |
|---|---|
| 按不同上游端点/模型拆分的 token 消耗 | ❌ **真缺口**——现在一个 Agent 调用的所有上游被合并成一个数字，回答不了"这个 Agent 的流量到底落到哪几个账户/模型上了" |
| $ 成本 / 缓存效率 / 每请求 token 分位 / 会话规模 | ✅ 已有，无需改动 |
| 缓存命中率的第二个口径（cached/输入总量） | 🟡 **建议不做**，见下 |

**关于"再补一个缓存命中率口径"**：现有的是 `cache_efficiency = cached/(cached+fresh)`，另一个口径
是 `cache_hit_rate = cached/tokens_in`，两者只差分母里的 `cache_write`。报表顶层（§1）两个都给了，
足够判断整体形势；在一张已经 8 列的按客户端表上再加一个高度相关的近义列，收益低于可读性损失——
按 §1 第三条标准，**不做**。

### 3.2 真缺口的解法：按 client 分组列出它命中的上游端点

不做"client × 虚拟模型"，做 **"client × 上游端点（`protocol:provider:model`）"**，理由是这个项目
的真实配置逼出来的：`config.mba.yaml` 里 `deepseek-v4-flash` **同时挂在 `volcengine` 和
`volcengine2` 两个账户下**。只按模型名拆分会把两个账户的消耗合并成一行，恰好抹掉"账户间是否
平衡"这个核心问题最需要的那一刀。按端点拆分则同时给出模型和账户归属。

呈现上**按 client 分组、组内按 token 降序列出它的端点**，不是一张 client×provider 的二维矩阵——
这一点很重要，它让前两稿列为"不建议做"的那个稀疏矩阵变得多余：**矩阵想回答的问题（谁在消耗哪个
账户）由这张分组表直接答了，且没有矩阵那种大片空单元格的可读性问题。**

## 4. 维度二：Provider

### 4.1 现状

**Provider 级别的汇总确实完全不存在**——这一条核对后成立。`vmr report` 只有
`protocol:provider:model` 这个更细的粒度（§5 的按端点表、§2 的按端点成本、§6.6 端点性价比），
从来没有把同一个账户下的多个模型加总。要看"volcengine2 这个 AFP 账户总共烧了多少"，今天得把
好几行手动相加——而 `config.mba.yaml` 里这个账户名下挂着 5 个模型，正是最需要汇总的情形。

### 4.2 保留的指标

| 指标 | 说明 |
|---|---|
| Token 消耗（整体 + 按模型拆分） | 上卷现有按端点数据；"按模型拆分"直接复用同账户下的端点行，不新建结构 |
| $ 估算 | 同上，上卷 |
| 缓存效率 | 该账户自己的计数汇总（比值的分子分母都可加，直接汇总即得，不存在精度问题） |
| ~~每请求 token / 延迟分位数（P50/P95）~~ | **不做**，见下方"一处刻意的简化" |
| 可靠性（尝试数/成功率/错误分类/失败尝试墙钟耗时） | 上卷现有 G 族字段。保留理由：一个账户即使额度充裕，错误率高也不该被判定为"该多导流量"，只看余量会得出错误结论 |

**一处刻意的简化：Provider 汇总全部从已完成的按端点结果派生，不新开一份原始数据累计。**
项目有一条硬原则"百分位不可加——每个桶必须用自己的原始切片算真分位数"，这意味着想给 Provider
一个真 P50/P95，就必须在聚合过程中再缓冲一整份逐请求的耗时/token 切片。但除分位数外，这张表要的
**其余每一项都是可加的**（token 各分量、请求数、尝试数、成功/失败数、错误分类计数、失败墙钟耗时、
$ 估算，以及由可加量算出的缓存效率比值）。于是取舍很清楚：**放弃 Provider 级分位数，换取"零新增
累计、零内存开销、聚合主循环一行不改"**——分位数本来也不是这张表要回答的问题（账户是否吃紧），
而每个端点自己的 P50/P95 在 §5 已经有了。需要延迟感的话补一个由 `dur_ms` 总和除以请求数得到的
**均值**即可，并如实标注它是均值而非分位数。

这条简化让第一批的实现形态变成"在聚合结束后，对已完成的按端点结果做一次纯函数式上卷"——与
`buildTools`/`buildCompactions` 这两个既有的"跑完再派生"函数完全同构，不是新发明的模式。
| **配置额度上限作为参照** | 新增，见 §4.3 |

### 4.3 额度参照：不做精确加权，只并排给一个诚实的参照数字

**问题**：Provider 维度真正想回答"这个账户是不是快用完了"。AFP 这类账户模型倍率差异极大
（kimi-k3 与 doubao-mini 差 40 倍），裸 token 数在模型混用的账户上参考价值有限。

**不采用的方案**：把 `internal/router/quota.go` 的加权公式（`model_multipliers` × `token_weights`
+ 向上取整）抽到公共叶子包给报表复用。这个方案本身是对的——`internal/pricing` 就是这么从路由半区
抽出来的（包注释原文"两个消费者，一份实现"）——但它是"更精确"，不是"更必要"：

- 它是所有改动里**唯一需要碰路由半区代码**的一处，风险与评审成本明显更高；
- 它要解决的"模型混用时裸 token 会误导"这个问题，在 §4.2 已保留的"按模型拆分"表出现之后已被
  大幅缓解——看着"doubao-mini 3M / glm-5.2 2M / deepseek-v4-pro 0.5M"，对照 config 里的倍率
  （0.25×/4.5×/5.5×）心算一下就知道量级。

**采用的方案**：把该账户在 `config.yaml` 里配置的额度（`metric` + `every` + `amount`）原样读出来，
与本次统计窗口的原始消耗**并排展示**，并明确标注"未做模型倍率加权、且统计窗口与账户计费周期不
对齐，仅供数量级参考"。这条标注不是免责套话——它是这个数字唯一诚实的读法，与项目里
`estimated_pct`、`⭐`、低置信度脚注是同一套风格。

好处是**完全不碰 `internal/router`**：`amount`/`metric`/`every` 是 `config.yaml` 加载期就已解析好
的静态值（`config.LimitConfig.Resolved`，`core.Limit` 的三个字段），`cmd/vmr/cmd_report.go` 已有
读 config 把解析结果传给报表的现成模式（`buildPricing`），照抄即可。

**什么时候升级到精确加权**：如果"裸 token + 配置上限"这个粗参照在实际运维中经常带偏判断，再回头
做不迟。届时那次抽取重构仍是对的方案，只是不必现在做。

### 4.4 输入长度分层分布：跟着精确加权一起挂起

这项指标（请求按输入长度落在 ≤32K / 32K~128K / >128K 哪一档，用于校准 AFP 类账户的经验系数）本身
很便宜，但它存在的**唯一理由**是给精确加权计算提供校准数据。既然精确加权挂起，它就没有消费者，
撞上 §1 第三条标准。**不单独做，与 §4.3 的加权计算绑定考虑。**

## 5. 维度三：Story（一次任务）内部的模型使用与切换

### 5.1 要回答的问题

一次任务执行中如果换了模型——需要某个能力、原模型失效触发 failover、或路由策略调整——**模型变化
可能直接影响这次任务的产出质量**。今天打开一份 Journey 分析文件完全看不到这件事。

### 5.2 为什么落在 `vmr story` 而不是 `vmr report`

第二稿曾把它挂在 `vmr report` 的会话分组上，理由是底层同为 `ctxgraph.Lineage`。**这个理由不成立**
——"底层数据结构相同"不等于"该放进同一个产物"。`vmr report` 一次运行覆盖成百上千个会话，塞进
单任务粒度的切换记录要么淹没读者、要么被压缩到没有信息量；而一个 Journey 文件本来就是讲一次任务
的，多一段"这次用了哪些模型"与它已有的"这次调用了哪些工具"（工具调用时序图）是同一抽象层级。

### 5.3 不做什么

- **不算成本**——单个任务的金额太小，算了也不会有人靠它决策；
- **不按 Provider/Client 二次拆分**——一个 Journey 天然属于一个 client；账户是否平衡是 Provider
  维度的职责；
- **不断言"为什么"换模型**——failover、能力路由、黏性到期后的自然轮换，这几种从审计记录**不总能
  确定分辨**。只给可验证事实，措辞延续 `vmr story` 全部 Finding 检测器既有的克制纪律。

### 5.4 最小指标集

| 指标 | 说明 |
|---|---|
| 该 Journey 用过的上游模型/端点列表 + 各自 token 与 Step 数 | 每个 Journey 都展示（单个页面不怕多一张小表，不同于聚合报表的规模顾虑） |
| 切换点：第几个 Step、从哪个换到哪个 | 只有真的发生过切换时才渲染这一小节 |
| 切换点是否恰好落在一个触发过 failover 的 Step 上（观察性标记） | 由 `len(Step.Rec.Attempts) > 1` 判定。措辞只写"这次切换发生在一个触发过 failover 的 Step 上"，不写因果断言 |

### 5.5 落点核对：两处必须纠正的实现细节

**① 模型名必须取自端点，不能取 `Manifest.Model`。** 核对 `internal/ctxgraph/manifest.go` 与
`internal/audit/audit.go` 后确认：

- `audit.Record.Model` 的注释原文是 `// virtual model`，`ctxgraph.Manifest.Model` 直接等于它 →
  **是虚拟模型名**（`coding`/`agent`），一个 Journey 里客户端始终请求同一个虚拟模型，**这个字段
  几乎永远不变**；
- 真实上游模型在 `Manifest.Endpoint`（= 最后一次 attempt 的 `protocol:provider:model` 标签），
  以及 `Step.Rec.Attempts[i]` 的结构化字段 `Protocol`/`Provider`/`Model`。

**照第二稿写法实现出来的会是一张永远显示"全程未换模型"的表**——这是本次核对避免的最大一处返工。

**② 端点标签有两种历史格式，需要走健壮取值。** `internal/report/detail.go` 的 `attemptUpstream`
已经处理了这件事：优先读结构化字段，旧日志（`/` 连接而非 `:` 连接）回退到按 `/` 切分。`internal/story`
不能 import `internal/report`（archtest 禁止），所以要么在 story 里复制一份，要么把这个 helper 下沉。
建议下沉到 `internal/audit`（两边都已依赖它，且这本来就是 `audit.Attempt` 自己的属性）——理由是
这个项目已经被"同一事实两份实现"坑过一次（`report` 私有的会话分组与 `ctxgraph` 分叉），一个
12 行的纯函数不值得再冒一次同类风险。

**③ 前一稿"`-compare`/`-corpus` 免费获得这个维度"的说法不准确。** 核对
`internal/story/compare.go` 与 `corpus.go` 后确认：两者各自持有一份**显式的 metric 枚举**
（`MetricCode` 常量表 + `metricDiff` 调用列表 + corpus 的 `metricKinds` 映射与取值 switch）。新增
一项标量指标需要在**四处**登记（含 i18n 标签），不是自动继承。且"按模型的 token 拆分"是**列表型
数据**，与 `ToolCallDist` 同类，根本进不了那套只吃标量的 Spearman/diff 机制。

**修正后的说法**：只有"模型切换次数"这一个**标量**适合登记进 `-compare`/`-corpus`，代价是四处小
改动（不是零）；列表型的按模型 token 拆分只在单 Journey 页面呈现。**是否登记那个标量，作为第一
梯队里一个可独立取舍的子项，不强制绑定。**

## 6. 实施建议：三个梯队

> **状态（2026-08-12，Sonnet 5）：第一梯队三批已全部实现**，落地细节见
> `docs/future-strategy/vmr_report_story_cost_dimensions_devplan_opus-5.md` 各批末尾的"完成情况"。
> 第二/第三梯队按本节原判断维持不变——均未实施，理由见下方各自小节（未发生变化，不是本次遗漏）。

### 第一梯队：建议现在做

共同特征：**不碰 `internal/router`，不引入新的跨包依赖**。第二稿的"第一批：把 ByClient 画成表"
因 §3.1 的核对结果**已经取消**（那张表早就存在）。剩下三批，按"缺口大小 × 与核心目标的距离"排序：

**第一批——Provider 维度汇总 + 额度参照（`vmr report`）。✅ 已实现。** 这是三批里唯一一个"完全不存在"的维度，
也最直接回答本文档的核心问题。内容：新增按 provider 分组的汇总（token/缓存/延迟分位/可靠性/$
估算）+ 该账户配置额度的并排参照。**排第一是因为它是唯一一个今天连近似答案都给不出的缺口**——
另外两批至少还有"手动相加"或"读 Journey 正文"这类笨办法。（唯一简化：如 §4.2 所述放弃了延迟分位数，
用均值代替——实现前就已决定，不是实施中的削减。）

**第二批——Client 维度按上游端点拆分（`vmr report`）。✅ 已实现。** 给每个 client 列出它命中的端点及各自
token（§3.2）。排第二是因为这个维度的其余指标今天已经能看（§5/§2/§6），缺的只是归属拆分这一刀。
