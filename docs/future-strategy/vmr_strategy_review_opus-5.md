## 0. Debrief 与结论先行

### 0.1 八条核心结论

1. **分发实验已经跑过一轮，失败了。** 22 篇以上内容、四个平台、二进制 + brew + CI 全就绪 → star 从 2 涨到 3。这不是"转化率低"，22 篇内容如果真的被人读到，1 个 star 的产出是不可能的。**这是曝光量近似为零，不是产品被看过之后被拒绝。**

2. **失败最可能的一环是渠道执行，不是内容质量，也不是产品。** 分发计划（`00-发布规划与检查清单.md`）自己点名的首发渠道是 **linux.do + V2EX + 掘金 + Show HN**——受众密度最高的四个。实际执行落在**知乎回答 + Reddit 回复 + Twitter**。这三者的共同点是：**都是"寄生在别人的注意力上"的格式**（答别人的问题、回别人的帖、发给没有粉丝的时间线），而前四个是"自带流量入口"的格式（发主题帖）。**计划选对了渠道，执行换成了另一批。**

3. **全部对外表达停在 2026-08-03 的产品状态，而项目在 08-07 交付了它最强的差异化能力。** 12 篇文章里提到"额度/套餐/quota/headroom"的次数是 **0**（唯一一次命中是 article-12 里"退还额度"这个无关词）。跨厂商额度配速——全项目唯一有硬市场数据支撑（81 个在售套餐调研）、唯一能算成钱、唯一不需要用户读任何报告就生效的能力——**在整个内容库里不存在**。

4. **护城河排序需要改：额度配速第一，`ctxgraph`/`story` 第二，字节记录最弱。** 内容策略 v3 的 24 个卖点里，第一梯队五项全是分析半区（story/compare/字节审计/语义分组/replay），路由半区一项都没进。这个排序在 08-07 之后已经过时。

5. **v2 的 P0 已被 `vmr diagnose` 实质完成，应当删除；三项 P1 需要重新裁决**（§5 逐项）：P1-1 软拦截 failover **降级**（卡的不是实现，是没有仪表）、P1-2 上下文超限 **维持 P1 且理由更强**（它是全清单 ROI 最高的一项）、P1-3 预算硬闸 **改名重定范围后仍成立，成本已降到原估的 1/3**。

6. **项目存在一处最值得指出的不对称**：VMR 建了一套精密的**事后**失控循环检测器（`exact_repeat_tool_call`，依据是 claude-code#15909 的"重试 300+ 次、耗时 4.6 小时"），却在**实时**路径上明确选择不作为。它是这条链路上唯一有能力叫停的组件，而它在看着。

7. **真正的竞争对手是"重跑一次"。** 能打过它的只有反复发生、可累加、可量化的痛。VMR 现在恰好有一个已交付的、属于这一类的能力（额度配速），但从未对外讲过。

8. **止损判断**：**不该现在触发，但理由与上一版不同。** 上一版说"实验没开始"，那是错的。正确的说法是：**这一轮实验测的是"AI 写的知乎回答能不能带来流量"，不是"linux.do/HN 上有没有人要这个东西"。** 后者仍未被测试。给它一次成本明确的机会（§8），跑完再裁。

## 2. 分发实验的复盘：它跑了，它失败了

### 2.1 先把"失败"定义清楚

22 篇内容 → +1 star。这个比例不构成"内容不够好"的证据——**它构成"几乎没有人看到"的证据**。一篇平庸的技术文章被 1000 人读到，也不会只换来 1 个 star。所以问题出在漏斗的第一格，不是后面几格。

### 2.2 三个可能的失败点，按我的置信度排序

**① 渠道格式错配（我的主要判断，高置信）**

对照 `00-发布规划与检查清单.md` 计划的渠道与实际执行的渠道：

| | 计划 | 实际 |
|---|---|---|
| 首发 | linux.do、V2EX（主题帖） | 知乎回答 |
| 第二波 | linux.do、掘金 | Reddit 回复 |
| 英文 | HN Show HN（主题帖）、r/LocalLLaMA、r/ClaudeAI（主题帖） | Reddit 回复、Twitter |

**计划里全是"发主题帖"，执行里全是"回别人的帖"。** 这不是同一类动作：

- **知乎回答**：你在别人的问题下和几十个答主竞争，冷启动账号排在末位，且平台对带链接的自荐答案有明确降权；
- **Reddit 回复**：埋在评论树里，可见度比自立主题低一到两个数量级；
- **Twitter 无粉丝**：曝光量约等于零。

而 **Show HN / linux.do / V2EX 主题帖** 是这个领域里少数几个"冷启动也能拿到几千次浏览"的格式。**计划识别对了，执行没跟上。**

**② 内容是"关于 VMR 的文章"，不是"VMR 产出的发现"（中高置信）**

内容策略 v3 §0.3 把方法论写得很对：

> "VMR 的内容不是功能公告，而是一连串的发现和洞察……读者被发现吸引，自然会问'你是怎么发现的'——这时 VMR 出场。"

**但产出物没有兑现这条方法论。** 抽查旗舰篇 `article-01`：开场是"昨晚我给 OpenClaw 安排了一个重构任务……第二天早晨醒来"，数字是 47 轮 / 40 万 Token / 12 个模块——读起来是**示意性场景**，不是一份可核查的实测数据集。标题《我用 VMR 看清了每一步》里，主角是 VMR。

对照项目**真实拥有**的证据（全部写在 v4 Analytics §6 里）：7112 条记录 / 809K 条消息实例 / 752 个会话；406,534 对 tool_call/tool_result 配对**零孤儿**；95.86% 的相邻编辑是纯追加、真正的历史断裂只占 1% 但集中在最长的会话里；一次真实压缩把 79 条消息压成 4 条；137 个 Journey 上 `exact_repeat_tool_call` 命中组的净工作时长中位数比未命中组**高 34%**；openclaw 与 lobster 跑同一个 A 股调研任务，**第一步就分道扬镳**（一个先查记忆、一个直接抓数据）。

**这些数字一个都没进文章。** 它们才是"发现"——每一个都能独立成篇、独立被转发、且只有 VMR 能算出来。已发布的内容用示意性场景替代了它们，等于**把唯一无法被复制的资产留在了硬盘上，拿可以被任何人编出来的故事去打市场**。

**③ AI 生成腔（中置信，但值得直说）**

12 篇文章 + 8 篇知乎回答全部由同一个模型批量生成，`Ver` 头一致、结构模板一致（TL;DR → 现象 → 原理 → 竞品对比 → 安装）。linux.do、V2EX、HN 的读者对批量 AI 推广文的识别率和敌意都很高，触发的往往不是无视而是反感。这条不能证实（没有平台数据），但它是把 ② 的伤害放大一个量级的因素：**示意性数据 + 模板化结构 + 批量投放，恰好是"AI 软文"的完整特征集。**

### 2.3 由此得出的一条纪律

> **有真实数据可用时，绝不写示意性数据。**

这不只是内容纪律，它和这个项目的核心主张是同一件事：VMR 全部说服力的来源就是"我记的是真的字节，不是我改写过的"。**用编出来的 47 轮去推销一个以"数据可信"为立身之本的工具，是在自毁前提。**

## 3. 定位：四类人群，头版对准了最拥挤的那一类

| 人群 | 规模 | 想要什么 | 现有满足者 | VMR 的对应能力 |
|---|---|---|---|---|
| **① Agent 使用者**（给 Claude Code 换模型） | 最大 | 换模型、别断、便宜、装得上 | CCR（36k）、CLIProxyAPI（45k） | 路由 + failover（已被追平） |
| **② 多套餐采购者**（同时买了 2–5 家 Token-Plan） | 中，在增长 | 别让任何套餐作废、别溢出到按量、别打掉 cache | **无人做到跨厂商配速** | 额度配速 + Sticky |
| **③ Agent 构建者**（在调自己的 prompt/框架） | 中 | 过程级评估、跨版本对比 | Langfuse / LangSmith / DeepEval（需埋点） | story / compare / corpus |
| **④ Agent 逆向者**（想搞清一个改不了的 Agent） | 小但独占 | 真实字节 + 上下文演化 | **无人** | 全套 |

**当前 README 头版对准的是 ①**（"Zero-Instrumentation Router & Flight Recorder"），次要叙事对准 ③/④，**② 完全缺席**——而 ② 是唯一一个痛能算成钱、每个计费周期复发一次、且解法不需要读任何报告的人群。

### 3.1 一条与内容策略 v3 的正面分歧：Claude Code 叙事

内容策略 v3 §0.1 明确否掉了 Claude Code 叙事，理由是：

> "Claude Code 属于闭环 CLI，VMR 默认不直接劫持其配置，用户需要手工设环境变量和重定向 Endpoint。"

**我不同意，理由有三：**

1. **这个理由在技术上不成立。** 设 `ANTHROPIC_BASE_URL` 和设 `OPENAI_BASE_URL` 是完全同等的动作，README 里两行并排写着。用"要手工设环境变量"否掉 Claude Code，等于同时否掉 VMR 的全部接入方式。
2. **它把因果搞反了。** Claude Code **闭源**这件事不是障碍，**是唯一的护城河来源**——你无法给它加 Langfuse 埋点、无法加 OTel、无法加任何 SDK，**但你能在它前面放一个 base_url**。VMR 因此是全世界唯一能回答"Claude Code 到底怎么管理你的上下文"的工具。这个"障碍"恰恰是内容独占性的全部来源。
3. **搜索量与认知度差着数量级。** OpenClaw / Pi Agent 的名字不构成流量入口，Claude Code 构成。一篇《我在 Claude Code 前面装了字节记录仪，跑了一周》有天然读者；换成 OpenClaw 就没有。

**结论**：内容策略 v3 §0.1 应当推翻。**Claude Code 不是"不成立的叙事"，它是四类人群里唯一能同时提供"大搜索量 + 结构性独占"的题材。**

| **字节级两层记录** | S3 | **最弱** | CCR 完全可以在 transformer 之前记一份客户端原始 body、之后记一份出站 body。**这不是架构障碍，是他们没想做。** 把对外表达锁在这里，是在展示自己最容易被追平的部分 |

### 4.1 为什么额度配速排第一

**它不是"多账号轮转"的加强版，是另一类问题。** 设计文档 §1.1 的论证很硬：套餐额度周期性作废、不结转，要最小化的是"周期结束时未用完的额度 + 用尽后溢出到按量计费的花费"——这是**配速问题**，不是负载均衡问题。直觉的 `remaining/total` 在重置日不对齐时给出**方向性反向**的结论（三个套餐重置日 1/15/20 号，今天 16 号，最该被优先烧掉的那个权重最低）。

四条难以复制的理由：

1. **认知门槛在市场调研里，不在代码里。** headroom 公式只有三行，但要知道"该用比值不是存量""周期最长的 tumbling Limit 是桶、其余是闸、闸只压不提""rolling 永不当桶"，前提是先有 81 个在售套餐的形态分布。**那份调研是资产，代码不是。**
2. **它要求先放弃"负载均衡"心智模型。** 所有现存的多 key 池化工具（new-api、gpt-load、各家单厂商中继）都建立在轮转/加权轮询上；而设计文档 §5.3 论证了 SWRR 在这里三重有害（需持久化累加器、只回答"选谁"不给 failover 顺序、撒开流量直接摧毁 prefix cache 局部性）。这是与它们的产品直觉正面冲突的方向。
3. **它必须与会话亲和共存才成立。** §6.1 的三条不变量（quota 在 `Sort` 之后、Sticky 在 quota 之后、quota 只重排从不淘汰）——少任何一条，就会一边省额度一边打掉 prompt cache，净效果为负。**能做对这一步的前提是先做过 Sticky。**
4. **企业网关的同名功能方向相反。** LiteLLM 的 budget/rate-limit 是**下游治理**（限制某个 key 花多少），VMR 的是**上游配速**（把已经花掉的套餐钱烧出价值）。前者省钱，后者防浪费，算法、数据源、失败姿态全不同。

**修正后的一句话表述**：

> **入口**：别人帮你在多个厂商之间轮转，VMR 帮你在每个套餐作废之前恰好把它烧完。
> **出口**：别人记下 HTTP 日志，VMR 把原始字节还原成 Agent 到底怎么想、怎么忘、在哪一步走岔的结构化叙事。

前半句卖给 ②（有钱的数字，立刻可懂），后半句卖给 ③/④（要读完才懂）。**先讲前半句。**

## 5. v2 特性清单重估（独立裁决）

用户明确要求不盲信 v2 文档。以下每一项都先核对代码，再给独立判断。

### 5.1 P0 `vmr.sh doctor` + `--json` → **删除，已被实质取代**

**核对**：`vmr.sh` 无 `doctor`；但 `vmr diagnose` 已经是四阶段一条命令——加载配置 → 跑与 `vmr check` **共享的** `config.Check` 一致性扫描（不干净就跳过后两阶段，因为"没必要为一个人还得先修声明的端点拨号"）→ DNS/TLS/代理可达性（代理场景不去直连上游，避免误报）→ 每端点一次真实最小请求 + 路由预览；并发受限执行、`-json`、`FailCount()` 驱动退出码。

**判断**：v2 定义 doctor 的目标是"一条命令给出配置/连通性/运行时的红绿灯摘要"，**`vmr diagnose` 已经覆盖了其中的配置与连通性两段**，缺的只有"运行中实例的健康态"——而那需要 `vmr status`，且 diagnose 的包注释已明确说明为什么它不该去碰（health 注册表是 per-process、从不持久化，一次性进程读不到）。

**再包一层 `doctor` 是负债**：多一个入口、多一份要同步维护的文案、多一个用户要学的名字，换来的只是把两条命令合成一条。`vmr check -json` / `vmr status -json` 是可有可无的边角（`cmdStatus` 底层本来就是拿 JSON 再重新格式化，加 flag 近似零成本，但也近似零价值）。**从清单里删掉，不要为了清单完整性造一个包装。**

### 5.2 P1-1 软拦截升级为可 failover → **降级到 P2；先做一件 0.2 天的事**

**核对**：`soft_block_detected` 仅写进 `attempts[].norm`；`norm` 只在 `internal/report/detail.go` 的逐请求详单里渲染；`internal/report/session.go:143` 的 `norm` 字段**赋值后零消费者**（唯一赋值在 :380）。**没有任何聚合统计。**

**独立判断，两条理由推翻 P1 定位：**

**① 决策门存在，但没有仪表。** v4 Core §5 白纸黑字写着这是"**第一阶段**：先把频率变成可量化的数字，再决定要不要做请求预处理"。观测跑了三周，**而"频率"这个数字至今没有任何人能看到**——要回答"软屏蔽到底多常见"，今天只能自己去 grep JSONL。**在这个数字缺席的情况下讨论"要不要做 failover"，是在没有证据的前提下动全清单里架构风险最高的代码路径**（要拆开"2xx 即刻上报健康并开始转发"这个隐含前提，v2 自估 2–3 人天且需额外回归验证）。

**② v2 自己收窄的范围，恰好覆盖不到最需要它的场景。** v2 把范围限定在 buffered（非流式）响应，并承认流式"技术上做不到 failover"（首字节已写出）。**而 Agent 流量绝大多数是流式的**——Claude Code、Cursor、OpenClaw 默认全流式。所以这个修复上线后，在真实 Agent 场景里的覆盖率可能接近零。这一点 v2 写了，但没有据此重新评估优先级。

**该做的是那件小事**：把 `session.go` 那个 dead field 接上，在 `vmr report` 加一节（或直接并进 §7 效率发现）统计 `norm` 各标记的出现频率与分布——`soft_block_detected` / `thinking_process_pattern_detected` / `crlf_framing_suspected` 都在等这个读数。**成本约 0.2 人天，直接解锁一个已经等了三周的决策门**，而且顺带把一个"写了没人读"的字段变成有用的。

**这一项是 v2 清单里最典型的一处误判**：它把 P1 定在"做修复"上，而真正卡住的是"没有数据做决定"。

### 5.3 P1-2 上下文超限独立错误类 → **维持 P1，且理由比 v2 更强；全清单 ROI 最高**

**核对**：`core.ErrorClass` 无 `ErrContextLimit`；`internal/adapter` 无任何 context-length 词表；`DefaultClassify` 的 400 分支依次过 contentHint → model-unknown 词表 → upstreamHint → **兜底 `ErrClient`**。也就是说，一个上游返回的 "maximum context length exceeded" **今天会被直接返回客户端，一次 failover 都不发生**——一个跑了两小时的 Agent 任务就此终止，即便候选队列里躺着一个 context 更大的端点。

**三条 v2 没有的新论据，让这一项的优先级不降反升：**

1. **项目自己的语料证实了这个场景是常态而非例外。** v4 Analytics §6 实测：95.86% 的相邻编辑是纯追加；存在 444 请求的单会话；`context_growth`（末轮/首轮 token 比）是一个专门设计的指标。**上下文单调增长是 Agent 的默认行为**，撞上限只是时间问题。
2. **预防层默认是关的。** `max_context_tokens` 条件路由的语义是"**未声明 = 不限制**"（v4 Core §6.4，为了旧配置零改动迁移）。绝大多数配置不会逐端点声明它，所以对默认配置而言，预防这一层根本没生效——反应层是唯一防线，而它现在是缺的。
3. **修复自带自愈，代价比 v2 估计的更低。** 我原本担心：修好之后，一个已经超限的长会话会不会每一轮都白付一次对小端点的失败尝试？**不会**——粘性指针在**每次成功后**都更新（v4 Core §6.5，"这是自愈设计，不需要额外的失效检测逻辑"），所以第二轮起 Sticky 会直接把请求送到那个成功的大端点。**这个机制已经在了，等于这个改动免费获得了收敛性。** v2 没有这条论证。

**成本与风险**：0.5–1 人天，改动面最小（在既有分类链上插一段中英双语词表 + 一个新 ErrorClass，行为与 `ErrContent` 同构：换端点、不惩罚端点健康）。误判的最坏后果是多一次无害切换。

**结论：这是全清单里 ROI 最高的一项，应当排在所有其他特性之前。**

### 5.4 P1-3 预算硬闸 → **改名、重定范围后成立；成本降到原估的 1/3**

**核对**：额度路由明确不熔断（设计文档 §12.1"耗尽处理：只降到梯队末位"，理由是"按估算值执行破坏性动作 = 自制故障"）。`quota.Registry` 已有 per-provider 周期计数 + 原子持久化 + 惰性重置。

**表面看，v2 的 P1-3 已被 quota 的决定否掉。我认为没有——两者解的是不同的问题：**

| | quota 配速 | v2 的 P1-3 |
|---|---|---|
| 解决 | 稳态：多套餐之间怎么分流才不浪费 | 尾部：一个失控 Agent 一夜烧光 |
| 触发条件 | 持续、渐进 | 突发、异常 |
| 判据精度要求 | 比值要对 | **只要数量级对**（今天的量是平时的 10 倍还是 1.1 倍） |
| 不做的代价 | 浪费一部分套餐 | **无界的真金白银** |

quota 反对熔断的论证——"计数器是估算值，按估算值执行破坏性动作等于自制故障"——**只对"额度耗尽"成立**。判断"这个虚拟模型在一小时内发了平时一天的量"不需要精确计量，±30% 的估算误差完全不影响结论。**把一条针对精确性的论证套用到一个不需要精确性的场景，是这两份文档之间没被发现的一处错配。**

**决定性的不对称**：不做，失败是**无界的**（钱）；做了，失败是**有界的**（一个请求被拒 + 一条能被解析的明确错误）。而这个项目自己的研究证明了风险真实存在——`exact_repeat_tool_call` 检测器的立论依据就是 `anthropics/claude-code#15909`（**重试 300+ 次、耗时 4.6 小时**）和 `#19699`（同一命令连续报错 7 次以上才被人工打断）。

**这里有全项目最值得指出的一处不对称**：VMR 花了两轮真实语料校准，建了一套精密的**事后**失控循环检测器；而在**实时**路径上，它是这条链路里**唯一有能力叫停**的组件（Agent 不会自己停——那正是失败模式；厂商不会停——他们在收钱），**它选择了旁观**。这与 §6 要讲的"诊断 vs 治疗"是同一件事。

**建议的重定范围**：

- **改名**：不叫 budget（那个词现在归 quota，而 quota 正确地拒绝了执法），叫 **runaway guard（失控闸）**；
- **判据**：per-virtual-model 的短窗口计数（滚动 1h 或当日），**只做 requests 或等权 token，不碰定价**——异常检测不需要金额精度；
- **动作**：触顶返回明确 429 + 可解析错误体（说清"虚拟模型 X 在 Y 窗口内已用 Z，阈值 W"），**绝不静默降级到便宜模型**（静默降级会让 Agent 在不知情的情况下换了个脑子，比直接失败更难排查——v2 这条取舍是对的，保留）；
- **检查点**：请求入口只查一次，不在每个 attempt 上查，避免"重试到一半突然被拦"的中间态；
- **重置语义**：进程重启即重置，文档直说"这是防呆，不是防欺诈"，**不为它引入新的持久化**（`quota.Registry` 的 `vmr-quota.json` 已在，可搭车，不新增子系统）。

**成本**：v2 估 1.5–2 人天，那是在 quota 不存在的前提下估的。现在周期数学、计数器、持久化、惰性重置全部现成，**实际约 0.5 人天**。

### 5.5 一处独立发现：`metric: cost` 的错误信息给了严格性，没给出路

**核对**：`internal/config/pricing.go` 的加载期错误文案质量很高——把"为什么四项必须齐全"讲清楚了（缺失当 0 会低估消耗 → 账号显得宽裕 → 拿到更多流量 → 超支）。**但没有一条错误信息告诉用户下一步能做什么。**

这与另一个已知事实叠加就变成了真问题：内置标准表的 `cache_read` 覆盖率 23%、`cache_write` 仅 8%，且**对国产第一方厂商明显偏弱**（设计文档 §4.2① 自述）。也就是说——**中国大陆用户，即目标人群，配 `metric: cost` 时撞上这个硬失败的概率最高**，然后得到一条解释得很好、但走不通的错误。

**建议**（约 20 行）：这条错误信息追加一句可执行的出路——

```
provider "xxx": metric: cost: 模型 "yyy" 缺 cache_write 费率。
可选出路：
  (a) 在 providers[].pricing.overrides 补全四分量（推荐，同时让 vmr report 的 $ 变准）
  (b) 改用 metric: tokens + token_weights 表达同一个折算比例，不需要绝对价格
  (c) 补一行到 standard_price_curated.yaml 并回贡（这个模型缺的是公开数据，不是你的配置）
```

**"失败得响亮"是对的（严格性不该动），"失败得没有下一步"不是。** 而且 (c) 顺带把一个报错变成了一个贡献入口。

### 5.6 v2 P2 清单：逐项 grep 后，维持不动

`client_ip` / `-no-sessions` / `replay -list` / `--format=curl` / `weight` 排序维度 / `/metrics` / `vmr watch` / 端点级 rpm 限流——**全部仍不存在**，且这半个月里**没有任何一项获得了新证据**（依然是零外部用户要求）。v2 说"等第一批用户反馈后再排"，这条判断至今成立，原样保留。

`strategy` 包目前只有 `priority` 一个 `Compare` 实现——`Dimension` 接口从设计之初就是为"任意组合多个维度"准备的，但两个月过去只有一个实现。**这不是缺陷，是一个应当被注意的信号**：那个接口的扩展性至今没有被任何真实需求验证过。

## 6. 真正的竞争对手是"重跑一次"

竞品地图把 CCR、LiteLLM、Langfuse 排出来比功能，但一个潜在用户面对"我的 agent 昨晚跑歪了"时，真实选项集是：

| 选项 | 成本 | 有效性 |
|---|---|---|
| **重跑一次** | 几分钟 + 几毛钱 | 对大多数偶发问题**有效** |
| 改 prompt 再跑 | 十几分钟 | 通常有效 |
| 装一个取证工具，学它的模型，等它攒够数据，读它的报告 | 数小时 + 数天 | 只对**反复发生**的问题有效 |

**"黑匣子"叙事在结构上打不过第一行。** 飞机黑匣子成立，是因为飞机不能重飞、失事代价无限大；Agent 可以重跑，失败代价通常是几毛钱和十分钟。用航空业的隐喻去卖一个可重试系统的取证工具，隐喻本身就在削弱说服力。

**能打过"重跑一次"的只有反复发生、可累加、可量化的浪费**：

- **"这三个套餐里有一个每月作废 40% 的额度"** —— 每个计费周期重新发生一次；
- "你 31% 的 input token 花在了从来没被调用过的工具 schema 上"；
- "你的 prompt cache 命中率是 18%，因为路由每次换端点"；
- "这个 Agent 每次 compaction 平均吞掉 12 个文件路径引用"。

### 6.1 但第一条和后三条不是同一类东西

后三条是**诊断**：VMR 把浪费指给你看，你自己去改配置、改 prompt。中间有一道"用户要读懂并采取行动"的落差，转化率天然很低。

第一条是**治疗**：额度配速直接改变路由行为，用户不需要读任何东西，省下的钱自己会出现在下个周期。

**这是全项目唯一一次从诊断跨到治疗**（§5.4 建议的失控闸会是第二次）。对一个 3 star、零流量、只能靠口碑的项目，一个"不需要任何阅读就能自证价值"的能力，价值比任何新增分析维度高一个数量级。

**头版承诺应当是**：

> **你买了几个套餐，它负责在每个套餐作废之前恰好把它烧完；顺便，它记下了这中间发生的每一个字节。**

黑匣子降为第二层叙事——它是"为什么这些数字可信"的依据，和 byte-faithful 在 v2 里被降到第三层是同一个道理。

## 7. 风险重排

| 风险 | 概率 | 影响 | 评估与缓解 |
|---|---|---|---|
| **1. 一轮分发失败之后动力枯竭** | **高（当前最大）** | 高 | 22 篇内容 → +1 star 的挫败感，比"还没开始做分发"大得多。缓解是把下一轮的成本与判据都写死（§8、§9），让它是一次**有边界的实验**而不是又一次开放式投入 |
| **2. 维护面超过单人可持续上限** | 中高 | 高 | 24 个包、33K 行生产代码、三协议 × 请求/响应 × 流式解析、五类编辑分类阈值、九条检测器、定价表、i18n 双语。这不是可继承性问题（文档确实扎实），是**日常回归成本**问题。缓解：冻结分析半区新维度（§8.4） |
| **3. `amount` 标定门槛，且失效方向与功能目的相反** | **高** | **高** | `amount` 必须按 vmr 观测口径标定（Credits 套餐差 3–8 倍、按 prompt 计数的套餐约 15 倍）。**标小了会把最该用的套餐排到最后**——首次配置就踩坑，体验是"我配了额度路由，它把我最该用的套餐排到了最后"。缓解：§8.1 |
| **4. `base_url` 这扇门被关上** | 低-中 | **致命** | 全部价值的前提是闭源 Agent 尊重 `ANTHROPIC_BASE_URL`/`OPENAI_BASE_URL`。厂商有关掉它的商业动机。缓解有限（企业 Bedrock/Vertex 场景在拉着这扇门不关），应记为不可控的存在性风险，并作为"不要在这上面押上过多工程"的依据 |

| 6. CCR 沿路径追平 | 中 | 中 | 从 v2 的"高"下调。它能追平的是弱护城河（字节记录、成本估算），追不平 `ctxgraph`，也追不平额度配速（§4.1 四条）。真正的问题仍是它有流量而 VMR 没有 |
| 7. Bus factor 1 | 高 | 高 | 文档 + archtest + 1:1 测试已把**可继承性**做到位。但可继承性 ≠ 有人继承；在 0 star 状态下这条等价于风险 1 |
| 8. LangSmith/Langfuse 赶超 | 低 | 低 | 从竞品报告的"高"下调。它们的商业模式决定了服务的是"在写自己 Agent 的团队"，永远不会去做"审计一个你改不了源码的 Agent"——那个人群不买席位 |
| 9. 顶层文档分散导致复核基于残缺图景 | **中（已发生两次）** | 中 | 竞品报告漏读 TokenPlan 设计文档，据此得出"不应继续加路由功能"的相反结论；本报告上一版犯了同一个错。**`CLAUDE.md` 只把 v4 Core/Analytics 列为必读，TokenPlan 那份只在表格行里被顺带提及。** 缓解成本几分钟：升格为并列第三篇必读 |

## 8. 建议

五条。**只有三条需要写代码，全部在 1 人天以内，且没有一条在增加分析能力。**

### 8.1 T0 · 代码 · 把额度配速的首次配置门槛砍掉（0.5–1 天）

### 8.5 T1 · 冻结分析半区新维度，明确拒绝 `vmr assess`

对既有竞品报告提出的 `vmr analyze`（自动化分析流水线）、`vmr assess`（LLM-as-judge 任务成败判定）、工具语义正确性、目标漂移曲线——**全部拒绝进入二进制**：

1. **它们是永久维护义务**，不是一次性交付。在 0 外部用户状态下增加永久维护面，是主动放大 bus factor 1 的风险（风险 2）。
2. **它们在 VMR 没有优势的赛道竞争。** LLM-as-judge 的质量取决于 prompt 工程与校准集，不取决于你的字节记录多完整。
3. **最关键：不需要写进 VMR 就能实现。** `vmr-report.json`（schema format 10）与 `journey-<id>.json`（九指标 + Findings）**已经是稳定的、固定英文的机器接口**（v4 Analytics §4.3 明确承诺过的契约）。任何人写 60 行脚本读 `journey-*.json` + 原始审计记录，喂给任意模型做成败判定，完全不碰 VMR 一行代码。

**替代方案**：`docs/` 里写一页《基于 `vmr-report.json` / `journey-*.json` 做二次分析》，把契约变成公开承诺，附一个示例脚本。**满足需求，同时把维护义务留在仓库之外。**

**这一条不适用于路由半区的 P3/P4。** 额度设计文档 §14.3 的 P3 触发条件是"P1/P2 上线后的运行数据显示 429 频率或尾延迟代价确实值得"——**这是全项目写得最好的一条触发条件**，它把"要不要做"绑定到可观测事实而非排期。原样保留，不要因为本节主张冻结分析半区就顺手把它冻了：一个是有触发条件的等待，一个是没有需求证据的扩张。

## 9. 要不要继续做，以及这次的止损线

**要，但这是最后一次以"公开项目"为目标的投入。**

### 9.1 为什么不是现在止损

上一版说"实验没开始所以不能判失败"——那个说法已被证伪。**正确的说法是：这一轮实验测的不是那个假设。**

- 假设是："linux.do / V2EX / 掘金 / HN 上，有一批人正在被多套餐额度和 Agent 黑盒困扰，看到就会想用。"
- 实测的是："AI 批量生成的知乎回答和 Reddit 评论，能不能带来流量。"

**后者的答案是明确的否，但它不能推出前者的否。** 用寄生格式测主题帖假设、用示意数据测数据可信度产品、用最弱的题材测最强的差异化——这一轮的三个变量全部设错了。

### 9.2 检查点（修订）

前提：§8.1–8.3 完成（约 2 人天代码）+ §8.4 第一篇按三条硬约束发布到主题帖渠道。

| 时间点 | 期望 | 未达成时 |
|---|---|---|
| 第一篇主题帖发布后 2 周 | 单帖 ≥2000 次浏览 **或** ≥10 条实质回复 | **先判渠道**：浏览量不够 = 渠道/标题问题，换题材再发一次；浏览够但无人回 = 内容/产品问题，进入下一行 |
| 第一篇发布后 1 个月 | ≥1 个非作者 issue **或** ≥30 star | 换渠道与题材再试一轮，**不改产品** |
| 第一篇发布后 3 个月（已换过一轮渠道） | ≥100 star、≥3 个非作者 issue | **触发止损** |

**新增第一行是关键**：上一版的检查点全是滞后指标（star / issue），无法区分"没人看到"和"看到了不想要"——而这恰好是这一轮失败最需要区分的两件事。**先量曝光，再量转化。**

### 9.3 止损意味着什么

停止新特性开发（上游协议跟随与缺陷修复除外）；停止分发投入；仓库保持公开；**自用特性不受限制**——额度配速、成本归因这类解决作者每天真实问题的东西，是这个项目继续存在的理由，与有没有外部用户无关。

**这不是失败。** VMR 在自用价值上早已回本。明确写下这条规则的意义在于：让"继续以公开项目为目标投入"变成一个每次都被主动确认的决定，而不是默认状态。

### 9.4 一条关于规划体系的观察

项目里存在两套论证质量差一个数量级的规划：

| | 特性侧（TokenPlan 那支） | 分发侧 |
|---|---|---|
| 论证依据 | 81 个在售套餐分布；等权记账高估 3–8 倍的量化；`remaining/total` 的反例 | "我们只有 3 个 star" |
| 决策留痕 | 决策表 + 否决提案表 + 边界限制表 + 落地现状表 | 一张 D1–D8 清单 |
| 触发条件 | "运行数据显示 429 代价值得" | 无 |
| 执行结果 | P1/P2 全交付，交付后还做了一轮复核修完七项 | 计划的渠道没执行，换成了更弱的 |

**这不是纪律问题，是论证质量的不对称。** 一个有 81 条市场证据的方向和一个只有"我们需要用户"的方向竞争注意力，结果是可预测的。因此建议的规则不是"加交替节拍"，而是作用在论证上：

> **任何分发动作开工前，必须先写出与特性设计文档同等质量的论证：服务哪一类人群（§3 四选一）、他们的损失能量化成什么数字、为什么这个渠道能触达他们、做完之后用什么可观测事实判断有没有用。写不出来的，删掉，不要挂在清单上假装是待办。**

§8.4 的第一篇文章可以立刻自检一次：服务人群 ②、损失是"每周期作废的套餐额度"（可算成金额）、渠道是 linux.do/V2EX/掘金（多套餐采购讨论密度最高）、判据是发布后 2 周的浏览量与"我三个套餐怎么配"这类提问。**这段论证够不够强可以争论，但它至少是同一种东西**——而"README 应该有截图"不是。

| `vmr diagnose` 已实质覆盖 doctor | 最高 | 读 `internal/diagnose/diagnose.go` 包注释与 `cmd_diagnose.go` flag |

| **失败点在渠道格式（主题帖 vs 寄生格式）** | **中高** | 计划渠道与实际渠道的对照是事实；"寄生格式曝光低一到两个数量级"是基于平台机制的一般性推理，**无该项目的平台数据** |
| "AI 生成腔加剧了失败" | **中** | 12 篇同模型批量生成是事实；社区反感是普遍观察，**无本项目的实证** |
| 额度配速是路由半区最强护城河 | 高 | §4.1 四条中第 1/3/4 条可直接核实；第 2 条（现存池化工具全部基于轮转）基于公开描述，**未逐个读源码** |
| P1-2 应维持最高优先级 | 高 | 三条论据均可核实（语料统计来自 v4 Analytics §6、`max_context_tokens` 默认语义来自 §6.4、Sticky 自愈来自 §6.5） |
| P1-3 应改名重定范围 | 中高 | 论证基于"异常检测不需要精确计量"这一推理；**失控 Agent 在本项目用户身上的实际发生频率未知**（引用的两个案例来自 claude-code issue，不是本项目语料） |
| `amount` 标定门槛会导致卸载 | 中 | 偏差量级（3–8 倍 / 15 倍）来自设计文档自述，可信；"用户会因此卸载"是推断，**无真实用户数据** |
| 推翻内容策略 v3 的 Claude Code 判断 | 中高 | 三条理由中前两条是逻辑论证；第三条（搜索量差数量级）**未查实际搜索数据** |
| `base_url` 被关闭的风险 | 中 | 无具体厂商信号，纯商业动机推理 |

**最大的信息缺口仍然是零真实用户反馈**，且这一轮分发没有缩小它——因为没有产生足够的曝光去获得任何反馈。§8 的全部动作服务于同一个目的：**把这个缺口从"完全未知"变成"至少有一个数据点"**。

**方法论教训**（两次犯同一个错，值得固化）：竞品报告漏读了 TokenPlan 设计文档，据此得出"不应继续加路由功能"的相反结论；本报告上一版漏读同一份文档，据此做出一个错误的"边界侵蚀"指控。**两次犯错的一方都以为自己读全了。** 这说明当前的文档拓扑（顶层设计文档六份以上、`CLAUDE.md` 只指向其中两份为必读）**会系统性生产这类错误**。风险 9 的缓解成本是几分钟，是本报告投入产出比最高的一条建议——尽管它最不像战略。

**本版未做的验证**（列出以免下次重复论证）：未实际部署 VMR 跑一次真实 Agent 任务复核 report/story 输出质量；未实际配置一次 `quota:` 块验证配置门槛的真实高度；未查各平台的实际发布链接与阅读数据（分发结果依据用户口述 + star 数）；未逐项核对 CCR / Langfuse 的最新能力；未独立验证 81 套餐市场快照的数据源（单一站点，快照日期 2026-07-26，其自述"超过三个月后引用前请重新核对"）。
