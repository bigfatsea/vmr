## 0. 项目基本情况与代码工程现状 (Project Reality)

### 0.1 VMR 项目背景与定位
VMR（Virtual Model Router）是一个单二进制、配置驱动、基于物理网络层（`base_url`）代理的 **AI Agent 飞行记录仪与透明路由中间层**。它面向 2026 年无人值守 AI Agent（如 Claude Code, OpenClaw, AutoGen, 自研 Autonomous Agents）的爆发时代，解决 Agent 后端黑盒运行、调试困难、上下文迷失、国产模型怪癖、多订阅套餐（Token Plan / Coding Plan）额度浪费等真实痛点。

## 1. 三份战略文档的强共识提炼 (Strong Consensus)

综合三份报告，全员在以下六大底层命题上达成了**绝对强共识**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      三方报告强共识底层框架                               │
├─────────────────────────────────────────────────────────────────────────┤
│ 1. 绝对本质：VMR 不是翻译 Gateway，而是 "Agent 飞行记录仪 + 路由中间层"  │
│ 2. 数据信任：字节级透传（Byte-Faithful）是可信度与审计的不可替代基石      │
│ 3. 架构隔离：离线只读分析（report/story/replay）与 Live 路由高可用物理解耦 │
│ 4. 核心建模：`ctxgraph` Git 式内容寻址快照图谱是处理多轮历史的最佳模型   │
│ 5. 最高 ROI 交付：`ErrContextLimit`（上下文溢出救场）已识别为核心缺口并全量落地   │
│ 6. 严明边界：严格遵守 "不做清单"（不做跨协议翻译、不做语义缓存、不做静默降级） │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.1 共识一：VMR 的本质是 "Agent 飞行记录仪"，路由是入口，分析才是护城河
三份报告均明确指出：VMR 绝不在 LiteLLM / Bifrost 等“企业级协议翻译网关”赛道。VMR 的真正定位是放在 Agent 宿主与上游 LLM 物理网络之间的**透明黑匣子（Flight Recorder）**。路由能力是获取第一手真实流量的入口，而把原始流量还原为 Agent 的心路历程与行为演化才是核心壁垒。

### 1.2 共识二：字节级透传（Byte-Faithful Passthrough）是保真度与信任的根基
VMR 在路由阶段对 HTTP Body 采取单趟免分配的字节级修改（仅就地替换 `model` 字段），绝不进行反序列化或跨协议字段转换（如 Anthropic ↔ OpenAI）。这保证了上游最新扩展（如 Anthropic `thinking` 过程）免适配透传，且离线审计日志拥有法律取证级的物理保真度。

### 1.3 共识三：离线只读消费是性能与正确性的天然边界
VMR 路由主线仅向磁盘追加 JSONL（`audit.Record`），完全不知道分析模块的存在。`vmr report`/`vmr story` 作为独立离线进程消费日志。这种设计确保了“分析层算法调整或崩溃绝对不影响路由转发毫秒级延迟（p95 < 10ms）”。

### 1.4 共识四：`ctxgraph` 基于 Git 思想的内容寻址模型极其硬核
Agent 每一轮请求都会重复吐出累积的历史上下文。`internal/ctxgraph` 将消息取 Hash 化为快照向量，通过判断相邻快照间的五类编辑（Append / ReplaceTail / Splice / Contract / Fork），实现了框架无关、无需埋点的会话与任务 DAG 确定性重建。实测 406,534 对 tool_call/tool_result 零孤儿。

### 1.5 共识五：上下文超限救场（`ErrContextLimit`）是全清单最高 ROI 且已落地的核心特性
三方曾认定：在多轮 Agent 请求中，长上下文超限返回 400 时，若被误判为 `ErrClient` 则会阻断 Failover。在最新的 VMR 实现中，这一缺口已被正式攻克：新增 `ErrContextLimit` 错误分类与词表嗅探，在长上下文溢出时自动 Failover 切换至更大窗口的候选端点且不惩罚原端点健康分，实现了长上下文 Agent 任务的无缝救场。

### 1.6 共识六：极其清晰的“不做清单”（Boundaries & Disregard）
绝对不做跨协议格式强转、绝对不做语义缓存（避免干扰 Agent 决策路径）、绝对不做静默模型降级、绝对不做 SaaS/多租户/复杂的 DB 存储捆绑。

尽管底层哲学一致，但三份报告在**护城河排序、分析功能落地方式、GTM 分发策略**上展现出重要分歧。

```
                              三方战略分歧焦点
                                     │
         ┌───────────────────────────┼───────────────────────────┐
         ▼                           ▼                           ▼
  [Custom-2 (v1.0)]         [Gemini 3.6 Flash]               [Opus 5 (v4.0)]
• 视角：轨迹分析 47 维度     • 视角：架构演化与第一性原理     • 视角：冷实核查与 GTM 止损
• 判定：分析太原始，应停建   • 提炼：预言机悖论与四阶逼近     • 判定：配速路由才是第一护城河；
  路由、全面产品化分析         评估；支持 Web UI (vmr ui)      强拒将 assess/analyze 写入二进制；
                                                              真实竞品是 "重跑一次"
```

### 2.1 Custom-2 Agent (v1.0) 的独立视角与局限
* **核心视角**：对照《Agent 运行时轨迹深度分析》47 个评估维度对 VMR 进行对照打分。
* **主要结论**：认为 VMR 数据采集世界级但分析极原始（仅实现约 1/3），主张“下一步战略重心绝不是继续加路由功能，而是把数据资产转化为分析产品”。
* **视角局限与分歧**：由于未读全额度路由设计文档（现 `VirtualModelRouter_Design_v4_Quota.md`），误以为“路由半区已无重大空间”，忽视了 Token-Plan 配速路由对多订阅小团队的巨大经济价值。

### 2.2 Gemini 3.6 Flash (Master Plan) 的独立视角与理论突破
* **核心视角**：从第一性原理分析 VMR 的双核本质，深入拆解 Agent 任务完成度判定的物理与认知边界。
* **理论突破——预言机悖论 (Oracle Paradox)**：指出没有任何自动化系统能在网络层 100% 精确判定“用户终态心理满意度”（评价者认知能力必须超出生长者）。指出传统侵入式框架宣称的成功率 90% 是偷换概念（仅是 Agent 主观打卡或固定沙盒测试集）。
* **解决方案**：提出 **任务完成度四阶逼近策略（Four-Tier Approximation Strategy）**（结构推断 → 可选 Header → LLM-as-judge 双端评估 → `ctxgraph` 纠错反悔追溯），并建议开发 Go embed 单二进制 Web UI (`vmr ui`)。

### 2.3 Opus 5 (v4.0) 的独立视角与严厉审视
* **核心视角**：基于代码库提交 `c62fa07` 与分发资产做地面物理诊断，复盘首轮分发实验的失败。
* **分歧点一：护城河重新排序（配速路由第一，字节记录最弱）**
  * Opus 5 认为，受限于“重跑一次”的竞争态，单纯的“黑匣子事后诊断”门槛高、变现难。**已落地的跨厂商 Token-Plan 额度配速（Headroom 算法）才是全项目唯一能直接算成钱、主动预防浪费的第 1 护城河**；`ctxgraph` 第二；字节记录最容易被竞品抄袭，属于最弱护城河。
* **分歧点二：坚定拒绝将 `vmr assess` / `vmr analyze` 写入 VMR 主二进制**
  * 强裁：在 3 star / 单人维护状态下，将 LLM-as-judge 等分析流水线硬塞进二进制是主动放大 Bus Factor 1 风险。VMR 应坚持提供极其稳定的 JSON 暴露契约（`vmr-report.json` 与 `journey-*.json`），将二次分析交由外部 60 行 Python 脚本处理。
* **分歧点三：真正的竞争对手是“重跑一次”**
  * 指出 Agent 偶发错误的解决成本极低（重跑一次几毛钱），导致“事后取证”非刚需；只有“每月确定性作废 40% 套餐额度”这类复发性、可累加的真金白银痛点才能打败“重跑一次”。

## 3. VMR 核心特性、设计哲学与核心竞争力 (Core Moats)

### 3.1 核心设计哲学 (Design Philosophy)
1. **字节级保真（Byte-Faithful）**：透明转发与保存真实网络字节，不自作聪明修改数据，以此构建法律取证级别的绝对信任。
2. **零代码侵入（Zero-Instrumentation）**：代理网络 `base_url` 路径，无需 Agent 应用安装任何 SDK 或修改源码。
3. **离线只读与彻底解耦（Offline & Non-blocking）**：分析逻辑不在在线请求路径上，维持极致路由性能与故障隔离。
4. **数据真诚与诚实边界（Honesty & Transparency）**：区分“规则事实（确定性）”与“LLM 推测（概率性）”，绝不在分析结果中混淆假象。

### 3.2 核心特性全景 (Core Capabilities)

```
                              VMR 双核核心能力矩阵
                                       │
         ┌─────────────────────────────┴─────────────────────────────┐
         ▼                                                           ▼
  [ 路由与高可用半区 (Live Proxy) ]                         [ 运行后黑匣子半区 (Offline Analytics) ]
• 三原生协议入口 (Chat/Anthropic/Responses)               • 两层原始字节物理落地 (Client & Upstream)
• 字节级免分配流式透传 (Splice Model)                     • vmr report (聚合成本/延迟/错误/Sess 分组)
• ErrorClass 动态感知 Failover                            • vmr story (基于 ctxgraph 的 Task/Step 重建)
• Session-Sticky Prompt Cache 局部性保护                  • vmr story -compare (行为剖面与分叉点比对)
• Token-Plan 额度感知动态配速路由 (Headroom)             • vmr replay (1-Click 精准单请求故障取证重放)
• 国产模型怪癖修复 (MiniMax Think / 软屏蔽检测)            • vmr diagnose (物理连通性与配置多阶诊断)
```

### 3.3 四重核心竞争力与护城河评估 (Moat Breakdown)

1. **第一护城河：跨厂商 Token-Plan 额度感知动态配速引擎 (Headroom 算法)**
   * *差异化*：业界唯一解决“多订阅套餐重置日错开”场景下配速优化的引擎。通过无量纲 Headroom 比值公式（$raw = \frac{1 - used\_frac}{time\_left\_frac}$）配合桶（Bucket）与闸（Gate）控制，超越简单的 Round-Robin 或比例加权；最新实现中果断移除了低频且过度建模的分时促销时间窗，保持了高可维护性。
2. **第二护城河：`ctxgraph` 无埋点 DAG 重建与上下文演化剖面**
   * *差异化*：无需 Agent 框架支持，纯结构推断还原会话/任务树，精准识别 Compaction 静默丢失的实体与九类行为异常 Finding。
3. **第三护城河：取证级两层原始字节记录与 1-Click 精准重放 (`vmr replay`)**
   * *差异化*：共用代理层的请求构建引擎，全网唯一能 100% 物理级复现上游大模型边缘 Bug 与软屏蔽的重放利器。
4. **第四护城河：国产厂商生态 Quirk 深度修复与软屏蔽可观测**
   * *差异化*：深度解决国内 MiniMax/DeepSeek 等端点 `<think>` 标签泄漏、Draft 溢出、200 OK 假成功软屏蔽检测，深度绑定国内 AI-native 团队。

## 4. 专项突破：如何深度提升 VMR 在 Agent Runtime 运行 Journey 的分析能力

在 Agent Runtime 运行轨迹（Journey）分析领域，针对目前 VMR “数据世界级、分析偏原始”的现状，结合 Gemini 3.6 Flash 的预言机理论与 Opus 5 的契约解耦哲学，提出以下**四大维度深度提升方案**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│              Agent Runtime Journey 分析能力四维升级路径                   │
├─────────────────────────────────────────────────────────────────────────┤
│ 维 1：语义级工具调用效能与结果吸收率 (Tool Result Utilization)          │
│ 维 2：连续目标漂移与子目标演化曲线 (Goal Drift Trajectory)             │
│ 维 3：任务完成度四阶逼近策略 (Four-Tier Approximation Strategy)         │
│ 维 4：交付架构升级——机器可读 Schema 契约 + 嵌入式 Web UI                │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.1 维度 1：从语法检测升级为“语义级工具调用效能与结果吸收率”
* **现状痛点**：目前仅有 `exact_repeat_tool_call`（语法精确重复检测），无法判定“工具参数是否合理”以及“工具返回的结果是否被后续推理真正吸收”。
* **提升方案**：
  1. **工具结果吸收率 (Tool Result Utilization Rate)**：利用 `ctxgraph` 跟踪 Tool Result 返回后的后续请求。若 Tool Result 返回了大量数据（如 10KB），但下一轮 Request Prompt 极剧收缩且未再提及其中关键变量，自动标记为 `Tool_Result_Ignored`（工具结果被静默忽略）。
  2. **工具调用失败连环追溯**：当检测到 Tool 报错后，追踪 Agent 是发起了语义修正，还是陷入无休止的参数试错（`Tool_Param_Fuzzing_Loop`）。

### 4.2 维度 2：连续目标漂移与子目标轨迹演化 (Goal Drift Trajectory)
* **现状痛点**：仅有规则化的 `plan_execution_misalignment` 离散标记，缺乏对 Agent 在数十轮交互中偏离初始 Task 目标的连续量化。
* **提升方案**：
  1. **意图锚点向量化 (Prompt Intent Anchoring)**：提取 Journey 的首个 User Message 作为元意图。
  2. **Step 级子目标偏移度**：利用轻量嵌入或关键实体重合度，对每一个 Step 的 Tool Call 意图进行漂移计分（Drift Score: 0.0 ~ 1.0）。在 `vmr story` 与前端中渲染为 **“任务意图漂移衰减折线图”**，帮助开发者精准定位 Agent 在第几轮开始“胡言乱语”或“忘记初始要求”。

### 4.3 维度 3：破除伪成功假象的“任务完成度四阶逼近策略”
基于预言机悖论，VMR 绝不可在网络层伪造“100% 确定用户满意”的假象，而是通过四阶梯递进逼近真实成功率：

```
                             ┌──────────────────────────────┐
                             │  阶梯 4: 跨 Journey 行为追溯  │  (ctxgraph 捕捉 5 min 内驳回/修正指令)
                             └──────────────┬───────────────┘
                                            │
                             ┌──────────────┴───────────────┐
                             │  阶梯 3: 离线 LLM-as-Judge   │  (第三方双端评级: 主观宣称 vs 客观匹配度)
                             └──────────────┬───────────────┘
                                            │
                             ┌──────────────┴───────────────┐
                             │  阶梯 2: 无侵入 Header 透传   │  (可选接收 X-VMR-Task-Status)
                             └──────────────┬───────────────┘
                                            │
                             ┌──────────────┴───────────────┐
                                阶梯 1: 物理与结构化特征推断     (零成本判定 NO_REPLY / EOF / 终止工具)
                             └──────────────────────────────┘
```

1. **阶梯 1：结构化特征推断（Structural Heuristics - 零成本）**
   * 若交互以 `NO_REPLY`、`EOF` 或终止工具结尾，打标 `Agent_Self_Declared_Completed`（Agent 主观宣称完成）。
2. **阶梯 2：无侵入 Header 扩展（Optional Header Transparency）**
   * 若宿主 CLI 知道退出码，自愿透传 `X-VMR-Task-Status: completed`，VMR 仅记录不强求。
3. **阶梯 3：第三方 LLM-as-Judge 离线评估（双端双标评级）**
   * 对比 Task 原始输入与最终 Output。在输出中区分两个严格分离的字段：
     * `Agent_Self_Perceived_Status`: Agent 是否自认为完成（主观事实）。
     * `Evaluator_Assessed_Score`: 评估模型对约束满足度的客观打分（打标 `LLM-inferred`）。
4. **阶梯 4：`ctxgraph` 跨 Journey 用户驳回追溯（User Rejection Tracking - 独家软核反例）**
   * **全行业最贴近“真实失败”的硬核指标**：若某 Task 在以“成功”形式结束后 5 分钟内，同一 Session 下用户发起了 `Fix this` / `仍报错` 或 `ReplaceTail` 擦除尾部，`ctxgraph` **强行将上一 Task 终态冲刷覆盖为 `Rejected_By_User`（被用户否定）**！

### 4.4 维度 4：交付架构升级——机器可读 Schema 契约 + 嵌入式 Web UI
* **暴露稳定 JSON 契约**：锁定 `vmr-report.json` (Format v10) 与 `journey-*.json`，将极复杂的 LLM 评估与规则扩展解耦给外部 Python 脚本/生态，保持 Go 主程序极其轻量。

### 5.1 近期核心代码 Task 详细裁决

#### 1. 【核心 P0】`ErrContextLimit` 上下文超限自动 Failover 救场 (✅ 已落地)
* **现状与落地**：已在最新代码中完全实现。在 `adapter/classify.go` 中新增 `contextLimitHint` 词表嗅探（精准排除“请求自身 `max_tokens` 参数超限”等换端点也无法解决的情形），归为 `core.ErrContextLimit`；路由循环中按无健康惩罚模式即刻 Failover 至大窗口端点，并由 `router_serve_test.go` 锁定回归测试。
* **价值**：最高。实测有效挽救了长上下文 Agent 任务因后备端点未被触发而异常中断的问题。

#### 2. 【核心 P0】`norm` 标记聚合统计与软屏蔽可观测
* **现状**：`session.go` 中的 `norm` 字段赋值后无消费方，导致 `soft_block_detected` 仅停留在单条日志中。
* **方案**：接通消费逻辑，在 `vmr report` 中聚合渲染软屏蔽与 Quirk 修复频次（成本约 0.2 天）。

#### 3. 【核心 P0】`vmr quota calibrate` 自动标定输出
* **方案**：增加辅助命令，基于过去 30 天 VMR 实际拦截的四分量 Token 流量，直接计算并输出可复制的套餐 `limits.amount` 建议值，解决 Credits 与 Token 口径不一致的配置痛点。

#### 4. 【核心 P1】Runaway Guard（失控闸）
* **方案**：区别于精密的配速 Router，为虚拟模型增加短窗口（如 1 小时）的纯请求数/等权 Token 流量失控防线。触顶即报 429，防止 Agent 死循环无界烧钱。
