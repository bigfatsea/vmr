## 一、功能模块与核心裁决全景

基于方案与落地过程，系统整体划分为 5 大领域功能模块与 21 项核心裁决：

- **模块 1：数据层切片核心（Slices Engine）**：负责将全量聚合指标解构为 5 大 Macro 领域切片（`summary`、`finance`、`reliability`、`workloads`、`context-efficiency`），补齐现算事实（置信度、成本覆盖率、亮点句、脚注），提供无损的单一真源（对应 D1, D2, D20）。
- **模块 2：Journey 与会话图谱（Journey & Trace Graph）**：负责单任务会话提取、步骤聚类、Blob 顶级自包含压缩、三级 Payload 匹配、LLM 行为深度归因与前驱截断（对应 D18, D19）。
- **模块 3：ViewModel 纯净序列化渲染器（ViewModel Markdown Engine）**：负责在内存中将领域切片转换为扁平排版结构，集成 i18n 多语言，以单一路径（全量与 `-render-only` 同轨）输出最终报表（对应 D3, D4, D5, D10, D11, D12）。
- **模块 4：轻量级前端 HTML 看板（SPA Dashboard Matrix）**：以 `go:embed` 常驻 6 大骨架页，基于内联 CSS 变量与原生 SVG，通过 `#data=` 传参实现动态加载与本地双击查看（对应 D6, D13, D14, D15）。
- **模块 5：系统级内容寻址缓存与安全服务（Cache & Safe Serve）**：基于 `internal/digest` 链式哈希实现的跨周期两级缓存，以及严格基于 Bearer 鉴权与目录隔离的 `/reports/` HTTP 托管（对应 D8, D9, D16, D21）。

  - **根因分析**：重命名通常依赖快速文本替换，但对由外部导入引用的别名、结构体私有字段或非导出常量容易遗漏；缺乏 AST 级的名称防重现守卫。
  - **建议方案**：使用 `archtest` 增加包名与导出的 AST 命名静态断言，扫描 `internal/` 仓内是否存在名为 `*story*.go` 的源码文件或名为 `Story` 的导出类型。
  - **ROI 评估**：高（投入数小时编写测试守卫，即可彻底消除新老开发者在业务建模上的概念混乱）。

- **ISSUE-02：CLI 命令与标志位参数残留与隐式兼容**
  - **问题描述**：`vmr story` 与 `vmr report` 子命令废弃，参数 `-corpus` 与 `-story-only` 分别更名为 `-benchmark` 与 `-journey-only`；初期仍保留隐式别名兼容。
  - **根因分析**：设计阶段对向下兼容的惯性妥协，违反了单一入口和原则明确的系统设计约定。
  - **建议方案**：在 `cmd/vmr` 中直接删除所有被废弃的子命令与 flag，一旦传入立即报 `flag provided but not defined` 并终止进程。
  - **ROI 评估**：极高（几乎零改动成本，切断用户的历史错误习惯，降低 CLI 参数矩阵维护负担）。

- **ISSUE-03：产物目录与索引文件的旧路径命名**
  - **问题描述**：磁盘输出目录历史为 `stories/`，索引文件为 `vmr-stories.*`，重构后应迁移为 `journeys/` 与 `journeys/index.*`。
  - **根因分析**：文件落盘路径定义分散在多个独立的写入函数中，缺少集中式的产物拓扑常量表。
  - **建议方案**：建立单一拓扑定义（如 `internal/report/paths.go`），所有磁盘写入均引用强类型拓扑常量。
  - **ROI 评估**：高（消除目录漂移隐患，提升产物目录的自解释性）。

- **ISSUE-04：学术化名词 `corpus` 混淆业务语意**
  - **问题描述**：用语原使用自然语言处理领域的语料库 `corpus` 指代多会话聚合统计，使用者不易理解。
  - **根因分析**：模块早期开发者带有浓厚的算法与学术背景，命名脱离了产品化视角。
  - **建议方案**：产品化收敛为 `Journey Benchmarks`，产物定为 `benchmarks.json` 与 `benchmarks.md`。
  - **ROI 评估**：中（显著降低用户的认知门槛与沟通解释成本）。

#### 2. 领域切片与 Schema 演进类

- **ISSUE-05：`vmr-report.json` 单体终结与兼容视图分歧（T1）**
  - **问题描述**：拆分切片时，关于是否保留 `vmr-report.json` 作为过渡大单体产生分歧，保留单体会导致双重真源与巨量冗余。
  - **根因分析**：担心下游消费方适配中断；但单体过大且存在嵌套，导致内存消耗成倍上升。
  - **建议方案**：坚持 D2 裁决，一步删除单体，宏观报表全量走 `macro/*.json`，在 `manifest.json` 中统一管理切片清单。
  - **ROI 评估**：极高（一劳永逸避免架构上的双数据源漂移，彻底解决大 JSON 解析内存瓶颈）。

- **ISSUE-06：统计置信度与低样本事实下沉缺口（T2）**
  - **问题描述**：Markdown 渲染时，对于样本数小于 20 或 Token 覆盖率不足的行自动追加角标（如 `⚠️low-n`），但该事实在原始 JSON 中不存在。
  - **根因分析**：展示逻辑向数据层反向渗透，渲染器私自定义计算口径，导致通过 API 读取 JSON 的下游无法获知该置信度事实。
  - **建议方案**：在数据聚合结构体中显式增加 `tokens_coverage_pct` 与 `dur_low_n` 字段，数据层计算落盘，渲染器只读取做样式映射。
  - **ROI 评估**：高（维护了“JSON 为唯一无损真源”的基本架构不变量）。

- **ISSUE-07：`CostCoverage` 成本覆盖披露缺乏强类型结构（T3）**
  - **问题描述**：关于未定价端点和估算降级的免责提示原先是动态拼装的字符串，缺乏结构化机读字段。
  - **根因分析**：开发时只考虑了报表文本渲染，忽略了下游自动化审计系统需要机读账单置信度的需求。
  - **建议方案**：定义结构体 `CostCoverage{ unpriced_count, incomplete_rate_count, degraded_estimate_pct }` 写入 JSON。
  - **ROI 评估**：中（提升账单审计的自动化能力，消除前端文本解析成本）。

- **ISSUE-08：脚注与免责声明下沉注册表（T4）**
  - **问题描述**：渲染器私自拼接脚注和免责声明文本，未在切片元数据中集中声明。
  - **根因分析**：UI 排版习惯驱动的代码结构，缺乏集中式的元数据治理。
  - **建议方案**：在 `meta` 下增加 `footnotes: map[string]string` 与 `disclaimers: []string`。
  - **ROI 评估**：中（规避多语言翻译时元数据漏译与渲染器硬编码）。

- **ISSUE-09：核心亮点句现算导致 `-render-only` 无法读取（T5）**
  - **问题描述**：报表首屏亮点（Highlights）在渲染期即时运算，导致仅执行渲染模式时无法从 JSON 提取已有亮点。
  - **根因分析**：Highlights 计算逻辑耦合在 Markdown 渲染模块内，未前置至数据聚合阶段。
  - **建议方案**：将亮点文本计算前置并存入 `macro/summary.json`。
  - **ROI 评估**：高（消除全量渲染与独立渲染之间的内容不一致）。

- **ISSUE-10：请求索引中缺少会话元数据投影（T6）**
  - **问题描述**：`requests/index.json` 原只记录单个请求指标，未投影其所属会话与任务标题，导致前端无法执行按会话聚合。
  - **根因分析**：请求提取与会话图谱分割在两个独立阶段，缺少反向索引回填步骤。
  - **建议方案**：在生成 `requests/index.json` 时，通过 `SessionAnalysis` 将 `session_id`、`session_title` 与 `journey_link` 作为扁平外键冗余进索引条目。
  - **ROI 评估**：高（大幅简化前端聚合筛选复杂度，避免前端做笛卡尔积联合查询）。

- **ISSUE-11：时间戳缺乏显示与原始双轨制（T7）**
  - **问题描述**：JSON 仅输出纯时间戳或纯本地化字符串，导致前端与后端对跨时区展示存在分歧。
  - **根因分析**：时区管辖权未理清，底层数据与表现层时间格式耦合。
  - **建议方案**：双字段输出：`ts`（标准毫秒或 RFC3339）保留原始事实，`ts_display` 记录经 `fmtutil.DisplayZone` 格式化的展示字符串。
  - **ROI 评估**：高（彻底解决跨端时间显示与排序对齐问题）。

#### 3. Journey、任务流与 LLM 解读类

- **ISSUE-12：LLM 智能解读内容未入 Journey JSON（N2）**
  - **问题描述**：Markdown 报表中展示了由大模型生成的分析归因（`llm_interpretation`），但同名 `j-<id>.json` 中未持久化该字段。
  - **根因分析**：LLM 调用发生在渲染前夕，且产物直接传递给 Markdown 拼接器，未反向更新到待序列化的 Journey 数据结构中。
  - **建议方案**：在执行完 LLM 解读后，立即写回 `JourneyReport` 结构体中的 `LLMInterpretation` 字段，然后再执行 JSON 落盘。
  - **ROI 评估**：高（修复 HTML 看板与 Markdown 内容不对齐的核心缺陷）。

- **ISSUE-13：三级 Payload 匹配机制容错能力不足**
  - **问题描述**：在从审计日志还原 Journey 步骤时，JSON 请求正文若存在空白符差异或轻微截断，会导致哈希匹配脱靶。
  - **根因分析**：仅采用严格的 SHA-256 全文哈希匹配，缺乏抗扰动能力。
  - **建议方案**：设计 `exact`（原始哈希）→ `normalized`（去除空白与无序键的规范化哈希）→ `positional`（时序序列定位）三级渐进匹配算法。
  - **ROI 评估**：高（大幅提升在非标准代理、流式截断等复杂真实环境下的日志恢复成功率）。

- **ISSUE-14：上下文 Compaction 截断误杀最终响应文本**
  - **问题描述**：为防止单任务详情 JSON 膨胀，系统对过长的前驱上下文进行摘录截断，但早期逻辑误将最后一步的实际回复文本也一并截断。
  - **根因分析**：截断过滤器采用统一的字符长度截断，未针对末尾输出步骤设置例外保护机制。
  - **建议方案**：在数据截断层中将当前步的 `RespText` 标记为受保护字段，截断策略仅施加于前序冗余 History。
  - **ROI 评估**：高（保护模型输出的完整可见性，保障审计溯源价值）。

- **ISSUE-15：Journey 产物命名与状态标记混乱**
  - **问题描述**：文件名早期采用 `journey-<id>.md`，且对未完成任务使用 `-partial` 后缀改变文件名，破坏了 URL 与哈希索引稳定性。
  - **根因分析**：将动态业务状态（是否中断）编码进了物理文件名，违反了内容寻址幂等性原则。
  - **建议方案**：强制统一为 `j-<id>.md` / `j-<id>.json`，未完成状态仅在数据体内部作为 `partial: true` 标记并在 UI 顶部挂载 Banner。
  - **ROI 评估**：高（稳定索引路径，杜绝因任务状态改变导致的跨文件死链）。

#### 4. ViewModel 与 Markdown 渲染引擎类

- **ISSUE-16：渲染双轨分叉导致内容漂移**
  - **问题描述**：全量分析直接拿内存对象渲染 Markdown，而 `-render-only` 读磁盘 JSON 渲染，两端产出 Markdown 出现格式差异。
  - **根因分析**：存在两套渲染入口，全量路径绕过了序列化/反序列化的确定性边界。
  - **建议方案**：强制单一路径（D11）：全量分析跑完后一律先落盘 JSON，再统一调用 `renderAllFromDisk` 从磁盘重装切片后渲染。
  - **ROI 评估**：极高（通过代码同轨彻底杜绝渲染逻辑分叉，实现 100% 字节级等价）。

- **ISSUE-17：Markdown 序列化器中包含未国际化的自然语言字符串**
  - **问题描述**：序列化代码中直接包含英文字符串（如表头、单位提示），导致切换为中文时报表部分区域仍为英文。
  - **根因分析**：开发者图省事在 Go 代码中拼接字符串字面量，未调用 `i18n` 查表。
  - **建议方案**：引入 AST 语法树检查测试（`vm_literals_test.go`），断言序列化器中禁止出现任何非结构性自然语言常量。
  - **ROI 评估**：高（自动化门禁杜绝国际化退化，保证多语言交付品质）。

- **ISSUE-18：语言切换参数静默忽略风险**
  - **问题描述**：在已有中文产物的目录上使用 `-render-only -lang en`，早期未明确拒绝，导致重新生成的报表标题变为英文但数据内容仍为中文。
  - **根因分析**：底层数据切片中的文本（如 Highlights、免责声明）是在数据生成阶段本地化的，单纯 render-only 无法重新翻译数据。
  - **建议方案**：显式断言检查：若 `-render-only` 传入的语言与 `manifest.json` 记录的语言不一致，进程直接退出并提示全量重跑。
  - **ROI 评估**：中（消除混杂语言报表的产生，引导用户正确执行分析）。

- **ISSUE-19：报表附录链接失效死链（N16）**
  - **问题描述**：`vmr-report.md` 附录仍保留回链至已按 D7 删除的 `vmr-requests.md` 的超链接。
  - **根因分析**：删除了请求索引 Markdown 文件，但未联动清理宏观报表 ViewModel 中的超链接拼接逻辑。
  - **建议方案**：更新 Markdown 序列化器中的回链，将其定向至 `requests/index.json` 或单请求钻取入口 `requests/details/r-<hash>.md`。
  - **ROI 评估**：中（修复明显的 broken link 体验缺陷）。

#### 5. HTML 看板、前端交互与图表渲染类

- **ISSUE-20：同页 Hash 切换不重载数据（U1 / A1）**
  - **问题描述**：用户在单任务详情页或对比页点击其他任务，URL 中 `#data=` 变化，但页面不更新。
  - **根因分析**：早期页面初始化仅在 `window.onload` 执行，未监听浏览器的 `hashchange` 事件。
  - **建议方案**：监听 `hashchange` 事件并触发重渲染。当前虽以 `location.reload()` 暴力解决，后续建议重构为轻量级 DOM 响应式重绘。
  - **ROI 评估**：高（修复用户报告的阻断级交互 Bug）。

- **ISSUE-21：Journey 对比看板与 Markdown 存在巨大展示代差（U2 / A2）**
  - **问题描述**：`journey-compare.html` 相比于对应的 `.md` 报表，丢失了 14 项关键对比指标、提示词对比与 LLM 解读。
  - **根因分析**：前端看板开发滞后，仅解析了基础字段，未对齐完整的对比 JSON 数据结构。
  - **建议方案**：重构 `journey-compare.html`，对齐 Markdown 的全部 14 项对比指标，完整呈现分叉点、系统提示词与 AI 归因结论。
  - **ROI 评估**：极高（大幅消除看板与报表之间的体验鸿沟，提升可视化核心竞争力）。

- **ISSUE-22：页面宽度标准不一（U3 / A3）**
  - **问题描述**：`tool-waste.html` 独占 800px 窄屏卡片风格，与其他看板的 1280px 标准不兼容。
  - **根因分析**：不同看板页面由不同人或不同时期编写，缺少全局 CSS 规范约束。
  - **建议方案**：统一定义并应用 `.container { max-width: 1280px; margin: 0 auto; }`。
  - **ROI 评估**：低（改动极其简单，但能显著提升产品视觉一致性）。

- **ISSUE-23：前端读取数据切片字段拼写错误（N15）**
  - **问题描述**：前端 JS 中出现读取不存在的属性（如拼写错误、驼峰与下划线混淆），导致表格和图表渲染为空白。
  - **根因分析**：前端骨架页脱离真实生成的切片运行，缺乏端到端的前端渲染自动化测试。
  - **建议方案**：编写基于真实生成切片的端到端自动化走查测试，或使用静态 JSON Schema 校验前端访问字段。
  - **ROI 评估**：高（扫除隐藏的白屏与空数据渲染故障）。

- **ISSUE-24：`request-browser.html` 存在 HTML 未转义风险（N8 / B6）**
  - **问题描述**：请求日志中的 Prompt 包含 `<script>` 或 HTML 特殊字符时，直接拼接 `innerHTML` 会导致破坏排版甚至 XSS。
  - **根因分析**：前端使用模板字符串直接拼接未经转义的用户外部输入内容。
  - **建议方案**：在 `common.js` 中提供强制字符转义工具函数 `escapeHtml(str)`，所有文本插值一律先经过转义。
  - **ROI 评估**：极高（保障本地与托管环境下的渲染鲁棒性与基本安全）。

- **ISSUE-25：延迟图表对缺失分位数进行虚假插值（B2）**
  - **问题描述**：`svgLatencyPlot` 在样本数不足时缺少 P90/P99，前端自动复制 P50 绘制水平线。
  - **根因分析**：图表绘制逻辑缺少对 null 值的断点处理，强行补零或补平以使线条闭合。
  - **建议方案**：对缺失的分位点断开绘制折线，并在对应点位显示 `N/A` 占位符或离散点，严禁伪造连续性。
  - **ROI 评估**：中（维护数据呈现的客观真实性，避免误导工程性能调优）。

- **ISSUE-26：单任务查看器详情视图缩水（B1）**
  - **问题描述**：`journey-viewer.html` 缺乏步骤耗时分布、Token 阶梯统计与工具调用入参展开。
  - **根因分析**：初版看板仅搭建了框架，未实现复杂的内层数据展开交互。
  - **建议方案**：参考 Markdown 详单，在前端实现基于 `<details><summary>` 的步骤详情折叠卡片与参数格式化器。
  - **ROI 评估**：高（提升交互式探索单任务执行链路的体验）。

- **ISSUE-27：看板内部中英文混杂（A6）**
  - **问题描述**：骨架页部分提示语、错误文案写了中文，破坏了骨架页代码的纯英文定位。
  - **根因分析**：编写局部功能时直接写入了中文提示。
  - **建议方案**：清理所有 HTML 骨架中的中文硬编码，骨架页严格维持纯英文，动态国际化仅由切片数据驱动。
  - **ROI 评估**：中（保持前端代码库的整洁与定位一致性）。

- **ISSUE-28：本地双击打开缺少清晰的跨域引导（A7）**
  - **问题描述**：用户以 `file://` 双击打开 HTML，浏览器阻断 `fetch` 导致白屏，用户不知所措。
  - **根因分析**：现代浏览器的安全同源策略严格禁止本地文件发起相对路径 fetch 请求。
  - **建议方案**：在各骨架页头部增加运行环境探测，一旦检测到 `location.protocol === 'file:'`，立即浮现顶部 Banner，引导用户使用 `vmr` 自带托管或启动本地静态服务器。
  - **ROI 评估**：高（直接消除首发用户的“本地文件无法使用”投诉）。

#### 6. 内容寻址缓存与 Digest 链类

- **ISSUE-29：私有哈希与 Digest 标准不统一**
  - **问题描述**：系统内不同子包各自定义哈希逻辑，存在简单拼装字符串并取 MD5 的做法，存在哈希碰撞与扩展攻击风险。
  - **根因分析**：缺乏系统级统一的基础哈希设计，各模块自成体系。
  - **建议方案**：坚决落地 D8 裁决，所有哈希计算必须统一收敛至叶子包 `internal/digest`，采用定长前缀的有序 SHA-256 链。
  - **ROI 评估**：高（奠定全系统可信内容寻址与长效缓存的底层基石）。

- **ISSUE-30：并发写入缓存时的文件竞争与损坏（F1）**
  - **问题描述**：在多个分析进程并发执行或后台探测时，同时写入缓存目录可能导致文件写出一半被另一方读取。
  - **根因分析**：直接使用 `os.Create` 写目标路径，未采取原子写入策略。
  - **建议方案**：采用标准原子落盘模式：先写入同目录下的 `.tmp` 随机临时文件，`Sync` 并关闭后，使用 `os.Rename` 原子覆盖目标文件。
  - **ROI 评估**：高（彻底杜绝高并发或异常中断下的缓存脏数据）。

- **ISSUE-31：缓存失效矩阵未覆盖动态汇率与端点过滤参数**
  - **问题描述**：修改了配置文件中的 `exchange_rate` 或报表过滤端点，再次运行 `vmr analyze` 时命中了旧缓存，输出了错误报表。
  - **根因分析**：Level-2 产物指纹计算仅包含了日志文件哈希与模型单价，漏掉了汇率等全局换算标量。
  - **建议方案**：完善 7 维失效指纹计算模型，将所有影响计算结果的配置字段均编码进 `digest` 链。
  - **ROI 评估**：高（维护缓存透明性，杜绝假命中导致的业务数据失真）。

#### 7. HTTP 托管、安全模型与鉴权类

- **ISSUE-32：`/reports/` 托管无 Key 时降级放行严重漏洞（D9）**
  - **问题描述**：服务配置开启了报表 HTTP 托管，但管理员未配置 `api_keys`，系统错误地将其降级为公开访问，导致包含敏感 Prompt 的数据泄露。
  - **根因分析**：开发人员误用了“未配置即开放”的默认开发便利思维，违反了最小特权安全准则。
  - **建议方案**：硬编码安全门禁：当托管开启且 `len(api_keys) == 0` 时，服务端对任何请求强制硬性返回 403 Forbidden，完全拒绝工作。
  - **ROI 评估**：极高（防御企业级严重安全泄露事故的关键防线）。

- **ISSUE-33：鉴权分层缺失导致骨架页无法正常首屏加载（N7）**
  - **问题描述**：将 HTML 骨架页也纳入严格的 Bearer 鉴权，导致用户在普通浏览器地址栏输入 URL 时直接被 401 拦截。
  - **根因分析**：未对静态静态资产（骨架 HTML/CSS/JS）与动态敏感数据（JSON 切片）实施分层鉴权策略。
  - **建议方案**：静态骨架页允许免鉴权直接访问（页面内不含任何私密数据）；所有 `macro/*.json`、`journeys/*.json`、`requests/*.json` 实施强制 Bearer 鉴权。
  - **ROI 评估**：高（使带有访问控制的 Web 界面成为可用的交互体验）。

- **ISSUE-34：静态下载链接在鉴权环境下 401 瘫痪（B3）**
  - **问题描述**：看板内嵌入的“下载原始 JSON”普通超链接，在开启鉴权的服务端由于无法在请求头带 Token，点击直接报错。
  - **根因分析**：静态 `<a>` 标签无法由 JS 注入自定义 HTTP Header。
  - **建议方案**：将下载按钮改造为 JS 事件触发：通过 `fetch(url, { headers: { 'Authorization': getAuthToken() } })` 获取二进制流后生成临时 Object URL 触发下载。
  - **ROI 评估**：高（修复受保护部署场景下不可用的功能缺陷）。

- **ISSUE-35：路径穿越与软链接提权风险**
  - **问题描述**：托管模块若直接根据 URL 路径映射磁盘，恶意攻击者可通过构造 `../` 或借助符号链接访问到服务器上的私钥或系统文件。
  - **根因分析**：缺少对请求路径规范化后的边界检查与物理符号链接解析限制。
  - **建议方案**：在响应请求前执行 `filepath.Clean`，使用 `os.Lstat` 逐级检查路径组件，严格拒绝任何软链接文件与跨根访问。
  - **ROI 评估**：极高（标准的生产级 Web 服务安全底线）。

#### 8. 可视化 Stage 1 专项缺陷类

- **ISSUE-36：会话甘特图长尾时间轴被压缩失真（FA-1）**
  - **问题描述**：一个长达 2 小时的会话中，几百毫秒的工具调用在甘特图上宽度小于 1 像素，无法被点击或悬停走查。
  - **根因分析**：时间轴采用单纯的线性像素映射，未设定最小渲染像素限制。
  - **建议方案**：在 SVG 绘制时引入动态对数缩放或强制设定最小渲染宽度（如 `min-width: 4px`），并提供时间轴局部缩放（Zoom/Pan）能力。
  - **ROI 评估**：高（直接改善复杂长会话调优时的可视化可用性）。

- **ISSUE-37：流式重试导致 Token 瀑布流计量虚高（FA-2）**
  - **问题描述**：一次 LLM 请求发生网络中断并自动 Failover 到备用 Provider 时，瀑布流中累加了两次输入 Token，导致视觉上消耗量成倍放大。
  - **根因分析**：可视化数据抽取层将审计日志中失败重试的 Attempt 记录简单相加，未区分重试衰减与有效结算。
  - **建议方案**：引入 `effective_attempt` 标志位，在瀑布流中将废弃重试以灰色虚线折叠展示，主计量只统计最终生效请求。
  - **ROI 评估**：中（提高成本可视化归因的准确度）。

- **ISSUE-38：工具调用误报死循环反模式（FA-3）**
  - **问题描述**：Agent 正常连续执行 5 次小文件编辑，系统视觉标红提示“检测到工具循环反模式”。
  - **根因分析**：反模式判定规则仅依据连续相同工具名称，未比对工具输入参数与返回值。
  - **建议方案**：引入参数语义指纹比较：只有在连续 N 次调用同一工具且参数哈希高度一致、输出均为报错时才触发死循环警报。
  - **ROI 评估**：高（消除虚假告警对开发者的干扰，保留真正有价值的异常警报）。

- **ISSUE-39：调用树折叠状态在视图切换后丢失（FA-4）**
  - **问题描述**：开发者耗费精力在前端展开了深层调用链，切换 Tab 回来后树结构全部重置折叠。
  - **根因分析**：折叠状态仅保存在组件瞬态 DOM 中，未持久化至浏览器的 `sessionStorage`。
  - **建议方案**：以节点路径为键，将展开状态同步至 `sessionStorage`，重绘时恢复记忆。
  - **ROI 评估**：低（极小的 JS 改动，极大提升深度探索时的操作舒适度）。

#### 9. 边界场景、零散缺陷与长尾问题

- **ISSUE-40：空审计日志导致 Benchmark 统计零除 Panic（N5）**
  - **问题描述**：输入日志为空或无有效会话时，运行 `-benchmark` 发生除零崩溃。
  - **根因分析**：非参数统计计算代码中，计算方差或分位数时假定了样本量 `n > 0`，缺少前置空集守卫。
  - **建议方案**：在进入复杂统计运算前增加快速检查：若样本量为 0，直接输出空态结构并安全返回。
  - **ROI 评估**：高（消除边缘场景下的程序崩溃，提升稳定性）。

- **ISSUE-41：孤儿清扫范围失控误删非任务文件（N13）**
  - **问题描述**：旧版清扫函数误删了 `compares/` 或临时目录下的有效文件。
  - **根因分析**：文件匹配通配符过于宽泛，且未校验目标目录的上级物理路径。
  - **建议方案**：落地 G8 测试守卫，清扫逻辑硬编码绑定至 `journeys/details/` 目录，禁止扩展。
  - **ROI 评估**：高（保护用户重要分析产物免受意外破坏）。

- **ISSUE-42：大型日志解析引发瞬态内存峰值（NEW-A）**
  - **问题描述**：处理数 GB 的压缩日志时，分析进程内存占用急剧飙升至数 GB。
  - **根因分析**：使用了全量一次性读取到切片中的模式，未充分利用流式反序列化。
  - **建议方案**：全面使用流式 Scanner，逐行解压、解析、归拢，及时触发 GC 或复用缓冲区。
  - **ROI 评估**：高（保障小规格容器或边缘设备上的平稳运行）。

- **ISSUE-43：真实线上端点抖动导致集成验收测试挂起（NEW-B）**
  - **问题描述**：端到端验收测试依赖线上真实 LLM 端点，在遇到网络丢包时无限制挂起。
  - **根因分析**：HTTP 请求客户端未设定显式的全局上下文超时（Context Timeout）。
  - **建议方案**：在所有真实测试调用中强制注入带 `30s` 超时的 Context，并支持 `-short` 参数在快速 CI 中跳过外部网络依赖。
  - **ROI 评估**：高（提升 CI 自动化构建流水线的确定性与执行效率）。

### 4.2 逐项详细剖析

#### NEW-01：金额格式化策略割裂导致宏观报表与前端看板同账不同数

- **问题描述**：
  同一份审计日志生成的财务切片，在 Markdown 报表（`vmr-report.md`）与 HTML 看板（`macro-dashboard.html`）中展示相同的端点总支出时，数字在末尾美分处出现明显差异。例如 Markdown 报表中根据 `fmtMoney` 规则将超过 $100 的金额省略小数（显示 `$124`），而前端看板表格由于采用通用两位小数规则展示为 `$124.36`；更严重的是，部分中间计算四舍五入时点不同导致累加总额相差数美分。
- **根因分析**：
  早期开发时为追求报表文本的“紧凑感”，在 Go 侧 `fmtutil` 中引入了“大于100抹分”的经验性规则；而后端开发者在编写前端看板时发现表格列必须对齐，硬编码了恒定两位小数逻辑。团队随后在发现冲突时未从架构底层解决数值展示协议，而是通过在测试用例中将金额校验注释掉（并在 `KNOWN_ISSUES` 中登记为“两套语境无需统一”）来绕过门禁，本质上是用妥协掩盖了数据呈现的割裂。
- **建议方案**：
  立足第一性原理，财务数据的严肃性高于排版紧凑感。废除“大于100抹分”的不可预期逻辑，在整个系统所有展现层（Go Markdown 序列化器与 JS 格式化器）统一执行标准财务展示协议：全部固定保留两位小数（即 `$124.36`），仅在微型图表坐标轴紧凑标尺上允许使用 `$124`。同时将 `fmt_cases.json` 重新纳入双端强制回归测试。
- **ROI 评估**：
  极高。改动仅涉及 `fmtutil` 单个函数与对应测试，能彻底消除用户对核心计费与报表数据真实性的信任危机。

#### NEW-02：架构方案凭空论证不存在的 `-from` CLI 参数建立错误推论

- **问题描述**：
  在架构重构基础方案（`analyze_architecture_redesign_opus-5.md`）第 1.1 节中，设计者为了论证任务头部状态（`IsPartialHead`）具有极高易变性，声称“把一个随 `-from` 翻转的量编进内容寻址的文件名将导致严重缓存漂移”。然而，核对实际 CLI 代码，`vmr analyze` 根本不存在 `-from` 这一参数，过滤完全由文件 Glob 输入决定。
- **根因分析**：
  方案设计者在推导理论模型时脱离了真实 CLI 实现代码，混淆了其他系统的概念或未落实的设计草案，在缺乏源码交叉核实的情况下写下了不实论据。
- **建议方案**：
  在架构方案与文档说明中纠正该事实陈述，基于真实的“日志文件分片边界与时序截断”重新陈述 `IsPartialHead` 的非幂等性根因，避免后续接手团队被不存在的 CLI 参数误导。
- **ROI 评估**：
  低（文档勘误性修复，但有助于维护技术资产的严谨性与权威性）。

#### NEW-03：看板利用 `location.reload()` 暴力解决路由刷新破坏 SPA 完整性

- **问题描述**：
  用户在单任务查看器（`journey-viewer.html`）或对比看板中通过下拉列表或候选链接切换到另一项时（URL 中的 `#data=` 变化），前端通过监听 `hashchange` 事件直接执行 `location.reload()` 强制刷新整个页面。
- **根因分析**：
  早期的骨架页采用了一次性的自执行函数（IIFE）绑定生命周期，没有建立组件化的“数据拉取 → DOM 局部清空与重绘”函数。为了最快速地让页面刷新，采取了销毁页面上下文并重新发起 HTTP 请求的极简手法。
- **建议方案**：
  将数据加载与视图渲染封装为显式的无状态纯渲染函数（如 `renderJourneyViewer(data)`）。在 `hashchange` 触发时，提取新的 `#data=` 路径，仅发起局部 `fetch` 并在内存中无缝替换 DOM 节点，保留页面滚动位置与用户界面的筛选器状态。
- **ROI 评估**：
  中。需要重构两到三个页面的生命周期，能极大提升分析平台的交互流畅度与专业质感。

#### NEW-04：骨架页静态下载链接在受保护生产环境中完全处于瘫痪态

- **问题描述**：
  在开启了 `/reports/` 安全托管服务并配置了 `api_keys` 的生产部署环境下，前端看板右上角的“下载数据”按钮（`<a href="..." download>`）在用户点击时直接报 HTTP 401 错误，数据导出功能完全无法使用。
- **根因分析**：
  静态 HTML 的 `href` 属性发起的 GET 请求由浏览器底层网络栈直接调度，无法挂载 JavaScript 内存中维护的 Bearer Authorization 请求头。设计者在设计 D9 安全隔离时，只测试了直接浏览器走查，漏掉了在受保护模式下的静态下载链接链路。
- **建议方案**：
  在 `common.js` 中将所有数据下载按钮重构为委托事件：拦截默认行为，通过 `fetch(url, { headers: { 'Authorization': getAuthToken() } })` 异步获取数据 Blob，再通过合成 `URL.createObjectURL(blob)` 触发无感下载。
- **ROI 评估**：
  极高。只需在 `common.js` 修改一个通用函数，即可修复受安全保护的商业生产环境下的核心功能瘫痪。

#### NEW-05：中文报表环境下的单版英文看板呈现割裂且缺乏国际化扩展点

- **问题描述**：
  系统在支持多语言报表（`vmr analyze -lang zh`）时，生成在 `reports/` 下的 Markdown 均为纯中文；然而，同目录下的 HTML 看板骨架页其导航栏、表头、按钮、图例文字全部固定为纯英文，用户在使用时体验割裂严重。
- **根因分析**：
  骨架页被设计为通过 `go:embed` 编译进单一二进制的单一 HTML 模板文件，且初期裁定“骨架页保持英文单版以维持简单性”。然而随着系统的国际化深入，单版英文已经成为体验瓶颈。
- **建议方案**：
  在 `common.js` 中内置极轻量的中英词典对象（约数十个词条），在 `initDashboard()` 阶段探测当前报表语言（从已 fetch 到的 `manifest.json.lang` 读取），动态替换页面上的静态文本节点（使用 `data-i18n` 属性）。无需维护多套 HTML 文件，兼顾极简架构与多语言体验。
- **ROI 评估**：
  中。以极小的前端 JS 改造代价，消除产品在多语言环境下的半成品观感。

#### NEW-06：延迟时序图在样本不足（low-n）时连线插值掩盖长尾性能风险

- **问题描述**：
  `svgLatencyPlot` 绘制不同时间桶的延迟折线时，如果在某个冷门时间窗口内仅有 1 次请求，后端由于样本量不足未计算 P90 与 P99；前端图表将缺失点直接用 P50 填充或通过跨点直接连线，在折线图上形成一条平滑的低延迟曲线，掩盖了长尾延迟缺失的真相。
- **根因分析**：
  图表生成器在处理空值或缺项时，为了保证 SVG `<path>` 路径的连续闭合，缺少对有效数据点的存在性断言，采用了“向前借值”或“假连线”的设计。
- **建议方案**：
  在 SVG 绘制算法中增加断点处理逻辑：遇到分位数为空的点，必须显式断开连续折线（形成一段空白或绘制虚线）；同时在对应时间点上绘制显眼的低样本标识（如小空心圆或感叹号），并在悬浮提示（Tooltip）中如实标注“样本过少，长尾分位数不具备统计意义”。
- **ROI 评估**：
  高。改动局限在 SVG 拼接模块，能够有效保障技术性能监控的客观性与严谨性。

#### NEW-07：缓存全局指纹未将运行时环境变量与代理配置纳入失效链条

- **问题描述**：
  在配置了 Level-2 产物切片缓存的环境下，如果开发者临时在环境变量中设置了 `HTTP_PROXY` 或覆盖了定价文件的临时覆盖参数，再次执行 `vmr analyze` 时会直接命中上次的缓存切片，导致分析过程未真正走网络请求或新定价未生效。
- **根因分析**：
  `internal/report/cache.go` 中的指纹计算函数（基于 `internal/digest`）仅序列化了静态输入日志哈希、核心结构体配置与显式 CLI 参数，漏掉了可能通过环境变量隐式注入的运行时环境上下文。
- **建议方案**：
  梳理影响数据解析与网络行为的环境变量白名单（如 `VMR_PRICING_OVERRIDE` 等），将有效生效的环境变量键值对显式序列化进全局 Digest 链中。
- **ROI 评估**：
  中。消除特定部署与调试场景下的隐蔽假命中问题。

#### NEW-08：单请求详情与证据链过度延迟物化在批量回溯场景下引发 I/O 抖动

- **问题描述**：
  系统裁决将 `requests/details/` 与 `requests/evidence/` 实行严格的“懒物化”（不预先批量写出，仅在点击查看时按需生成）。但在用户使用静态 HTTP 服务器走查或批量下载多个单请求分析时，后台由于需要即时解压审计日志定位单行，引发剧烈的磁盘随机寻道与 CPU 尖峰。
- **根因分析**：
  由于审计日志以 `.jsonl.zst` 块压缩格式存放，随机定位一个请求需要解压整个压缩块；在连续请求多个不同详情时，解压工作被重复执行，缺乏轻量级的块级解压复用或快速预解压索引。
- **建议方案**：
  保持全量分析时不产生海量微小 Markdown 文件的同时，在机读索引 `requests/index.json` 中增加该请求在压缩日志中的字节偏移量与块 ID；并在按需物化模块中引入一个容量有限（如 10 个 Block）的最近解压块 LRU 缓存，避免跨步骤重复解压。
- **ROI 评估**：
  高。在不破坏磁盘空间占用的前提下，将深潜钻取单个请求详情的响应延迟从数百毫秒降低至数毫秒。
