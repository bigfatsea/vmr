# vmr 日志分析体系重构 — 开发计划（阶段划分）

## 0. 本文定位

三份文档，三个层级，不重叠：

| 文档 | 回答什么 | 细节粒度 |
| --- | --- | --- |
| `story_report_architecture_opus-5.md` | 为什么这样设计、事实依据是什么 | 方案级，含实测数据与取舍论证 |
| **本文（DevPlan）** | 分几个阶段做、每个阶段的边界与验收 | **里程碑级，不涉及源码细节** |
| 各阶段的 ActionPlan | 这一阶段具体动哪些地方、怎么改 | 执行级，**每个阶段开工前单独编写** |

**为什么 ActionPlan 不现在写**：每个阶段验收后都会改变下一阶段的前提——命名规则可能微调、
某个减法可能比预想的更彻底、某项验收可能推翻一条预判。现在写下的源码级细节，到那时多半已经失效。
所以本文只定**边界与验收**，不定实现路径。

**约定**：每个阶段开工前，基于该阶段起点的**真实仓库状态**重新做一次分析，产出该阶段的
ActionPlan；不沿用本文对后续阶段的任何预判。

## 1. 总体思路（简述）

论证在架构文档，这里只留骨架。

**要解决的问题**：`vmr report` 与 `vmr story` 消费同一份审计日志、跑在同一根解析骨架上，
却各自为政——没有共同的地址，产物之间走不通；人读的文件塞满了机读的内容，机读的文件是空的；
派生层到处在复制源数据而不是引用它。

**目标形态**是一张 3×2 的表：**变焦倍率**（宏观全量聚合 / 中观单任务叙事 / 微观单请求法证）
× **读者**（人读求跳转效率 / 机读求完整可寻址）。六个格子各司其职，格与格之间靠链接连成一个套件。

**三条主线**贯穿全部阶段：

1. **一套坐标** —— 每条审计记录一个跨半区通用的稳定地址；派生产物的命名、引用、跳转全部由它派生。
2. **分层归位** —— 人读层只留脊柱与链接，机读层承载结构，正文只在证据层存一份。
3. **导航闭环** —— 三个倍率之间可双向行走，落地页可用。

**不做的事**（架构文档已论证）：不引入数据库、不做单遍流式扫描引擎（重复解析的解药是缓存覆盖率，
见 P3）、不动已校准的检测判据、不为将来可能的 Web 服务做预备实现（只在设计上留出空间）。

## 2. 阶段划分原则与通用完成定义

### 2.1 划分原则

- **按模块切，不按工作量切**。一个阶段是一个语义完整的单元（一层产物、一套身份、一条闭环），
  哪怕它内部有大有小。
- **每个阶段自身可验收**。验收标准必须是能在真实日志上观察到的现象，不是"代码写完了"。
- **阶段之间只允许单向依赖**。不设并行分支——两个阶段同时改同一层产物，golden 基线会互相污染。
- **前置阶段优先交付可见价值**。无架构依赖的体验修复排在地基改造之前，这样即使后续阶段延期，
  已投入的工作仍然有产出。

### 2.2 通用完成定义（每个阶段都适用，后文不再重复）

1. 全量测试与架构边界检查通过。
2. 用真实审计日志重跑，逐项肉眼核对本阶段声称改变的产物。
3. 基线快照更新，且 diff 中每一处变化都能对应到本阶段的某项任务。
4. 用户可见的变化写入变更日志；涉及命令行用法或产物路径的，同步更新用户指南及其中文兄弟文档；
   涉及既有设计文档结论的（尤其 `docs/VirtualModelRouter_Design_v4_Analytics.md`），同步更新对应
   章节——文档记录的是当前状态，不是变更留痕。
5. 本阶段确认或推翻的取舍登记进已知问题清单——**在源码注释里论证过但没登记的取舍，等于没论证**。
6. 阶段收尾做一次**边界复核**：本阶段是否改变了后续阶段的前提；若改变，在本文对应阶段处标注，
   由下一阶段的 ActionPlan 承接。

## 3. 阶段总览

| 阶段 | 主题 | 核心交付 | 依赖 |
| --- | --- | --- | --- |
| **P0** ✅ | 基线归位 | 仓库状态与文档描述一致 | — |
| **P1** ✅ | 中观叙事层补全 | 决策脊柱成为可信、完整的任务叙事 | P0 |
| **P2** ✅ | 坐标层与微观层重建 | 同一条记录在任意路径下生成的详单逐字节相同 | P0 |
| **P3** ✅ | 证据层瘦身与共享条目 | 派生产物的体积与重复解析同时回落 | P2 |
| **P4** ✅ | 中观机读层归位 | 机读产物承载完整结构，正文按坐标引用 | P2, P3 |
| **P5** ✅ | 人读层瘦身 | 任务报告回到"脊柱 + 链接"形态 | P1, P4 |
| **P6** ✅ | 套件闭环、命令行收敛与口径收尾 | 一次调用产出完整套件，三层可双向行走，统计口径干净 | P2, P3 |

**三条不可绕过的硬依赖**（绕过就会造成真实的信息或一致性损失）：

- **P5 依赖 P1** —— 脊柱不覆盖无工具调用的步骤时删掉事实层，删掉的是最终交付物那一步。
- **P5 依赖 P4** —— 事实层是叙事结构在派生产物里的唯一载体，先删后补会留下一个真丢结构的版本。
- **P3/P4/P5 依赖 P2** —— 引用要能解析、链接要能算出来，都以稳定坐标与确定性命名为前提。

P6 依赖 P2 与 P3（导航边要能算出地址；"一次调用产出完整套件"要以缓存载荷补齐为前提，否则默认
路径会付掉全量扫描的代价），但**不依赖 P4/P5**——P3 完成后即可开工，不必等中观层两个阶段先完成。
**这只是排期顺序上的自由度，不是并行开工的许可**：P6.2 的导航边（如"journey 报告头 → 返回入口"）
与 P4/P5 改的是同一份 journey 产物，仍受 2.1 节"不设并行分支"的硬约束——可以选择先做 P6 再做
P4/P5，或反过来，但不能两边同时改。

### P3 · 证据层瘦身与共享条目 ✅ 已完成

**状态**：执行记录见 `docs/future-strategy/story_report_p3_action_plan_sonnet-5.md` §9。真实语料
（322 条记录）验证：`details/*.json` 副本清零、默认运行不再物化详单、322 份详单共享 10 个

`-req`/`-print` 落地。

**目标**：让派生层停止复制源数据——**体积**回落到与信息量相称的量级，**重复解析**回落到与新增
数据量相称的量级。

**范围**：逐请求 JSON 副本的去留、详单的生成时机、按坐标直取原始记录的能力、重复大块内容的
共享化、解析缓存的存储形态与载荷范围。

| 任务 | 说明 | 验收标准 |
| --- | --- | --- |
| **P3.1** 移除逐请求的 JSON 副本 | 微观机读层改为直接以坐标定位审计记录本身——那一格本来就存在，不需要再物化一份同构副本 | 派生目录体积显著回落；不再存在与源数据同构的副本 |
| **P3.2** 按坐标取出记录的原语 | 补上"把坐标解析成这条记录的原文"这个能力——删掉副本之后，微观机读层需要它来接管。（重放本身不受影响：它今天已经能直接对着原始审计文件按行定位；要做的是把几种记录选择写法收敛成同一种坐标形式） | 在没有任何派生产物的干净环境下，既能按坐标取出记录原文，也能按坐标重放 |
| **P3.3** 详单改为按需且幂等 | 默认运行不再全量物化详单；索引与脊柱照常渲染链接（名称可算，不依赖文件是否已存在） | 默认运行的产物集合回到索引量级；重复运行不重复写盘；链接在目标缺失时可当场补齐 |
| **P3.4** 重复大块内容落成共享条目 | 系统提示词、工具声明集合等被多个视图重复引用的内容，改为内容寻址的共享条目，各视图只持引用 | 批量渲染任务报告时，同一份系统提示词只落盘一次 |
| **P3.5** 缓存与索引分家 | 索引保持人可读的规模与形态；解析缓存改为分片存储与紧凑编码，两条命令共用同一份 | 索引文件回到可随手查看的量级；连跑两条命令只产生一份缓存；新增一个日志文件只写入一个新缓存条目 |
| **P3.6** 缓存载荷扩大到每条记录的全部事实 | 缓存今天只装了解析结果的一半（内容寻址部分），导致全量报表的热缓存收益只有 1.17 倍，而任务索引是 5 倍。补齐之后，两条命令在稳态下都只需读取新增或变化的文件 | 全量语料的重复运行耗时降到个位数秒；成本正比于新增数据量而非历史总量 |
| **P3.7** 缓存补 schema 版本戳 | 今天的命中判据只有文件内容哈希，改了提取逻辑会静默复用旧缓存；载荷扩大后风险面同步扩大 | 提取逻辑变更后缓存整体失效并重建，不会产出用旧口径算出的数字 |

**阶段验收**：一次全量运行的派生产物总体积与其信息量相称；重复运行的耗时降到个位数秒
（两项都给出与本阶段前的对比数字）；缓存与索引的职责边界清晰。**实际结果为部分达成**：体积与
共享条目两项完全达标，重复运行耗时从 71.8s 降到 16.2s（收益 1.17×→5.2×），未到"个位数秒"——

## 6. 调整机制

**允许的调整**：范围缩减、阶段顺序调整（在不违反三条硬依赖的前提下）、相邻阶段的任务合并。

**不允许的调整**：跨阶段并行推进同一层产物；沿用未经重新分析的 ActionPlan 开工。

**每阶段收尾的边界复核**，回答三个问题：

1. 本阶段是否产生了架构文档未预见的事实？若有，先更新架构文档，再进入下一阶段。
2. 本阶段是否改变了后续阶段的前提？若有，在本文对应阶段标注，并作为下一份 ActionPlan 的输入。
3. 本阶段是否暴露了某个原以为需要的任务其实不必要？**主动删任务比补任务更值钱**——本方案在
   设计阶段就有过多次"减法解开了一条依赖"的经历，实施阶段同样适用。

**一条贯穿始终的提醒**：每当写下"因为现状是这样，所以要那样"，把它翻成"现状本来就该这样吗"
再问一遍。本方案的设计过程中，多处早期结论正是败在没问这一句。
