## 0. Debrief：核心结论先行

### 0.1 一句话结论

Agent 运行时分析（Runtime Analysis）不是单一指标，而是一个**五层评估体系**：从黑盒（最终结果）→ 玻璃盒（轨迹路径）→ 白盒（单步决策）→ 行为模式（循环/漂移/冗余）→ 系统级（上下文管理/错误传播）。目前学术界和工业界的共识是：**仅评估最终输出会遗漏 20-40% 的质量问题**，过程级评估是 Agent 系统迭代的核心杠杆。

## 1. 领域全景：学术、工具、方法论三视角

### 1.1 学术研究脉络

Agent 运行时分析的学术研究大致经历了三个阶段：

**第一阶段（2022-2023）：架构导向**
- 以 ReAct (Yao et al., 2022)、Tree of Thoughts (Yao et al., 2023)、Reflexion (Shinn et al., 2023) 为代表
- 核心贡献：定义了 Agent 的基本执行范式（规划-行动-观察循环）
- 评估方式：以任务成功率为主，过程分析是副产品

**第二阶段（2023-2024）：基准构建**
- AgentBench (Tsinghua, 2023)、SWE-bench (Princeton, 2023)、GAIA (Meta, 2023)、ToolBench、API-Bank、τ-bench (Princeton, 2024)
- 核心贡献：建立了各领域的 Agent 能力评测基准
- 局限：绝大多数是**结果导向**的评估，只看最终答案对不对

**第三阶段（2025-2026）：过程级评估兴起**
- **AgentProcessBench** (2026)：1,000 条轨迹 + 8,509 个人工标注 action，首次系统研究 step-level 评估
- **EnConda-bench** (ICLR 2026)：面向软件环境配置的过程级评估，支持错误定位与修复分析
- **τ²-Bench** (2025)：双控制环境，支持细粒度 step-level 错误分析
- **Goal Drift 研究** (2025)：系统研究目标漂移问题，发现长程任务中这是主要可靠性问题
- **Agentic AI Fault Taxonomy** (2026)：基于 13,602 个 issue 的 5 大类故障分类
- **From Plan to Action** (2026)：计划合规性研究，提出 PCPC 指标
- **MAST** (2025)：多 Agent 系统 14 种失败模式分类

**关键洞察**：过程级评估（Process-based Evaluation）是 2025-2026 年 agent 评估领域的核心趋势。两篇 KDD 2025 / arXiv 2025 的 survey 都明确指出——"现有评估碎片化严重，过程级评估是重要但被忽视的方向"。

### 1.3 方法论演进：从结果到过程

评估粒度的三级跃迁（Langfuse 提出，已成为行业共识）：

| 层级 | 评估方式 | 能回答的问题 | 信息量 | 实现成本 |
|------|---------|-------------|:------:|:--------:|
| L1 黑盒 | 只看最终输出 | "成功了吗？" | 低 | 低 |
| L2 玻璃盒 | 轨迹路径评估 | "在哪一步失败的？" | 中 | 中 |
| L3 白盒 | 单步决策评估 | "为什么这一步做错了？" | 高 | 高 |

DeepEval / Langfuse 进一步将 L2-L3 细化为三层评估架构：

```
        ┌─────────────────────────────┐
        │    End-to-End Level         │  整条轨迹
        │  - Task Completion          │  - 是否完成任务
        │  - Step Efficiency          │  - 用了多少步
        │  - Plan Quality/Adherence   │  - 计划好不好、执行守不守
        └──────────────┬──────────────┘
                       │
        ┌──────────────┴──────────────┐
        │    Action Layer             │  动作级
        │  - Tool Correctness         │  - 工具选对了吗
        │  - Argument Correctness     │  - 参数对不对
        │  - Tool Use P/R             │  - 该用的用了吗/没用的用了吗
        └──────────────┬──────────────┘
                       │
        ┌──────────────┴──────────────┐
        │    Reasoning Layer          │  推理级
        │  - Reasoning Relevancy      │  - 推理跟目标相关吗
        │  - Reasoning Coherence      │  - 推理逻辑自洽吗
        │  - Faithfulness             │  - 答案基于证据吗
        └─────────────────────────────┘
```

## 2. 效率维度：成本、速度、token 利用率

效率是最容易量化、也是最早被关注的维度。所有可观测平台都默认提供这些指标。

### 2.1 Token 效率

**核心指标**：
- **总 token 消耗量**：单次任务所有 LLM 调用的 input + output tokens 之和
- **单位任务成本**：按模型定价换算的美元成本（输出 token 通常比输入贵 2-5 倍）
- **Token 效率比**：`有效产出 token / 总 token`，衡量"废话率"
- **Token 增长曲线**：`context_tokens vs steps` 的增长模式

**为什么重要**：
- 直接映射成本——成本分布的长尾（P95/P99）比均值更重要
- 上下文线性增长 = 成本线性增长 + 推理质量下降（context rot）
- Manus 团队实测：工具输出占总 token 的 67.6%，todo.md 反复重写浪费约 30% token

**参考值**：
| 任务类型 | 总 token 量级 | 步骤数 |
|---------|:------------:|:------:|
| 简单（单工具调用） | < 5K | 1-3 |
| 中等（多步工具组合） | 10-50K | 5-15 |
| 复杂（深度研究/编码） | 100K-1M | 20-50 |

**实操方法**：
```python
# 从原始数据提取
total_input_tokens = sum(msg['usage']['input_tokens'] for msg in llm_calls)
total_output_tokens = sum(msg['usage']['output_tokens'] for msg in llm_calls)
total_cost = total_input_tokens * input_price + total_output_tokens * output_price

# 按步骤画 token 增长曲线
context_sizes = []
for i, call in enumerate(llm_calls):
    context_size = sum(len(m['content']) for m in call['messages'])  # 近似
    context_sizes.append(context_size)
# 绘制折线图，观察是线性增长、超线性增长、还是有压缩拐点
```

### 2.2 步骤效率

**核心指标**：
- **总步骤数**：完成任务的 LLM 调用轮次 / 工具调用次数 / agent loop 迭代次数
- **步骤效率比**：`实际步骤数 / 理论最少步骤数`（DeepEval `StepEfficiencyMetric`）
- **重试率**：`retry_count / total_tool_calls`——同一操作被重复执行的比例

**参考值**：
- 优秀 Step Efficiency < 1.5（实际步数仅比最优多 50% 以内）
- 一般 1.5-3.0
- 差 > 3.0（大量冗余）
- 健康重试率 < 5%；需要关注 > 15%

**实操方法**：
- 重试检测：用 `(tool_name, args_hash)` 二元组检测完全重复的调用
- 相似重试：用 embedding 相似度比较工具调用参数，>0.9 视为同一操作的重试
- 理论最少步骤数：需要人工标注或 LLM-as-judge 评估"最少需要几步"

### 2.3 时间效率

**核心指标**：
- **端到端延迟**：从用户输入到最终答案的墙钟时间
- **每步延迟分布**：按 span 类型（LLM / tool / plan / retrieve）分组统计
- **瓶颈定位**：耗时 Top 5 的步骤类型

**参考值**：
- 对话类任务 P95 < 5s
- 研究/分析类 P95 < 60s
- 编码类可到数分钟

## 3. 质量维度：正确性、工具使用、推理

质量是核心。与普通 LLM 评估不同，Agent 质量不仅看最终答案，还要看**路径质量**。

### 3.1 任务完成度（End-to-End）

**任务完成率（Task Completion Rate）** 是最顶层的结果指标。

| 评估方式 | 适用场景 | 准确度 | 成本 |
|---------|---------|:------:|:----:|
| 自动判定（有标准答案/测试用例） | 编码、数学、有确定答案的 QA | 高 | 低 |
| LLM-as-judge | 开放性任务、主观质量评估 | 中 | 中 |
| 人工标注 | 业务正确性、复杂任务 | 高 | 高 |

**分级评估（推荐）**：不要做二元判定，分三级更有信息量：
- **完全完成**：所有子目标达成，无明显缺陷
- **部分完成**：主要目标达成，但有遗漏或瑕疵
- **未完成**：核心目标未达成

**注意事项**：仅靠任务完成率会系统性高估质量——Wei et al. (2023) 发现仅评估最终输出比全轨迹评估多通过 20-40% 测试用例，因为目标漂移、过程错误等问题在最终答案中不明显。

### 3.2 工具使用质量（Action Layer）

这是 Agent 特有的核心评估维度，也是过程级评估最容易落地的部分。

| 指标 | 定义 | 计算方法 |
|------|------|---------|
| **工具选择准确率** | 选对工具的比例 | `correct_tool_calls / total_tool_calls` |
| **工具选择精确率** | 调用了且确实该调用 / 总调用数 | 区分"乱调用"（precision 低） |
| **工具选择召回率** | 该用工具时确实用了 / 该用的场景数 | 区分"该用不用"（recall 低） |
| **参数正确率** | 参数格式+内容正确的比例 | 格式层（JSON schema 校验）+ 语义层（LLM 判断） |
| **工具结果利用率** | 工具输出中有多少被后续推理实际引用 | 引用 token / 工具输出 token |

**实操方法**（从原始 message list 提取）：
```python
# 从 response 中提取 tool_calls
tool_calls = response.get('tool_calls', [])
for tc in tool_calls:
    tool_name = tc['function']['name']
    tool_args = json.loads(tc['function']['arguments'])
    
    # 1. 格式校验：参数是否符合 schema
    schema = tool_schemas[tool_name]
    format_ok = validate_json_schema(tool_args, schema)
    
    # 2. 语义校验：这个场景下该调用这个工具吗？（需 LLM-as-judge）
    semantic_ok = llm_judge(f"当前情境：{context}\n调用工具：{tool_name}，参数：{tool_args}\n是否合理？")
    
    # 3. 后续是否使用了结果？（看后续 message 中是否引用了该 tool 结果的关键内容）
```

### 3.3 推理质量（Reasoning Layer）

推理质量最难评估，但决定了 Agent 的上限。

| 指标 | 定义 | 评估方法 |
|------|------|---------|
| **推理相关性** | 每步推理与当前子目标的相关度 | LLM-as-judge 逐步骤评分 |
| **推理连贯性** | 推理步骤之间的逻辑一致性 | LLM-as-judge 检查逻辑链 |
| **答案忠实度** | 最终答案是否基于检索/工具结果，而非编造 | `claims_supported_by_context / total_claims` |
| **答案相关性** | 答案是否直接回应了原始问题 | LLM-as-judge 或 embedding 相似度 |

**忠实度（Faithfulness）的特殊重要性**：
Agent 可能在工具结果不足时编造信息补全答案，造成幻觉。生产级 RAG 系统的忠实度应 > 80%。检测方法：把最终答案拆分为若干 claim，逐条验证是否能在工具返回/检索结果中找到依据。

### 3.4 计划质量与遵循度

| 指标 | 定义 | 评估方法 |
|------|------|---------|
| **计划质量** | 初始计划是否合理、完整、有序 | LLM-as-judge：完整性、可行性、逻辑顺序 |
| **计划遵循度** | 实际执行与既定计划的吻合程度 | LLM-as-judge 对比 plan vs trajectory |
| **规划偏离分析** | 量化执行路径与计划的偏差 | 序列编辑距离 + 新增/跳过步骤数 |

**关键研究发现**（From Plan to Action, arXiv 2604.12147）：
- 随着轨迹增长，初始计划在上下文中的显著性下降，导致偏离率上升
- 周期性 plan reminder 可显著改善计划遵循度
- 提出 PCPC（Plan Compliance and Plan Completion）双指标

**区分"计划差"vs"执行差"**：
- 如果计划好但执行经常偏离 → 问题在执行层（提示词、工具选择能力）
- 如果计划本身常被推翻 → 问题在规划层（任务分解能力、预估能力）

## 4. 行为模式分析：从轨迹中挖掘"性格特征"

行为模式分析是过程级评估最有价值的产出之一。它不看单个步骤的对错，而是看整条轨迹的"行为模式"——就像分析一个人的做事风格。

### 4.1 循环检测（Loop Detection）

**死循环是生产 Agent 的第一杀手**——浪费成本、卡死任务、耗尽上下文。

**三种检测方法**：

| 方法 | 原理 | 准确度 | 计算成本 |
|------|------|:------:|:--------:|
| **精确匹配法** | 哈希 `(tool_name, sorted_args, result_preview)` 三元组，重复出现 = 循环 | 高（精确重复） | 低 |
| **状态相似度法** | 用 embedding 比较连续 K 步的"观察+动作"对，相似度 > 阈值 = 循环 | 中（可检测相似但不完全相同的循环） | 中 |
| **进度停滞法** | 设定 max_steps 无进展（子目标无新增完成）= 死循环 | 低（需定义"进展"） | 低 |

**实操建议**：
- 维护最近 N=10 步的状态历史窗口
- 每步检查是否出现重复
- 循环占比应 < 2% 的任务
- 自动在 step budget 耗尽前终止（防 token 爆炸）

### 4.2 冗余步骤检测

**定义**：对任务推进无贡献的步骤。

**常见冗余类型**：
1. **重复信息获取**：同一文件/网页/数据被多次读取
2. **无效验证**：反复运行相同测试，结果无变化
3. **过度探索**：在已排除的方向继续投入步骤
4. **过度规划**：反复制定/修改计划但不行动

**检测方法**：
- 精确匹配：完全相同的工具调用（不算 retry 的那种）
- 内容相似度：工具返回结果的 embedding 相似度 > 0.9
- LLM-as-judge：给定完整轨迹，标注"可删除且不影响结果"的步骤

### 4.3 目标漂移检测（Goal Drift）

Agent 特有失败模式：**单步都正确，整体结果错了**。

**三种检测方法**：

| 方法 | 原理 | 适用场景 |
|------|------|---------|
| **语义漂移法** | 每步子目标 embedding 与原始任务 embedding 的余弦相似度，绘制漂移曲线 | 通用 |
| **关键词覆盖法** | 原始任务中的关键约束/实体在后续步骤中被提及的频率变化 | 有明确实体/约束的任务 |
| **LLM-as-judge** | 每 N 步评估"当前执行方向是否仍然服务于原始目标" | 高精度需求 |

**相关研究**（Goal Drift, arXiv 2505.02709）：
- 长程任务中 goal drift 是主要可靠性问题之一
- 随着对话轮次增加而加剧
- intrinsification（工具目标变成永久目标）是潜在安全风险

### 4.4 工具使用模式挖掘

**方法**：
- 提取工具调用序列（tool name n-gram）
- 用序列模式挖掘（PrefixSpan / SPADE）找频繁子序列
- 或把每条轨迹的工具序列 embedding 后聚类

**价值**：
- 识别"最佳实践路径"（高频且高成功率的模式）→ 可固化为 prompt 中的推荐路径
- 识别"问题路径"（高频且低成功率的模式）→ 重点改进

### 4.5 决策一致性 / 方差

同一任务多次运行，Agent 行为的变异程度。

**衡量方法**：
- 成功率的标准差（N 次运行）
- 轨迹相似度（工具序列编辑距离 / Jaccard 相似度）
- 输出结果的一致性（embedding 相似度）

**为什么重要**：高方差 = 不可靠；生产系统需要行为可预测。
- 高确定性任务方差应 < 10%
- 方差分析是 A/B 测试的基础——方差太大，小样本的对比结果不可信

### 4.6 错误传播路径分析

**核心问题**：小错误如何通过多步推理放大为最终失败？

**分析方法**：
1. 从失败结果反向回溯，定位第一个出错的 step（"根因步骤"）
2. 计算错误传播距离：从根因到最终失败经过了多少步
3. 统计哪些步骤类型最常成为根因

**洞察**：
- "最后一步犯错"容易修（提示词微调即可）
- "早期错误被放大"需要系统性改进（规划能力、验证机制）
- 多 Agent 系统中，级联失败（compounding errors）是主要问题

## 5. 上下文管理分析：隐形的质量杠杆

上下文是 Agent 的"工作记忆"。上下文管理的好坏直接影响推理质量，但很少被显式分析。

### 5.1 上下文膨胀率

**定义**：上下文窗口大小随步骤数的增长速度。

**实操**：
- 每步记录 `context_tokens`（可通过 request 中所有 message 的总 token 估算）
- 拟合增长曲线
- 区分增长来源：系统提示 / 对话历史 / 工具输出 / 检索结果

**健康指标**：
- 健康增长 < 2K tokens/步
- 工具输出占比通常 > 60%（Manus 实测 67.6%）
- 如果是超线性增长 → 可能存在上下文膨胀失控

### 5.2 Context Rot（上下文腐烂）

**定义**：随着上下文窗口填充，推理质量下降的现象。

**检测方法**：
- 按上下文 token 数分桶（0-32K, 32-64K, 64-128K...）
- 统计每桶的任务成功率 / 工具调用准确率
- 质量开始显著下降的点 = "腐烂阈值"

**关键发现**：
- 模型标称 1M 上下文不代表 1M 内质量一致
- 有效窗口通常远小于标称值（Phil Schmid 经验：多数模型 < 256K）
- 质量-上下文大小曲线的拐点 = pre-rot 阈值，应在触达前触发 compaction

### 5.3 上下文利用效率

| 指标 | 定义 | 计算方法 |
|------|------|---------|
| **检索命中率** | 检索到的文档中有多少被最终答案引用 | `referenced_chunks / retrieved_chunks` |
| **工具结果利用率** | 工具输出中有多少 token 在后续推理中被提及 | `used_tokens / total_tool_output_tokens` |
| **Lost in the Middle** | 中间位置信息被引用的比例 | 按位置分桶的引用率曲线 |

**参考值**：RAG 场景 context precision 理想 > 70%。

**为什么重要**：塞进去的信息不代表能用。低效注入 = 浪费 token + 干扰推理。

### 5.4 信息遗忘率

**定义**：早期提供的关键信息在后续步骤中被"遗忘"的频率。

**检测方法**：
1. 标记初始上下文中的关键事实点（key facts）——可以人工标注，也可以让 LLM 提取
2. 每 N 步或在最终答案中检查这些事实是否被正确保留/引用
3. `forgotten_facts / total_key_facts` = 遗忘率

**这是长任务质量下降的主因之一**。改进手段包括：周期性 key facts 提醒、工作记忆压缩、显式记忆管理。

### 5.5 上下文污染指数

| 子指标 | 定义 |
|--------|------|
| **冗余率** | 相似/重复信息占比（embedding 相似度 > 阈值的 chunk 对） |
| **无关率** | 与当前子目标相似度低的上下文占比 |
| **冲突检测** | 上下文中存在矛盾陈述的次数 |

污染信息干扰注意力、降低推理质量、浪费 token 预算。

## 6. 失败模式分类：从症状到根因

了解 Agent 怎么失败的，比知道它失败了更重要。以下是三个主流分类体系的整合。

### 6.1 Agentic AI Fault Taxonomy（架构视角）

来源：Characterizing Faults in Agentic AI (arXiv 2603.06847)，基于 13,602 个 issue + 385 个深度编码案例。

| 层级 | 故障大类 | 典型表现 | 运行时可检测性 |
|------|---------|---------|:--------------:|
| L1 | 认知控制与编排层 | 死循环、任务拆分不合理、handoff 丢失 | 中-高 |
| L2 | 代理与执行层 | 选错工具、参数格式错、执行顺序混乱 | 高 |
| L3 | 感知与记忆层 | 遗忘早期信息、重复检索、检索不相关 | 中 |
| L4 | 运行时与环境层 | 429 限流、文件系统状态错、网络失败 | 高 |
| L5 | 系统可靠性层 | 超时未处理、重试风暴、状态不一致 | 中 |

### 6.2 RCA Agent 失败分类（领域视角）

来源：Why Do AI Agents Systematically Fail at Cloud Root Cause Analysis?（1,675 次 agent runs）

**内部推理失败（Intra-Agent Reasoning）**：
1. **幻觉式解读**（71.2%）—— 解释工具结果时产生幻觉
2. **探索不完整**（63.9%）—— 探索空间不完整，遗漏关键路径
3. **过早锁定假设**—— 忽略反面证据，confirmation bias
4. **相关 vs 因果混淆**
5. **证据权重误判**

**多 Agent 通信失败（Inter-Agent Communication）**：
6. 交接中信息丢失
7. 角色边界模糊
8. 协调死锁

**环境交互失败（Agent-Environment Interaction）**：
9. 误解工具输出格式
10. 基于过时状态做决策
11. 忽略操作的副作用
12. 环境非确定性导致混乱

### 6.3 多 Agent 系统失败分类（MAST 框架）

来源：Why Do Multi-Agent LLM Systems Fail? (arXiv 2503.13657)，3 大类 14 种模式。

| 阶段 | 失败类别 | 具体模式 |
|------|---------|---------|
| 执行前 | 规格缺陷 | 需求不完整、角色定义模糊、工具规格不一致、输出格式不兼容 |
| 执行中 | 代理错位 | 目标不一致、通信中断、信息传递丢失、错误委派、重复劳动 |
| 执行后 | 终止缺口 | 过早终止、验证不完整、验证错误、无最终汇总 |

### 6.4 生产环境 7 大常见失败模式

来源：Latitude.so - Detecting AI Agent Failure Modes in Production

1. **Goal Drift（目标漂移）** — 长任务中逐渐偏离
2. **Infinite Loops（无限循环）** — 重复相同操作无进展
3. **Tool Confusion（工具混淆）** — 描述相似的工具导致选择振荡
4. **State Inconsistency（状态不一致）** — 内部状态与环境脱节
5. **Cascading Failures（级联失败）** — 小错误通过多步放大
6. **Premature Termination（过早终止）** — 未完成就宣布完成
7. **Context Bloat（上下文膨胀）** — 历史积累导致质量下降

## 7. 跨 Agent 对比方法论

同一任务在不同 Agent 系统/模型/配置上的完整运行轨迹，怎么对比？

### 7.1 对比框架：五维矩阵

| 维度 | 核心指标 | 优化方向 | 数据可获得性 |
|------|---------|:--------:|:------------:|
| **质量** | 任务完成率、正确率、忠实度、推理质量 | ↑ 越高 | 中-高 |
| **效率** | token 消耗、步骤数、延迟 | ↓ 越低 | 高 |
| **成本** | 每任务美元成本 | ↓ 越低 | 高 |
| **鲁棒性** | 成功率方差、错误恢复率、循环率 | ↑ 越高 | 中 |
| **行为模式** | 计划遵循度、目标漂移量、工具使用多样性 | 视场景 | 中 |

### 7.2 A/B 实验三步法（Langfuse 推荐）

**Step 1：宏观视图（高水位指标）**
- 平均得分、成本、延迟的快速对比
- 快速识别潜在改进或回归

**Step 2：基线对比（The Diff）**
- 聚合指标总览：得分 + 成本 + 延迟的综合权衡
- 隔离回归 + 根因分析：失败案例成对对比
- 深入单个 trace 调试

**Step 3：统计显著性检验**
- 计算置信区间，不要被随机波动误导
- 样本量计算公式基于成功率和期望检测的最小差异

### 7.3 轨迹对齐与对比

**核心挑战**：不同 Agent 的步骤粒度不同——A agent 一步做三件事，B agent 分三步做。直接对比步骤数不公平。

**对齐方法**：

| 方法 | 原理 | 准确度 | 计算成本 |
|------|------|:------:|:--------:|
| **子目标对齐** | 先提取两条轨迹各自的子目标序列，再对齐子目标 | 高 | 高（需 LLM） |
| **功能对齐** | 按"做了什么事"而非"调用了什么工具"对齐 | 中-高 | 中 |
| **工具序列编辑距离** | 直接计算工具调用序列的 Levenshtein 距离 | 低 | 低 |
| **Embedding 轨迹相似度** | 每步状态 embedding 后计算轨迹相似度曲线 | 中 | 中 |

**推荐流程**：
1. 先用工具序列编辑距离做粗筛（快速找差异大的轨迹对）
2. 再用子目标对齐做精细对比（LLM-as-judge 提取子目标并对齐）
3. 最后对齐到同一组子目标后，在每个子目标内对比：用了几步、多少 token、是否一次成功

### 7.4 帕累托前沿分析（Pareto Frontier）

质量提升往往伴随成本上升。帕累托分析找出"无法在不降低质量的前提下降低成本"的最优配置。

**做法**：
- 对每个 Agent 版本/配置，绘制 `(quality_score, cost)` 散点图
- 用 Pareto dominance 找前沿点
- 每月/每版本更新帕累托图，观察前沿是否向外推进

**质量-成本权衡的三个区域**：
- **前沿上**：最优配置（降本必降质，提质必提本）
- **前沿内**：有改进空间（可以提质又降本）
- **前沿外**：不可能区域

### 7.5 综合评分：Trajectory Quality Score (TQS)

多维度加权为单一分数，用于版本对比、回归检测、质量趋势监控：

```
TQS = w1 * TaskCompletion     // 结果正确性 (权重最高)
    + w2 * StepEfficiency     // 步骤效率
    + w3 * ToolCorrectness    // 工具使用正确率
    + w4 * PlanAdherence      // 计划遵循度
    + w5 * ReasoningQuality   // 推理质量
    + w6 * SafetyCompliance   // 安全合规
```

各维度均归一化到 [0, 1]，权重之和 = 1。权重根据业务场景调整。

**注意**：综合评分是便捷工具，不能替代分维度分析。TQS 下降了，要拆开看是哪个维度掉的。

## 8. 落地指南：从原始 LLM 调用数据到分析结果

你有什么？——几十轮 LLM 调用的完整 request/response，包括 message list、工具调用、系统提示等全部原始数据。

你能做什么？——以下是从易到难的 7 步分析流水线。每一步都可以独立运行，不需要全套。

### 8.1 Step 1：数据清洗与结构化

**目标**：把原始数据变成可分析的结构化格式。

**从 request 中提取**：
- `model`：模型名
- `messages`：完整消息列表
  - 从中解析：system prompt、user messages、assistant messages、tool messages
  - 从 assistant message 中提取：tool_calls（name, arguments, id）
  - 从 tool message 中提取：tool_call_id、content（工具返回结果）
- `temperature`、`max_tokens` 等生成参数
- `timestamp`：调用时间

**从 response 中提取**：
- `usage.input_tokens`、`usage.output_tokens`、`usage.total_tokens`
- 延迟（request 发出到 response 返回的时间差）
- 错误信息（如果有）

**数据结构建议**：
```python
# 每轮 LLM 调用
{
    "step_id": 1,
    "timestamp": "2026-08-09T12:00:00Z",
    "model": "gpt-4o",
    "input_tokens": 3500,
    "output_tokens": 450,
    "latency_ms": 1200,
    "system_prompt_hash": "...",  // 或内容摘要
    "messages_count": 15,
    "tool_calls": [
        {"name": "web_fetch", "args": {"url": "..."}, "id": "call_abc"}
    ],
    "tool_results": [
        {"id": "call_abc", "content": "...", "tokens": 800}
    ],
    "error": null,
    "finish_reason": "tool_calls"
}
```

**分组**：按任务（task_id）、按模型版本、按日期分组。

### 8.2 Step 2：基础效率指标（零门槛，纯计算）

**直接算，不需要任何 LLM 判断**：

| 指标 | 计算方法 | Python 伪代码 |
|------|---------|--------------|
| 总 token | 所有 step 的 input + output 之和 | `sum(s.input + s.output for s in steps)` |
| 总成本 | 按模型价目表换算 | `sum(s.input * in_price + s.output * out_price)` |
| 总步骤数 | LLM 调用次数 | `len(steps)` |
| 工具调用次数 | 所有 step 的 tool_calls 数 | `sum(len(s.tool_calls) for s in steps)` |
| 端到端延迟 | 第一步到最后一步的时间差 | `steps[-1].timestamp - steps[0].timestamp` |
| 工具错误率 | 返回错误的工具调用占比 | `error_tool_calls / total_tool_calls` |
| 重试率 | 相同工具+相似参数的重复调用 | 见 §2.2 |
| token 增长曲线 | 每步的累计 context token | 见 §5.1 |

**输出**：
- 汇总表（均值、P50、P95、P99）
- 分布直方图（token 分布、步骤数分布、延迟分布）
- 异常值列表（成本 Top 5%、最长轨迹、零工具调用）

### 8.3 Step 3：工具调用质量分析（半自动）

需要一点逻辑判断，但大部分可自动化：

**3a. 格式级分析**（全自动）：
- 工具调用参数是否符合 JSON schema？→ 格式正确率
- 调用了不存在的工具？→ 幻觉工具率
- 工具返回错误？→ 错误率（区分 4xx/5xx/超时/限流）

**3b. 序列级分析**（半自动）：
- 工具调用序列是否合理？（比如先读文件再改文件，而不是反过来）
- 有没有"工具 A 返回了 B 所需的信息，但 B 没用到"？
- 工具调用的 n-gram 模式统计（哪些工具经常一起出现）

**3c. 语义级分析**（需 LLM-as-judge）：
- 这一步真的需要调用工具吗？（该用工具时用了吗？不该用时用了吗？）
- 工具参数的内容是否合理？（格式对不代表语义对）
- 工具结果是否被后续推理正确使用了？

### 8.4 Step 4：行为模式检测（半自动到自动）

**循环检测**（全自动）：
- 精确匹配循环：`(tool_name, args_hash)` 三元组重复出现
- 相似度循环：最近 K 步的工具+结果 embedding 相似度 > 阈值
- 进度停滞：连续 N 步子目标无更新

**冗余检测**（半自动）：
- 重复读取：同一文件/URL 被读取多次且内容未变
- 重复计算：相同输入的计算/搜索被执行多次

**目标漂移检测**（需 LLM-as-judge）：
- 每 5 步检查一次：当前方向是否还在服务原始目标？
- 绘制漂移曲线（与原始目标的语义相似度变化）

### 8.5 Step 5：上下文管理分析（半自动）

**上下文增长分析**（全自动）：
- token-vs-steps 折线图
- 按来源拆分（系统提示 / 对话历史 / 工具输出）
- 增长模式判断（线性 / 超线性 / 有压缩拐点）

**上下文利用分析**（需 LLM-as-judge）：
- 工具结果利用率：工具输出中有多少被后续引用
- 关键信息保留率：初始关键事实在后续步骤中的保留程度

**Context Rot 检测**（需要多任务数据）：
- 按上下文大小分桶，统计每桶的成功率
- 找质量下降的拐点

### 8.6 Step 6：失败根因分析（深度分析）

对失败的任务做根因定位：

**反向回溯法**：
1. 从最终失败结果出发
2. 反向检查每一步，找到第一个出错的步骤（根因步骤）
3. 按失败分类体系（§6）归类
4. 统计：根因步骤的类型分布、错误传播距离分布

**失败模式聚类**：
- 把失败的轨迹 embedding 后聚类
- 每个簇人工分析典型案例，提取失败模式
- 统计各失败模式的占比和成本浪费

### 8.7 Step 7：跨版本/跨 Agent 对比（最高阶）

见第 7 章完整方法论。快速上手版：

1. **确保公平对比**：同一任务集、同一预算限制、同一评估标准
2. **宏观指标对比**：五维矩阵雷达图（质量/效率/成本/鲁棒性/行为）
3. **成对案例分析**：挑几个典型任务，逐步骤对比两个 Agent 的执行路径
4. **帕累托前沿**：质量-成本散点图 + 前沿线
5. **TQS 综合评分**：单数值对比 + 分维度拆解

### 8.8 优先级建议：先做什么？

| 优先级 | 分析项 | 投入 | 产出 | 推荐理由 |
|:------:|--------|:----:|:----:|---------|
| P0 | 基础效率指标 | 低 | 高 | 零门槛，立即可用，成本优化直接见效 |
| P0 | 循环检测 | 低 | 高 | 死循环是最大浪费，检测简单 |
| P1 | 工具调用格式分析 | 低 | 中 | 自动化程度高，发现明显错误 |
| P1 | 重试率分析 | 低 | 中 | 识别工具不可靠或 agent 不会处理错误 |
| P2 | 工具调用语义分析 | 中 | 高 | 深入理解 agent 决策质量 |
| P2 | 目标漂移检测 | 中 | 高 | 发现"单步都对但整体跑偏"的隐性失败 |
| P2 | 失败根因分类 | 中 | 高 | 指导改进优先级 |
| P3 | 上下文利用效率 | 中 | 中 | 需要较多人工标注 |
| P3 | 推理质量评估 | 高 | 中 | 评估成本高，适合抽样 |
| P3 | 跨 Agent 对比 | 高 | 高 | 需要两套系统，适合选型期 |

## 9. 置信度与信息缺口

### 9.1 置信度评估

| 结论类别 | 置信度 | 依据 |
|---------|:------:|------|
| 领域整体趋势（过程级评估兴起） | 高 | 多篇 2025-2026 顶会/arXiv 论文 + 主流平台一致方向 |
| 效率指标体系（token/步骤/延迟/成本） | 高 | Langfuse/LangSmith/DeepEval 等多平台共识 |
| 工具使用质量评估方法 | 高 | API-Bank / ToolBench / τ-bench 多基准验证 |
| 行为模式检测方法（循环/冗余/漂移） | 中-高 | AgentProcessBench / Goal Drift 论文 + 工业界实践 |
| 上下文管理分析维度 | 中 | 分散在 RAG 评估、context engineering 文章中，agent 专门研究较少 |
| 推理质量自动评估 | 中 | LLM-as-judge 有已知偏差，需人工校准 |
| 跨 Agent 对比方法论 | 中 | A/B 实验框架成熟，但轨迹对齐方法尚无标准 |
| 综合评分体系（TQS 等） | 中-低 | 各平台自定义权重，无行业标准 |
| 失败模式分类的完整性 | 中 | 现有分类基于特定领域（编码/RCA），通用分类仍在演进 |

### 9.2 信息缺口

1. **中文资源稀缺**：绝大多数高质量资料是英文的，中文社区在这个领域的深度讨论较少
2. **开源 Agent 框架的运行时分析能力参差不齐**：LangGraph 很强，很多框架很弱，没有统一标准
3. **缺乏面向个人/小型项目的轻量分析工具**：现有平台要么功能重（Langfuse/LangSmith），要么是基础设施（OTEL），缺少"给我一堆 trace 文件，跑个分析报告"的轻量工具
4. **Process Reward Models (PRMs) 尚不成熟**：step-level 评估主要靠 LLM-as-judge，专用的过程奖励模型还在早期
5. **不同架构 Agent 的可比性问题**：ReAct 式、规划式、图式、多 Agent 式——不同架构的轨迹结构差异大，统一对比框架缺失
6. **长期运行（>100 步）的 agent 行为模式研究少**：多数基准和研究集中在 10-30 步任务

### 9.3 下一步建议（如果要继续深挖）

1. **动手搭一个分析原型**：基于你已有数据，先把 P0-P1 的自动化分析跑起来（效率指标 + 循环检测 + 工具格式校验），看能发现什么
2. **人工标注 20-30 条轨迹**：标注任务完成度 + 每步工具调用正确性 + 失败根因，建立黄金标准集
3. **尝试 LLM-as-judge 自动评估**：用人工标注集校准 judge prompt，然后批量跑
4. **考虑是否接入标准 tracing 栈**：OpenTelemetry + Langfuse/MLflow 可以省很多自己造轮子的时间
