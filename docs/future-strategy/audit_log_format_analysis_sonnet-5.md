# 审计日志格式分析：JSONL 是否仍是合理选择

> **性质**：§0–§5 是容器/文件层面的分析，§2.1 的具体缺口经二次核实后已直接修复（见该节，改动本身
> 不在本文档——在 `internal/audit/read.go`/`read_test.go`）。§6 是应用户追加要求做的第二轮分析：
> **单条记录 JSON 本身**（key/value/结构）有没有优化空间，结合 `report`/`story` 的真实消费路径
> 逐字段核查——**这一部分严格只是分析，未落地任何改动**。全部结论基于对 `internal/audit`/
> `internal/reqdetail`/`internal/story` 源码的逐行核查，与 `logs/` 目录下 39 个真实审计文件
> （2026-07-14 至 2026-08-16，压缩前约数 GB 级）的实测数据。

---

## 0. 现状速写

`internal/audit`（`audit.go`/`housekeep.go`/`read.go`）实现的格式：

- **容器**：NDJSON（每行一个完整 `json.Encoder.Encode` 输出的 `Record`，非 pretty-print）。
- **文件粒度**：`{log_dir}/vmr-audit-YYYY-MM-DD.jsonl`，**纯按日期轮转**，无体积触发。
- **写入路径**：单个全局 `sync.Mutex` 保护的 `O_APPEND` 写入；JSON 编码在锁外完成（`sync.Pool` 复用
  buffer），只有最终 `f.Write(buf.Bytes())` 在锁内——已经是"编码并行、写串行"的合理设计。
- **压缩**：日期滚动后异步 zstd（`housekeep`），保留期外删除（默认不删）。
- **读取原语**：`OpenLogFile`（透明识别 `.zst`）+ `ForEachLine`（`bufio.NewReaderSize` 逐行扫描，
  128MB 单行上限，超限跳过不中止）+ `LineAt`（按 1-based 逻辑行取原始字节）。
- **记录结构**：`Client`（客户端↔vmr）+ `Attempts[]`（vmr↔上游，每次 failover 一条）两层，`Message.Body`
  是 `any`（合法 JSON 存 `json.RawMessage`，否则存字符串）——**字节忠实透传**的直接体现，不做任何
  结构化改写。

## 2. 判断：整体是合理选择，暴露的具体缺口已复核并修复一处、搁置一处待确认

### 结论先行

**NDJSON + 按日 zstd 轮转，对这个项目的定位（单机、字节忠实、AI-native 小团队、审计日志需要被
`jq`/`DuckDB` 等外部工具直接消费——见 `audit` 包文档注释）是恰当的选择，不建议整体重构。**
代码里发现的两处缺口——`LineAt` 无提前退出、轮转无体积上限——二次核实后**处置不同**：前者根因
明确、修法唯一、且不改变任何既有调用方的行为，已直接修复；后者涉及实时写入路径与一个没有唯一
正确答案的阈值取舍，判定为"存疑"，按要求**不改动，只在 §2.2 报告分析结果供你确认**。

### 2.1 [已修复] `LineAt`/`ForEachLine` 原本没有提前退出，查询代价 = 全文件而非目标行位置

**复核确认根因无争议**：`read.go` 的 `LineAt` 原实现用 `ForEachLine` 定位第 N 行，其回调
`func(line []byte)` 没有返回值、无 `context`、无 sentinel error 之类的"停止"信号通道，循环体自身
也没有在命中目标后 `break`——**即使目标行是文件第 5 行，扫描仍会解压并走完整个文件到 EOF**。
这是一个纯机械的、可由 Go 编译器边界检查覆盖的问题，不存在语义分歧。

**修法**（`internal/audit/read.go`）：把 `ForEachLine`/`LineAt` 共用的行扫描循环下沉为一个私有
`scanLines(r, maxLine, fn func(line []byte) bool, onSkip)`——`fn` 返回 `false` 时立即停止读取
剩余内容；`ForEachLine` 保持导出签名与行为**完全不变**（内部只是 `scanLines` 的一层薄包装，回调
恒返回 `true`），因此仓库里另外 8 处生产调用点（`ctxgraph/scan.go`、`ctxgraph/records.go`、
`report/aggregate.go`/`session.go`/`detail.go`、`replay/replay.go` 两处）**零改动、零行为变化**——
这是判定"低风险"的关键：新增能力完全局部于 `LineAt` 自己，不需要触碰任何其他调用方。
`LineAt` 改为直接调用 `scanLines`，命中目标行即返回 `false` 停止扫描。

**顺带修复一个同函数内、此前从未被验证过的次要 bug**：`LineAt` 原来传给 `ForEachLine` 的
`onSkip` 参数是 `nil`，而其自身的行号计数器 `n` 只在 `fn`（真正的行回调）里递增——doc comment
却明确声称"a too-long skipped line still advances the counter"。也就是说，**如果目标行之前
出现过一行超过 `MaxLogLine`（128MB）而被跳过，`n` 会少加 1，导致 `LineAt` 悄悄返回错误的一行**，
且不报错。今天从未触发（真实语料最大单条记录 3.72MB，远低于 128MB），但既然同一处函数正在改写，
一并修正：`onSkip` 闭包补上 `n++`，让计数口径与 doc comment 描述的、以及其它调用点已经在遵守的
约定一致。

**回归测试**（`read_test.go`，新增两条，均已跑绿）：`TestScanLines_StopsEarly` 用一个自定义
`countingReader` 证明——在一段远超 `bufio` 1MB 内部缓冲区的输入里，一旦 `fn` 返回 `false`，
底层 reader 被要求提供的字节数远少于全部输入（不是"断言恰好停在哪一行"这种依赖 `bufio` 内部
细节的脆弱断言）；`TestScanLines_OnSkipAdvancesCallersOwnCounter` 直接复现"跳过一行后目标行计数
错位"的场景，钉住上面那条次要 bug 的修复。

**实测效果：确有提升，但不是天真预期的"O(1)"——诚实记录，不夸大**。修复前后各跑 5 次取最小值，
同一个 373 行/380MB（解压）压缩文件：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 取第 5 行 | 0.225s | **0.129s（↓43%）** |
| 取第 373（最后）行 | 0.223s | 0.222s（符合预期：目标在文件尾部，提前退出没有收益空间） |

**根因追查确认了为什么不是"接近 0"**：`OpenLogFile` 用的 `github.com/klauspost/compress/zstd`
解码器默认并发度是 `min(GOMAXPROCS, 4)`——即便调用方只 `Read()` 了很少的字节就停止，解码器内部
已经起了多个 goroutine **提前解压后续数据块**并缓冲起来，这部分工作在我们发出"停止"信号之前已经
发生，不会被早退回收。也就是说，**当前的瓶颈已经从"Go 层的逐行扫描"（本次已消除）转移到"zstd
解码器自己的预读并发"**——这是本次验证过程中新发现的一层，**没有一并处理**：要不要为
`LineAt` 单独关闭解码并发（`zstd.WithDecoderConcurrency(1)`）会改变一个被 8 个其他调用点共用的
`OpenLogFile` 原语的行为，其中多数调用点是"反正要扫全文件"的批量场景——那些场景恰恰从并发解压
里受益，为了单条查询的尾部收益去关掉它们的并发，净效果未经验证、可能是负的。**判定为存疑，
不在本次改动范围内**，记录在案供后续单独评估（需要先做的是一次真实的 profile，而不是直接调参）。

**回到今天是否真的重要的问题**：仍然像修复前分析的那样——今天唯一生产调用点是人工触发的
`vmr replay -req`（`replay.go:412`），不在任何自动化热路径或循环里，43% 的常数级改善不解决
"O(文件大小)" 这个渐进复杂度本身。真正的渐进复杂度修复（§2.1 原分析里的"行偏移量旁路索引"）
仍未做——它能把"扫描到目标行"变成"直接 Seek"，收益与文件大小成正比而不是一个常数百分比。
`scanLines` 的提前退出是这条路径的**必要前提**（没有它，"扫到目标行就停"这件事在语义上都不成立），
但不是终点。这条更彻底的修法本身涉及新增缓存 schema（旁路索引落进 `.parse-cache/`），有明确的
方向但不是"改一个函数体"这么局部，**本次判定其风险等级高于"加一个提前退出"，未一并实施**，
仍按下方 §2.2 的方式记录为待确认项，而不是直接动手。

### 2.2 [待确认，未改动] 纯按日轮转，无体积上限——复核后判定不满足"低风险"门槛

`housekeep.go` 的轮转判据只看文件名里的日期（`auditFileRE`），不看体积。真实语料证实这不是假设
风险：同一个月内单日文件解压体积从 27MB 到 380MB（**14× 方差**），且没有任何机制阻止更极端的
情况（一次长 agent 会话的突发流量可以让单日文件膨胀到 GB 级——一条记录本身已经观测到 3.72MB）。
文件越大，§2.1 里"目标行落在文件尾部"的最坏情况就越贵。

**复核结论：根因清楚，但修法不满足"明确、无争议、低风险"这条门槛，三点具体理由**：

1. **触碰的是实时写入路径，不是离线读取路径。** §2.1 的改动只影响 `vmr replay` 这一个人工触发的
   离线命令；体积轮转要在 `Logger.Write`——**每一次请求都会调用**的函数——里加判断。今天的轮转
   判据只在日期变化时才重新 `os.OpenFile`（`l.f == nil || date != l.date`），零额外开销；体积判据
   需要知道"当前文件已经写了多少字节"，要么在 `Logger` 上新增一个原子计数器（每次 `Write` 后累加，
   低成本但需要正确处理"读取旧文件已有体积"的启动态）、要么每次 `Write` 后 `os.Stat`（多一次系统
   调用，量级上不算大但发生在请求路径上，不是可以随手接受的改动）。这不是"改不动"，而是这类改动
   照项目自己的纪律（`router`/审计写路径变更需要额外审慎）理应有一次独立评估，不该顺带在一次
   "分析文档追加任务"里拍板。
2. **没有唯一正确的阈值。** 200MB？500MB？取决于用户单机的内存/磁盘特征和典型请求体大小分布，
   本次审计手上没有依据给出一个不是"拍脑袋"的数字——而"给一个不确定对不对的默认值"本身就是
   `KNOWN_ISSUES` 反复强调要避免的假精度。
3. **触碰一份已经写进代码注释、被多处依赖的坐标唯一性假设。** `ctxgraph/reqcoord.go` 的坐标唯一性
   论证原文依据是"审计文件名带日期，跨目录同名在实践中不发生"。同一天内出现多个文件（无论用什么
   命名规则区分，如 `vmr-audit-YYYY-MM-DD.2.jsonl`）不会破坏这条唯一性本身（`req` 坐标是
   `basename:line`，不同 basename 天然不冲突），但**这份文档记录的假设文本需要跟着更新**，且要
   核实 `CheckPathCollisions`（坐标唯一性的运行时断言）与任何按"文件名里只有一个日期"做假设的
   周边逻辑（如有）不会因为同一天出现第二个文件而误判。这类核对本身不难，但足以让这条改动脱离
   "低风险"的范畴，需要作为一次独立、有明确验收标准的改动来做，而不是顺手写。

**不改动，报告如上，等待你确认方向**（是否要做、阈值取多少、文件名后缀方案）。如果确认要做，
建议单独立项，而不是揉进这次的分析追加任务。

### 2.3 一个更彻底但明确不建议现在做的选项

把 `.zst` 换成"可跳转 zstd"（seekable format，按帧切分、每帧独立可解压+索引）能在旁路索引之上
再把"解压目标行之前的全部数据"这一步也省掉——但引入新容器子格式，且 §2.1 已经证明当前的真实
瓶颈来源里有相当一部分是解码器自身的默认并发预读，不是"顺序解压太慢"；在旁路索引方案的收益都还
没有实测验证之前，就去动压缩容器格式本身，是在一个尚未确认规模的第二层问题上超前投入，不建议。

## 3. 为什么这是合理选择：逐项对照

### 3.1 与项目定位的匹配度

`internal/audit` 包文档原话："alongside whatever external scripts (jq, DuckDB, …) also read these
files directly"——**审计日志被设计为一个有外部消费者的稳定契约**，这与架构文档为派生 JSON
（`vmr-report.json` 等）拍板的"没有稳定外部客户、可以自由重构"前提**刚好相反**。这个区分本身就是
一条支持 NDJSON 的论据：越靠近数据源、越需要被第三方工具直接消费的层，越应该用一种没有专有读取器
门槛的格式——`jq`/`zstdcat | jq`/`DuckDB read_json_auto` 都能直接读，换成任何专有二进制格式或
数据库文件都会立刻打破这条契约。

### 3.2 Schema 演进成本

`Record`/`Attempt`/`Message` 全部字段都带 `omitempty`，新增字段是纯加法、旧文件天然兼容（缺失字段
解码为零值）。P0–P15 全程新增了 `Req`/`ClientKeyTag`/`ErrorClass` 等多个字段，从未触发任何迁移
脚本——这是 JSON 相对列式/二进制格式最直接的胜出项，对一个仍在快速演进 schema 的项目权重很高。

### 3.3 压缩效果：实测 48× 印证了"不必在源层去重"的判断

会话内每一轮请求都会把此前的完整对话历史重新发送一遍（chat completion 协议本身如此，不是 vmr
的选择）——这是 §2.2 观测到的"单条记录可达 3.72MB"、"文件体积随请求量陡增"的根本原因。
**这份冗余不是储存格式的缺陷，是被审计协议本身的性质**：一条记录必须完整保留客户端实际发送的
字节（字节忠实是路由半区的核心不变量），不能因为内容与上一条重复就只存差量——那样就不再是"这次
请求实际发生了什么"的忠实记录，而是一个需要额外还原步骤才能读懂的编码。

真实语料的 zstd 压缩比高达 **48×**，恰好说明：这份协议层冗余**已经被通用压缩算法几乎完全吃掉**，
不需要在写入格式层面再做一次"聪明"的结构化去重。这与 story/report 派生层（P13）处理"93% 是
重复拷贝"的问题时选择的方案是同一个判断在两个不同层面的体现——**派生层的去重面对的是"同一份内容
被渲染进多份可读文档"，本质是展示冗余，可以用坐标引用消除；审计日志层面对的是"协议本身要求
每轮重发完整历史"，本质是数据冗余，用压缩消除，不该也不需要用结构改写消除**。把这两类冗余混为
一谈、试图在源头就"去重存储"，会把一个原本单遍 `O_APPEND` 就能完成的写入变成一个需要感知会话
边界、内容寻址、增量重建的有状态写入路径——这正是 P2/P3 好不容易在**派生层**才做成的事情，
把它下放到**审计层**会让本该是"傻瓜式追加"的最底层数据源背上"必须先分析、才能落盘"的负担，
一旦分析逻辑本身有 bug，损坏的就是唯一的事实来源，而不是一份可以随时重新生成的派生产物。

### 3.4 崩溃安全性：已验证的优雅降级，非新发现

`ForEachLine` 对超过 128MB 的单行不中止扫描、只跳过并计数；`ctxgraph/scan.go`/`report/*.go` 的
每个消费点都把 `json.Unmarshal` 失败当作"这一行不算数"而非致命错误（`noBody++` 计数，扫描继续）。
这意味着进程崩溃在一次 `Write` 系统调用中途留下的截断尾行——NDJSON 格式众所周知的失效模式——
在这个项目里已经被**每一个读取路径**优雅处理，不会导致整份文件不可读。这不是本次新增的判断，
是核查现有代码后确认"这类风险已经被覆盖"，一并记录以完整回答"这个格式是否可靠"这个问题。

### 3.5 并发写入路径

全局 `sync.Mutex` 只包裹文件系统调用本身，JSON 编码（真正的 CPU 开销）在锁外用 `sync.Pool` 并行
完成——`KNOWN_ISSUES §1.10` 已经登记"write 系统调用在全局锁内"这一点，判定为**未经证明的瓶颈**，
本次审计复核该判断依然成立：单次 `write()` 对本地文件系统的开销以微秒计，锁的粒度已经是"只锁
真正需要串行化的那一小步"，不存在需要重新论证的新证据。不重复登记。

## 4. 考虑过、判定不必要的备选方案

| 备选 | 为什么不做 |
| --- | --- |
| **换成 SQLite（单文件嵌入式库）** | 能换来索引化随机访问与事务保证，但要为多 MB 级的 `Body` 字段设计 BLOB 存储、把"O_APPEND 追加一行"换成"事务提交"、把"整份文件是不是损坏"这类肉眼可判断的问题换成"数据库文件是不是损坏"——三者都在拿"随机访问变快"换"最底层数据源变得更难被人/脚本直接触碰、更难在损坏时抢救"，而 §2.3 的旁路索引方案已经用零格式改动的代价换到了同一个随机访问收益 |
| **换成 Parquet/列式格式** | 该格式的收益（列裁剪、向量化扫描）主要服务于"扫描大量记录做聚合统计"，但这份数据 90% 以上的字节体量集中在 `Body` 这一个（近乎）不可拆列的大字段里——列式存储在这个字段上退化成普通行式存储，收益覆盖不到主要的字节量。且 Parquet 是批量攒行组写入的格式，与"来一个请求就要立刻落盘、不能等batch攒够"的审计语义冲突 |
| **换成二进制序列化（CBOR/MessagePack/Protobuf）** | 这份数据里绝大多数字节本来就是自由文本（对话内容），JSON 的结构开销（引号、转义、逗号）相对文本本身占比很低，换二进制编码不会带来数量级的体积收益，却会直接关掉 `jq`/`grep`/`zstdcat \| less` 这条本项目文档明确承诺过的调试通路 |
| **写时按会话去重（增量存储）** | 见 §3.3——把"感知会话边界"这个目前只存在于**读取/派生层**（`ctxgraph`）的能力下放到写入路径，会让审计日志从"无状态追加"变成"有状态重建"，一旦这层逻辑出 bug，出问题的是唯一权威数据源而不是可重新生成的派生产物。zstd 已经把这部分冗余的存储代价压到了可忽略的量级（48×），不值得为了一个已经被通用压缩解决的问题引入这个风险 |

---

## 5. 容器层结论（§0–§4）

**格式选择本身合理，不建议重构**：NDJSON 对齐了"字节忠实、单机、外部工具直接消费、schema
持续演进"这几条项目自身的既有约束，压缩比实测 48× 说明协议层的固有冗余已经被通用压缩基本吃掉，
崩溃/损坏容错也已经在每个读取路径上验证过。

两处具体缺口的处置：`LineAt` 无提前退出——根因单一、修法唯一、8 个其他调用点零影响——**已直接
修复**（§2.1）；轮转无体积上限——触碰实时写入路径、阈值无唯一正确答案、涉及需要同步更新的坐标
唯一性假设文档——**判定不满足直接修复的门槛，报告结论，未改动**（§2.2），等待你确认。

## 6. 单条记录 JSON 结构复审：key/value/结构本身是否有优化空间

> 本节回应追加的第二个问题：不只看"文件容器"，看**一行 JSON 内部**——它的字段设计，结合
> `report`/`story` 的真实消费路径，有没有必要在**审计日志生成端**（`internal/audit`/`server`/
> `router` 的写入路径）做调整。**只做分析，不落地任何改动**。

### 6.0 方法

不做泛泛的"JSON 设计最佳实践"式点评，而是逐字段核对**谁在读它**——用 `grep` 找出 `Record`/
`Attempt`/`Message` 每个字段在 `internal/report`/`internal/story`/`internal/reqdetail`/
`internal/replay`/`internal/ctxgraph`/`internal/chatmsg` 里的真实读取点，区分"核心分析路径依赖"
"仅取证/展示用途""从未被读取"三类，再判断每一类各自该不该调整。

### 6.1 【重大发现】`Attempt.Request.Body` 是 `Client.Request.Body` 的近乎逐字节复制——且已有的
     响应侧去重先例让这看起来更像一处遗漏而非刻意设计

**实测（单条真实记录，07-25 语料）**：

| 字段 | 字节数 |
| --- | --- |
| `client.request.body` | 162,534 |
| `attempts[0].request.body` | 162,549 |

两者逐字段 diff：**唯一差异是 `model` 字段**（`"agent"` → `"doubao-seed-2.0-lite"`）——`messages`
（对话历史，占大头）、`tools`、`tool_choice`、`stream`、`stream_options` 全部逐字节相同。这正是
`CLAUDE.md` 记录的"三处字节忠实的例外"之一——**模型名重写**——的直接体现：路由半区把虚拟模型名
换成真实上游模型名后转发，除此之外不改一个字节。

**这不是孤例，是这份协议的确定性行为**。批量核查两个真实场景：

| 场景 | 样本 | 结果 |
| --- | --- | --- |
| 单次尝试（无 failover） | 07-20 全天 373 条记录 | **373/373（100%）** 的 `attempts[0].request.body` 与 `client.request.body` 的差异字段集合恰好是 `{model}` |
| 多次尝试（failover，07-21 语料） | 2 条代表性记录，分别 2 次尝试 | 每次尝试各自的差异字段集合同样恰好是 `{model}`——3 次独立请求发送/转发（1 客户端 + 2 上游），同一份 ~220–390KB 的 `messages` 载荷被逐字节复制了 3 遍 |

**量级**：07-20 这一天，`attempts[*].request.body` 合计 224,468,752 字节，占该文件解压后总体积
（380,079,561 字节）的 **59%**——而这部分字节，理论上**全部可以从 `client.request.body` +
`Attempt.Model`（已经存在的字段）无损推算出来**，不需要额外存一个字节。

**与既有设计的不对称，值得特别指出**：`Attempt` 的响应侧**已经**做了这件事——doc comment 原文
"On the successful attempt the response body is omitted: passthrough means it is byte-identical to
Client.Response.Body"，并配一个 `Norm []string` 字段记录应用过的正规化步骤名。也就是说，
**"一份内容可能被存两遍，就该只存一遍 + 一个指向差异的说明"这条判断，写入端在响应侧已经做了，
在请求侧却完全没做**——两侧面对的是同一种冗余（转发前后基本相同、只有小范围可枚举的改写），
处置方式却不对称。这更像是实现时的疏漏，而非"请求侧有正当理由必须整份复制"的刻意设计。

**为什么这与 §3.3 否决的"写时按会话去重"是完全不同性质、风险低得多的优化**：

| | 写时按会话去重（§3.3/§4 已否决） | 本节：请求体去重 |
| --- | --- | --- |
| 作用范围 | 跨记录（本轮 vs 上一轮，需要会话/lineage 边界判定） | **单条记录内部**（client vs 自己的 attempts） |
| 需要的状态 | 写入路径要能识别"这是同一个会话的第几轮"——目前只有读取层 `ctxgraph` 有这个能力 | **不需要任何状态**——`router` 写这条记录的当下，`client.request.body` 与要转发给上游的 body 都已经在内存里，差异（改了哪个字段）是路由逻辑自己刚刚做出来的决定，不是需要"分析"才能得到的信息 |
| 重建方式 | 需要跨记录拼接，且拼接规则依赖 `ctxgraph` 的 lineage/缝合算法（会演进、曾经改过口径） | 单记录内 `client.request.body` 覆盖 `model` 字段 → 得到 `attempt.request.body`；已知的例外（下方）需要额外一两个字段，同样不跨记录 |
| 风险 | 分析逻辑一旦有 bug，损坏的是唯一权威数据源 | 重建规则极其简单（一次字段替换），且**已有先例**（响应侧的 `Norm` 机制）证明这类"存差异不存全量"的设计在这个项目里可行、可维护 |

**已知的例外情况，任何方案都必须先处理，不能只覆盖常见情况**：`imgprep` 的图片降采样是请求侧
**第二个**字节忠实例外（`CLAUDE.md` 明确点名的"三处例外"之一）——发生降采样时，转发给上游的请求
体里图片数据本身也会变，`attempts[*].request.body` 与 `client.request.body` 的差异就不再只是
`model` 字段。真实语料里样本记录都不含图片，未覆盖到这条路径，**不能假设它不存在**。

**分析结论（不建议现在实施，原因见下）**：这是本文档目前发现的**单条记录内部占比最大的一处可论证
去重空间**（真实语料 59% 的文件字节），且去重机制本身风险可控（单记录内、无状态、有先例）。
但落地涉及三件都不轻的事，**判定超出"分析文档顺手改"的范围，留给你决定是否要单独立项**：

1. **改变审计记录的对外 schema**——`Attempt.Request.Body` 从"总是有值"变成"多数情况下省略、
   靠 `Attempt.Model` 重建"，这是一个会被 `jq`/`DuckDB` 之类外部脚本直接感知的破坏性变更（§3.1
   已论证这份格式是有外部消费承诺的），需要一次显式的版本沟通，不是内部重构。
2. **必须先把"差异字段集合恰好是 `{model}`"这件事在写入端就地判定并编码，而不是留给读取端猜**——
   例如复用 `Attempt` 已有的 `Norm []string` 模式，加一条 `"request_identical_to_client_except_model"`
   之类的显式标记；一旦这个标记与实际内容不符（例如未来出现第三种请求侧改写却没人记得同步这条
   判断），后果是"读到的内容是错的"而不是"读到的内容是多余的"——这正是本文档 §2 类问题里最需要
   警惕的一类失效模式，必须有对应的写入期自检（例如 debug/测试环境下双写校验）。
3. **读取端（`internal/reqdetail` 的 `renderBodyDiff`）今天已经在展示"两者的差异"**，这恰好说明
   读取端的心智模型本来就是"这是一份 diff"而不是"这是两份独立数据"——但要改的地方不止这一处，
   `internal/replay`/`vmr replay -req` 若要重放某次具体的 attempt（而非 client 请求），也需要
   知道如何从省略的字段重建出真正发给上游的字节。

### 6.2 其余字段级检查：确认不需要调整

| 检查对象 | 结论 |
| --- | --- |
| **Headers（`Client.Request/Response.Headers`、每个 `Attempt.Request/Response.Headers`）** | 实测单条记录里每份 header 集合 300–650 字节，相对动辄 10 万+ 字节的 body 是噪声量级。虽然同样存在"大部分 header 键值跨 attempt 重复"的现象，但绝对字节收益太小，不值得为此设计一套单独的去重机制——`headers` 不建议动 |
| **`Message.Body any`（合法 JSON 存 `json.RawMessage`，非法则存字符串）** | 已经是避免"先序列化成字符串、读的时候再反序列化一次"这种双重开销的高效编码，`reqdetail`/`chatmsg` 直接对 `map[string]any`/`json.RawMessage` 操作，未见可优化空间 |
| **`Record.Facts *core.RequestFacts`（图片/工具检测、预估 token 数）** | 这是"在写入期就该算好"这类字段的**正确先例**，但先例的正当性来自**它首先是路由决策需要的信息**（选路由前就要知道有没有图片/工具），分析半区读到它是顺带受益，不是它存在的理由。**不建议把这个模式继续往"分析专属的派生字段"方向扩展**——`chatmsg`/`ctxgraph` 已经在做的角色 token 占比、工具签名等提取，一旦也搬进写入路径，就会把"审计写入"和"分析逻辑演进"耦合在一起：分析口径每改一次，就要求写入路径（在请求服务热路径上）跟着改一次，直接违反 `CLAUDE.md` 的"两半区、一个契约"——`report`/`story` 不import `router`/`server`，但如果写入端开始为它们预先计算专属字段，等于反向耦合。**判断：`Facts` 已经是这条界线的正确位置，不建议进一步前移** |
| **`ReplayOf`/`ClientKeyTag`/`ErrorClass` 等既有小字段** | 全部命中"P0–P15 期间新增、体积可忽略、omitempty 兼容旧文件"这一类，符合 §3.2 论证的 schema 演进方式，无需调整 |
| **顶层 key 命名（`dur_ms` vs 更短的键名等）** | 不值得优化——键名在 zstd 压缩后的边际字节成本趋近于零（重复键名进入压缩字典），而 `jq`/`DuckDB` 场景下可读的键名比省下几个字节更有价值，见 §3.1 |

### 6.3 本节小结

**除 §6.1 一项外，字段级设计没有发现其他值得跟进的问题。** `Facts` 字段的存在方式恰好划出了一条
清楚的原则："只有路由决策本身需要、且计算成本低到可以放进请求热路径的信息，才适合在写入期落进
记录；纯粹服务分析读取的推导，应该留在读取/派生层"——这条原则同时**支持**保留 §6.1 现状的克制
（不要把"能重建"当成"必须重建"的借口去仓促修改一个有外部消费承诺的格式），也**支持** §6.1 指出
的方向本身没有违反这条原则（去掉一份可确定性重建的重复字节，不是"预先做分析"，是"不重复存储路由
半区自己刚刚做出的一次确定性改写"）。

## 7. 综合结论

- **容器格式（NDJSON + 按日 zstd）**：合理，不建议重构。
- **`LineAt` 无提前退出**：根因清楚、修法唯一、零副作用——**已修复**（`internal/audit/read.go`，
  两条新增回归测试）。
- **轮转无体积上限**：根因清楚，但修法要触碰实时写入路径 + 无唯一阈值 + 需要同步更新一份坐标
  唯一性假设文档——**判定不满足直接修复门槛，报告分析结果，等待你确认**，不在本次改动。
- **`Attempt.Request.Body` 复制 `Client.Request.Body`**（真实语料 59% 的文件字节）：本文档目前
  发现的最大一块单记录内部优化空间，机制本身风险可控（单记录、无状态、有响应侧先例），但落地是
  一次有外部契约影响的 schema 变更，需要独立评估与显式版本沟通——**只分析，不实施，留给你决定
  是否值得单独立项**。
- 其余字段级检查（headers、body 编码、`Facts` 的定位、既有小字段）**均确认现状合理，无需调整**。
