## 0. 任务 Debrief

### 0.1 这份文档解决什么问题

项目此前有两份并行的前瞻性文档：一份是战略层面的（定位、商业化、竞品、退出条件），一份是战术层面的（六项候选特性的落地方案分析）。三周下来两者都产生了漂移：

- **战略文档的漂移**：它的竞品扫描停留在"LLM Gateway 赛道"这个框架里，而过去半年真正爆发的是**Agent CLI 路由**这个相邻赛道——一个 36k star 的直接对手完全不在它的雷达上。它的 A1–A26 候选清单里也有相当一部分已经实现了。
- **特性文档的漂移**：六项候选里，两项（条件路由框架 + Sticky Model、成本核算报表）已经完整落地，还有若干旧清单项被顺带做掉了，但文档仍把它们列为"待办"。

两份文档合起来 900 多行，其中相当比例是已完成事项的历史记录、逐轮修订的批注、以及指向对方的交叉引用。继续在上面打补丁的成本已经高于重写。

### 0.2 做法

1. **逐条实测实现状态**，不看文档自述。例如判断"成本核算是否已实现"，看的是 `pricing.yaml` 是否存在、`cmd_report.go` 有没有 `-pricing` flag、聚合结构体里有没有 `CostEstimate` 字段；判断"上下文超限错误类是否已实现"，看的是 `internal/core/core.go` 的 `ErrorClass` 枚举里有没有对应值。已实现的项**直接从路线图删除**，不保留为历史记录——历史记录属于 git log 和设计文档，不属于战略规划。
2. **重扫竞争格局**。旧文档的名单按原样核对了一遍最新数据，同时补了它完全没有覆盖的一类对手。**能力判断落到可引用的原文上**，不用印象——这条纪律在本轮直接推翻了一个初稿结论（§3.2）。
3. **重新推导优先级**，而不是把旧清单排个序。三周的执行结果本身改变了约束条件（见 §1.4、§5），排序依据也必须跟着变。

### 1.2 已建成的能力

按用户可见价值分组，全部为已实现并有测试覆盖的能力：

**路由与可靠性**
- 双协议入口（OpenAI `/v1/chat/completions`、Anthropic `/v1/messages`），同协议族内路由，永不互译
- 按错误类分级的健康状态机：冷却、指数退避、半开单飞恢复；`Retry-After` 遵循；内容策略拒绝换端点但不惩罚端点健康
- 恢复探测始终用后台探针（2026-08-02 起移除了"下一个真实请求当探针"的被动模式），恢复检测完全脱离真实流量
- 条件路由框架：端点声明 `capabilities: [image, tools]` 与 `max_context_tokens`，不满足的端点在准入阶段被淘汰；上下文估算过高时有回退规则兜底，保证保守估算永不误杀本可成功的请求
- Sticky Model 会话亲和：多轮对话钉在上游 prompt cache 已经预热的那个端点上，避免"更聪明的路由"反而推高成本
- `priority` 排序维度、并发闸、分级超时、全局与 per-provider 代理、配置热重载

**可观测性**
- 两层审计 JSONL（client↔vmr、vmr↔upstream），每次 failover attempt、每项响应归一化动作都记录；历史文件自动 zstd 压缩与过期清理
- `vmr report`：会话 → 任务 → 轮次的 agent 语义分组、每轮增量标记、工具声明与实际调用的对比分析、按模型/端点/客户端/时段多维聚合、真百分位延迟与 TTFT、逐请求详单导出
- 成本估算：`pricing.yaml` 侧车文件，支持多币种与时间窗定价，报告内冻结本次使用的价目表快照

**调试工具**
- `vmr diagnose`：配置校验 → 环境检查（代理感知的 DNS/TLS）→ 连通性测试（nonce 回显校验，识别"200 但模型没真跑"）→ 路由预览
- `vmr replay`：三种定位方式（`-line`/`-ts`/`-detail`）从审计记录重建并重发请求，与真实流量共用同一段请求构建代码，支持 `-dry-run` 与 `--record`
- `vmr check` / `status` / `dirs`；`vmr.sh` 的 dev 模式与 service 模式（launchd / systemd）

**厂商 quirk 修复**（每项都有严格的内容守卫，存疑即不改）
- MiniMax `<think>` 块剥离、纯文本 "Thinking Process:" 草稿剥离
- 软屏蔽标记检测（`input_sensitive` / `output_sensitive`）——仅观测
- thinking 剥离规则失效的观测告警（内容仍具编号推理小节形状但未命中现有守卫时打标）

**工程基础设施**
- `internal/archtest`：把架构不变式（import 边界、核心文件行数上限）写成可执行测试
- fuzz 测试（`FuzzRewriteModel` / `FuzzRewriteStream`，已实际抓到一个 nil map panic）
- `loadtest/`：mock 上游 + 目标生成器 + 压测 runner

## 3. 竞争格局（2026-07-27 重扫）

### 3.1 赛道需要重新划分

旧的分析把所有对手放进一个"LLM Gateway"框架里比较，这个框架已经不能解释现实。实际存在三个不同的赛道，它们的用户、采购逻辑、竞争强度都不一样：

**赛道 A：企业 LLM Gateway**——LiteLLM、Bifrost、Portkey、Higress、AISIX、Helicone、TrueFoundry、Kong AI Gateway。
面向团队/企业，核心诉求是统一接入、成本治理、可观测性、guardrails、RBAC。翻译型架构是这个赛道的默认选择，因为"一个 API 打通 1000+ 模型"就是它的产品承诺。**vmr 不在这个赛道，也不应该进去**——进去就要做 DB、Web UI、多租户，那是 55k star 项目的主场。

**赛道 B：Key 池 / 中转分销**——new-api、one-api、gpt-load、aiproxy。
面向"我有一堆 key / 我要二次销售"，核心是渠道管理、余额、兑换码、负载均衡。中国团队主导，市场饱和。**与 vmr 正交**，且 vmr 明确不进入。

**赛道 C：Agent CLI 路由**——claude-code-router、CLIProxyAPI、claude-code-mux、以及各种"Claude Code 接国产模型"的小工具。
面向个人开发者，核心是"让我手里这个 agent CLI 用上别的模型 / 别的账号"。**这才是 vmr 实际身处的赛道**，也是旧文档完全没有覆盖的赛道。

这个重新划分带来两个后果，一好一坏：

- **坏消息**：vmr 所在的赛道比旧文档以为的拥挤得多，**而且对手在向 vmr 的方向收敛**。`claude-code-router` 36.2k star、`CLIProxyAPI` 45.2k star，都在解决用户心里的同一个问题（"我的 Claude Code 怎么用上别的模型"），而 vmr 是 2 star；更关键的是前者已经补上了 failover、请求日志和成本估算（§3.2）。
- **好消息**：这个赛道的规模被验证了。36k + 45k star 说明需求是真实且巨大的。旧文档担心的是"这个小众需求会不会根本没人要"，实测答案是——要的人非常多，只是他们目前用的是别的工具。

### 3.2 直接对手

#### claude-code-router（36.2k star，JavaScript，活跃）

**旧文档完全没有收录的最直接对手。** Node.js CLI，把 Claude Code 的请求路由到 OpenRouter / DeepSeek / Ollama / Gemini / 火山引擎等，靠一套 transformer 插件做请求改写。

**必须先纠正一个想当然的判断。** 本次核对前，基于"它是个换模型的小工具"的印象，本文档的初稿曾断言它没有 failover、没有日志、没有成本核算。**读了它的 README 之后，这三条全错**：

| 能力 | 实际情况（引自其 README） |
|---|---|
| 自动 failover | **有**——"retries, credential pools, key rotation, and ordered fallback models"，还有 provider 的 connectivity checks |
| 请求日志 | **有**——请求日志含"resolved provider, model, and credential; status; latency; tokens" |
| 成本 | **有**——dashboard 里有 estimated cost 与 token 用量 |
| 请求改写 | 有——"request rewrites"，跨协议时"API endpoints are adapted automatically" |

**这是本次复核最重要的发现，它压缩了 vmr 的差异化空间**：一个 36k star 的对手已经沿着"路由 → failover → 日志 → 成本"这条路收敛到了和 vmr 相当接近的功能列表，而且它有 Web dashboard，装起来是一条 `npm` 命令。

**剩下的真实差异**（收窄后，但仍然成立）：

- **改写型 vs 透传型**。它靠 transformer 把请求转成各家格式，新参数、新字段要等插件跟进；vmr 的未知参数原样透传，上游当天发布的能力当天可用。
- **日志的粒度不同**。它记的是元数据（provider/model/status/latency/tokens）；vmr 记的是**两层完整字节**（客户端看到的 + 上游实际收发的）+ 每次 failover attempt + 每项归一化动作。前者能告诉你"这次请求失败了"，后者能告诉你"上游到底收到了什么、返回了什么"。
- **agent 语义的组织方式**。它是按请求平铺的日志列表；vmr 是会话 → 任务 → 轮次的分组，含每轮增量与工具声明/实际调用对比。
- **可回放**。vmr 能把任意一条历史记录原样重发；它没有等价能力。
- **会话亲和与 prompt cache**。vmr 有 Sticky Model；未见等价机制。
- **形态**。它是 Node.js + dashboard；vmr 是单二进制、零运行依赖、无 UI。

**对 vmr 的意义**：它证明了需求，也占住了这个需求最直白的表达方式（"给 Claude Code 换模型"）。vmr 不能在这条赛道上正面比"支持多少家模型"，也**不能再简单地说"只有我有 failover 和日志"**——必须比**记录的深度**（字节级两层 + agent 语义 + 可回放）和**透传的正确性**（不改写就不会改坏）。

**威胁等级：高**，且比初稿评估的更高。它不只是占住了搜索词，它的功能列表也在向 vmr 靠拢。vmr 结构性做不到的是它的分发（Node 生态 + dashboard 的低门槛），vmr 结构性领先的是记录深度与透传正确性——**后者必须成为对外表达的核心，因为它是唯一不会被这条收敛路径追平的东西**。

#### CLIProxyAPI（45.2k star，Go，活跃）

把 Claude Code / Codex / Gemini CLI / Grok 的 **OAuth 订阅**重新打包成标准 API。上游是订阅而非 API key，与 vmr 的输入侧完全不同。

- **与 vmr 的关系**：更像上下游而非竞争——用户完全可能用 CLIProxyAPI 把订阅变成 API 端点，再把这个端点配进 vmr 的候选池。
- **威胁等级**：低。但它的 45k star 说明 Go 写的、单二进制的、面向 agent CLI 的工具在这个人群里完全跑得通，这是对 vmr 技术选型的正面验证。

#### claude-code-mux（520 star，Rust，2025-11 后无提交）

功能描述与 vmr 高度重合：优先级路由、自动 failover、Anthropic 原生兼容、18+ provider（含 MiniMax、Kimi）、约 5MB 内存、<1ms 路由开销。

- **最有价值的信息不是它做了什么，是它死了。** 2025-11-19 之后没有任何提交，520 star 停在那里。
- **可以读出的判断**：这个位置有人试过，做到 500 star 量级，然后作者不做了。这既说明"路由 + failover"本身不足以形成持续吸引力（500 star 后没有社区接手），也提示 vmr 需要一个比"更快更小的路由器"更难被复制的东西——审计与报表就是那个东西（§4.2）。
- **威胁等级**：低（已停更），但**警示等级高**。

#### LiteLLM（54.8k star，Python，活跃）

翻译型的事实标准，YC W23，有商业版。100+ provider、9 种协议端点、PostgreSQL dashboard。哲学与 vmr 相反：它把所有 API 重写为 OpenAI 格式。

- **不变的判断**：他们不会加 byte-faithful 模式，这是哲学级冲突而非功能缺口——他们的整个价值主张就建立在"替你翻译"上。
- **威胁等级**：中。不是产品替代威胁，是**注意力威胁**——任何人搜"LLM gateway"先看到的是它。

#### Bifrost（6.8k star，Go，活跃）

Maxim AI 出品，Go 语言，主打极致性能（自述 50x faster than LiteLLM、sub-11μs 开销）、MCP 支持、Web UI、语义缓存、集群模式。仍是翻译型。

- **与 vmr 的差异**：同语言、同"高性能"叙事，但产品形态是企业 gateway（Web UI + 集群 + 治理），与 vmr 的单机 Unix 工具形态不重叠。
- **威胁等级**：中。它是"Go 写的 AI Gateway"这个搜索词的占位者。

#### Portkey Gateway（12.6k star，TypeScript，2026-05 后无提交）

1600+ 模型、50+ guardrails、observability。**2026-03 起 gateway 核心转为 Apache 2.0**，商业化在其托管平台侧。最近两个月无提交，可能是开源核心进入维护模式、精力转向云产品。

#### gpt-load（6.3k star，Go，活跃）

Go 写的多 key 轮询/负载均衡代理。赛道 B，与 vmr 正交，但同为 Go + 单二进制 + 面向中国用户，是渠道传播上的参考对象。

### 3.3 能力对照矩阵

按"记录深度"分层，每层内按 star 数升序（只列在这个维度上可比的项目，纯 agent 框架与推理基础设施不在内）：

| 记录深度 | 项目（按用户规模升序） |

| **字节级两层 + agent 语义 + 可回放** | **vmr（2）** —— 独占，无第二个 |
| 请求元数据 + 成本 + 可视化 | Helicone（6.0k）、Bifrost（6.8k）、Portkey（12.6k）、claude-code-router（36.2k）、LiteLLM（54.8k） |
| 基础转发日志 | claude-code-mux（520，已弃）、gpt-load（6.3k）、new-api（43.6k）、CLIProxyAPI（45.2k） |

**vmr 独占最深的一层，同时是全表用户规模最小的一个。**

第一层的领先难以被快速追上，但原因不是技术难度——**是架构前提**。要做到字节级两层记录，必须先放弃翻译；而放弃翻译就等于放弃"一个 API 打通 1000+ 模型"这个所有对手赖以生存的产品承诺。这是一道他们不会跨的门槛，不是一个他们没排上期的功能。

而用户规模的落后是**完全人为的**：它的直接原因是"装不上"（§3.3 倒数第二行），不是产品能力问题。

### 3.5 2026 年赛道的三个新趋势，与 vmr 的取舍

行业公开讨论里，2026 年 AI Gateway 的三个"新一代必备能力"是：MCP 流量治理、语义缓存、按消费方的成本治理。逐条给出 vmr 的立场：

| 趋势 | vmr 的立场 | 理由 |
|---|---|---|
| **MCP 流量治理** | 不做 | MCP 是 agent 与工具之间的协议，不在 LLM API 路径上。vmr 位于 agent 与模型厂商之间，MCP 流量根本不经过它。把它塞进来需要一个全新的入口和一套全新的语义，与"单一关注点"直接冲突。**但要在文档里明确回答这个问题**，因为用户会问 |
| **语义缓存** | 不做 | 与 byte-faithful 直接冲突：返回一个"语义相近"的缓存响应，意味着客户端拿到的不是上游此刻会返回的字节。对 agent 场景尤其危险——agent 依赖响应做下一步决策，一个"差不多"的响应会静默改变执行路径。这是 vmr 明确让给 Bifrost/Portkey 的能力 |
| **按消费方的成本治理** | 部分做，方向不同 | 报表侧的成本归因已经落地。**实时预算硬闸**（§6.2 P1）是合理的下一步，但形态必须是"触顶明确拒绝并给出可解析错误"，而不是企业 gateway 那种"按 team/key 配额 + 降级到便宜模型"——静默降级会让 agent 在不知情的情况下换了个脑子，比直接失败更难排查 |

这三条应该原样写进对外文档的 FAQ。**明确说清楚不做什么、以及为什么不做，是小工具区别于大平台的产品表达方式**，比列一堆特性更有说服力。

## 4. 核心战略判断

### 4.1 是否值得继续做

值得，但**继续做的内容必须变**。

支撑"值得"的证据：技术差异化经受住了独立审计与压测；赛道 C 的 36k + 45k star 证明需求规模真实；唯一在做同一件事的 Rust 项目已经停更，说明位置空着。

**但要诚实地记下差异化在收窄**：三周前可以说"只有 vmr 有 failover 和可观测性"，现在不能了（§3.2）。剩下的护城河是明确的五项（§3.3 第 6–10 行），它们建立在"不翻译"这个对手跨不过去的架构前提上，所以短期内不会被追平。**但这也意味着窗口是有限的**——差异化每窄一分，"先把东西发出去"的紧迫性就高一分。这是本文档把分发排在所有特性之前的第二个理由（第一个理由见 §5.1）。

但"值得继续做"不等于"值得继续按现在的方式做"。当前的投入结构是：约 100% 工程，约 0% 分发。而当前的瓶颈 100% 在分发侧。继续按这个结构投入，边际价值接近零——第 82 次提交不会带来第 3 个 star。

### 4.2 定位重述：从"byte-faithful 路由器"到"agent 运行的黑匣子"

这是本文档最重要的一处判断变更。

**问题**：`byte-faithful` 是一个**实现属性**，不是**用户收益**。没有人会因为"字节保真"去下载一个工具——用户不知道自己需要它，也不知道缺了它会怎样。当前 README 的头版承诺是"透明路由 + 自动 failover"，而 §3.2 的核对已经证明：**这恰好是 claude-code-router 和所有企业 gateway 都已经提供的表层功能**，vmr 在这个维度上无法用 2 star 的身份赢得比较。

**用户真正会为之下载工具的问题**是这一类：

> 我的 agent 昨晚跑了一整夜。它做了什么？花了多少钱？中间失败过几次？为什么那次卡住了？那个空回复是怎么回事？我能把那一次原样再跑一遍看看吗？

前两问现在已经有别人能答（CCR 的日志 + 成本估算）。**但从"为什么那次卡住了"开始，vmr 是唯一能答的**——因为回答它们需要的不是统计，是**当时那一刻上游到底收到和返回了什么字节**，以及**把那一刻重放一遍**的能力。

vmr 能答，因为它同时具备四个条件，缺一不可：

1. **位于必经路径上** —— agent 与模型厂商之间，所有流量都过它
2. **两层完整记录** —— 客户端看到的和上游实际收到/返回的，都在
3. **agent 语义的组织方式** —— 不是一堆平铺的 HTTP 日志，而是会话 → 任务 → 轮次，每轮的增量、工具声明与实际调用的对比
4. **可回放** —— 任何一条记录都能原样重发，复现当时发生了什么

这四条里，第 3 条和第 4 条是全表唯一（§3.3），第 1、2 条是 byte-faithful 的**结果**——正因为不做翻译，记录下来的才是真实发生的字节；正因为记录的是真实字节，回放才能复现；正因为能复现，quirk 修复才敢做。

**所以对外表达的顺序应该反过来**：

| 层次 | 现在的说法 | 应该的说法 |
|---|---|---|
| 头版 | The transparent LLM router for AI agents | agent 运行的黑匣子：昨晚那次失败，能查到上游到底收发了什么，还能原样重放 |
| 第二层 | byte-faithful 透传 | 自动 failover，无人值守时供应商挂了也不中断 |
| 第三层 | 自动 failover | byte-faithful 透传——这是上面两条能成立的技术前提 |

注意第一行的措辞：**不能只说"能看到花了多少钱"**，那一条已经被追平（§3.2）。头版必须落在"字节级 + 可重放"上，那才是无法被翻译型架构追平的部分。

byte-faithful 不该消失，它是**可信度依据**：为什么你该信任这份记录？因为 vmr 从不改写你的请求，记录里的就是上游收到的。它应该出现在"为什么可信"的位置，而不是"这是什么"的位置。

**这个重述不需要写一行代码**——能力已经全部实现了。它改的是 README、文章标题、和第一屏该放什么截图。

### 4.3 形态选择

| 形态 | 判断 | 说明 |
|---|---|---|
| 个人单机 Unix 工具 | **默认形态，维持** | 单二进制 + 一份 YAML。与项目基因、维护规模、技术选型完全一致 |
| Agent 优先定位 | **主定位，强化** | 见 §4.2 的重述。这是唯一能赢的赛道 |
| 与某个 agent runtime 深度绑定 | **不锁定** | 保持"可插拔组件"关系。单一客户依赖是真实风险，且会让其他 runtime 的用户觉得这工具不是给他们的 |
| 本地 AI Gateway 平台（team/RBAC/dashboard） | **不做** | 需要 DB、需要企业级团队规模，且 LiteLLM 已占满 |
| 云端 SaaS | **不做** | OpenRouter 统治该形态，且个人无法承担 7×24 SLA |
| 商业版（source-available） | **不主动做，保留为应急** | 只有在真有企业客户上门时才重新评估 |

### 4.4 与 agent runtime 生态的关系

vmr 与 OpenClaw 之间存在一个需要明确表态的既成事实：**`internal/report` 里编译进了 OpenClaw 的客户端方言知识**——信封 JSON 块的识别、时间前缀、`chat_id` 正则、`heartbeat` / `dream_diary` 两个定时任务类别，共 33 处，分布在 6 个源文件里（另有 Claude Code 的 `metadata.user_id`）。

**这件事的两面**：

- **正面**：agent 会话分组正是 `vmr report` 相对通用日志分析工具的核心差异化，而它必须依赖某个客户端的具体消息格式才能做到。这些启发式写得很克制——失配无害，标不出就不标。**这个耦合换来的是真实价值，不是技术债。**
- **负面**：一个协议无关、厂商无关的路由器，其二进制里编译进了某个特定 agent 应用的消息格式与定时任务名称。问题不在于它们存在，在于它们的位置（清理方案与触发条件见 §7）。

**关系定位**：vmr 是任何 agent runtime 的**可插拔组件**，不是任何一家的内置件。README 现在的措辞（"任何 OpenAI/Anthropic SDK"）已经规避了排他表述，应保持。深度绑定单一 runtime 是真实风险——它会让其他 runtime 的用户觉得这工具不是给他们的，而"其他 runtime 的用户"恰好是待开拓的全部增量。

**同时这也是一条尚未使用的分发渠道**：进入 agent 工具的 setup 文档是获客效率最高的路径之一，但它依赖对外联系，vmr 单方面完成不了（见 §5.2 的 D8）。

### 4.5 版本策略与稳定性承诺

当前状态：唯一的 release 是 `v0.1`，无二进制、无 `vmr version` 子命令、代码已领先 tag 约 50 个 commit。这个状态既不利于分发，也不利于建立"这个东西可以依赖"的印象。

**建议的版本策略**：

- **不急于 1.0**。1.0 是一个承诺，不是一个里程碑庆典。在拿到外部用户反馈之前打 1.0，等于在没有验证过的接口上冻结兼容性。合理的触发条件是"配置格式经过至少一批外部用户实际使用且没有暴露需要破坏性修改的设计问题"，而不是某个日期。
- **`v0.x` 阶段按需发版**，每次发版必须带二进制（这是 D1 的产物，之后就是零成本的重复动作）。
- **`config.yaml` 是公共 API**。它是用户唯一的接口面，且严格 YAML 校验意味着任何字段变更都是硬失败而非静默降级。应当明确承诺：0.x 阶段允许加字段、不允许改语义；1.0 之后不做破坏性变更，即使为此付出实现上的代价。
- **`vmr version` 子命令**是发布二进制的必要配套——用户报 bug 时第一件事就是问"你用的哪个版本"，而现在无法回答。归入 D1。

这条承诺的意义不只是对用户：它同时是**对未来接手者的约束**，避免项目在换手后因为"顺手改了个配置字段名"而破坏既有用户。

### 4.6 商业化的现实评估

**结论不变：不现实，且不应作为目标。**

需要补充的是一点更诚实的说法：旧文档把商业化归入"暂时不现实"，语气上留着未来转正的余地。基于三周的实际数据，应该说得更直白——**在 2 star、0 issue 的状态下讨论商业化模式是本末倒置**。任何商业化路径的前置条件都是"有人在用"，而这个前置条件目前完全不成立。

vmr 的价值应当明确锚定在三处，且这三处已经足够：

1. **自用生产力** —— 作者本人的多账号、多厂商、无人值守 agent 场景，这是真实的、每天在发生的价值
2. **知识资产** —— 167KB 设计文档 + 231 行遗留问题清单 + 可执行的架构不变式测试。这套东西的可继承性远超代码本身
3. **可能的载体引流** —— 如果未来有某个 agent 产品需要"透明的失败路由 + 可审计"作为差异化能力，vmr 是现成的；另外它本身也是一份可展示的工程作品

不必为了"商业化可能性"去做任何产品决策。这一条应该写进 README 的定位里——**明说这是个人工具、不打算 SaaS 化、不会有 enterprise 版**，反而是这类工具建立信任的方式。

## 5. 战略优先级：分发压倒特性

### 5.1 为什么这是当前唯一重要的事

三个事实叠加：

1. **产品侧已经过关**。第一梯队问题为空，压测数据齐全，架构不变式有测试锁定。不存在"再打磨打磨就能发布"的状态——它已经可以发布了。
2. **零外部反馈**。所有优先级判断都是单人推断。在拿到第一批真实用户之前，任何特性排期都是在猜。
3. **最大的障碍是最便宜的**。`v0.1` release 没有二进制附件，README 的安装方式是 `go build`。这意味着**每一个不装 Go 工具链的人（也就是绝大多数 Claude Code 用户，他们主要是 JS/Python 背景）在第一步就被挡住了**。修这个的成本是几小时。

第 3 条尤其值得单独说：vmr 的核心卖点之一是"单二进制、零依赖、开箱即用"，而它当前的实际安装体验是"先装 Go，再 clone，再编译"。**产品承诺与实际体验之间的这个矛盾，是当前最严重的问题，且与代码质量完全无关。**

## 6. 特性路线图

### 6.1 筛选原则

在拿到第一批真实用户之前，特性筛选的第一原则从"工程 ROI"改为：

> **这个特性能否直接帮助获取或留住前 50 个用户？**

同一批候选在两种排序下顺序完全不同。举例：软拦截升级 failover 在工程 ROI 排序下靠后（2–3 人天、架构风险最高），在新排序下靠前（它是中文场景独有的痛点，是文章选题 2 的实际支撑，也是没有任何对手能提供的能力）。

保留的既有边界（这些不变）：不破坏 byte-faithful；不引入新运行时依赖；不引入 DB/Web UI/RBAC；保持单二进制；不做规则引擎或条件表达式 DSL；每个特性默认配置就能用，不引入"实验模式"开关；**新增特性必须能用审计 JSONL 自我验证**——用户排错时永远只需要看一个地方，这是"可调试性"作为核心定位的直接推论，也是判断一个特性是否属于 vmr 的最好试纸。

### 6.2 候选清单

**本文档写成后已落地（2026-07-28）**——不占本节排期，列此以免重复论证：`vmr version` + 运行实例版本上报（`/admin/status` 的 `instance.version`，靠 Go 自带 VCS 戳，零构建配置）；热重载结果与配置新鲜度上报（`config_stale`/`reload`，关掉"进程在服务一份与磁盘不符的配置而外部看不出来"这个静默失败面）；`vmr.sh ps`（本机全部实例：端口 + 配置 + 版本）与 `vmr status -addr/-brief`；`vmr.sh` 原生命令透传；响应头 `X-VMR-Route-Reason`/`X-VMR-Failover`；`attempts[].upstream_model` 采集；report 新增 §6.5 Sticky 有效性与 §6.6 端点性价比，渲染层按章节拆文件并纳入 archtest 行数预算。


**常设义务 —— 不占排期，但优先级高于一切特性**

**协议前向兼容跟随。** OpenAI / Anthropic 每次协议演进（新参数、新事件类型、新的 thinking / reasoning 形态、Responses API 之类的大版本），vmr 都必须保持可用。byte-faithful 设计让这件事在绝大多数情况下是**零改动**的——未知参数原样透传，新特性当天可用，这正是相对翻译型网关的结构性优势（对方每次升级要改 N 个翻译器）。

但"绝大多数"不是"全部"，需要主动盯的有两类：一是错误分类词表（新厂商、新措辞），二是响应归一化里那几条厂商 quirk 守卫（上游改了措辞，守卫就会静默失效——`thinking_process_pattern_detected` 这个观测标记存在的全部理由就是提前发现这种失效）。

**这条不是一个可以"做完"的特性，是一条持续义务**，且它是 vmr 存在价值的底线：一旦某天上游发了新东西而 vmr 用不了，byte-faithful 的全部论证就同时失效了。

**P0 —— 服务于分发（与 §5.2 的 D5 是同一项）**

**`vmr.sh doctor` + `check`/`status`/`dirs` 的 `--json`**

- **问题**：新用户排查"为什么连不上"时，要分别跑 `vmr check`（纯文本）、`vmr diagnose`（已有 `-json`）、`vmr status`（纯文本、依赖进程已启动）三条命令自己拼线索。
- **方案**：`cmdStatus` 底层本来就是对 `/admin/status` 发 GET 拿 JSON 再重新格式化成文本，加 `-json` 只是跳过重新格式化这一步，接近零成本；`cmdCheck` 需要先把过程式打印抽成结构体再分两种模式，稍多一点工作量；`vmr.sh doctor` 依次跑三者并拼一个红绿灯摘要，进程未启动时 status 段要优雅报 "not running" 而不是让整条命令失败。
- **为什么是 P0**：它是唯一一个直接产出演示素材的特性。"一条命令看清一切"的那一屏截图，是文章和 Show HN 帖子最好的开场。
- **成本**：0.5–1 人天。

**P1 —— 真实痛点，且是差异化能力**

**1. 软拦截（2xx 但内容为空/被替换）升级为可 failover**

- **问题**：国产厂商特有的"HTTP 200 但内容被替换/清空"的软屏蔽。agent 完全无感知，基于空回复继续往下跑。无人值守场景下比 429 更危险，因为 429 会触发现有 failover，软拦截不会。目前 vmr 只做检测打标（`soft_block_detected`），不影响转发也不影响健康。
- **方案要点**：
  - **范围收窄到非流式（buffered）响应**。缓冲路径本来就是"整个 body 读完、规整化完、再一次性写出"，天然满足"检测完再决定转发还是 failover"的时间顺序。流式路径从第一个 payload event 起就在边读边转发，检测点出现时字节可能已经写给客户端了，**技术上做不到 failover**，只能继续保持仅观测。这一点必须在实现和文档里都写清楚，不能承诺做不到的事。
  - 关键架构改动是把"2xx 即刻上报健康并开始转发"这个隐含前提拆开，插入一个"先决定要不要 failover，再上报健康"的判断点。流式转发路径必须保持零改动。
  - **判据要收窄**：要求"标记命中 **且** 有效内容为空/极短"，避免把"确实有标记但正文还有内容"的情况也切掉。
  - 错误语义直接复用现有的 `ErrContent`（换端点、不惩罚端点健康），不新增 ErrorClass——软拦截的效果就是"这条请求被内容策略拦了，换个端点也许能过"。
- **为什么在 P1**：它是全表唯一的能力（§3.3），是中文文章选题 2 的实际支撑，也是"无人值守 agent 静默吃错误回复"这个最危险场景的唯一防线。
- **成本**：2–3 人天。是清单里架构风险最高的一项，需要额外的回归验证。

**2. 上下文超限（context length exceeded）独立错误类 + failover**

- **问题**：长会话 agent 跑到某个点，请求体超过便宜端点的 context 上限，厂商返回 400。当前分类逻辑会把这类 400 归到"请求本身有问题、不 failover、直接返回客户端"，一个跑了两小时的任务就此终止——即使候选队列里可能正躺着一个 context 更大的端点。
- **方案要点**：在现有的分类链上插一段中英双语词表匹配（`maximum context length`、`context_length_exceeded`、`too many tokens`、`输入长度超过` 等），位置放在内容策略词表之后、模型词表之前，避免 model 相关词表误吞。新增一个 `ErrContextLimit` 错误类，行为与 `ErrContent` 同构：换端点、不惩罚端点健康（端点没病，是这个请求太大）。
- **风险很低**：词表误判的最坏情况只是多切换一次，不会造成安全问题，适合"宁可宽松"的判定策略。
- **成本**：0.5–1 人天。清单里改动面最小、复用度最高的一项。

**3. per-virtual-model 预算硬闸**

- **问题**：现在的健康机制全是事后反应。对 bootstrap 用户还有一个更根本的风险——**一个进入死循环的 agent 可以在一夜之间烧掉整月额度，vmr 全程忠实转发，一句话不说。**
- **方案要点**：
  - 新增一个内存态的预算注册表（结构仿健康注册表），key 为虚拟模型名，值为今日已用 token/成本 + 上次重置时间。
  - 配置侧给虚拟模型加一个可选的日预算字段。建议**先只做 token 预算**作为 MVP（不依赖价目表，可独立交付），成本预算作为后续增量——成本核算已经实现，接上不难，但两者可以分开排期。
  - 检查点放在请求入口，**只检查一次**，不要每个 attempt 都查——这样行为对客户端是确定的（要么整个请求被拒，要么不受预算影响），避免"重试到一半突然被预算拦下"的诡异中间态。
  - 触顶行为必须是**明确拒绝 + 可解析的错误**（说清楚"虚拟模型 X 今日预算已用尽，阈值 Y，已用 Z"），**绝不静默降级到便宜模型**——静默降级会让 agent 在完全不知情的情况下换了个脑子，比直接失败更难排查。这是本项最重要的取舍。
  - 重置语义：每日零点重置，**进程重启也重置**。明确接受这个弱语义并在文档里直说"这是防呆，不是防欺诈"。不要为了持久化这个状态引入文件或 DB——那是滑向"vmr 需要持久化状态"的第一步。
- **成本**：1.5–2 人天（纯 token 版本）。

**P2 —— 等第一批用户反馈后再排**

这一档的共同特征是：都是合理的改进，但**没有一项被外部用户要求过**。在拿到真实反馈之前，它们的相对顺序是猜的，因此不预先排期。

| 项 | 一句话 |
|---|---|
| `vmr report -no-sessions` | 跳过会话分析，加速大日志场景（百万行下会话分析仍是分钟级） |
| 审计记录加 `client_ip` | 支持按来源 IP 聚合 |
| `vmr replay -list` | 不解码全部内容，只列摘要表，便于在 GB 级日志里定位回放目标 |
| `vmr replay --format=curl` | 体验糖，成本很低，可与上一项一起做 |
| `vmr diagnose --diff-config` | 热重载被拒时指出是哪个字段导致的。**部分已覆盖**：`/admin/status` 与 `vmr status` 现在会报出最近一次重载被拒及其原因、以及配置文件比运行中的配置更新，剩下的增量只是"定位到具体字段" |
| `weight` 排序维度 | 同 priority 内按权重加权随机。已有过一轮方案设计，未落地 |
| 端点级 rpm/并发限流 | 主动避免 429。现有 failover 已把 429 的用户可见伤害压得很低，价值中等 |
| `/metrics`（Prometheus 文本格式，手写无依赖） | 有真实用户要接监控时再做。**OpenTelemetry exporter 与端到端 trace 归入同一条**——三者解决同一个诉求（接入既有监控栈），应当一起设计并只选其一落地，不要各做一半 |
| `vmr watch`——实时 tail 审计日志 | `vmr status` 已覆盖健康态，这一条补的是"看着请求实时流过"。演示效果好，实用价值中等 |
| provider health score（成功率/延迟的精细统计进 `vmr status`） | 现有健康机制是二值的（可用/冷却中）。精细化后能看出"这个端点在变差但还没到冷却"。离线侧已由 report §6.6 端点性价比部分覆盖（成本/单位产出 + 失败尝试累计耗时），这一条剩下的是**实时**视图 |
| 上游凭证轮换（key rotation） | 单账号多 key 时有用。mTLS 一并归入本条，但没有任何证据表明目标用户需要它。与 CCR 分析报告的 T1-1 多 Key 池是同一件事，那边有更完整的阻力分析（`Endpoint.Name()` 不含 key 指纹是真正的工作量所在） |
| `audit_rotate_interval: hour｜day` | 当前只有天级轮转。当前流量级别够用 |
| 客户端中途断开的可区分性 | 目前流中途断开与完整成功在审计里完全一样，会污染 p95 分析。需要改审计 schema，是一次跨包变更 |
| 直连语法 `model: "provider:model"` | 绕过虚拟模型直达指定 provider，调试用 |
| Endpoint 级参数覆盖 | 强制 temperature、注入 OpenRouter 路由参数等 |
| gemini 协议入口 / embeddings / images 路由 | 新增协议族，等有人要 |
| `vmr replay` 的响应 diff 视图 | 现状是只打印新响应，对比靠用户自己 diff |
| 请求预处理插件（敏感词过滤） | 对软屏蔽的唯一**事前**防线。本轮明确不预留接口——插件的词库形态、替换策略、是否按 provider 差异化都未定，先挖的接口大概率对不上，预留即负债 |

**已评估、判定价值不足以进入候选池的**（列在这里是为了下次不必重新论证）：`vmr convert-config`（从 OpenRouter 配置转换）、`--web` 报告模式、`-pprof` flag、`vmr admin replay`（生产进程内回放，离线 `vmr replay` 已覆盖核心场景）、`vmr report --diff baseline.json`（无真实用户反馈驱动）、跨请求复用检测结果（当前 per-attempt 已够用）。

### 6.3 明确不做

| 项 | 理由 |
|---|---|
| 翻译模式 / bypass mode | 与 byte-faithful 直接冲突。要 LiteLLM 风格就该去用 LiteLLM |
| 语义缓存 | 见 §3.5。对 agent 场景是正确性风险 |
| MCP 网关 | 见 §3.5。不在 LLM API 路径上 |
| Web UI / Dashboard / DB 后端 / RBAC | 违反单二进制与零依赖，且被现有产品完全占据 |
| 分布式 / 多机协调 | 与单机 Unix 工具形态冲突 |
| 远程管理 API | 违反 loopback-only admin 的安全设计 |
| `.so` 运行时插件 | 违反单二进制。编译期注册（blank import）是唯一的扩展方式 |
| 请求签名 / provenance | 与信任模型冲突，且上游厂商有自己的认证方案 |
| 让价目表进入实时路由决策 | 一个会过期的外部文件不该进实时路径。成本只做事后算账 |
| 把 report 拆成独立二进制 | 12MB → 7MB 不是真实收益，却要牺牲"单二进制"这一核心定位 |
| 引入 DuckDB / cgo 做聚合 | 与"纯 Go、无 cgo、自包含"定位直接冲突 |
| 通用 HTTP provider（用户自定义请求/响应映射） | 本质是给用户一门映射 DSL，与"不做规则引擎/条件表达式"这条边界冲突。协议扩展的正确形态是新增一个编译期注册的 Adapter 包 |
| 非 HTTP 传输（gRPC / mcpo 等） | 目标场景（OpenAI/Anthropic 兼容厂商）全部是 HTTP，没有需求驱动 |

## 7. 工程债与可维护性

当前无第一梯队问题。以下是已识别、有价值但成本或风险不低的项，**全部有明确的触发条件，在触发条件出现之前不做**——这是刻意的克制，不是拖延：

| 项 | 触发条件 |
|---|---|
| `vmr report` 的两趟完整扫描合并为单趟 | 真的收到"报告跑太慢"的投诉时。会话分析器需要"全部记录到齐"才能做全局 join，改造成流式形状约 200+ 行，且要碰最微妙的启发式 |
| report 全内存聚合的记录量上限（千万级约 640MB） | 真的撞到内存墙时。方案是利用输入时间有序做流式分桶，跨日界即 finalize 并释放；**不接受用近似算法换内存**——真百分位是这份报表有意识的产品不变式 |
| agent 客户端方言收拢为 `internal/report/dialect/` 子包 | 接入第二个 agent 客户端时。现在只有一个实现，抽象一个只有一个实现的接口是投机性泛化 |
| 六个聚合桶类型的泛型化（约 1,200 行 → 300 行） | 代码量收益最大，但会改变对外 JSON 数据契约（同名字段的 `omitempty` 标签在不同类型上并不一致），必须接受一次 Format 号升级并用真实日志逐字节比对 |
| ingress 侧请求体的多遍扫描融合 | 存在明确风险来源：图片检测喂的是无 fallback 的硬性淘汰条件，判错直接导致 503，历史上出过一次真实误判事故。当前 p50 是 1–2ms，**不存在性能危机来正当化这个风险** |
| 审计落盘的 write syscall 移出全局锁 | 审计落盘成为实测瓶颈时。需要处理背压与关停语义（丢一条审计 vs 让关停挂住） |

**可继承性方面**已经做得比较扎实，不需要额外投入：167KB 设计文档覆盖每个决策的理由与取舍、231 行遗留问题清单逐条实测、架构不变式已写成可执行测试（import 边界、核心文件行数上限）、测试与生产代码接近 1:1。

唯一值得补的是 **CI**（§5.2 的 D2）——它同时是工程保障和仓库页上的信任信号。

## 8. 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **在无人使用的状态下持续投入而耗尽动力** | **高（当前最大风险）** | 高 | 这是本文档的核心议题。缓解手段是 §5 的分发优先 + §9 的止损规则。**风险不是"代码不够好"，是"好代码没人看见"，而后者会比前者更快耗尽动力** |
| 过度工程相对于用户规模 | 高（已发生） | 中 | 近 1.5 万行测试对应 0 个外部用户。缓解不是减少测试，是**把新增工程投入暂停**，先验证需求 |
| **claude-code-router 沿"路由→failover→日志→成本"路径持续追平** | **高（已发生，且被本次复核低估过）** | **高** | 见 §3.2 的实测更正。它已经有 failover、请求日志、成本估算。缓解**不是加快做特性**（那是在它选的赛道上比谁跑得快），而是把对外表达锁死在它架构上做不到的部分：字节级两层记录、agent 语义分组、可回放（§3.3 第 6–10 行）。**这条风险的真正危险在于识别延迟——本文档初稿就基于过时印象误判了它** |
| 上游厂商 API 变更导致失效 | 中 | 高 | byte-faithful 设计天然免疫：未知参数原样透传，新特性当天可用，零改动。这是相对翻译型网关的结构性优势 |
| Anthropic/OpenAI 自己出官方路由/网关 | 低 | 高 | 不太可能覆盖"多厂商 + 多账号 + 国产中转"这个组合，那与他们的商业利益相反 |
| 中国监管变化影响中转生态 | 中 | 中 | vmr 是本地工具、不持有 key、不做分销，监管暴露面低于 key 经销商类产品。但它服务的场景会受影响 |
| LiteLLM/Bifrost 加 byte-faithful 模式 | 低 | 高 | 哲学级冲突，他们的整个价值主张建立在翻译上。即便加了，agent 语义审计仍需要一次独立的产品决策 |
| 作者精力/生活变化 | 中 | 高 | 设计文档 + 遗留清单 + 架构不变式测试已经把可继承性做到位。这条风险已被结构性缓解 |
| 单一 agent runtime 依赖 | 低 | 中 | 已规避——README 措辞是"任何 OpenAI/Anthropic SDK"，不是"为某某而生" |

## 9. 成功度量与止损规则

旧文档有退出条件但没有先行指标，也没有"投入多久还不行就停"的规则。这一节补上——**没有止损规则的长期项目，最终是靠动力枯竭来结束的，那是最糟糕的结束方式。**

### 9.1 先行指标

star 数是滞后指标且容易自我欺骗。以下按信息量从高到低排序：

| 指标 | 含义 |
|---|---|
| **非作者提交的 issue 数** | 信息量最高。一个真实 issue 意味着有人装上了、跑起来了、遇到了问题、并且认为值得反馈 |
| **外部博客/帖子的自然提及** | 说明有人认为它值得告诉别人 |
| release 二进制的下载数 | 比 star 更接近"真的在用" |
| star 数 | 最容易看但信息量最低 |
| fork / PR | 长周期指标，6–12 个月内出现算正常 |

### 9.2 检查点

前提：§5.2 的 D1–D7 全部完成（预计 3–4 人天，应在 2026-08 内完成）。

| 时间点 | 期望 | 若达不到 |
|---|---|---|
| **完成 D1–D7 后 1 个月**（约 2026-09） | 至少 1 个非作者 issue **或** 20+ star | 检查是不是渠道选错了或表达方式不对，**换一轮选题与渠道再试一次**，不改产品 |
| **完成 D1–D7 后 3 个月**（约 2026-11） | 50+ star，2+ 非作者 issue，1 篇外部提及 | 分两种情况：**跌破 §9.3 的止损线**（零外部 issue 且 <20 star）→ 触发止损；**在止损线之上但未达期望** → 判定为"有需求但增长慢"，维持分发投入、继续按 §6.2 推进 P1，不加码 |
| **6 个月**（约 2027-02） | 200+ star，第一个外部 PR | 未达成但 3 个月检查点未触发止损时，维持现状继续推进，不加码 |

### 9.3 止损规则

> **如果分发动作全部完成、并且换过一轮渠道与选题之后，3 个月内仍然是零外部 issue 且不足 20 star，判定为"这个形态的需求不足以支撑公开项目"，转入自用模式。**

转入自用模式意味着：停止新特性开发，只做上游协议跟随与缺陷修复；停止传播投入；仓库保持公开（知识资产的价值不因用户数为零而消失）；不再更新本文档。

这不是失败。vmr 在自用价值上早已回本——它每天在解决作者真实的多账号、多厂商、无人值守问题。**明确写下这条规则的意义在于：让"继续投入"变成一个每次都被主动确认的决定，而不是一个默认状态。**

## 10. 退出条件与知识资产

### 10.1 退出条件复核

| 条件 | 是否满足 | 证据 |
|---|---|---|
| 某个现有成熟项目完整覆盖 vmr 的独特能力组合 | 否，**但比三周前接近了** | §3.3 第 6–10 行的五项仍是全表唯一（字节级两层记录、agent 语义分组、可回放、会话亲和、quirk 修复）。但 claude-code-router 已追平 failover / 日志 / 成本三项——**这条应作为下次复核的重点观察项** |
| 作者失去动力 | 否 | 21 天 81 次提交 |
| 范式转移（agent 不再以 LLM API 为核心） | 否 | 无迹象 |
| 需求根本不存在 | **否，且已被证伪** | 赛道 C 的 36k + 45k star 证明需求规模真实。问题从来不是"有没有需求"，是"这些人不知道 vmr 存在" |

**四个条件全部不满足，应当继续。** 但"继续"的具体含义已经变了——见 §9.3 的止损规则。

### 10.2 如果未来退出

若某天条件满足，最自然的路径是把 vmr 作为知识资产保留（仓库公开、设计文档完整），而不是迁移到某个替代品——因为**不存在能替代它的东西**，迁移意味着接受能力损失。届时的选择是"接受用别的工具并放弃这些能力"，而不是"换一个等价物"。

### 10.3 知识资产

这部分的价值独立于用户数，且已经形成：

- 167KB 中文设计文档，覆盖每个决策的理由、取舍表、以及"看着奇怪但故意不改"表
- 231 行遗留问题清单，逐条实测核对，含明确的"为什么现在不做"与触发条件
- 架构不变式的可执行测试化（import 边界、文件行数预算）
- 一套关于"byte-faithful 路由 + agent 语义审计"的完整设计思路，包括所有走过的弯路

代码可以被任何人重写；**定义"为什么这么做"的文档才是不可替代的部分**——任何继承者都需要它才能再次做出正确决策。
