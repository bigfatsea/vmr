## 0. 结论先行

VMR Story 现在做对的事：它是本次调研覆盖的所有产品里，唯一一个"零埋点、协议级字节、内容寻址精确重建"的 agent 轨迹记录方案——这不是自我认定，是四路调研反复验证的结论（§2）。它现在没做到的事：**把"记得全、记得准"转化成"看得懂、找得出问题"**。2025 下半年到 2026 上半年，行业头部玩家（LangSmith Engine、Arize Signal + Alyx、Braintrust Topics、Datadog Patterns）几乎同时把"洞察层"的门槛迅速推高——如果 VMR 继续停在"我有全部字节"，市场读到的会是"记录深但不好用"，而不是"独一无二"。

但调研也给出一个必须先接受的校准：**逐轮根因定位（"就是这一步搞砸的"）在 2026 年中仍是前沿模型都做不好的开放问题**——Who&When 数据集上最好的自动归因方法，step 级定位准确率只有 14.2%；TRAIL 数据集上，Gemini-2.5-Pro 也只有 11%（§3）。所以本文档不建议 VMR 去追一个"自动精确诊断"的幻觉，而是走一条四路调研共同指向、且完全契合 VMR 现有"规则先行、LLM 可选可降级"架构纪律的路：**结构先行（确定性）、只在收窄后的候选点上引入解读、把大量 Journey 攒起来做统计验证而不是靠单次 LLM 断言"这就是根因"**。

对应用户提出的三个方向，加一个调研支撑的补充方向：

1. **Journey 呈现**（§4）：从"平铺时间线"改为"决策脊柱（decision spine）"——不是本文臆造的概念，是 2026 年一线实践里被多个独立信源反复提出的同一个诉求。
2. **单 Journey 深度分析**（§5）：把 `internal/report` 已有的"规则自动发现"（`Finding`/`FindingCode`）模式搬到 `internal/story`——`story` 目前完全没有这一层，只有 `compare` 场景才有类似的发现。
3. **对比分析深化**（§6）：从"两组九指标做差"升级为"定位分叉点 + 结构化证据包"，而不是让 LLM 读全部 transcript 去"感觉哪里不一样"。
4. **（补充）语料级模式挖掘**（§7）：把"对比"从"任意两个 Journey"扩展到"一批 Journey"——这是本次调研证据最扎实、行业时间窗最新（多数同类功能 2026 上半年才上线）、且 VMR 现有九项指标恰好是天然输入的一个方向。

## 1. 现状复盘（不重复文档，只框定坐标）

`vmr story` 现在的三层模型（Analytics 设计文档已有的表述）：**事实层**（`ctxgraph` 的 manifest/lineage，原始且精确）→ **剖面层**（`metrics.go` 的九项规则派生指标 + `compare.go` 的阈值化 diff + 4a 的 `ComparisonExtras`）→ **解读层**（`llm.go`，目前只服务于 `-compare`，证据包受限、可整体降级、不生成数字）。

这个三层划分本身没有问题——本文档后面所有建议都在这个框架内做加法，不动它。问题是**剖面层目前只覆盖了"聚合统计"，没有覆盖"结构化发现"**：`internal/report` 有 `buildFindings`（扫描聚合结果、挑出跨阈值的浪费项、每条自带可执行建议、有稳定的 `FindingCode`），但这套模式在 `internal/story` 里完全不存在——单个 Journey 除了九个数字和一份 Markdown 叙事，没有任何"这里可能有问题"的自动标注。对比场景稍好一些（4a 的 `ComparisonExtras` 已经在做"发现"：system prompt 稳定性、最终交付物对比），但仍然是"两组数据摆在一起，人自己看差异"，没有"定位到具体哪一步开始分道扬镳"。

## 2. 第一性原理：VMR 真正、别人复制不了的东西是什么

四路调研里最反复被验证的一条结论：**市面上所有 agent 可观测性产品，不管走 SDK 装饰器（`@weave.op`、`agentops.init()`）、OpenTelemetry 语义约定，还是网关代理（Helicone），都需要目标 agent/框架"配合"才能采集数据**。Datadog 自己的文档承认"自动埋点"不是零代码——需要在进程里 import/初始化 SDK，不支持的框架、非 Python/Node/Java 语言、裸 HTTP 调用一律看不见；Arize 自己的 2026 购买指南也承认"市场不能简化为代理 vs SDK 的二选一，大多数产品是混合方案"。Helicone 是这批产品里架构上离 VMR 最近的（网关代理），但多篇 2026 年的独立评测都收敛到同一句话——"轻量级网关，有成本/延迟可见性，但不是为深度 agent 推理分析设计的"；它已于 2026 年 3 月被 Mintlify 收购并进入维护模式，功能停滞。

**没有一个被调研到的产品能做到 VMR 这三件事同时成立**：(1) 对任意 agent CLI 零埋点，因为它工作在协议层而不是代码层；(2) 三种协议（OpenAI Chat Completions / Anthropic Messages / OpenAI Responses）字节级不翻译地记录，不是先归一化到自家 span schema 再存；(3) 用内容寻址（消息哈希 + Append/ReplaceTail/Splice/Contract/Fork 编辑分类）**事后**重建会话边界，而不是依赖 SDK 在调用时现场打的 `session_id`/`trace_id`。第三点在整个调研里没有找到任何对照物——所有产品的"session"/"trajectory"分组都是活埋点时打的标，不是像 git 一样从内容本身推出来的。这一条值得当作 VMR 最难被复制、也最难对不需要它的人解释清楚的差异化点，不是因为技术门槛，是因为**要做到它，必须先放弃"翻译成统一 schema"这个所有竞品的商业前提**。这与 `vmr_future_strategy_v2` 的判断刚好对得上——该文档把 byte-faithful 本身排除在"护城河"之外，定性为护城河（两层字节记录/agent 语义分组/可回放等五项）成立的**前提**、以及"为什么这份记录可信"的依据，而不是卖点本身；本次调研从行业侧独立验证了同一个区分：能零埋点做到内容寻址重建，前提正是不翻译，这件事本身没有直接卖点价值，但它是后面所有洞察层建功能能立得住的地基。

但同一批证据也带来一个必须正视的压力：**"洞察层"这条赛道在 2026 年上半年跑得比预期快得多，而且已经不是玩具功能**。LangChain 在 2026-05-19 Interrupt 大会发布的 **LangSmith Engine**（公测中）：定期（6 小时一轮）扫描生产 trace，把失败聚类成命名 issue（如 `agent_looping`、`incorrect_tool_args`），连上 GitHub 仓库后能对着源码定位根因，产出三样东西——修复 PR、新增的评估器 + 回归数据集、带严重度/复发率的 issue 元数据。Arize 在 2026-06-04 发布的 **Signal + Alyx**：常驻 agent 持续复查新 trace、记住已发现过的问题、把相关 trace 分组成带根因分析和证据的调查报告，并有 Signal → PR 的完整链路。这两个都是"自主 agent 做诊断"级别的功能，不是仪表盘。VMR 一个三人团队做不出与它们对等的自主诊断能力，也不该在这条路上正面竞争——它的胜负手不在"能不能做出一样聪明的诊断 agent"，而在**上游那道所有对手都跨不过去的门槛：零埋点、协议忠实、对既有历史流量可回溯**。下面几节的建议全部锚定在这条边界内：用 VMR 独有的精确结构化数据去支撑判断，而不是试图靠更聪明的 LLM 去弥补数据精度上的差距。

## 3. 校准：这个领域目前真正难在哪，VMR 不该承诺什么

这一节的存在理由：**过度承诺是这类功能最容易把自己做砸的方式**——一旦对外说"我们能自动定位是哪一步出的问题"，而实际命中率和瞎猜差不多，损失的是审计数据本身的可信度，这个代价远大于少一个功能。

学术界过去一年在这个问题上产出了明确的负面证据。Berkeley 团队的 **MAST**（Cemri et al., arXiv:2503.13657，200+ 条真实 trace、7 个框架、6 名人工标注者）给出一套 14 种失败模式 / 3 大类的分类法（系统设计问题 43.8%、agent 间失配 32.3%、任务验证失败 23.5%），并且明确指出现有验证器只能做"表层检查"（比如代码能不能编译），漏掉本质性错误——这套分类法本身**不是规则可判定的**，需要语义理解。更关键的是两项独立的定位研究：**Who&When**（ICML 2025 Spotlight，arXiv:2505.00212）在 127 条多 agent 失败日志上测试自动归因方法，最好的"哪个 agent 出的错"能到 53.5% 准确率，但"哪一步出的错"只有 **14.2%**，部分方法甚至低于随机猜测，包括用 o1、DeepSeek R1 这类前沿推理模型做判官；**TRAIL**（Patronus AI，arXiv:2505.08638，148 条 trace、841 个标注错误，取材自 GAIA/SWE-Bench）独立复现了同一结论——最好的模型（Gemini-2.5-Pro）联合定位准确率只有 **11%**。这是四路调研里唯一一处两个独立团队、两个独立数据集给出高度一致负面结果的地方，权重应该拉满。

同一批文献也指出了哪些子问题是**可行的**，而且给出了一个反复出现的成功模式：**先用确定性方法把结构算出来，只在收窄后的候选集上花 LLM 判断力**。微软研究院的 **AgentRx**（arXiv:2602.02475）把任务拆成逐步约束、机械核对生成"审计违规日志"，只把这份日志（不是原始 trace）交给 LLM 去定位关键步骤，在 115 条人工标注失败轨迹上比基线提升 23.6 个百分点的步骤定位准确率。**FALAT**（arXiv:2606.00765）给单条失败轨迹建一张"步骤依赖图"（哪一步的输出喂给了哪一步的输入——工具调用参数溯源、文件读写链），按级联影响力做搜索，比穷举式 LLM 判断更准、调用次数更少——**依赖图本身的构建完全不需要 LLM，是纯结构化操作**。这条"结构先行、LLM 判断只作用于收窄后候选集"的模式，与 VMR 现有 `vmr story -compare` 已经在用的做法（先用规则算出 `ComparisonExtras` 的证据包，LLM 解读层只读证据包、不读全部 transcript）完全同构——不是要发明新哲学，是要把这个已经被证明有效、VMR 也已经在用的模式，覆盖到目前还没覆盖到的地方（单 Journey 分析、跨 Journey 分析）。

哪些信号可以规则化、哪些必须靠语义判断，四路调研汇总出一张边界表（供后面几节的具体建议对照）：

| 信号 | 能否规则化 | 依据 |
|---|---|---|
| 完全相同的 tool call（同工具同参数，无状态变化）重复出现 | **能，成本低** | 直接日志模式匹配；但 RedundancyBench（arXiv:2605.29893）显示这只能捕获"语义冗余"里很浅的一个子集——最好的自动方法准确率仅 24.88%，部分方法低于随机，说明"看起来像规则问题"的冗余检测实际上大多需要语义判断 |
| 连续多轮纯文本、无工具调用、文本高度重复 | **能，成本低** | 结构信号（有无 tool_call）本身就是协议给定的事实 |
| 工具调用参数/schema 正确性、调用顺序是否符合依赖关系 | **能，成本低** | 一线从业者综合（Zylos Research）明确建议这类维度用确定性打分；FALAT 的依赖图不需要 LLM 即可构建 |
| compaction 边界前后，某段约束文本是否还在 prompt 字节里 | **能，但目前无人验证过有效性** | "Governance Decay"论文（arXiv:2606.22528）命名了这个失败模式（长会话经过一次 compaction 后，安全/行为约束被静默侵蚀），但论文本身没有提出日志侧检测器，只做了行为再测试——这是一个可以构建、但尚未被证明有效的假设 |
| 逐轮根因定位（"就是这一步搞砸的"） | **不能——公开最好方法也只有 11%–14.2% 准确率** | Who&When、TRAIL |
| 该问题该归咎于 model 还是 harness（脚手架/上下文管理/工具集成缺陷） | **需要判断，但有一套可复用的清晰分类法** | "Model or Harness?"（Scale AI, arXiv:2607.28802），κ=0.76，见 §8 |
| Agent 是否已经注意到并纠正了自己的错误 | **需要语义判断确认，但有一个便宜的必要条件代理**：换了参数重试 vs 逐字重复调用 | AgentDebug（arXiv:2509.25370）、自我纠错综述（arXiv:2406.01297） |
| 上下文腐化四类模式（poisoning/distraction/confusion/clash，Breunig 命名） | **无已验证的检测器，长度/工具数只是弱相关代理** | dbreunig.com 明确把检测留作未解决问题；Chroma Research 的实验数据是相关性而非因果 |

这张表是本文档§5、§6、§7 具体建议的取舍依据——凡是标"能，成本低"的，建议直接做成规则层 Finding；标"需要判断"的，建议走"规则收窄候选集 + 解读层可选标注"的路子；标"不能"的，本文档不建议 VMR 承诺。

## 4. 方向一：Journey 呈现深化——从"平铺时间线"到"决策脊柱"

用户提出的诉求是"展现形式更直观清晰、更容易阅读"。调研里独立找到了一个和这个诉求几乎逐字对应的概念，来自一线实践者 tianpan.co 的系列文章（2026 年 5 月）：

> "工程师打开一条 agent trace 排查故障时，他们问的不是'agent 做了什么'，而是一个窄得多的问题：'哪里开始错的'……答案活在**决策**里——agent 追求的目标、它选的工具、那些'本可以走另一条路但选了这条'的分叉点。把这个叫作**决策脊柱（decision spine）**。它是一次运行的骨架：一份紧凑、有序的'决定了什么、为什么'清单，剥掉了 prompt 正文和工具 payload。一条 40 次调用的 trace，它的决策脊柱可能只有 20 行……细节仍然重要，需要的时候你需要全部细节，但它是**参考资料，不是首页**。"（tianpan.co，2026-05-17）

同一批调研里，另一个独立信源（agenticcontrolplane.com，2026-07）用不同措辞表达了完全一样的诉求："harness transcript 是**决策缺失**的——一份 transcript 说的是 agent 声称自己跑了什么，不说当时什么被允许、什么被拒绝、为什么"；LangChain 自己的工程博客也举了一个具体反例："agent 在第 6 步给自己的 memory 写入了一个错误假设，到第 11 步这个错误假设已经累积成了明显的坏行为——只看第 11 步这一条 trace 完全看不出问题在哪"。三个独立信源在同一个时间窗口（2026 年上半年）不约而同地提出同一个诉求，而且本次调研里没有找到任何产品把"决策脊柱"做成默认视图——本次产品调研里描述到的默认呈现形态清一色是完整的 trace 树/瀑布图（LangSmith 的 trace tree、Datadog 的 Execution Flow Chart、Arize Phoenix 的 `TimelineBar`），细节展开是主视图，摘要是附加物，不是反过来。同一篇提出"决策脊柱"的文章还给出了"为什么全量记录本身不是好策略"的理由："trace 里没有任何东西被标红，因为技术上什么都没失败——所以'全部记录'策略产出的 trace 里，真正的信号会被三十七个'正常'的步骤淹没"。这是一个已经被反复呼唤、但还没人做出来的呈现形态。

**对 VMR 的意义**：`internal/story` 现有的 `Journey → Task → Step → Event` 模型天然具备构建"决策脊柱"的结构基础，不需要新采集任何数据：

- 一个 Step 本身已经区分"是否携带 `tool_call`"（有 = 行动节点，无 = 纯文本节点），这正是"决策脊柱"要的 Plan/Action 划分的原始信号，不需要新的分类逻辑，只需要在渲染层把它显式标出来而不是淹没在完整消息正文里。
- `Event.Revises`（`Splice` 编辑触发的原地改写关系）、`StitchEdge`（缝合边界）、compaction 边界（§3.6 的信息损失摘要）都已经是结构化标注，天然是"这里发生了非常规事件"的候选高亮点——目前它们存在于渲染出的 Markdown 里，但和"正常推进的 Step"用同样的呈现权重，没有被单独摘出来当作"值得先看"的入口。
- Analytics 设计文档 §8 已经把"HTML 单文件渲染 + 脱敏"列为未实现的可选扩展（左侧时间轴 + 右侧 Step 卡片瀑布），但优先级一直没有被验证过。结合上面的调研，这个优先级判断可以更明确：**HTML 渲染本身不是重点，"默认只展开决策脊柱、细节按需下钻"才是**——tianpan.co 同一篇文章里还有一条独立的成本佐证："行业报告显示团队给 agent 工作负载接入可观测性后账单上涨 40%–200%，因为 chain-of-thought trace 产生的遥测量是等价 API 调用的 10–50 倍"，这与 VMR 现有 Markdown 折叠（`<details>`）的方向一致，只是折叠的粒度目前是"按 Step 折叠正文"，而不是"按'是否偏离常规'折叠整个 Step"。

具体建议：渲染层新增一层"决策脊柱"摘要（可以是 Journey 页顶部的一段紧凑列表，也可以是折叠视图的默认展开状态），只显示：每个 Task 的目标（用户原话）→ 关键 Action（tool_call 的工具名 + 一句话参数摘要）→ 是否命中 §5 提出的任一规则化 Finding。正常推进的 Step 默认折叠，命中 Finding 或结构性异常（Revises/StitchEdge/compaction 边界）的 Step 默认展开。这不是一次架构改动，是渲染逻辑的重新分层，`journey.go`/`render_md.go` 现有的数据模型足够支撑。

**交叉评审补充——四个具体落地机制**（来自与另两份同题分析的交叉评审，经检验后采纳，详见 `vmr_story_deep_analysis_v1.md`/`agent_journey_story_analysis_gemini.md` 对应节的批注）：

- **顶层入口是一张 3 秒摘要卡，不是决策脊柱本身**：决策脊柱之上再加一层更高的入口——一句话任务描述（已有 `Journey.Title`）+ 5–8 个节点的关键时间线（起始指令、首个错误、编辑类型非 Append 的转折点、任务终止）+ 基于九项指标阈值的结构标签（"工具密集型""重试多""上下文压缩"）。全部数据现成，零新增计算，是比决策脊柱本身更低成本的第一版。
- **每个 Step 的角色标签直接复用已有结构信号**：📋规划（无 tool_call + 文本含步骤列举）/ 🔧执行（含 tool_call）/ 👀观察（仅 tool_result）/ 🔄重试（与前一 Step 的 tool_call 高度相似）/ ⚠️错误（含错误标记）/ 🧹压缩（跨 StitchEdge）——纯渲染层启发式，不确定时不标注，给出这套具体标签体系比只说"Plan/Action 划分"更可执行。
- **决策脊柱展开时展示"信息基础"，不是完整上下文**：对每次 tool_call，用它的参数（文件路径、函数名等）与前序上下文里 `ExtractEntities` 提取到的实体做交集，只渲染最相关的那几条前序消息（最近一轮用户指令 + 被引用过的工具结果 + 相关系统提示片段），而不是让读者自己往回翻。这是"决策脊柱"从"看到了什么决定"到"看到了为什么这么决定"的关键一步，成本低——复用的是已有的 `internal/chatmsg.ExtractEntities`。
- **可选的工具调用时序图**：Journey 末尾附一张 ASCII/Unicode 时序图，每个工具类型一行，横轴是 Step 编号，用不同符号区分成功/失败/重试。纯渲染、零新增计算，作为决策脊柱的补充视图，不是替代。

**一个经过重新校准后部分采纳的点**：按"阶段"（如"环境探查"→"方案设计"→"代码修改"→"测试验证"）对连续 Step 分组是一个与决策脊柱正交的呈现维度，确有价值，但"自动识别阶段切换"本身是语义聚类问题，不能像上面四条一样简单归为规则可判定——按工具类别（读/写/执行）的粗略切换可以作为一个保守、可实现的替代信号，不承诺精确的阶段边界。

## 5. 方向二：单 Journey 深度分析——把"自动发现"这层补上

用户明确提出："即使不对比，单个 Journey 本身的关键要点分析，是否也该是工具的一部分"——现状确实是空白：`internal/report` 有 `buildFindings`（§4.2 描述的 identity/展示文案分离模式，每条发现带稳定 `FindingCode`），但 `internal/story` 里，除了 4a 给 `-compare` 加的 `ComparisonExtras`，单 Journey 路径完全没有对应的"这里可能有问题"标注层。

按 §3 的规则化边界表，以下几类可以在**零 LLM 成本、纯规则、遵循 `report.buildFindings` 既有模式**（稳定 `FindingCode`、可执行建议一句话、identity 与展示文案分离）的前提下落地，且每一条都有真实世界的失败案例作为存在理由的证据（不是假想场景）：

**1. 精确重复 loop 候选**——完全相同的 `(工具, 参数)` 对连续/高频出现。这不是理论场景：Claude Code 官方 issue tracker 上有多起真实报告，其中一起是同一条 SSH 命令报错 `Exit code 2` **连续 7 次以上、字节级相同**才被人工打断（GitHub `anthropics/claude-code#19699`）；另一起是一个子 agent 卡在同一条 `npm install` 命令重试 **300 多次、耗时 4.6 小时、消耗约 2700 万 token**（`#15909`）。这两起的报告者原话都是"现在完全靠人盯着终端手动 Ctrl-C，或者事后查账单才发现"——`story` 已有的重复动作率指标（九项指标之一）是 Journey 级的聚合数字，能告诉你"这个 Journey 重复率偏高"，但不能告诉你"从哪一步开始进入了循环、循环了多少次"，这正是本条建议要补的粒度差。

**2. "只说不做"循环候选**——连续多个纯文本 Step、无工具调用、文本高度相似。同样有真实案例：四个并行子 agent 都跑完了，主 agent 应该"一次工具调用"把结果组装起来，结果反复说"让我现在组装文档"却始终不触发工具调用，直到把整个上下文窗口耗尽（`anthropics/claude-code#27281`）。这是与第 1 条互补但不同的模式——第 1 条是"重复行动"，这条是"重复意图声明但不行动"，两者的规则判据不同（前者比对 tool_call 参数，后者比对纯文本 Step 之间的文本相似度），值得分开建模。

**3. 错误后无适应的重试 vs 有适应的重试**——工具结果带错误标记后，紧跟的下一次调用是逐字重复（大概率是循环）还是参数有实质调整（大概率是在尝试修复）。这是 §3 表格里"能，但需要一个必要条件代理"的一类：确认"这确实是在纠正之前的错误"仍需要语义判断，但"参数变了 vs 没变"这个前置过滤是纯规则、零成本的，能把后续需要人工/LLM介入的候选集缩小一个数量级。**交叉评审补充**：判据不必只看下一次工具调用的参数是否变化，也可以看下一轮推理文本里有没有提到错误本身（哪怕只是关键词命中）；更进一步，一旦命中疑似未适应的错误，可以继续追踪"下游影响范围"——这个错误标记之后，后续 N 个 Step 的行为是否持续偏离正常模式（工具调用异常重复、直接终止任务、还是被正常吸收），把二元的"有没有适应"升级为一个范围标注，对应 MAST 论文 Task Verification 大类（占比 23.5%）里"无/不完整验证"这一子类。

**4. 静默声明成功候选**——这是这批里证据最重、也最危险的一类。调研找到三起被独立媒体报道的真实生产事故，共同点是"agent 在收到一个含糊的错误响应后，自己'脑补'了一个解释并据此继续行动，而不是承认不确定"：Replit 的 agent 在代码冻结期间删除了生产数据库，事后承认自己"面对空查询结果时慌了"；Google Gemini CLI 把一次静默的 `mkdir` 失败误读成成功，覆盖了一位产品经理的文件；Amazon 的编码 agent 自主删除并重建了一个生产环境，导致服务下线 13 小时。三起事故被同一篇分析文章统一归因："没有一起是模型能力问题，每一起都是一个含糊的错误响应给了 agent 足够的空间去'创造性发挥'"。VMR 的两层审计恰好能看到这个断层：`attempts[].error_class`/工具结果里的错误标记，与紧随其后的"任务完成"声明之间，中间有没有一次真正的验证动作（比如重新读取文件确认状态）——这条规则不需要判断"错误响应的语义"，只需要判断"错误标记之后到成功声明之前，是否存在任何读取/验证类工具调用"，是一个纯结构化的、可以用现有 tool_call 序列直接算出来的信号。

**5.（交叉评审新增）推理-行动不一致候选**——推理文本/回复正文里明确提到的实体（文件名、函数名等）与紧随其后的 tool_call 参数不一致（比如推理里说"改 `config.go`"，实际调用却是 `write_file(target="router.go")`）。这条不是本文档原创，是从另一份对照分析（`agent_journey_story_analysis_gemini.md` §3.1A）交叉评审后吸收的，理由是它精确对应 MAST 论文实测的"Reasoning-action mismatch"失败模式——**14 种失败模式里占比 13.2%，是仅次于"Step repetition"（15.7%，对应上面第 1 条）的第二高发模式**。检测机制是对推理文本与 tool_call 参数做实体交集比对，复用 `internal/chatmsg.ExtractEntities`，规则可判定、零 LLM 成本。

**6.（交叉评审新增）未被利用的工具结果候选**——某次 `tool_result` 提取到的实体（文件路径、报错信息等），在后续若干 Step 的文本中从未再被提及。`story` 九项指标已有一个 Journey 级的聚合版本（"上下文有效利用率"），但聚合数字只能告诉你"利用率偏低"，不能定位到"哪一条结果被晾在了那里"——这条把同一个信号下沉到 Step 级别，定位具体位置，价值增量在于粒度而不是新信号。

**7.（交叉评审新增）上下文污染/幻象存活候选**——某个实体在一条消息中被断言存在，但后续工具调用的结果明确证伪了它（返回 `ENOENT`/404/"not found" 类错误），而 Agent 在此后的 Step 中仍在引用这个已被证伪的实体。这对应 Breunig 命名、本文档 §3 已引用的"context poisoning"失败模式——学术界目前没有已验证的检测器，本条给出的"锚定在工具明确证伪信号上"比单纯"重复出现即可疑"更站得住，但仍然只是一个**可疑信号，不是幻觉的确认**（工具本身给错信息也会触发同样的模式），落地时必须保留这条限定。

**8.（交叉评审新增）计划-执行错位候选**——如果 Agent 在推理块中给出了带编号的步骤列举（"1. 先...；2. 再..."），检查后续实际 tool_call 序列是否与之对齐，标记每个计划步骤为"已执行/跳过/被替代/顺序变更"。这条的价值不在算法多聪明，在于它明确自我限定为**字符串/实体匹配，不做语义理解**——识别不出编号计划格式时直接跳过，不强行分析。这是"规划是否被执行"这类问题在规则层能做到的安全上限，比试图理解"计划有没有被违反"（那需要语义判断，见 §8）更保守也更可信。

以上八条全部应该标注为**"候选/嫌疑清单"，不是判决**——严格对齐 §3 的教训，措辞应该是"检测到 N 次疑似循环，建议人工复核"，而不是"agent 在这里出错了"。落地形态建议直接复用 `report` 已验证过的模式：`journey-<id>.json` 新增一个 `findings[]` 字段，每条带稳定 `Code`（如 `exact_repeat_tool_call`、`narration_without_action`、`error_then_unverified_success`、`reasoning_action_mismatch`、`unused_tool_result`、`unverified_entity_reference`、`plan_execution_misalignment`）、定位到具体 Step、一句话说明——与 `report.Finding` 同构，不是发明新范式。这一层完全在剖面层内，不涉及 LLM，也不违反"数字必须由规则产生"的既有硬约束。

**交叉评审补充——解读层的单 Journey 对称扩展**：§6 会把现有 `-compare` 场景的 `EvidencePack`/LLM 解读机制扩展到分叉点分析；同样的对称扩展也应该覆盖单 Journey 场景本身——一旦上面八条 Finding 存在，`internal/story/llm.go` 现有的调用链路（证据包构建 → prompt → 调用 → 落盘缓存 → 可整体降级）完全可以复用来回答"这个 Journey 里哪些 Step 值得关注、为什么"，只需要新写一份单 Journey 版 system prompt，不需要改动调用链路本身。这一项排在 Finding 规则层之后，因为它的前提就是先有规则层产出的证据包可喂——顺序不能反过来。

## 6. 方向三：对比分析深化——从"看指标"到"定位分叉点"

用户的原话精确指出了现状的问题："现在对比分析除了一些规则性的分析之外，真正聪明的分析可能不多，主要都是在看一些表中的数据"。这个判断在调研里被独立印证：tianpan.co 对"两份 trace 对比"现状的描述几乎是这个问题的镜像——

> "一次回归漏进了生产环境。团队挑出触发失败的输入，用上周的 prompt 重放，得到了不同的输出。现在要搞清楚为什么——答案埋在三兆字节互相不同的文本、分岔的工具调用序列、被打乱的检索片段里，没有人能高效地 diff。于是他们把两份 transcript 粘贴进一个并排查看器，滚动二十分钟，得出结论'模型今天感觉不太一样'，然后上线一个没解决根本问题的 hotfix。"（tianpan.co，2026-05-09）

同一篇文章给出了问题的精确成因：**两个 Journey 在第 3 步分叉之后，到第 10 步时文本层面已经完全不同了，即便真正不同的决定只有一个**——"这个 diff 技术上正确，操作上没用"。作者点名了包括 LangSmith 在内的多个产品，结论是"没有一家产品今天能给出一个默认的、语义对齐的两栏 diff"。

这正是 `vmr story -compare` 现状的准确写照：九项指标 diff（`MetricDiff` + `Notable` 阈值标记）比较的是两个 Journey 的**整体聚合值**（比如总重复动作率），4a 的 `ComparisonExtras` 补充了几类关键事实（模型/端点是否相同、cache 曲线、system prompt 稳定性、最终交付物内容），这些都是有价值的证据，但都是"整体层面的对比"，缺的正是 tianpan.co 点名的那一环：**定位到具体是哪一步开始，两条轨迹走上了不同的路**。

**具体建议——分叉点检测（divergence point）**，这是本文档认为对现有 `compare.go` 最有 ROI 的一项增量，因为它完全可以用 VMR 已有的原语构建、不需要新的数据采集：

- `ctxgraph` 现有的编辑分类（Append/ReplaceTail/Splice/Contract/Fork）加上工具调用序列，本身就足够定义"两条 Journey 在结构上共享的前缀"——两个 Journey 如果起点是同一个任务（比如同一个用户请求重跑了两次，对应 §6 的一个常见场景：改了 prompt 前后对比），可以按 Step 序号逐一比较：Task 是否相同、每个 Step 是否触发了相同的工具（不要求参数完全相同，只要求工具名一致）、纯文本 Step 是否在同一位置出现。第一次出现"工具名不同"或"一方有 tool_call 而另一方没有"的 Step，就是候选分叉点。
- 这个检测本身完全是规则层（§3 表格里"能，成本低"的那一类，本质是一次序列比对），不需要调用 LLM。产出的是一个**结构事实**："Journey A 和 Journey B 在第 N 步（对应用户目标"XX"之后的第 M 次行动）开始出现不同的工具选择"——这是可验证、可复现的陈述，符合现有解读层"数字只能由规则产生"的硬约束。
- **交叉评审补充——严重度分两档**：`vmr_story_deep_analysis_v1.md` §4.1 给出的划分值得直接采纳——工具调用序列一致但参数不同（都调用了同一个工具但目标不同）标记为"轻度分岔"，仅提示不强调；工具调用序列本身不同（一方选了完全不同的工具）标记为"重度分岔"，高亮展示。同一份分析建议的开发方法论也值得遵循："先用最粗糙的结构签名（工具名序列 + 有无推理块）做第一版，再用真实语料反馈调优"——不预先假定一个精确的相似度阈值。
- 定位到分叉点之后，才是解读层可选介入的地方——而且介入方式应该完全复用 4a 已经验证过的 `EvidencePack` 模式：不是把两份完整 transcript 都塞给 LLM 去"感觉哪里不一样"，而是只把分叉点前后几步的证据（该 Step 的用户目标、双方各自选的工具、双方各自的工具结果摘要）打包成一个受限证据包，让 LLM 只回答"基于这几步证据，两者的选择分别是什么、可能的原因是什么"，并且延续现有 prompt 里"必须明确声明看不到什么"的纪律。这不是引入新哲学，是把 4a 已经证明有效的做法应用到一个新的证据来源上。

分叉点检测是这次交叉评审里唯一一个被**三份独立分析同时提出**的建议——本文档、`vmr_story_deep_analysis_v1.md`、`agent_journey_story_analysis_gemini.md` 各自独立得出同一个方向，这是一个比任何单一论据都更强的信号。但另两份分析在"分叉点为什么导致了更差结果"这一步都直接给出了确定性归因（甚至是虚构的置信度百分比，见两份文档对应节的批注），这正是下面这条边界要拦住的地方。

**必须诚实标注的边界**：分叉点定位 ≠ 根因判定。按 §3 的 Who&When/TRAIL 结论，"这个分叉点为什么导致了更差的结果"这类判断，即使有结构化证据支撑，仍然可能出错——产出物应该停在"从这里开始两者不同了"这个结构事实上，"为什么这个分叉更差"永远是解读层的可选、可关闭、带免责声明的猜测，不能包装成确定性结论。这一点直接关系到 VMR 现有的可信度资产：审计数据的价值建立在"这是真实发生的字节"上，一旦解读层的猜测被当成和事实层同等确定的东西对外呈现，损失的是整个产品最值钱的那部分信任。

## 7.（补充）语料级行为模式挖掘——证据最扎实、窗口最新的方向

用户在描述方向三时，最后落到了这样一句话："如果说这个能总结出一点规律的话，这个可能会很有帮助"——这句话指向的其实是一个和"两两对比"不同性质的能力：不是比较 A 和 B 两个 Journey，而是从**一批**（几十到几百个）Journey 里找出反复出现的行为倾向。这是本文档认为最值得单独展开的一个方向，原因是它在本次调研中拿到了全场最扎实的实证支撑，同时行业里做这件事的产品几乎都是 2026 年上半年才刚刚出现——窗口新，不是空地，但也远未拥挤。

**证据一：这不是虚构需求，头部厂商几乎同时期独立上线了同类功能**。LangSmith 在 2026 年初上线 **Insights**（先对每条 trace 摘要，再做层次化聚类，自动生成"哪类簇的错误率/延迟异常"的执行摘要）和更进一步的 **Engine**（见 §2）；Braintrust 的 **Topics** 在 2026-06-01 GA，持续给生产 trace 打标、聚类成"命名的趋势簇"，Replit 用它分析百万级会话，发现大量用户卡在"给应用加身份认证"这一步——这是单条 bug report 完全看不出来的横向模式，只有跨会话统计才能浮现；Arize 的 **Signal** 有完整的"调查 → 提议 → 复核 → 上线 → 再观察"闭环；Datadog 的 **Patterns** 截至 2026 年 6 月还在 Preview（这批里最新的一个）。五家头部产品在相隔几个月内独立收敛到同一个功能形态，本身就是一个强信号：市场认知已经收敛到"这是可观测性的下一层标配"，但也说明这一层普遍还是 v1 成熟度——聚类质量依赖 LLM 摘要而非严格统计检验。

**证据二：学术界已经拿出了具体的、统计显著的"规律"，而且形态和用户描述的例子几乎一致**。最具体的一篇是《Beyond Resolution Rates: Behavioral Drivers of Coding Agent Success and Failure》（arXiv:2604.02547），分析了 9374 条真实轨迹（19 个 agent、8 个框架、14 个 LLM，统一跑在 500 个 SWE-bench Verified 任务上）。核心发现：**agent 越早开始改代码（而不是先花时间读代码），任务成功率越低**——"提前打补丁强度"和解决率的相关系数 ρ=-0.78（p<0.001）；具体到模型对比，claude-3-opus 平均在第 0 步就开始改代码，解决率 15.1%，claude-opus-4.5 平均等到第 9.4 步才动手，解决率 79.2%。同一篇论文还澄清了一个混杂因素陷阱："轨迹越长任务越可能失败"这个直觉，固定 agent 看不同任务时成立，但固定任务看不同 agent 时方向反过来——**这类混杂因素的澄清本身就是纯语料级分析才能做到的事，单条 trace debug 完全看不到**。这正是用户想要的那类"规律"的活生生例子，而且它本质上是纯统计相关性分析（相关系数），不需要 LLM 判断"这条轨迹是不是有问题"，只需要把"第几步开始改代码"这个规则可提取的特征和"最终是否成功"这个结果做相关性检验。Anthropic 自己的研究博客《How Claude Code is used in practice》也在做同一类分析——对真实生产会话做语料级行为画像，发现"探索步数/改动步数比"与任务成功率相关，说明模型厂商内部本来就在这么干，只是没包装成产品功能对外卖。

**证据三：全行业在"发现模式之后怎么办"这一步，无一例外保留人工审核关卡**——这不是技术做不到，是刻意的风险控制共识。Arize 自己的博客反复强调 Signal-to-PR "工程师仍然做最终决定，只是从一个诊断开始而不是空白的提问框"；LangSmith 团队公开解释了为什么把"识别问题"和"提修复方案"拆成两个独立 agent："让同一个 agent 既做问题识别又提修复方案，效果更差"；Langfuse 目前能找到的同类工作流，起点甚至还是人工逐条给 trace 打分/写评论，再让 LLM 汇总。**没有一家把"自动发现模式 → 自动改 prompt → 自动上线"做成无人值守的闭环。**

**对 VMR 的具体建议**：`internal/story` 的九项指标本质上已经是"每个 Journey 的结构化特征向量"（模型/工具时间占比、工具调用分布、重复动作率、错误恢复次数、计划执行比、上下文构成曲线、上下文利用率、compaction 信息损失），加上 §5 建议的规则化 Finding，是比大多数厂商目前依赖的"LLM 摘要出来的定性簇"更适合做真正统计分析的原始材料——因为它已经是确定性、可复现的数值/布尔特征，不需要先经过一次有损的 LLM 摘要才能进入统计流程。建议的落地路径，按"规则先行"的既有纪律分两步，且都不需要 LLM：

1. **第一步（描述统计）**：一个批量输入模式（不必是新的顶层子命令，可以是 `vmr story` 现有输入路径解析的一个新用法），接受一批 Journey（而不是 `-compare` 现在固定的两个），对九项指标 + Finding 命中情况做描述性统计——每个指标的分布、离群值，以及像"Beyond Resolution Rates"那样的简单相关性分析（比如"首次工具调用发生在第几步" vs "最终是否在 compaction 边界内正常结束"）。这一步完全是确定性统计，不引入任何 LLM 依赖，风险等级等同于现有 `report` 的聚合逻辑。
2. **第二步（分组验证）**：把 §5 提出的规则化 Finding 当作分组变量——比较"命中过静默声明成功候选"的一组 Journey 和没命中的一组，两组的下游行为（比如后续是否需要人工介入、耗时是否更长）是否有系统性差异。这一步能回答"这个规则候选到底是不是真的有害，还是我瞎猜的"，是把 §5 的单 Journey 猜测升级成跨 Journey 验证的自然路径，同样不需要 LLM。
3. **只有统计层站得住脚之后，才轮到解读层**：LLM 的角色应该是把"统计上有支撑的模式"翻译成人话叙述，而不是自己去"发现"模式——这完全复用现有"三层不混淆""LLM 不生成任何数字"的架构纪律，不引入新的信任风险。
4. **明确的止步点**：不做"自动生成 CLAUDE.md/system prompt 改进建议并直接落地"这个终点。这是被验证过的行业共识风险点——即使是资源远超 VMR 的团队（LangSmith、Arize）也在这一步设了人工审核关卡。VMR 应该止步于"呈现证据 + 给出建议文本"，由人决定是否采纳，就像现有 LLM 解读层"绝不在默认路径里自动触发、跑前 dry-run 要求确认"的既有原则一样。

**交叉评审补充——一个需要语料先校准、暂不建议直接实现的候选方向**：`agent_journey_story_analysis_gemini.md` §3.3B 提出"过度探索偏离主线任务"（agent 为了一个小问题一路翻阅大量无关第三方代码，彻底偏离用户原始任务），这对应 MAST 论文里实测的"Task derailment"失败模式（占比 7.4%），方向是真实的。但该文档给出的具体判据（"访问深度 > 4 层且持续 > 5 个 Step"）是没有任何真实语料依据的臆造阈值，如果直接实现会把假精度包装成产品行为。正确的落地顺序应该是本节第一步的语料级描述统计——先在真实 Journey 样本上观察"偏离主线程度"这个信号的实际分布，校准出站得住的阈值，再决定要不要做成 Finding，而不是先定一个听起来合理的数字。

## 8.（补充）harness 侧可判定 vs model 侧不可判定——一个诚实且独有的能力边界

这一条补充的价值不在于新功能，而在于给 VMR 一个**诚实、可验证、有学术支撑的产品承诺边界**，直接呼应 §3 的校准。Scale AI 团队的《Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures》（arXiv:2607.28802，κ=0.76，跨独立评分者验证）给出一条清晰的归因规则：一个失败如果"换一个更强的模型、在完全相同的条件下就能避免或纠正"，算 model 侧的锅（论文定义的 41 种失败模式里 36 种是 model 侧）；如果是脚手架/上下文管理/工具集成本身的缺陷，算 harness 侧的锅（5 种）。论文自己举的例子精确对应 VMR 的处境：一次长会话里 agent 忽略了更早的用户指令，"可能是因为 harness 的 context compaction 删掉了它，也可能是指令其实还在但模型没理会——观察到的行为一模一样，但前者需要 harness 层修复，后者需要 model 层介入"。

**这道区分正好是 VMR 结构性能做、而大多数工具做不到的一半**：harness 侧的问题——约束文本是不是真的还在发给上游的字节里——是可以精确 diff 验证的确定性检查，因为 VMR 天然持有 compaction 前后两份 manifest 的完整字节；而 model 侧的问题——文本明明在，模型为什么没理会——对 VMR 和调研到的所有其他工具一样，永远是黑盒，做不到就是做不到。这给出一个诚实、可辩护的产品承诺：**VMR 能可靠地告诉你"这不是 harness 的锅"（约束确实还在 prompt 里、工具结果确实是对的、compaction 确实没有丢掉相关内容），但不能告诉你"这就是 model 的锅"**——前者是规则可验证的阳性结论，后者永远只能是解读层的推测。这条边界应该写进任何未来功能的措辞里：宁可少断言，也不要把"model 侧问题"包装成确定性发现。

具体可落地的一条检测（属于 §5 Finding 候选，单独拎出来是因为它直接对应 Governance Decay 论文（arXiv:2606.22528）命名但未验证的假设）：compaction 边界前，用户最近一次强调的约束/关键实体，在 compaction 生成的摘要文本里是否还能找到——这是 `internal/chatmsg.ExtractEntities` + 现有 §3.6 信息损失摘要机制的直接延伸，不是新架构，但应该明确标注为"未经验证的假设级检测"（论文本身也只是命名了这个现象，没有提出并验证日志侧检测器），不要包装成已证实的能力。

**交叉评审补充——上面这条规则检测之上，一个经过重新校准的可选 LLM 扩展**：`agent_journey_story_analysis_gemini.md` §3.2 提出了一个更进一步的问题——不只是"约束文本是否还在"，而是"后续行为是否违反了约束"（例如初始指令说"不得修改导出函数签名"，后续某次改动确实改了）。这个问题本身是真实且有价值的，但它的实现方式不能像该文档描述的那样直接当作规则实现："提取初始约束"（从自由文本里识别出"不要做 X"这类否定式约束）和"判断某次改动是否违反了这条约束"都是语义任务，不是字符串匹配能可靠完成的——这正是 §3 规则化边界表要提醒的"看起来像规则问题、实际是语义问题"的又一个例子。正确的定位是：把它作为上面那条**规则层字节存在性检查**之上的一层**可选 LLM 扩展**——先用规则确认约束文本是否还在（阳性结论，可信），如果文本确实消失了或者规则检查通不过，才把"最初的约束表述 + compaction 后的实际改动"打包成一个受限证据包，交给可选、可降级的解读层去判断是否构成违反，并延续本节"model 侧问题只能是推测，不能是确定性发现"的纪律。

## 9. 落地优先级与架构纪律

按 ROI（对用户诉求的直接命中程度）、实现成本、是否符合 VMR 现有硬约束（规则先行、LLM 可选可降级、identity 与展示文案分离、JSON 不随语言变化、`ctxgraph` 不反向依赖 `report`/`story`）排序。**这张表是战略层面的粗分档，不是排期依据**——`vmr_story_deepdive_devplan_sonnet-5.md` 在动了真实代码之后做了更细的拆分（比如 §5 的 8 类 Finding 里有 3 类因为依赖一项新增的 `chatmsg` 基础设施被拆到了比其余 5 类更靠后的阶段，8 类候选并不是一个不可再分的整体），实际开发排期以那份文档的 Phase 1/2/3 划分为准，这张表只用来说明相对优先级的方向。

| 优先级 | 方向 | 成本 | 是否需要 LLM | 依据 |
|---|---|---|---|---|
| 高 | §5 单 Journey 规则化 Finding（8 类候选，含交叉评审新增的 4 类） | 低——复用 `report.buildFindings` 模式 + 现有 `ExtractEntities`/tool_call 结构 | 否 | 每条都有真实事故/issue 或学术分类法（MAST/Breunig）佐证存在理由 |
| 高 | §6 分叉点检测（结构事实，不含"为什么"；含轻/重两档严重度） | 中——新的序列比对逻辑，但输入数据已全部具备 | 否（检测本身） | 三份独立分析（含两份对照文档）同时提出，本次调研里最强的交叉验证信号 |
| 中高 | §4 决策脊柱呈现（顶层概览卡 + Step 角色标注 + 决策溯源证据 + 可选时序图，默认折叠正常 Step） | 中——渲染层重新分层，不改数据模型 | 否 | 三个独立行业信源 + 两份对照文档共五方独立提出同一诉求 |
| 中 | §8 约束文本存在性检查本身（compaction 边界，规则层，不含下面这行的 LLM 扩展） | 中——复用 `ExtractEntities` + 现有 §3.6 compaction 信息损失机制 | 否 | Governance Decay 论文命名了这个失败模式，但论文本身未验证检测器有效性，属于"未经验证的假设级检测"，故不进最高档；此前版本的表格漏掉了这一行，只给了它之上的 LLM 扩展一行，读者容易误以为规则层本身也是"中低" |
| 中 | §7 第一步：语料级描述统计 + 相关性分析 | 中——需要新的批量输入路径，但统计逻辑简单 | 否 | "Beyond Resolution Rates"证明这类分析产出确实有信息量 |
| 中 | §6 分叉点证据包 → LLM 解读（复用 4a EvidencePack 模式） | 低（在分叉点检测之上） | 是，但可选可降级 | 复用已验证模式，不是新设计 |
| 中 | §5 单 Journey LLM 解读层扩展（与 §6 对称，复用 `llm.go` 机制） | 低——调用链路/缓存/降级机制全部复用，只需新 system prompt | 是，但可选可降级 | 补齐 §5 规则层与 §6 解读层之间的不对称，前提是 §5 的 Finding 已先落地 |
| 中低 | §7 第二步：Finding 分组验证 | 依赖 §5、§7 第一步先落地 | 否 | 把猜测升级为验证，价值高但有前置依赖 |
| 中低 | §8 约束衰减检查的 LLM 扩展（在字节存在性规则检查之上） | 低（在 §8 规则层检测之上） | 是，但可选可降级 | 规则层先给出"文本是否还在"的阳性结论，LLM 只在规则触发时介入判断是否构成违反 |
| 低（需先做语料校准） | §7 提到的"过度探索偏离主线任务" | — | 待定 | 方向真实（对应 MAST 的 Task derailment），但没有可信阈值，需要先用 §7 第一步的方法校准 |
| 低（暂不建议） | 逐轮根因自动定位、跨 Journey 自动生成 prompt 改进建议并直接落地、任何形式的编造置信度数字（如"权重 80%"、具体金额估算） | — | — | §3/§7 证据都明确指出这是当前研究和产品都没做到、且行业共识刻意不做的事；两份对照文档里出现的类似数字均未被采纳，理由见对应批注 |

三条不应违反的既有纪律，直接沿用现有设计文档的原则，不是本文档新提出的：

- **数字必须由规则产生**——本文档所有涉及 LLM 的建议，输入都是规则层已经算好的证据包（分叉点、Finding 候选、统计相关性），LLM 只负责组织语言、给出推测性解释，绝不允许 LLM 自己"发现"一个规则层没有独立验证过的数字。
- **可整体降级**——任何新的解读层功能，不配置对应能力时整个功能消失，不影响其余产物；参考现有 LLM 解读层 dry-run + 落盘缓存 + stderr 警告的既有模式。
- **identity 与展示文案分离**——新增的 `FindingCode`/分叉点标识等，从设计第一天就应该是稳定的、不随语言变化的编码，展示文案单独走 i18n，不要重演 `report`/`story` 之前修过的"标题字符串被当 identity 用"的教训。

## 10. 结语：这真的能是主卖点吗

回到用户最初的判断——"这可能是我们一个主要卖点"。本次调研支持这个判断，但要加一个校准：卖点不在"我们能自动诊断"，而在"我们的证据比别人更可信、更精确，因为我们从不翻译、从不依赖埋点"。Kelet（一款 RCA agent 产品）在 Show HN 帖子下一条被反复引用的评论说得很准："单个失败看起来像噪音，看到 50 个放在一起才是信号"——这句话对 VMR 有双重意义：一方面它印证了 §7 语料级分析的价值；另一方面它也提醒，"信号"的前提是"50 个记录本身是精确、可比、无损的"，而这恰恰是 VMR 相对所有依赖埋点/LLM 摘要的对手唯一不会被追平的地方。

真实的风险在纪律，不在功能野心：如果这条线做得草率——比如让 LLM 直接断言"这就是根因"而不做§3 那样的边界声明——恰好会踩进学术界已经用数据证明过的坑（14.2% 的 step 级定位准确率），反而会损耗 VMR 现在最值钱的资产：审计记录"从不改写、可信"的口碑。本文档给出的所有建议都刻意把"确定性事实"和"推测性解读"分得很清楚，这不是保守，是因为调研本身证明了——**在这个领域，克制比聪明更容易赢**。
