## 1. gpt-5.6-terra 报告逐项核实

**总体印象**：三份里信噪比最高的一份。它的 Package 1 是本次核实中**唯一一条我前一轮完全没覆盖、
且经实测确认为真实缺陷**的发现。但它的 Package 2 的量化经不起实测。

### 1.1 Package 1 — 详单产物的缓存键不完整（它定级"高"）

**它的主张**：`EnsureRendered` 在 `os.Stat(target)` 成功后立即返回；文件名只由记录/`req` 派生，
不含 `lang` 或 `evidenceDir`。后果是先以英文生成的详单会被后续中文运行复用；删除 evidence 目录后
已有详单不会重建其链接目标。

**核实 (A) 读码**：`internal/reqdetail/ensure.go:41-65`。主张属实。更值得记下的是**它的 doc comment
在自己的论证中间写下了自己的反证**：

> A pre-existing file with this exact name is guaranteed byte-identical to what Render would produce
> now — the name is a pure function of (rec.TS, rec.Model, RealModel(rec), rec.Outcome, req) and
> **Render is a pure function of (rec, m, prev, prof, lang, linkEvidence)** — so an existence check
> is a correct and sufficient skip condition, not an approximation

同一句话里同时说明了：文件名不含 `lang`/`linkEvidence`，而 `Render` 依赖它们。结论"存在性检查是充分的"
由此不成立。第 50 行 `linkEvidence := evidenceDir != ""` 与第 51-58 行的 evidence 生成**全部位于
"文件不存在"分支内**，所以第二个场景也成立。

**核实 (B) 实测 E1**：

```
# 同一输出目录，先英文后中文渲染同一条 journey
vmrbin2 analyze -lang en -o lang1 -journey j-openclaw-…-8b175da9 <一天日志>
vmrbin2 analyze -lang zh -o lang1 -journey j-openclaw-…-8b175da9 <同一天日志>
```

结果：journey 报告变成中文（"决策脊柱"），但它链接的 22 份详单**全部仍是英文**
（`## ① Client → VMR Request` / `### Messages (3)`）。与全新中文目录生成的同名文件 `diff` → DIFFERENT。
新目录里该文件是 `## ① Client → VMR 请求` / `## ② VMR → 上游（1 次尝试）`。

**核实 (B) 实测 E2**：删掉 `lang2/evidence/`（2 个文件）后重跑同一条 journey → `evidence/` 仍是
**0 个文件**，而 journey 报告头部与 22 份详单各自的 2 条 evidence 链接全部指向不存在的文件。
即 **1 + 44 = 45 条死链接，且任何次数的重跑都不会修复**。

> terra 只写到"已有详情也不会重建其死链接目标"。实测比它说的多一格：**journey 报告自己的系统提示词
> 链接也死了**——因为 `writeJourneyFile` 每次都重写 journey.md（渲染 evidence 链接），但
> `EnsureJourneyDetails` → `EnsureRendered` 全部命中 skip，evidence 永远不会被写。

**根因评估**：terra 写的是"把'记录身份稳定'误当成'渲染表示稳定'"。**这个概括准确，但可以更进一格**：
真正的谓词是 `os.Stat(target) == nil ⇒ 内容正确`。这个谓词沿三个轴不成立——`lang`、`linkEvidence`
模式、以及（低概率的）哈希碰撞。**terra 把第三个轴单独立成了 Package 2，实际上它们是同一个缺陷。**

**建议评估**：terra 建议"将渲染版本（至少语言、evidence link mode、模板版本）写入可检验的
metadata/sidecar，并在不匹配时原子重写；不要把语言塞进坐标或记录身份"。

- "不要把语言塞进文件名/坐标"——**同意，且理由比它给的更硬**：`reqdetail.FileNameForManifest` 的
  全部价值在于"只凭 Manifest 就能算出链接目标、无需 I/O"（脊柱每步的链接、请求索引的 `detail_file`
  字段都依赖这一点）。把 lang 编进文件名会让同一条记录在两种语言下有两个地址，直接破坏 P2 建立的
  "同一条记录一个稳定地址"。
- "sidecar metadata"——**这是过度设计**。每份详单配一个 sidecar 文件意味着产物文件数翻倍，而
  P3.1 刚刚为了消除同构副本删掉了 `details/*.json`。
- **更简单的方案**：详单正文里已经有天然的版本信号。最省的做法是在页面里写一行机器可读的渲染指纹
  （语言 + evidence 模式），`EnsureRendered` 命中 `Stat` 后读该行（几十字节）比对，不匹配就重写。
  这既保留了"名字可算、无需 I/O 即可渲染链接"，又把 skip 谓词从"假设"变成"校验"。
  代价是每次 skip 多一次小 read——相对于它今天可能返回错误内容，这是必要成本。
- **还有一个更省的选项值得并列**：`vmr analyze` 一次运行内 lang 是恒定的，把 lang 纳入
  **输出目录**（而不是文件名）也能消除污染。但它会让同一批详单在两种语言下各存一份，与
  "blob 只存一份"冲突，且脊柱链接的相对路径要跟着变。**不推荐，但应在 ActionPlan 里显式否决，
  以免被当成遗漏重提。**

**判定**：✅ **问题成立（实测复现），根因准确，建议方向对但实现方案可以更省。定级"高"合理。**
这是三份报告贡献的最高价值一条。

### 1.2 Package 2 — 32-bit 截断 MD5 用于内容寻址（它定级"中"）

**它的主张**：`ReqHash8`/`contentHash8`/`toolsHash8` 只用 MD5 前 32 bit 作文件名；命中已存在文件时
不校验内容。以约 11,374 个独立值估算，32-bit 生日碰撞概率约 **1.5%**，语料增长时迅速恶化。

**核实 (A) 读码**：`ctxgraph/reqcoord.go:69-72` 确认 `ReqHash8` = md5 前 4 字节；
`reqdetail/evidence.go` 的 `contentHash8`/`toolsHash8` 同口径。skip-without-verify 属实。

**核实 (B) 实测 E3（全量 11,274 条记录）**：

| 指标 | 值 |
| --- | --- |
| distinct `req` | 11,274 |
| distinct `hash8` | **11,274（0 次碰撞）** |
| distinct 详单文件名 | **11,274（0 次碰撞）** |
| distinct 文件名前缀 `ts_virtual_real_outcome` | 11,264 |
| 被 2 条记录共享的前缀 | **10 个（覆盖 20 条记录）** |

**这组数字推翻了它的量化，分三层说清楚**：

1. **1.5% 这个数字本身没算错，但它算的不是文件名碰撞。** 它是"n 个值里存在至少一对 hash8
   相同"的先验概率（1 − exp(−n²/2·2³²)）。报告取 n ≈ 11,374——那是架构文档 §2.2 在长期累积的
   解析缓存上测得的历史 manifest 数；**当前 34 文件语料的地面真相是 11,274 条**
   （`zstdcat logs/*.zst | wc -l` 与 `vmr report` 的 `meta.records` 一致）。两个 n 给出的先验都是
   约 1.5%，结论不受影响。而实测在真实的 11,274 条上**一次都没发生**——与 1.5% 的先验完全相容
   （98.5% 的情况就是不发生），但这意味着它描述的是一个**尚未发生的风险**，不是一个已存在的缺陷。
   报告把它写成"证据/后果"，量级定位偏了。
2. **hash8 根本不是详单文件名的唯一判据。** 文件名是
   `{ts 到毫秒}_{virtual}_{real}_{outcome}_{hash8}.md`。实测前缀自身就已近乎唯一
   （11,264/11,274），只有 10 个前缀被两条记录共享。真正的文件名碰撞需要
   **hash8 碰撞 ∧ 前缀相同**，条件概率约 `10 × 2⁻³² ≈ 2.3×10⁻⁹`——比它给的 1.5% 低**九个数量级**。
   `FileName` 的 doc comment 写着"hash8 是唯一性的保证，前缀纯属装饰"，这句话在设计意图上成立，
   但用来评估风险时会误导：装饰性前缀事实上在承担绝大部分区分度。
3. **h8 确实是唯一判据的地方是证据层**（`evidence/sysprompt-<h8>.md`、`tools-<h8>.md`）。
   实测 E4（四日抽样 2,939 条）：**60 个 sysprompt + 11 个 tools = 71 项**。在 n=71 时先验碰撞概率
   约 `6×10⁻⁷`；即便长期累积到 n=1000，也只有约 `1.2×10⁻⁴`。

   > 顺带一个对**架构文档**的订正：§7.6c 写"共享条目去重后的基数是个位数到几十（一个客户端一份
   > 系统提示词）"，用来论证"不需要引用计数与 GC"。四天抽样已经是 60 个 sysprompt，**"个位数到
   > 几十"这个量级判断已经被真实数据超过**。结论（不做 GC）仍然成立——71 个文件、512KB 量级不值得
   > 引入生命周期管理——但支撑它的那个数字应当更新为实测值。

**真正该保留的是它的后果判断，不是它的概率**：一旦碰撞发生，`ensureEvidenceFile`/`EnsureRendered`
的 skip-on-exists 会让第二份内容**静默变成第一份内容**——不是报错，是错答案。这与 Package 1 的
失效模式完全相同。

**建议评估**：它建议"新文件名改为 SHA-256 至少 96 bit 截断，或保留短显示名但以全 hash 校验文件内容"。

- 第一个选项（换 SHA-256/96bit）**成本被低估了**：它会让全部既有详单与证据文件名失效（需整目录
  重建），并且要同步改 `FileNameForManifest`/`FileNameForRecord`/`SysPromptEvidenceFileName`/
  `EnsureToolsEvidence` 四处命名口径 + 架构文档 §7.3c 写死的"md5 前 4 字节"惯例。
  为一个实测 `2.3×10⁻⁹` 的详单风险付这个代价，不成比例。
- 第二个选项（**以内容校验替代盲信文件名**）恰好与 Package 1 的正确修法是同一件事。
  **这才是应该采纳的那一半**——修 Package 1 的"校验而非假设"顺带就覆盖了 Package 2 的后果。

**判定**：⚠️ **机制成立、后果判断成立；量化不成立（实测 0 碰撞，且详单风险被高估九个数量级）。
不应作为独立 Package——合并进 Package 1 的"把 skip 谓词从假设改成校验"。**

### 3.2 §6.1 — "`<50KB` 是以简单 2 步任务推算的经验数字" — ❌ 虚构前提

**它的论证链**：`<50KB` 只是"设计期以简单 2 步任务推算的经验数字"→ 所以 22 步/33 次调用的复杂任务

实测同一条 journey 今天是 **107KB**——**同一样本上 2 倍以上的偏差**，不是样本错配。

sonnet-5 用一个虚构的前提（"2 步任务"）把一个真实的估算偏差解释成了"样本不同所以正常"，
并据此给出"设计完全站得住脚"的裁决。**诊断的方向（纪律成立、体积不随对话长度膨胀）是对的，
但为它辩护的那条论证是伪造的。**

> 这条对我前一轮 full review 也有意义：我在 §2.5 把 `<50KB` 判定为"从未成立的估算"并直接作废了它，
> 结论一致，但我当时给的理由（"没把每步都要展示工具参数与结果算进去"）应当补上这个更硬的事实：
> **预测与实测是同一条 journey，偏差 2 倍以上**。

### 3.3 §4.4 — 报告体积区间 "86KB–506KB" — ⚠️ 数据过期

**核实 (B)**：单日 6 条 journey 实测 **107KB / 132KB / 171KB / 192KB / 384KB / 609KB**。
86KB–506KB 是 P6 复盘时的数字，P9 之后上界已抬到 609KB。它沿用了旧数字未复测。

### 3.4 §2.2(1) — "消除了 12GB 级别的冗余写盘放大" — ⚠️ 夸大且遗漏

**核实 (A)**：架构文档 §7.6c 的原始测量是"59 条记录 → `details/` 合计 60MB（`.json` 40MB + `.md` 20MB）……
按比例全语料约 12GB"。删除的是 `.json` 那一份，占 40/60 = **约 2/3**，即约 8GB，不是 12GB。

**核实 (B)**：剩下的 `.md` 路径在默认 `vmr analyze` 上实测全量语料 **3.44GB**（P9 执行记录）。

所以准确表述应是"消除了约 8GB 中的同构副本，剩余 3.4GB 仍在默认路径上写出"。它的表述让读者以为
体积问题已彻底解决。

### 3.5 §2.3(3) — 描述准确但未看出其后果 — ⚠️

它写："每步头部挂载 `→ detail` 链接，并在渲染时通过 `EnsureJourneyDetails` **幂等补齐缺失详单**"。
这句描述完全准确——**而这正是默认 `vmr analyze` 产出 164MB / 3.5GB 的机制**。
报告把它作为"✅ 完全落实"的证据，没有追问"批量渲染 238 条 journey 时这个补齐意味着什么"。

**这与 gemini §4.3 是同一类错误**：把机制描述正确，但没有把机制乘以规模。

## 4. 三份报告的横向评估

### 4.1 同一个盲点

**三份报告没有一份测量过默认 `vmr analyze` 的产物体积。**

- gemini 明确断言"内存峰值完全可控"（§4.3），基于一个虚构的候选数量（2~10 vs 实测 238）；
- sonnet-5 准确描述了 `EnsureJourneyDetails` 的幂等补齐机制（§2.3(3)），但没有乘以规模；
- terra 没有涉及。

而这正是我前一轮 full review 判定为最重的一条。**三份独立报告同时漏掉它，说明这不是偶然疏忽，
而是一个方法论问题**：三份都以"逐文件读代码 + 跑测试套件"为方法，而**产物体积不是任何一个测试
断言的对象**，也不是任何一个函数读起来会显眼的性质——它只在"把机制乘以真实规模"时才出现。

这与 full review §2.1 记录的"三次验收漂移"是同一个机制的第四次显现：**验收/复查的对象是
"代码做了什么"，而不是"跑一遍产出了什么"。**

### 4.2 三种失效模式

| 报告 | 主要失效模式 | 证据 |
| --- | --- | --- |
| gpt-5.6-terra | **过度量化**：把先验概率当成已发生的后果（Package 2 的 1.5%） | 实测 0 碰撞；详单风险被高估 9 个数量级 |
| Gemini 3.7 Flash | **合理化补全**：把"读到函数名"当成"读过实现"，具体格式串/常量/引文按合理形态补出 | 8 条抽查中 3 条虚构、1 条数量级错误 |
| Sonnet 5 | **为结论找前提**：先有"设计站得住脚"的裁决，再补一个能支撑它的前提 | §6.1 的"2 步任务"与文档原文矛盾 |

三者共有一条：**都给出了"100%/完全落实"级别的总评**（terra 稍克制，用的是"总体已正确落地"）。
在一次以找问题为目的的复查里，这个总评本身就是一个应当被怀疑的信号。

### 4.3 值得借鉴的形态

- **sonnet-5 的 §4"决策 + 备选 Option + 选择理由 + ⚠️ 待决策点"**：这是三份里最有价值的产出形态。
  它把"已经定了什么"和"还需要谁来拍板"分开，后者恰恰是 P6.5 那次"未经确认即执行"的教训所指向的
  缺失环节。我前一轮 full review 的 Package 表只有"内容 + 验收"两列，**没有一列标明哪些需要用户拍板**。
- **terra 的"已直接处理"与"整改 Package"分离**、每个 Package 都给"证据/后果/根因/建议"四段式：
  比笼统的问题列表更容易被后续 ActionPlan 直接消费。

该报告 §3 把 `internal/archtest/file_sizes_test.go` 的改动描述为"收紧 `report/detail.go` 行数豁免
预算（1150 → 350）"并判定"正确"。**实际的 diff 还连带删掉了 `internal/config/config.go` 的 750 豁免
条目**，而该条目上方的注释（"If config.go crosses this, split by concern…"）随之悬空，指向了
`detail.go` 这一行。

核实：`internal/config/config.go` **699 行**，默认预算 **700**——它不需要豁免，所以 `archtest` 仍然
全绿，删除没有被任何测试发现。

**判定：保留删除，但要让它成为一个有意识的决定。** 豁免表的语义是"给确实超出默认的文件开口子"；
给一个 699 行的文件挂 750 的豁免，等于预授权 51 行未挣得的增长——**正是同一份报告拿来收紧
`detail.go`（1150 → 350）的那个理由**。既然那个理由成立，它对 config.go 同样成立。

代价必须写清楚而不是留成暗坑：**config.go 现在只剩 1 行余量，下一次增行就会触线**，届时 `archtest`
会要求按职责拆分而不是重新加豁免。已做两件事让它变成响亮的失败而不是意外：
(1) 修好悬空注释，把"该拆不该再加豁免"的意图挂回正确位置；
(2) 在 `KNOWN_ISSUES §1.5`（那条目正是为"贴线文件"存在的）如实登记 699/700 这个当前状态——
在此之前该条目还写着"全仓已无贴线文件"。
