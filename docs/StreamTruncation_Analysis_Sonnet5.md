# VMR 流式响应 truncated 问题分析

分析范围：`logs/vmr-audit-2026-07-09.jsonl` 中的两条 `truncated` 记录 + `internal/router/router.go`、`internal/router/response.go`、`internal/audit/audit.go`、`internal/server/server.go`、`internal/health/health.go` 相关代码路径。**本轮只分析，不改代码。**

---

## 1. 结论先行（TL;DR）

用户的推测**基本成立，但需要精确一步**：不是"LLM 服务商在超时时间内没有返回完整 response"，而是**上游（MiniMax-M3）在流式生成过程中途完全静默（≥120s 无任何字节，包括心跳），VMR 自己的 idle 看门狗把连接打断**。这不是网络层掉线（没有 TCP RST/FIN），更像是 MiniMax 服务端在生成过程中卡死或挂起。

VMR 在这一刻**已经把 HTTP 200 和响应头发给了客户端**（流式响应从第一个字节起就"已提交"），所以：
- VMR 架构上**不可能**对这次请求做 failover（哪怕候选列表里还有 opencode / deepseek / openrouter 三个健康端点）；
- 中断时**没有补发** `data: [DONE]` 或任何收尾帧，客户端拿到的是一个在 SSE 语义上"没说完就断了"的流；
- 该端点的健康度在中断发生前就已经被标记为 `ReportSuccess`（因为成功判定发生在收到响应头那一刻，早于流拷贝阶段），所以**这次卡死完全不会影响后续请求的路由决策**——下一次请求大概率还是优先打给刚刚卡死的 MiniMax。

这三点合在一起，就是"OpenClaw 的 Agent 直接报错"的根本原因：Agent 侧的 SSE/流式客户端读到一个协议上"不完整"的流，只能把它当错误处理，而不是简单的重试逻辑就能兜住的正常情况。

最优先要做的不是调大超时（治标且可能有害），而是**把这次故障变得可见、可路由、可优雅收尾**——详见第 6 节。

## 3. 代码路径追踪：truncated 是怎么产生的

### 3.1 idle 看门狗（`internal/router/router.go:441-499` `copyFlush`）

```go
timer := time.NewTimer(idle)             // idle = Timeouts.StreamIdle，默认 120s
...
case <-timer.C:
    return errors.New("stream idle timeout")
```

`copyFlush` 把上游 body 逐块转发给客户端，每收到一个 chunk 就 `timer.Reset(idle)`。**只要连续 120 秒没有收到任何一个字节（哪怕是 SSE 心跳注释），计时器就会触发**，`copyFlush` 返回 `"stream idle timeout"` 错误。

这不是"总耗时超过 120s"，而是"两次数据到达之间的静默间隔超过 120s"——记录 1 总耗时 129.58s、记录 2 总耗时 151.41s，都明显长于 120s 本身，说明模型**先正常吐了一段内容**（分别约 9.5s 和 31.4s），然后**彻底停止发送任何字节**，直到 120s 静默窗口耗尽。

### 3.2 提交点：为什么不能 failover（`router.go:391-438` `tryOne`）

```go
// Success: report health, then forward. From the first byte written the
// response is committed — no failover past this point.
rt.Health.ReportSuccess(key)
...
w.WriteHeader(resp.StatusCode)   // 200 已经写给客户端
...
copyErr := copyFlush(w, rbody, snap.Cfg.Timeouts.StreamIdle.D())
status := "ok"
if copyErr != nil && r.Context().Err() == nil {
    status = "truncated" // upstream died mid-stream; the response is already committed
    att.Error = "truncated: " + copyErr.Error()
}
```

一旦 `w.WriteHeader(200)` 执行，HTTP 响应就已经"承诺"给客户端了——这是 HTTP 协议本身的限制，不是 VMR 的设计缺陷：**响应头一旦发出，就不能再换一个端点重新来过**。所以 `Serve()` 的 failover 循环（第 216-230 行，会依次尝试 opencode → deepseek → openrouter 三个候选端点）**完全没有机会介入**——`tryOne` 返回 `(true, nil)`，`done=true` 直接结束整个请求。

### 3.3 中断时没有补发收尾帧（`internal/router/response.go`）

`respStream`（负责 SSE 归一化，包括把 `[DONE]` 补齐给没发的上游）只在 `Read()` 收到 `io.EOF` 时才调用 `finish()` → `appendDone()`：

```go
if err == io.EOF {
    s.finish()
    s.done = true
}
```

但 idle 超时走的是另一条路径：`copyFlush` 的计时器在**自己的 goroutine**里触发，跟 `rbody.Read()` 是否返回 `io.EOF`无关；触发后 `copyFlush` 直接返回错误，`tryOne` 里 `defer body.Close()` 才把底层连接关掉、解除内部读 goroutine 的阻塞。`respStream.finish()` **全程没有被调用**。

结果：
- 已经完整到达 `\n\n` 边界的 SSE 事件（也就是日志里那句"写到一半"的内容）已经被转发；
- 还没攒满一个完整事件的尾部字节（`pending`）被静默丢弃，从未发给客户端；
- **没有 `data: [DONE]`，没有任何 `finish_reason`，没有 error 事件** —— 客户端看到的就是连接原样结束。

Go 的 `net/http` 在 handler 函数返回时会自动补上 chunked encoding 的终止块（`0\r\n\r\n`），所以从**纯 TCP/HTTP 分帧层面**这个响应是"语法完整"的；但从 **SSE / OpenAI 流式协议的语义层面**，它是不完整的——没有任何信号告诉客户端"到这里为止，后面还有没有内容、内容有没有生成完"。

### 3.4 outcome 字段为什么仍是 "ok"（`internal/server/server.go:116-126`）

```go
switch {
case rw.status == 0 && r.Context().Err() != nil:
    rec.Outcome = "canceled"
case rw.status < 400:
    rec.Outcome = "ok"          // ← 200 已经写出去了，永远落在这一支
default:
    rec.Outcome = "error"
}
```

`Outcome` 只看**最终写给客户端的 HTTP 状态码**，跟流有没有中途断掉无关。项目自己的设计文档（`docs/VirtualModelRouter_v2_Fable5.md:341`）对此有明确说明，这是**有意为之**的设计：

> "成功尝试后流中断时 `error` 为 `"truncated: <原因>"`，客户端已收到 2xx，outcome 仍为 ok——status 与 error 并存即'当时 200 但中途断了'"

也就是说：要检测这类故障，分析脚本必须去查每条记录的 `attempts[].error` 字段，而不能只看顶层 `outcome`。这个设计本身逻辑自洽（"outcome 描述的是 HTTP 语义上的成功/失败，不是内容完整性"），但代价是：**任何只看 `outcome` 统计成功率的下游工具（包括未来可能写的监控/告警）都会完全看不到这类故障**——这正是本次分析靠 `grep "error":"truncated"` 才挖出来、而不是从 outcome 分布里一眼看出来的原因。

### 3.5 健康度信号盲区（`router.go:395` + `internal/health/health.go`）

```go
rt.Health.ReportSuccess(key)   // 在 copyFlush 之前就已调用
```

`ReportSuccess` 在**流拷贝开始之前**就把该端点标记为健康、清空失败计数和冷却时间。等到 120 秒后 idle 超时真的发生，`ReportFailure` / `ReportNeutral` 都不会被调用——**这次卡死对该端点的健康状态没有任何负反馈**。

后果：下一个请求进来，`Serve()` 里的健康过滤（`rt.Health.Available`）和多维排序（`strategy.Sort`）看到的 MiniMax 仍然是"零失败、无冷却"的状态，大概率**继续把它排在候选列表第一位**（配置文件 `config.yaml` 里 `agent` 模型的 endpoints 顺序确实是 `minimax → opencode → deepseek → openrouter`）。也就是说，**同一个端点可以反复卡死，而路由策略对此完全无感知**。

## 4. 应用场景分析：为什么这里特别容易踩雷

1. **`agent` 模型的请求都是长上下文、多轮工具调用会话**——两条 truncated 记录的消息数分别是 268 和 273，说明是 OpenClaw 这类编码 agent 在长任务链路中反复调用 chat/completions。上下文越长、思考越复杂，MiniMax-M3 这种带推理/thinking 能力的模型触发生成阶段异常卡顿的概率也越高（223 条其它记录里绝大多数都成功打到了同一个端点，卡死是低概率尾部事件，但一旦命中就是硬失败）。
2. **`stream: true`**：流式请求把"响应完整性"这件事从"一次原子的 HTTP 事务"变成了"一段持续几十秒到几分钟的活体连接"，中间任何环节静默都会被放大成用户可感知的故障。非流式请求反而不会有这个问题（`response_header` 超时兜底，要么完整拿到 body，要么在写头之前就失败，天然可以 failover）。
3. **`X-VMR-Attempts` 显示只尝试了 1 次**：候选列表里另外 3 个端点（opencode/deepseek/openrouter）在这两次请求发生的时间点大概率是健康可用的，只是根本没有机会被尝试——这不是"没有备选"，而是"架构上来不及切换"。
4. **发生频率**：225/226 条记录都命中过 MiniMax（几乎是所有请求的首选端点），其中仅 2 条以 truncated 收场，粗略故障率 **≈0.9%**。绝对数字不高，但因为是"硬失败"（agent 直接报错而非优雅降级），对使用体验的伤害远大于故障率本身反映的比例——尤其是发生在一个已经跑了 130~150 秒、消耗了大量上下文 token 的长任务中途，用户重跑一次的代价很高。

## 5. 为什么这会让 OpenClaw 的 Agent 直接报错

Agent 侧的 SSE 客户端（无论是 OpenAI 官方 SDK 还是自实现的 fetch/reader）在解析流式响应时，通常依赖以下几种"这一轮回复结束了"的信号：

- 收到 `data: [DONE]`；
- 收到带 `finish_reason`（`stop` / `tool_calls` / `length` / …）的 delta 块；
- 服务端主动发送 error 事件。

VMR 在 idle 超时打断连接时，**上述三种信号一个都没有发出**，客户端只会看到"连接在没有预警的情况下结束了"。这对一个健壮的流式客户端来说是**唯一合理的解读就是异常**：它无法区分"网络抖了一下"和"服务端认为回复已经完整只是忘了发 [DONE]"，所以最安全、也是大多数实现实际采取的做法就是**抛错**，而不是把已经收到的半句话当成正式回复喂给下游逻辑——尤其考虑到这类 agent 经常在流里携带 `tool_calls.arguments`（分片 JSON），如果真的把一个不完整的工具调用参数当完整的去解析/执行，后果会比"抛错重试"严重得多。

换句话说：**Agent 报错不是 bug，是它在做正确的事**；真正该修的是"VMR 中断连接时没有给出任何可解释的终止信号"，以及"这次中断本可以在更早的候选轮换阶段被规避掉"。

## 6. 潜在解决方案

按"改动范围 / 风险 / 收益"排列：

### 方案 A：调大 `stream_idle` 超时
- 做法：把 120s 改成比如 180s/240s。
- 评价：**不推荐单独使用**。两次故障的静默窗口都是"模型先正常吐字若干秒，然后彻底哑火"，不是"模型一直在慢慢想但还没吐字"。调大超时只是让用户多等更久才等到同样的失败，treat the symptom 而非 root cause；如果 MiniMax 真的会无限期卡死，调大超时甚至会增加"一个请求占着连接池/并发槽位不释放"的资源风险。唯一值得做的情况是：先确认 MiniMax-M3 官方文档/support 反馈其"深度思考"场景下真实存在超过 120s 的合法静默（而非卡死），否则不建议改。

### 方案 B：中断时补发规范的收尾帧
- 做法：`copyFlush` 检测到 idle 超时后，不直接返回错误了事，而是让 `respStream` 补发一个语义完整的收尾——比如构造一个 `finish_reason: "error"`（或自定义如 `"upstream_stall"`）的 delta 块，再补 `data: [DONE]`（openai 协议）或对应的 anthropic 流结束事件。
- 评价：**性价比很高**。改动集中在 `router.go`/`response.go` 内部，不影响其它路径；把"裸断连"变成"协议上合法的、明确标注了错误原因的结束"，很多 SDK 会把这种情况处理得更体面（至少能拿到明确的错误信息而不是一个诡异的连接重置）。但**治标不治本**：Agent 依然会认为这轮回复失败，只是失败得更清楚。需要分别处理 openai/anthropic 两种协议格式，且要注意别把这个"合成的错误帧"误当成模型真实输出持久化进对话历史。

### 方案 C：把 truncation 纳入 outcome 与健康度信号
- 做法：
  1. `rec.Outcome` 增加一档，比如 `"truncated"`（不是简单归为 error，因为 HTTP 语义上确实是 2xx），让监控/统计能直接看到这类故障，不用逐条 grep `attempts[].error`；
  2. `tryOne` 里，`copyFlush` 报错时补一次健康度负反馈（`ReportFailure` 或至少一次短冷却的 `ReportNeutral` 变体），让路由策略在短期内自然把流量导向候选列表里的下一个端点，而不是无脑地一直优先选中刚刚卡死的那个。
- 评价：**性价比最高、风险最小**。纯 VMR 内部改动，不改变对客户端的响应内容，只是让"故障"这件事变得可观测、可路由。缺点是它**不能挽救已经发生的这一次请求**——只能降低"同一个端点连续多次坑到同一批请求"的概率，属于面向未来请求的改进，不是面向当次请求的补救。

### 方案 D：服务端"无感续写"（seamless resume）
- 做法：检测到 idle 超时后，VMR 把已经流出去的部分内容拼回 assistant 消息（`role: assistant, content: <已生成的部分>`），追加一条"继续"的user/system 指令，重新发给候选列表里的下一个端点，把续写结果无缝地继续以 SSE 形式转发给客户端——对 Agent 而言，看起来就是同一条流，只是中间稍微卡顿了一下。
- 评价：**理论上最优雅，工程量和风险也最大**。难点包括：
  - 如果中断发生在一段 `tool_calls.arguments` 的分片 JSON 中间，"续写"在语义上几乎无法安全拼接（不同模型对"续写一个没写完的 JSON 片段"支持程度参差不齐，容易生成脏数据）；
  - 需要在 respStream 层面维护"已发送给客户端的 raw 内容"和"喂给下一个端点的对话历史"两份状态，并处理协议差异（openai/anthropic）；
  - 换端点续写意味着换了一个不同的模型/厂商，续写出来的内容风格可能和前半段不一致；
  - 测试难度显著上升（跨端点、跨 attempt 的状态机）。
- 只有在方案 B/C 上线后仍然频繁出现且用户体验诉求确实是"绝不能让 agent 感知到任何一次故障"时，才值得投入。

### 方案 E：客户端（OpenClaw）侧重试
- 做法：在 OpenClaw 的请求层捕获"流异常终止"错误，整条请求重试（可选：重试时把候选 endpoint 加入黑名单提示，或者干脆换一个虚拟模型）。
- 评价：实现简单，但**成本转嫁到了客户端**——对于 268/273 条消息、跑了 130~150 秀的长上下文请求，整条重放意味着重新消耗一次几乎等量的 token 和时间，用户体验依然差，只是不再"报错"而是"卡更久"。而且这个仓库改不了 OpenClaw 的代码，属于另一个项目的工作范围。

### 方案 F：纯观测性改进（低风险兜底项）
- 做法：不管选不选上面任何方案，至少在 `vmr report` 或类似的分析脚本里把 `attempts[].error` 里 `truncated:` 前缀的记录单独统计出来，做成一个可以长期盯的指标（频率、命中哪个端点、静默窗口长度分布），用来验证方案 A~D 的实际效果，以及及早发现某个 provider 的稳定性正在变差。

## 7. 最优选及理由

**推荐组合：方案 C（outcome + 健康度联动）为第一优先级，方案 B（补发合规收尾帧）为第二优先级，二者可以在同一次改动里一起做；方案 F 作为验收和长期监控手段。方案 A 不单独采用；方案 D 列为观察后续故障频率再决定是否投入的候选项；方案 E 建议同步反馈给 OpenClaw 侧作为独立的健壮性改进，但不应作为 VMR 侧问题的替代方案。**

理由：

1. **方案 C 是唯一能真正降低"再次踩雷"概率的选项**，而且改动被限制在 `router.go`/`health.go`/`audit.go` 内部，不触碰对客户端的响应格式，风险最低、回归测试成本最小。它直接对症下药解决了本分析发现的两个真实缺口：`outcome` 掩盖故障、健康度信号提交过早导致坏端点无法被路由策略规避。项目设计文档已经明确承认 outcome 的当前语义是"有意为之"，所以这不是修 bug，而是在现有设计基础上**补一层可观测性和路由自愈能力**，改动方向和现有架构（被动健康检查、冷却退避）是一致的，不是另起炉灶。
2. **方案 B 能直接改善"Agent 直接报错"这个症状本身**，成本可控，且是对协议正确性的补全（VMR 本来就有 `[DONE]` 补发逻辑，只是漏了这一条异常路径），做起来是对现有 `response.go` 设计的自然延伸，而不是新增一套机制。
3. **方案 A 单独使用是有害的**：它不解决"模型彻底卡死"这个根因，只会让用户在同样会失败的请求上等更久，还可能放大并发资源占用问题。除非先拿到 MiniMax 官方对"深度思考场景合法静默时长"的确认，否则不建议改动这个数字。
4. **方案 D 收益最大但代价也最大**，在没有验证方案 B/C 效果之前投入是过度工程——先用低成本手段把故障发生频率和用户体验降下来，如果监控（方案 F）显示问题依然频繁复现，再评估是否值得做"无感续写"这种复杂度高、边界情况多的方案。这也符合"MVP-first、按需再迭代"的实践取向：不要在验证问题严重程度之前就上最重的方案。
5. **方案 E 治标不治本、且改动不在这个仓库**：适合作为 OpenClaw 自身健壮性的独立改进（任何调用外部流式 API 的客户端都该有这层兜底），但不能替代 VMR 侧本该做的可观测性和路由修复，两者应该并行推进而不是二选一。

## 8. 补充分析：同会话复现证据 + 更优的请求级重试方案

用户在跟进讨论中提出一个关键反证：**同一个 MiniMax-M3 端点，同一时段服务其它 agent / 其它任务都正常，只有这一个 agent 在特定任务上偶发卡死**——如果是端点整体不稳定，failover-降权这类"惩罚端点"的方案是对的；但如果是"这个端点对这一类特定上下文/任务会卡"，那么正确的应对应该是"仅这一次请求换模型重试"，而不是把整个端点的健康分打低。这个判断需要先验证两条 truncated 记录是不是真的和"特定上下文"相关，而不是随机噪声。

### 8.1 逐条消息比对：两次 truncated 是同一个会话在同一个任务点上连续踩雷

对两条记录的 `client.request.body.messages` 数组做逐条哈希比对（而不是只看第 2 节里的摘要字段），发现：

- **前 262 条消息逐字节完全相同**——两条记录来自同一个 Feishu 会话（工作在一个叫 "amberark" 的 logo 设计任务：Python 脚本批量生成 28 种风格的 logo 提示词 + HTML 页面）。
- **记录 1**（11:23:59）：会话推进到"读了一条 2305 字的 tool 结果后，助手需要继续输出"这一步，模型正常吐字约 9.5s 后彻底静音，129.58s 触发 idle 超时。
- 用户在对话里追加了新指令（"两个 prompt 不用分开…每种风格的 logo 构成元素应该不同…重新生成 HTML 页面"），agent 据此**重新执行了同一批工具调用**（记录 2 里出现了跟记录 1 结尾长度完全一致的 610 字 / 2305 字 tool 结果，说明是重跑了同样的操作），一路推进到"检查上轮编辑是否完成"（agent 自己发现上次的 batch 进程已死、诊断出一个 HTML 转义 bug），最后又要求模型"重写 STYLES + 生成器"。
- **记录 2**（11:29:55，约 6 分钟后）：模型再次正常吐字约 31.4s，然后又是彻底静音，151.41s 触发 idle 超时。

也就是说：这不是两次随机的、互不相关的故障，而是**同一个任务、同一个"要求模型一次性产出结构复杂、覆盖 28 种风格各自定制描述的长输出"这个生成节点上，先后两次都在正常输出到一半时卡死**。当天 225 次 MiniMax 调用里 223 次成功，说明端点本身整体是健康的；卡死高度收敛在这一个任务点上，支持"跟特定上下文/任务复杂度相关，而非端点整体不稳定"这个判断。

同时可以进一步排除内容合规：VMR 的 `response.go` 专门检测 MiniMax 的"软拦截"标记（2xx 响应里嵌 `input_sensitive`/`output_sensitive`），两条记录的 `norm` 字段都只有 `model_rewrite`，没有 `soft_block_detected`；内容本身（logo 设计 prompt 优化的中文讨论）也没有任何敏感特征。如果是合规拦截，理应直接报错或触发软拦截标记，而不是流式生成到一半悄无声息地哑火——这与观察到的现象不符。

### 8.2 为什么"调超时"和"调 max_tokens"都不能解决这类问题

- `stream_idle` 超时只影响"多久才发现故障"，不影响"故障会不会发生"——两次卡死都是模型正常吐字若干秒后**彻底停止**，不是"吐字变慢"，调大超时只是让用户等更久才等到同样的失败。
- `max_tokens` 控制的是"最多允许生成多少 token"，跟"生成过程中会不会卡死"没有因果关系——两次卡死都发生在远没有触及输出长度上限的地方（才吐了几十个字）。
- 真正可能有实际效果、但**不属于 VMR 配置项**的方向：触发点是"要求模型一次性产出一段结构复杂、要覆盖 28 种风格各自不同描述的长输出"，这类"长上下文（270+ 条消息）+ 高复杂度单轮结构化长输出"在很多 LLM serving 链路里都是尾延迟/挂起的高发场景（很可能与 MiniMax-M3 的 thinking 推理阶段有关，这是 VMR 看不到、也控制不了的上游内部实现）。把这种"一次性产出 28 份内容"的任务在 agent/prompt 层面拆成分批调用，大概率能降低触发概率——但这是任务设计层面的规避，不是 VMR 能配置出来的东西。

### 8.3 更优方案：把这条 route 改成非流式（`stream: false`），复用已有的 pre-commit failover

第 3.2 节指出的硬限制依然成立：HTTP 流式响应一旦发出状态码和响应头就无法撤回，协议层面没有"作废重来"的原语，所以"客户端完全无感知地换模型续写"在当前框架下做不出干净的方案（方案 D 的"续写"对结构化代码/HTML 输出还有语法断裂风险，不推荐用于这类任务）。

但有一个**不需要改动任何 VMR 代码、可以立即使用、并且天然满足"仅这一次任务级重试、不伤害端点整体健康度"这个诉求**的方案：

把这条 route（或者至少这一类"长输出、结构复杂"的任务）的请求改成 `"stream": false`。

原理：非流式请求下，MiniMax 必须先把**完整响应算出来**才能给 VMR 返回 HTTP 头（非流式响应是一个整体 JSON body，没有分片发送的理由——这也是 `response.go` 里"非 SSE 响应＝客户端反正要等完整 body"这条注释本身的假设）。如果模型在生成过程中卡死，VMR 等到的不是"流中途断掉"，而是 **`response_header` 超时**（`internal/config/config.go` 默认 `DefaultHeaderTimeout = 120s`，可调）——这时响应**还没有提交给客户端**（`w.WriteHeader` 还没执行到），`router.go` `Serve()` 里现成的 failover 循环会按候选顺序（minimax → opencode → deepseek → openrouter）**自动尝试下一个端点**，这条路径已经在代码里跑通，只是流式请求走不到这里。

对"会不会连累端点整体降权"这个顾虑：这类超时归为 `core.ErrTransient`（`internal/health/health.go`），冷却时间起步只有 **2 秒**（`transientBase`），指数退避、连续失败才会涨到分钟级（上限 5 分钟）——跟"因为一次任务失败就把端点长期打入冷宫"是完全不同量级的事情，本质上就是"这次跳过，几秒后照样可用"，不会实质性影响同一时段内其它任务对该端点的正常路由。这跟"仅针对这一次任务换模型重试，不影响端点整体信誉"的诉求已经高度吻合。

代价：这条 route 会失去逐 token 的流式体验，agent 要等完整响应一次性到达。对自动化 coding agent（不是人眼盯着打字机效果看）而言，这个代价通常远小于"直接报错、整段 130~150 秒的长任务要重新来过"的代价。

落地方式排序：
1. **零代码改动**：由 OpenClaw 在调用这个虚拟模型时把请求体的 `"stream"` 改成 `false`（可以只在识别出"长结构化生成"这类任务时才这样做，而不是整条 route 一刀切，保留其它场景的流式体验）。
2. **需要写代码的后续方向**（本轮不做）：如果希望 VMR 自己就能做到"对上游用非流式换取可 failover 的能力，但对客户端仍然模拟出流式接口"，需要新增一个 per-model 或 per-route 的"upstream 强制非流式、下游按客户端请求的协议重新分片输出"特性——工程量和方案 D 类似，同样建议先观察方案 B/C 上线后的效果，视故障复现频率再决定是否值得投入。

### 8.4 结论

本节的新证据（同会话在同一任务节点连续两次复现、内容合规已排除）加强了第 7 节的结论：方案 C（outcome + 健康度联动）+ 方案 F（可观测性）依然是第一优先级，用于让这类故障对全局路由和监控可见；在此基础上，**"把长输出/高复杂度任务改成非流式调用"是目前性价比最高的请求级规避手段**——它不需要 VMR 改代码，直接复用已经在生产中跑通的 pre-commit failover 路径，且冷却代价轻微，基本等价于用户想要的"仅这一次任务换模型重试"，比方案 D（服务端无感续写）更简单、更安全，可以作为短期内优先尝试的动作。
