## 文章 1：给 Claude Code 装个黑匣子——那次失败，我能把上游收发的原始字节翻出来重放一遍

**目标平台**：linux.do（首发）、V2EX（同日或次日）

**叙事策略**：场景故事 → 问题 → 工具怎么解决 → 为什么别的工具做不到 → 安装

**字数**：约 2500–3000 字

---

### 正文

上周四凌晨三点，我的 Claude Code 挂了一次——不是那种"啪一下就报错停掉"的挂法，是那种更让人头大的：它对着一个空回复继续往下跑了。

我是第二天早上看 `vmr report` 才知道的。那个会话的审计记录里有一条标注：`"soft_block_detected": true`。某家国产模型供应商在凌晨时段悄悄把请求拦了，返回了一个 HTTP 200、body 里只有一句话"您好，我无法处理此请求"。不是 429，不是 503，就是 200。

Claude Code 拿到了这个回复，当成了模型的正常输出，基于它继续做下一步决策。然后整个任务在一条幻觉路径上跑偏了。

这不是供应商的 bug——从他们的角度看，这是内容策略。但**从 Agent 的角度看，这比直接返回 5xx 更危险**——5xx 好歹能触发重试或 failover，200 但内容被替换/清空的"软屏蔽"，Agent 完全不知道出了问题。

---

#### 为什么会这样

Agent（Claude Code / OpenClaw / Cline 等）的运行方式和人不一样。人看到模型输出了莫名其妙的一句话会立刻意识到出问题了；Agent 只会把它当下一轮的 context 吃进去，然后继续往前跑。**在无人值守的长任务里，一次软屏蔽足以让跑了几个小时的会话前功尽弃。**

而大多数人——包括我——在配置 Agent 的时候做的事很简单：把 `ANTHROPIC_BASE_URL` 指向某个中转/代理/路由器，填上国产模型的 API Key，就完事了。

问题出在中转那一层。大部分 LLM 网关/路由器的工作方式是"翻译型"——它们会把你的请求先翻译成自己的内部格式，再翻译回目标供应商的格式。这个过程里，它们关心的东西是"把请求正确翻译过去"，不关心"响应的 body 到底是不是模型真正的输出"。

---

#### 我给 Claude Code 装了个黑匣子

所以我在三周前开始写 VMR（Virtual Model Router），一个专门为 Agent 场景设计的透明 LLM 路由器。它做的事说起来简单——挡在你的 Agent 和 LLM 供应商之间，把每一层收发的原始字节都记下来——但这恰好是翻译型网关结构性做不到的事。

它的核心设计选择就一个：**永远不做翻译**。不把 OpenAI 协议翻译成 Anthropic 协议，不把请求"规范化"成内部格式再还原。你的客户端发出的每一个字节——包括那些刚上线还没人有空适配的新参数——原样转发给上游。上游返回的每一个字节——包括那些文档里没写的行为——原样记录。

只有两个例外：把虚拟模型名（你配置的 `coding`、`claude`）替换成真实的上游模型名；以及针对已知的厂商怪癖做守卫式修复——如果你用 MiniMax，你可能注意到它有时候会在输出前面塞一段 `<think>...</think>` 标签，VMR 会把它剥掉。**仅此而已。**

---

#### 翻出那次凌晨三点的失败

回到那次软屏蔽。

在 VMR 的审计日志里，那次请求的记录长这样（简化）：

```json
{
  "ts": "2026-07-24T03:14:22+08:00",
  "model": "coding",
  "attempts": [
    {
      "endpoint": "minimax/MiniMax-M3",
      "status": 200,
      "soft_block_detected": true,
      "upstream_body_snapshot": "您好，我无法处理此请求。"
    },
    {
      "endpoint": "openrouter/z-ai/glm-5.2",
      "status": 200,
      "upstream_body_snapshot": "这是关于您请求的代码...（正常输出）"
    }
  ]
}
```

注意这里有两层记录：客户端发给 VMR 的（没被改写）、VMR 发给上游的（model 名字被替换了）。还有两次 attempt——第一次被 MiniMax 软屏蔽了，VMR 检测到后自动切换到了第二个端点（OpenRouter 上的 GLM-5.2），还**没有惩罚 MiniMax 端点的健康状态**——软屏蔽不是端点挂了，只是这个请求命中了内容策略，换个模型就过了。

**这件事没有任何其他工具能做到。** 不是"VMR 做得更好"——是**根本做不到**。

为什么？因为所有翻译型网关（LiteLLM、Portkey、甚至 36k star 的 claude-code-router）都在请求到达之后先把它翻译成自己的内部格式。这个过程里，它们关心的东西是"把请求正确映射到目标供应商的格式"——响应 body 的内容是什么、有没有被供应商悄悄替换，不在它们的设计范围内。而且它们根本**没有存两层完整字节**——它们只存了元数据（哪个模型、多少 token、花了多少时间），不存"上游到底收发了什么"。

VMR 存了。因为它不翻译——请求到达后，它看了一眼 model 字段做了什么替换，其余原样转发。响应回来，它看了一眼有没有已知的 quirk 需要修复，其余原样记录。既然记录的是真实字节，**就可以回放**——`vmr replay -ts "2026-07-24T03:14:22+08:00"` 能把那一次请求原样重发，看上游此刻返回什么。

---

#### 不只是查错：`vmr report` 读得懂 Agent 在做什么

单条请求的两层记录是"黑匣子"的原材料。但 VMR 不只是存原始数据——它还做了一层 Agent 场景特有的分析。

`vmr report` 把审计日志变成报表时，它不是把请求按时间排成一张大表——它按 **会话 → 任务 → 轮次** 把请求分组：

```
Session 2026-07-24
  ├── chat_id=abc123 (1h22m, 💬22, 🛠️14, ⚡15.2s avg)
  │   ├── Turn 1     → 🆕 初始任务描述 → 模型输出 + 2 次工具调用
  │   ├── Turn 2     → 🆕 工具结果 + 模型继续 → 1 次工具调用
  │   └── ...
```

🆕 前缀标记的是**这一轮新增的请求内容**——你一眼就能看出 agent 在这一轮给了模型什么新信息，而不是把整个 conversation history 从头看一遍。

另外还有一张**工具声明与实际调用对比表**：你的 agent 配置里声明了 15 个工具，但过去 7 天有 3 个从来没被调用过。这意味着你也许可以把它们从配置里删掉，节省 token。

这是给 agent 场景从零设计的分析方式。通用日志分析工具（ELK / Grafana）能给你按 HTTP 状态码做饼图，但它不知道"这一行 JSONL 和那一行 JSONL 属于同一个多轮对话的同一个任务"。

---

#### 和 claude-code-router 比一下

我知道你在想什么："claude-code-router 36k star，这个 2 star，凭什么让我换？"

实话实说：**CCR 是很好的工具，它在它的设计哲学里做到了最好。** 但它和 VMR 在根本设计上不同：

| | VMR | claude-code-router |
|---|---|---|
| 请求处理 | 字节级透传，不做翻译 | Transformer 插件改写 |
| 新参数支持 | 上游上线当天即可用，vmr 零改动 | 需要插件适配 |
| failover | ✓ | ✓ |
| 请求日志 | ✓（两层完整字节） | ✓（元数据级：provider/model/status/latency） |
| 成本估算 | ✓ | ✓ |
| **能翻出上游到底收发了什么原始字节吗？** | **能** | 不能——它只记元数据 |
| **能把那次失败原样重放吗？** | **能** | 没有等价能力 |
| **能按 Agent 会话/任务/轮次分组吗？** | **能** | 按请求平铺 |
| 安装 | 一个 Go 二进制文件 | npm（Node.js + dashboard） |
| 国产厂商 quirk 修复 | 有（MiniMax thinking 剥离、软屏蔽检测） | 无 |

如果你关心的问题是"我的 Agent 昨晚跑了什么、花了多少钱、失败了几次"——CCR 能回答。如果你关心的问题是"**那次失败到底是上游收到了什么、返回了什么，我能不能复现那一刻**"——**只有 VMR 能回答。**

这两类问题需要的是深度不同的记录——一个是统计，一个是取证。前者很多工具能做，后者需要"不翻译"这个架构前提——而这个前提，所有翻译型网关都不会接受，因为它与"一个 API 打通 1000+ 模型"这个产品承诺直接冲突。

---

#### 装起来试试

```bash
# macOS
brew install bigfatsea/tap/vmr

# 或直接下载二进制（macOS / Linux × amd64 / arm64）
# https://github.com/bigfatsea/vmr/releases/latest

# 从配置样例开始
curl -o config.yaml https://raw.githubusercontent.com/bigfatsea/vmr/main/config.example.yaml
# 编辑 config.yaml，填上你的 API Key（支持 ${ENV} 语法）

# 校验配置 + 打印路由表
vmr check -c config.yaml

# 跑起来
vmr start -c config.yaml
```

然后把 Agent 该怎么跑怎么跑。VMR 在背后静静地记所有东西。过一天跑 `vmr report`，你会对"自己的 Agent 到底在做什么"有一个全新的理解。

**项目地址**：[github.com/bigfatsea/vmr](https://github.com/bigfatsea/vmr)

MIT 开源。单二进制，零数据库，零依赖。不 SaaS 化，不卖企业版。就是一个我自己每天在用的工具——觉得可能对你们也有用，所以发出来。

## 文章 2：国产模型返回 200 但内容是空的——聊聊我发现的软屏蔽和 thinking 泄漏

**目标平台**：linux.do（首发）

**叙事策略**：现象描述 → 为什么危险 → 技术分析 → 工具解决 → 引申

**字数**：约 2000–2500 字

---

### 正文

如果你在国内用国产模型跑 Claude Code 或其他 Agent，你应该对这种情况不陌生：

- 发了一条请求，HTTP 状态码 200
- 但响应内容不是你问的东西——可能是一句"您好，我无法处理此请求"，也可能干脆是一个空的 `content` 字段
- Agent 不报错，因为 200 就是成功——它拿着这个"回复"继续往下跑

这种现象有个名字：**软屏蔽（Soft Block）**。它和 429（Rate Limit）、503（Service Unavailable）不一样——那些好歹是明确的错误，Agent 和网关都能识别并处理。软屏蔽是**伪装成成功响应的拒绝**。

我最近在写 VMR（一个给 Agent 用的 LLM 路由器，等下细说）的过程中，花了不少时间专门处理国产模型生态里的这些独特行为。这篇文章想分享一下我发现的几种模式，以及为什么它们对 Agent 比对人危险得多。

---

#### 模式一：软屏蔽——2xx 但内容被替换

**触发特征**：
- HTTP 状态码 200（有时是 201 或其他 2xx）
- `choices[0].message.content` 不是预期的模型输出
- 常见替换内容：`"您好，我无法处理此请求"`、`"抱歉，我不能回答这个问题"`、空字符串
- 有时伴随特定的响应头或响应体里的标记字段

**为什么对 Agent 危险**：
人在看到"您好，我无法处理此请求"时会立刻知道这不是模型真实的回答——这是因为**人同时在读内容和判断内容质量**。Agent 不做这个判断——它的下一个 API 调用是把整个 `messages` 历史（包括这条"我无法处理"）塞进新的请求里，然后问模型"基于以上对话，下一步做什么"。

模型的反应是不可预测的。它可能：
- 忽略那条奇怪的回复，继续正常推理（最好情况）
- 把"无法处理"理解为"任务被拒绝了"，改变执行策略（中等危害）
- 基于这条幻觉回复发展出一整条错误的推理链（最坏情况）

在无人值守的深夜长任务里，第三种情况足以让一个跑了两小时的任务静默偏航。

---

#### 模式二：thinking 泄漏

**触发特征**：
- 国产模型（尤其是 MiniMax）在某些模式下会把内部推理链暴露在输出里
- 形式可能是 `<think>...</think>` XML 标签包裹的一段文本
- 也可能是纯文本的 "Thinking Process:" 开头的一个段落

**为什么对 Agent 危险**：
这些 thinking 内容**不是给客户端看的**。它们是模型内部的推理草稿——可能包含：
- 被模型自己推翻的推理路径
- 对用户指令的重新解读（有时是误读）
- 模型对自己能力边界的自我评估

把 thinking 泄漏到对话历史里，相当于让 Agent 多了一段来源不明的上下文。下一轮 Agent 会把这段 thinking 的内容当成正常的对话历史吃进去——而这段内容可能包含已经被模型自己否定了的判断。

---

#### 我怎么在 VMR 里解决这两个问题

先说清楚：**这些是上游厂商的行为，VMR 不能阻止它发生。** VMR 做的事是在网关层**检测**和**修复**。

**软屏蔽检测**（当前为观测模式，不自动 failover）：

VMR 在解析响应时，对某些已知的软屏蔽模式做内容检测。如果命中，会在审计记录里打上 `"soft_block_detected": true` 标记。

目前做的事：
- 检测已知的软屏蔽文本模式（如"我无法处理此请求"及变体）
- 打标记到审计 JSONL 里——`vmr report` 报表里会单独统计软屏蔽比例
- 观测数据积累中——未来（P1）会把软屏蔽升级为自动 failover（非流式路径），这样 Agent 不会拿到那个空回复

**thinking 剥离**（自动修复，有守卫）：

对 MiniMax 的 thinking 泄漏，VMR 在流式转发过程中检测 `<think>` 标签的开启和闭合，在转发给客户端之前剥掉中间的内容。对于纯文本的 "Thinking Process:" 草稿模式，也有对应的匹配逻辑。

每一条修复都有严格的触发守卫：
- 只在确认识别到已知模式时才干预
- 守卫失效时（比如上游改了 thinking 的格式）会自动打观测标记 `thinking_process_pattern_detected`，提示"有个 thinking 模式看起来像但我们没拦截，该检查了"
- 其余 99.9% 的响应字节原样通过——包括那些"看着有点可疑但实际上不是 thinking"的内容

---

#### 为什么别的工具做不到这件事

翻译型网关在处理响应时只关心一件事：**把响应从供应商的格式翻译成客户端期望的格式**。它检查的是 JSON 结构、字段映射、HTTP 状态码——**不检查 `content` 字段里的文本内容是不是模型真正的输出。**

要做到 VMR 这种级别的检测，你需要两个前提：
1. **不翻译响应**——如果响应被重新序列化过一次，软屏蔽的文本模式可能已经被"规范化"掉了
2. **两层完整记录**——你需要同时看到"上游实际返回了什么"和"客户端收到了什么"，才能在审计里标出差异

这两个前提都与翻译型网关的架构直接冲突。不是他们"没想到要检测"——是他们的架构不支持。

---

#### 最后说一句

这篇文章不是为了让你觉得"国产模型不行"——不是的。MiniMax / DeepSeek / GLM / Kimi 这些国产模型的性价比和中文理解能力是真的强，很多场景下比 OpenAI/Anthropic 的正价接口更合适。

问题是**这些模型生态里有一些独特的边缘行为**，而现有的工具链（无论是官方 SDK 还是第三方网关）基本没有针对它们做过适配——因为大多数工具是英文社区写的，开发者自己不用国产模型。

VMR 是我自己在用国产模型跑 Agent 的过程中长出来的。thinking 剥离和软屏蔽检测是**真的踩过坑然后修的**，不是看了文档猜出来的。如果你也在用国产模型跑 Agent，可以试试——如果遇到新的 quirk，提个 Issue，我会认真看。

## 文章 3：Claude Code 半夜挂了怎么办——按错误类分级的自动故障切换

**目标平台**：V2EX（首发），掘金（后续）

**叙事策略**：痛点直击 → 为什么简单的重试不够 → VMR 的解决方案 → 技术细节 → 安装

**字数**：约 1500–2000 字

---

### 正文

如果你让 Claude Code 跑一个长任务（比如重构一个模块、生成一组测试、处理一批文件），半夜去睡觉，第二天早上看到的可能是：

- "Connection timeout"——供应商那边挂了
- "429 Too Many Requests"——被限流了
- "Insufficient balance"——账号欠费了
- 或者更糟：什么都没报错，但任务跑到一半停在那了

不管哪个结果，你都得手动重跑。如果任务跑了三个小时才挂的，那三小时的 context 和进度就全没了。

这就是 VMR 解决的第一个问题——但它的做法和你想的可能不太一样。

---

#### 为什么简单重试不够

大多数 HTTP 客户端的重试逻辑是：失败了 → 等一秒 → 再试 → 还是同一个 URL。对 Agent 场景，这有两个问题：

**问题一：不是所有错误都应该重试同一个端点。**

- 429（Rate Limit）→ 重试同一个端点可能有用（等冷却），也可能换个 key 或换个账号更好
- 400 因为 API Key 过期 → 重试 100 次也还是 400
- 400 因为 Context 太长 → 换成 context 更大的端点就能过
- 5xx 因为供应商挂了 → 换一家供应商
- 2xx 但内容是空的（软屏蔽） → 换一家供应商，但不要惩罚被屏蔽的端点——它没病，只是不接你这个请求

"一个重试策略应对所有错误"在 Agent 场景下不够用。

**问题二：重试不应该惩罚端点。**

如果有人发了一个带敏感词的请求，被供应商的内容策略拦截了（返回 400 或特定错误），你不应该因此把整个端点标记为"挂了"。那个端点对其他人、对其他请求还是健康的——只是这个特定请求被拒绝了。

**问题三：恢复时不应该让真实流量当小白鼠。**

一个端点冷却 30 秒后，你要怎么知道它恢复了？最简单的做法是让下一个真实请求去试——但这意味着那个不幸的请求要被拖慢，而且在并发场景下，所有在等这个端点的请求都会被堵在那一个"探测请求"的耗时里。

---

#### VMR 的解法：按错误类分级的健康状态机 + 独立恢复探测

VMR 把上游返回的错误分成四类，每类有不同的冷却策略和切换行为：

| 错误类别 | 触发条件 | 冷却时间 | 是否换端点 | 是否惩罚端点 |
|---|---|---|---|---|
| Rate Limit（限流） | 429 + `Retry-After` 头 | 服从 `Retry-After`，无头时指数退避 | 是 | 是 |
| Auth / Bad Request | 401 / 403 / 400（非 context） | — | **否**，直接返回客户端 | 否——返回 400 不是端点的错 |
| Context Length Exceeded | 400 + context 相关措辞 | — | **是**，换 context 更大的端点 | 否——端点没病，是这个请求太大 |
| Content Policy | 400 + 内容审核相关措辞 | — | **是** | **否**——端点健康，只是不接这个内容 |
| Upstream Error | 5xx / 连接失败 | 指数退避（1s→2s→4s…max 30s） | 是 | 是 |
| Soft Block | 2xx + 内容为空/被替换 | — | 是（P1，当前仅观测） | 否 |

**恢复探测默认走独立通道**：冷却到期后不会让下一个真实请求去冒险——VMR 发一个极小的 echo-nonce 请求（`{"messages":[{"role":"user","content":"ping"}]}`）去探测端点是否恢复。这个探测的耗时不影响任何真实请求。如果探测成功，端点恢复健康，下一条真实请求正常走。

如果探测失败，继续冷却。真实流量完全不需要等待或担心被"探测请求"拖慢。

---

#### 一个真实例子

假设你的 `coding` 虚拟模型配了三个端点，按优先级排列：

```
1. minimax/MiniMax-M3   (context 上限低，便宜)
2. deepseek/deepseek-v4-pro  (context 上限高，中等价位)
3. openrouter/z-ai/glm-5.2  (备用)
```

**场景**：凌晨 3 点，一个长对话 agent（已经积了 100 轮 context）发请求。

1. **MiniMax** → 返回 400 `"maximum context length exceeded"` → VMR 识别为 context 超限，换到 DeepSeek，不惩罚 MiniMax
2. **DeepSeek** → 成功返回。后续请求因为 Sticky Model 继续留在 DeepSeek（prompt cache 已预热）
3. 半小时后 DeepSeek 突然返回 503 → VMR 标记冷却，换到 OpenRouter
4. 一分钟后 DeepSeek 冷却到期 → VMR 发 echo-nonce 探测 → DeepSeek 回应正常 → 恢复健康，下一个请求可继续用

整个过程 Agent 完全不知道发生了什么——它只是在跑，VMR 在底下默默切换。

---

#### 和直接配多个 API Key 有什么区别？

有人可能会问：我直接给 Claude Code 配三个 API Key 不行吗？

Claude Code 本身不知道"什么时候该换 key、换哪个 key、换了之后对前一个 key 什么态度"。它是一个客户端，不是一个路由器。它的重试逻辑是为同一个 key 的临时网络波动设计的，不是为"这个 key 欠费了 / 这个供应商挂了 / 我这个请求太长了"设计的。

VMR 做的事情刚好是 Claude Code 不应该做的——在客户端和供应商之间做智能路由，让客户端保持简单。
