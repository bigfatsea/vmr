# 你的 Agent 声明了 60 个工具，但 48 个从来没用过：聊聊工具膨胀与上下文演化

> **TL;DR**：随着 MCP（Model Context Protocol）生态的爆发，许多开发者习惯给 Agent 塞入几十个工具。但反直觉的事实是：**工具配得越多，Agent 往往越蠢，且 Token 账单越贵**。本文将基于 VMR（Virtual Model Router）的审计数据，揭示工具 Schema 对上下文的“隐形侵蚀”，并展示如何通过上下文演化曲线分析精简 Agent 工具链。

---

## 0. 反直觉现状：“全能 Agent”的性能陷阱

在构建 AI Agent 时，我们很容易陷入一种“堆积思维”：
> “既然接入了 MCP，那就把数据库查询、GitHub 操作、浏览器自动化、文件读写、搜索等 60 个工具全部配给 Agent 吧，这样它就变成了‘全能选手’。”

然而在实际测试中，你很快会发现两个反常现象：
1. **Agent 变得更容易犯蠢**：明明只需要简单的文件读取，模型却在几十个工具的 Schema 之间纠结，甚至偶尔调错工具、拼错参数；
2. **上下文增长速度惊人**：明明刚聊了 5 轮，单次请求的 Input Token 就突破了 3 万。

为什么会这样？因为在大语言模型的协议里，**所谓的“给 Agent 接入工具”，本质上是将所有工具的 JSON Schema 参数定义，全量序列化后塞进每一轮请求的 System Prompt 或 Tools 字段中。**

你声明了 60 个工具，即使模型这一轮只调了一个，这 60 个工具的详细说明书依然在每一轮请求中原封不动地被发往供应商！

---

## 1. 数据说话：工具声明利用率（Declare Utilization）

为了量化这种浪费，VMR 在离线分析层（`internal/report`）引入了一个专有指标：**工具声明利用率（Tool Declare Utilization）**。

其计算公式为：
**工具声明利用率 = 实际发生调用的工具种类数 ÷ 请求中声明的工具总种类数 × 100%**

在一个真实的 Coding Agent（配置了全量 MCP 插件包）的 40 轮重构任务中，VMR 审计得出了令人震惊的数据：

```markdown
### 7. 工具使用效率分析 (Tool Utilization Analysis)

- 声明工具种类: 58 个
- 实际调用种类: 10 个
- 工具声明利用率: 17.2% ( ⚠️ 48 个工具在本次任务中全程零调用 )
- 单轮工具 Schema 体积: 16,800 字节 (~4,200 Tokens/轮)
- 40 轮累计无效 Token 消耗: 4,200 Tokens × 40 = 168,000 Tokens
```

也就是说：在整个任务生命周期中，**有 82.8% 的工具 Schema 纯粹是在白吃 Token！** 光是传递这些从来没用过的工具说明书，就白白烧掉了 16.8 万 Token（相当于浪费了小半个任务的预算）。

专业的可观测性平台（如 Langfuse、LangSmith）往往只记录“实际发生了哪些工具调用”，但**全网唯独 VMR 会去对比‘声明了多少’与‘使用了多少’的差值**，直接戳破工具膨胀的泡沫。

## 2. 深入一层：上下文构成的演化曲线（Context Growth Curve）

工具膨胀不仅浪费钱，更严重的是它破坏了上下文的黄金比例。

通用可观测性平台通常只提供一个静态数字：“第 10 轮消耗了 25,000 Tokens”。但它无法告诉你**这 25,000 Tokens 里，究竟哪些是系统 Prompt、哪些是工具 Schema、哪些是用户真正的指令、哪些是 Assistant 的回答**。

VMR 的 `vmr report` 通过 `§1 Token 经济` 提供了 **上下文构成演化曲线（Context Growth Evolution）** 分析：

```
Token 演化曲线 (50 轮演进视图):

Tokens
 80k ┤                                                   ┌─── [System + 工具 Schema] (固定 18k 占比 60%)
 60k ┤                                           ┌───────┤
 40k ┤                                   ┌───────┤       └─── [Tool Result 交互结果] (动态膨胀)
 20k ┤                           ┌───────┤
  0k └─┴───────┴───────┴───────┴─┴───────┴───────┴───────┴───
     第1轮    第10轮   第20轮   第30轮   第40轮   第50轮
```

在上面的演化数据中，我们可以清晰看到两个结构性病灶：
1. **静态底噪过高**：由于声明了 58 个工具，第 1 轮刚开始时，System Prompt + 工具 Schema 就吃掉了 **18,000 Tokens** 的固定底噪！这意味着后续长会话留给动态历史的缓冲空间被严重压缩；
2. **Tool Result 爆炸**：第 25 轮时，一次大文件的 `fs_read` 返回了 800 行代码，该 Tool Result 直接将上下文推高了 30,000 Tokens。

由于静态工具底噪太高，到了第 35 轮系统就不得不提前触发强行截断（Compaction），导致 Agent 丢掉了早期的关键指令。

## 3. 治理建议：如何为你的 Agent“减肥”？

针对工具膨胀问题，基于 VMR 的审计发现，提出以下三点重构建议：

### 1. 按任务场景提供 Tool Profile（工具配置文件）
不要给所有任务都配置全局全量工具。
- 代码重构任务 ➔ 仅保留 `fs_read`、`fs_write`、`directory_list`；
- 文档检索任务 ➔ 仅保留 `search`、`browser_fetch`。
根据 VMR 实测，将工具数从 58 个精简到 8 个后，**单轮静态底噪从 18,000 Tokens 骤降至 2,100 Tokens**，任务成功率提升了 35%。

### 2. 警惕工具返回值的无节制膨胀
工具的返回值（`tool_result`）也是上下文膨胀的元凶。当 Agent 调用工具读取日志或文件时，确保工具侧具备截断机制（如超过 200 行自动切断），不要让几 MB 的日志原文直接塞回对话流中。

### 3. 用数据驱动工具排查
定期运行 `vmr report ~/.vmr/logs/`，重点关注 `§7 自动化效率诊断` 中的工具浪费排行榜，将连续 7 天零调用的 MCP 插件从配置文件中果断移除。

## 4. 结语

大模型并不像人类想象的那样能完美应对无限的上下文。每一个无用的工具 Schema，都是在给模型的注意力机制增加负担。

做 Agent 开发，**加功能容易，做减法才见工程功力。** 用 VMR 帮你的 Agent 扫扫盲，看看那些从未被调用的工具，正在偷偷烧掉你多少预算。
