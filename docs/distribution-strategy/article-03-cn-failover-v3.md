# 设计一个 LLM 端点的健康状态机——VMR 的错误分类与冷却策略

如果你要给一个 LLM 路由器设计健康状态机，第一反应可能是"5xx 就切，其他返回客户端"。这个策略能覆盖 80% 的场景。剩下的 20% 是这篇文章要讨论的——以及为什么它们才是真正难的地方。

以下每个设计决策都对应 VMR 中的一个实际实现点。但本文的重点不是 VMR，是**这些决策本身**——如果你在写自己的 LLM 路由层，可能会遇到同样的问题。

---

## 决策一：不是所有 4xx 都应该 failover

直觉上：4xx = 客户端错误 = 换端点没用 = 返回给客户端。

实际情况：

**401 Unauthorized** → Key 过期了。**应该**换端点（另一个 key 还能用），**且**应该给这个端点长冷却（这个 key 短期内都不可用）。

**402 Payment Required** → 欠费了。同上——长冷却，换端点。

**400 Bad Request + body 里是 "content management policy"** → 内容审核拦截。**应该**换端点（另一个供应商可能不拦截这个内容），**但不应该**惩罚端点健康（端点没病，只是不接这个内容）。

**400 Bad Request + body 里是 "maximum context length exceeded"** → 上下文太长。**应该**换端点（换 context 上限更高的端点），**但不应该**惩罚端点。

**400 Bad Request + body 里是 "invalid value for parameter 'temperature'"** → 你的请求确实有问题。**不应该**换端点——每个端点都会拒绝。

结论：**4xx 不是一个类别，是一个需要按 body 内容细分的领域。** 分类器的输入不只是 HTTP 状态码，还包括响应 body 的文本内容。

VMR 的 `DefaultClassify` 函数（`internal/adapter/classify.go`）当前做了这些区分：401 → `ErrAuth`、402/404 → `ErrEndpoint`、400 + content policy 关键词 → `ErrContent`、400 + 未知模型 → `ErrEndpoint`、其余 4xx → `ErrClient`。context 超限的独立识别是 P1 规划中的增量。

## 决策二：不是所有冷却都应该一样长

直觉上：失败了就冷却 30 秒。

实际情况：

- **Rate Limit（429）** → 冷却时间应该服从 `Retry-After` 响应头。供应商告诉你"30 秒后再来"，你没必要等 60 秒，也不应该只等 5 秒。
- **Auth 错误（401）** → 应该**长冷却**。一个过期的 key 在接下来几分钟甚至几小时内都是过期的。短冷却意味着反复尝试——每次尝试都是浪费一次 failover 机会。
- **Transient（5xx/超时）** → 应该**短冷却 + 指数退避**。供应商可能只是临时过载，1 秒后可能就好了。但如果第一次重试还是 5xx，退避到 2 秒、4 秒、8 秒……上限 30 秒。

VMR 的实现：`Health.ReportFailure(key, class, retryAfter, now)` 根据错误类别和可选的 `Retry-After` 头决定冷却时长。`ErrAuth` 和 `ErrEndpoint` 走长冷却，`ErrTransient` 走指数退避，`ErrRateLimit` 服从 `Retry-After`。

## 决策三：恢复探测不应该用真实流量

直觉上：冷却到期后，让下一条真实请求去试。

实际情况：如果下一条真实请求是一个 Agent 的长对话（可能几万 token），而端点还没恢复，这个请求就会被卡住，直到超时。而且在并发场景下，所有在等这个端点的其他请求也会被这个"探测请求"阻塞。

VMR 的默认行为（active probe mode）：冷却到期后，VMR 在后台发一个极小的 echo-nonce 请求——`{"messages":[{"role":"user","content":"ping"}]}`——去探测端点。这个探测不经过真实流量路径，不占用真实请求的等待时间。探测通过 → 端点恢复健康 → 真实请求正常走。探测失败 → 继续冷却，真实请求完全不受影响。

一个请求几十毫秒的额外延迟 vs 一个请求被卡住 30 秒——这是为什么 active probe 是默认模式。

---

## 决策四：不是所有拒绝都应该惩罚端点

直觉上：端点返回了错误 → 端点健康度下降。

实际情况：如果一个请求被内容策略拦截（`ErrContent`），那是这个请求的问题，不是端点的问题。把这个端点标记为"不健康"会导致：
- 后续的、内容合规的请求也会避开这个端点
- 可用的候选端点池被人为缩小
- 如果有多个端点都有内容策略（不同的敏感度），你可能在几个端点之间来回切换，每个都被短暂冷却——但没有一个是真正"挂了"的

VMR 的做法：`ErrContent` 触发 `Health.ReportNeutral(key)`——释放当前探测槽位（如果有），但不增加冷却或降低健康分数。端点保持健康，只是这个特定请求绕过它。

---

## 决策五：多轮对话应该钉在同一个端点上

直觉上：每次请求选最优端点。

实际情况：多轮对话的 Agent 会话，上游供应商会把前面的 context 缓存起来。如果你中途换了一个端点，新端点没有这个缓存，下次请求就要重传全部 context——直接等于多花钱。

VMR 的 Sticky Model：一旦一个多轮对话在一个端点上成功完成了一轮，后续同一会话的请求会优先回到这个端点。只有在这个端点当前不可用（冷却中）时，才会切换到下一个候选。切换后，Sticky 重新钉到新的端点上。

这不是"最聪明的路由"，这是"最不蠢的路由"——它知道什么时候该保持不动。

---

## 这些决策放在一起

一个 LLM 端点的健康状态机，实际需要处理的是：

- 6 种错误类别（不是 2 种"成功/失败"）
- 3 种冷却策略（不是 1 种"冷却 30 秒"）
- 2 种恢复探测模式（不是 1 种"让真实流量去试"）
- 1 种惩罚豁免（内容策略拒绝不惩罚端点）
- 1 种会话亲和（多轮对话不随意切换）

如果你在写自己的路由层，这些决策可以作为参考。实现参考见 VMR 的 `internal/router/router.go`（failover 主循环，155 行）和 `internal/adapter/classify.go`（错误分类，约 120 行）。
