# Agent 跑长任务总挂？为什么简单的 HTTP 重试远远不够：聊聊分级故障切换

> **TL;DR**：夜间运行的 Agent 跑长任务时，常常因为某个 API 节点发生 429 限流或 401 密钥失效而中途溃败。许多开发者尝试用简单的 retry（重试 3 次）来解决，但结果往往是：坏 Key 被重复重试 3 次导致直接封号，或者敏感词拦截导致整个健康端点被误拉入黑名单。本文将分享 VMR（Virtual Model Router）如何通过 **6 级错误分类状态机、主动后台探针与网络转发嗅探**，为 Agent 打造坚固的无人值守故障自愈体系。

---

## 0. 现象：为什么简单的 `Retry(3)` 会搞砸一切？

在普通的 Web 开发中，处理 HTTP 失败通常很简单：加一个 retry 循环，重试 3 次。

但在 Agent 场景下，**将所有失败同等对待的简单重试，不仅无法解决故障，反而会搞砸整个系统**：

- **场景 A（401 鉴权失败）**：供应商账号余额耗尽或 API Key 被撤销。如果不加区分地重试 3 次，不仅无济于事，还会白白浪费 3 次请求的墙钟等待时间；
- **场景 B（429 速率限制）**：上游触发限流，返回了 `Retry-After: 20` 响应头。如果盲目以 500ms 间隔立即重试，会进一步恶化上游限流，导致 IP 被短时间封禁；
- **场景 C（内容合规拦截）**：请求命中了敏感词。如果不加区分地把这个端点标记为“健康度下降并冷却 10 分钟”，后续所有正常的请求都会失去这个高性价比端点；
- **场景 D（中转网关转发失败）**：第三方中转层返回了一个模糊的 400，错误信息里写着 `"Upstream request failed"`。如果误将其判为客户端格式错误（`ErrClient`），系统就会直接放弃 Failover，导致整个长任务在半夜打断。

---

## 1. VMR 的解法：6 级精细化错误分类体系

在 VMR（Virtual Model Router）中，所有的上游响应在进入健康状态机前，必须经过分类器（`internal/adapter/classify.go`）的严格嗅探，划分为 6 级明确的错误语义：

```
                              ┌────────────────────────┐
                              │ 上游返回 HTTP 状态/Body  │
                              └───────────┬────────────┘
                                          │
    ┌──────────────┬──────────────┼──────────────┬──────────────┬──────────────┐
    ▼              ▼              ▼              ▼              ▼              ▼
 ErrClient      ErrAuth       ErrRateLimit   ErrEndpoint    ErrTransient   ErrContent/
(4xx 格式错)   (401/403)       (429 限流)     (404/坏Key/    (5xx/网络错)   ErrContextLimit
  │              │              │            upstreamHint)      │            (合规/超限)
  ▼              ▼              ▼              ▼                ▼              ▼
不 Failover   长冷却(10m+)    尊重 Retry-After  长冷却(10m+)    短退避(2s指数) 换端点零惩罚
原样给客户端  换端点切换      换端点切换     换端点切换     换端点切换     换端点切换
```

### 1.1 错误语义与处理策略详解

1. **`ErrClient`（客户端请求格式错误）**：如 JSON 语法错误、必须字段缺失。**绝不 Failover**，直接将上游错误原样透传给客户端，防止坏请求把所有候选端点试一遍。
2. **`ErrAuth`（鉴权/余额故障）**：401/403（非内容拦截）。表明该 Key 已失效或欠费，触发**长冷却（10分钟起）**并立即切换到下一个候选 Endpoint。
3. **`ErrRateLimit`（429 限流）**：**严格遵循上游的 `Retry-After` 标头**（支持秒数或 HTTP Date 格式）。若上游指定了等待 15 秒，则将该端点隔离 15 秒，期间新请求自动绕过该端点。
4. **`ErrEndpoint`（端点永久损坏）**：404 模型不存在，或命中 `upstreamHint`（网关转发失败嗅探，如 `"upstream request failed"`）。长冷却并切换，防止中转层报错导致 Failover 中断。
5. **`ErrTransient`（瞬态故障）**：5xx 服务器错误、529 拥塞、网络超时。触发**短退避（2s 起始指数退避）**并迅速切换。
6. **`ErrContent` / `ErrContextLimit`（内容拦截 / 上下文超限）**：最特殊的分类！立即 Failover 寻找更大的模型或备用端点，但**对当前端点的健康度打 0 分惩罚（ReportNeutral）**。

## 2. 探针隔离：真实流量与恢复探测解耦

常规网关的健康恢复机制往往是**“把真实用户的下一个请求当探针”**：
当一个端点从冷却中恢复时，网关把真实用户的请求发过去试水。如果该端点依然没好，这个真实用户的请求就成了“牺牲品”，遭遇漫长的超时或二次失败。

VMR 把恢复探测跟真实流量彻底解耦：

```
[端点进入冷却] ───退避计时结束───► [半开单飞状态 (Half-Open)]
                                      │
                                      ▼
                     [后台 Goroutine 发送 nonce 微型探针]
                        ├── 探针成功 ➔ 彻底恢复，恢复全量流量
                        └── 探针失败 ➔ 加深退避，不影响任何真实请求
```

- 当端点到达恢复时间点时，VMR 的后台探针 Goroutine（`internal/router/probe.go`）会自动构造一个带一次性 `nonce` 回显要求的微型请求；
- 探针独立运行，**完全不占用任何真实客户端请求**——真实请求在探针出结果之前，永远被路由到下一个候选，不会等它、也不会替它试水；
- 只有当探针确认回显正确后，该端点才会被重新放归候选池。

## 3. 运维体验：响应头透传与调试诊断

为了让 Failover 的整个过程透明可查，VMR 会在发回客户端的 HTTP 响应头中注入追溯信息：

- **`X-VMR-Route-Reason`**：说明当前选中的路由逻辑（如 `pick=order eligible=3/3 cooldown=1`）；
- **`X-VMR-Failover`**：记录本次请求中发生过的失败尝试（如 `deepseek/chat:429, minimax/m2:500`）。

当新部署环境出现网络连通性问题时，不需要去猜测配置，运行一行诊断子命令：

```bash
vmr diagnose
```

VMR 会按顺序执行：**配置格式校验 ➔ 代理感知的 DNS/TLS 检查 ➔ nonce 回显连通性测试 ➔ 路由预览**，以卡片形式给出明确的红绿灯诊断报告。

## 4. 总结

无人值守的 Agent 就像在旷野中长途奔袭的车辆，API 的波动和故障是无法避免的坑洼。

一个优秀的网关，不应该只是简单地“坏了就重试”，而是应当像一位经验丰富的手动挡司机：**精确识别故障类型、合理档位退避、并在后台完成静默修整。**
