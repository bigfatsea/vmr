# 为什么我做了个“不翻译”的 LLM 路由器？反主流设计的工程思考

> **TL;DR**：开源界 99% 的 LLM 网关（如 LiteLLM）都在讲同一个故事：“将上百个供应商的 API 统一翻译成标准的 OpenAI 格式”。而我写 VMR（Virtual Model Router）时，却选择了完全相反的路线——**绝对不跨协议翻译，做字节级保真（Byte-faithful）的透传路由器**。本文将分享为什么“双协议透传”是更适合 AI Agent 场景的架构抉择，以及它为开发者带来的三大核心价值。

---

## 0. 现状：翻译型网关的繁荣与隐患

当下，大部分开发者在选型网关时，首先被吸引的是那些宣称“一个 API 打通 1000+ 模型”的产品。

这种**翻译型架构（Translation Gateway）** 的原理很直观：
网关在入口处接收 OpenAI 格式的请求，内部解析为自定义的中间表示（Intermediate Representation），然后通过数十个各种语言编写的 Adapter/Transformer 插件，重新拼装成 Anthropic、Gemini、DeepSeek 等供应商的底层 API。

在普通的“单轮聊天”或简单的 RAG 场景下，翻译型网关表现得很好。

**但当你的系统演进到复杂的 AI Agent 场景时，翻译型架构的硬伤开始集中爆发：**

1. **上游发布新功能，你必须等网关更新**：当 OpenAI 推出新的 `developer` role 或 Responses API，或者 Anthropic 发布新的 `thinking` 字段时，翻译型网关因为不认识这个新字段，会在内部解析时直接将其**静默丢弃**；
2. **“翻译税”导致双向流式延迟**：将 Anthropic 的 SSE 事件流（`message_start` ➔ `content_block_delta`）实时翻译成 OpenAI 的 `chat.completion.chunk` 流，逻辑极其繁琐。网关在中间做序列化与反序列化，付出了昂贵的 CPU 开销和延迟损耗；
3. **审计日志变成了“二手伪数据”**：由于响应体经过了网关的重新拼装，你在本地数据库里看到的日志，并不是供应商服务器当时发回的真实字节。

---

## 1. 反主流抉择：双协议透传，永不翻译

面对这些痛点，我在设计 VMR 时做出了一个极其果断的架构抉择：

```
POST /v1/chat/completions ── OpenAI 协议     ──► 只路由到 OpenAI 兼容端点 (字节透传)
POST /v1/messages         ── Anthropic 协议  ──► 只路由到 Anthropic 兼容端点 (字节透传)
```

**VMR 同时暴露两个聊天入口，但在内部不做任何跨协议转换！**

VMR 的底层模型改写器（`internal/adapter/openai` 与 `anthropic`）使用了一套极轻量的**零分配单趟字节拼接算法（Zero-allocation Byte Splice）**：
在内存中定位顶层 `model` 键的偏移量，直接进行前缀、新模型名、后缀的三段拼接，**除此之外，客户端发来的所有原始 Header、未知 JSON 字段、空白符全盘保留，原封不动地发给上游！**

---

## 2. Byte-faithful 带来哪三大核心价值？

不去追求“一个接口打通 1000+ 模型”的虚名，做“字节保真”的透传路由器，究竟能为开发者带来什么？

拆解为三条你能直接感知的工程收益：

### 收益 1：上游新功能发布当天就能用，无需等待网关更新
由于 VMR 只做顶层字节扫描来提取路由所需字段（model/stream/tools），绝不去完整反序列化请求体中的其他字段，上游厂商无论是今天发布了一个新的推理参数 `reasoning_effort`，还是明天在 JSON 中增加了一个自定义扩展字段：
**这些新参数会自动穿透 VMR 抵达上游！**
你不需要等待 VMR 提交新 Commit 或发布新版本，上游发布新特性的当天，你就可以在代码里直接使用。

### 收益 2：请求与响应字节零损耗，完美契合 Prompt Cache
正如我们在前文所提到的，供应商的 Prompt Caching 引擎对输入前缀极其敏感。
翻译型网关在重新反序列化 JSON 时，常常会打乱 Key 的顺序，或者丢失某些边缘 Header，导致上游前缀缓存彻底失效。
而在 VMR 中，**你的请求里的每一个字节都原封不动到达上游**，天然保证了前缀哈希的 100% 匹配，锁住 90% 的缓存折扣。

### 收益 3：审计记录是绝对的“原始事实”
在 Agent 故障排查与对撞分析中，可信度高于一切。
因为 VMR 从不改写响应体，VMR 在本地 JSONL 中记录的**两层字节审计（客户端侧 + 上游 Attempt 侧）是不可篡改的底层事实**。
当上游抛出偶发格式错误时，你手里的审计记录就是最坚固的证据，甚至可以通过 `vmr replay` 原样重发复现。

## 3. 性能基准： Sub-10ms 的物理极限开销

放弃了复杂的数据转译与中转层逻辑，带来的另一个直接红利就是极致的性能。

在 `loadtest/` 压测基准中（模拟 150 req/s 并发流量，11 个典型 Agent 交互场景）：
- **路由与透传开销**：在 9 个场景中，VMR 引入的代理开销 p95 **低于 10ms**（真实中位数为 1-2ms）；
- **资源占用**：内存占用稳定在几十兆，二进制文件仅 12MB，无 cgo，零外部运行依赖。

对比依靠 Python/Node 运行、动辄占用数百兆内存的企业网关，VMR 的极轻量设计让它可以轻松作为 sidecar 部署在任意边缘服务器或本地开发机上。

---

## 4. 总结：做减法的工程哲学

在软件工程中，“做加法”总是诱人的——支持更多协议、内置更多 API 转换器、加一个漂亮的 Web 界面。

但有时候，**真正的工程突破来自于“做减法”**。

通过放弃跨协议翻译这一诱人但包袱沉重的承诺，VMR 换来了绝对的字节保真、当天可用的前缀透传、Sub-10ms 的极低开销、以及不可篡改的 Agent 黑匣子审计。
