# 国产模型返回 200 但内容是空的——聊聊合规软屏蔽与 Thinking 泄漏

> **TL;DR**：在使用国内大模型 API（如 MiniMax、DeepSeek、Qwen 等）运行 Agent 时，你是否遇到过一种极其怪异的现象：**HTTP 响应码是 200 OK，但返回的 text 内容却是空的（或者只有一段合规提示）**？对于人类聊天，看到空回复顶多重新发一条；但对于无人值守的 Agent，**拿着空回复继续往下跑会导致整个任务逻辑死锁**！本文将剖析国产模型特有的生产环境“坑点”，并分享如何在网关层实现静默自愈。

---

## 0. 现象：无人值守 Agent 的“软屏蔽”杀手

随着 DeepSeek、MiniMax、Qwen 等国产高质量模型的爆发，越来越多的国内开发者开始将 Agent 的底层模型切换为国产 API。

然而，在无人值守的 Agent 场景中，国产 API 生态带来了一个海外模型（OpenAI/Anthropic）几乎不会遇到的特殊技术陷阱：**合规软屏蔽（Soft-Block）**。

### 什么是软屏蔽？
传统的合规拦截往往抛出标准的 HTTP 错误码（如 `403 Forbidden` 或 `400 Bad Request`，并在 Body 中带上 `content_filter` 错误码）。这类明确的错误很容易被网关或 SDK 捕捉并触发重试。

而**软屏蔽**则是：供应商在网关层或安全审核层拦截了敏感文本，但**HTTP 响应码依然忠实地返回 `200 OK`**！
其 Body 返回体通常有两种表现形态：
1. **空内容形态**：`choices[0].message.content` 为空字符串 `""`，或只包含空白换行；
2. **替换标记形态**：Body 内嵌入了厂商特有的合规标记（如 MiniMax 的 `input_sensitive` 或 `output_sensitive`），正文被替换为“*输入内容包含敏感信息*”。

### 为什么软屏蔽对 Agent 是致命的？
如果你在网页上和 AI 聊天，看到空回复，你只需重新点一次生成。

但 Agent 是一个依据上一轮回复做出下一步决策的状态机！当模型返回空字符串时：
- Agent 无法提取出任何 `tool_call` 工具调用；
- Agent 的 Prompt 逻辑误以为模型给出了“否认”或“忽略”的回答；
- 在接下来的 10 轮中，Agent 会拿着这个空上下文不断重复询问，陷入**静默死锁**（Silent Deadlock），直到 Token 预算耗尽！

## 1. 另一个泥潭：思维链（Thinking）泄漏与格式污染

除了软屏蔽，国产模型在推理能力（Thinking Process）的输出处理上也存在不少“小动作”。

例如 MiniMax 等模型在输出思维链时，经常会在 Response 文本的前部直接抛出原始的 `<think> ... </think>` 标签块，或者输出纯文本的 `"Thinking Process:\n1. ..."` 思考草稿。

如果你的 Agent 框架不支持格式化解析这类草稿：
- 草稿文本会被误当成最终代码直接写入文件；
- 嵌套的 `<think>` 标签会导致 JSON 格式解析崩溃；
- 包含在思考过程中的临时文件名会被后续轮次误当成真实存在的文件。

通用跨国网关（如 LiteLLM、Bifrost）的架构建立在“统一把所有响应转译为 OpenAI 格式”之上，**他们完全没有针对中国厂商特有的合规标记和思维链标签做过任何特殊清洗。**

---

## 2. 解决方案：VMR 的静默检测与审计

针对国产生态的这些特定 Quirk，VMR（Virtual Model Router）在响应侧归一化器（`internal/router/responsefix.go`）中专门加入了严格的检测逻辑。

```
客户端 (Agent) ◄─── VMR 路由器 ◄─── 供应商 A (HTTP 200 空内容 / 软屏蔽)
                       │
                       ▼ (检测到合规标记)
                打上 `soft_block_detected` 审计标记
                原样转发响应给客户端（不改字节）
                       │
                       ▼ (事后通过 `vmr report` 发现)
                运维人员分析软屏蔽分布，调整路由策略
```

### 1. 软屏蔽检测（当前为观测模式，自动 Failover 正在开发）

VMR 在响应归一化阶段会检测已知的软屏蔽模式：
- 命中合规标记（`input_sensitive` / `output_sensitive` / 特定敏感词模式）；
- 提效后的实际文本为空或极短；

当检测命中时，VMR **当前只做观测标记**——在审计 JSONL 中记录 `soft_block_detected`，**原样把响应转发给客户端，不改字节、不自动切换端点**。

这个设计的逻辑是 VMR 的核心方法论——**观测先于行动**。先把软屏蔽的发生频率变成可量化的数字（通过 `vmr report` 可以清晰看到哪个供应商在哪个时段敏感率最高），等数据能回答"这种情况一个月发生几次"之后，再决定要不要做自动 Failover。

> ⏳ **路线图预告**：非流式路径的软屏蔽自动 Failover（检测到后自动切换到下一端点，且不惩罚被拦截端点的健康度）已列入 P1 开发计划，预计在 v0.3 版本中上线。为什么不能惩罚健康度？因为被拦截是因为"当前这一条请求包含敏感词"，供应商端点本身完全健康——如果因为一次敏感词就将端点拉入 10 分钟冷却期，一次误触就会把所有健康端点全部打下线。

### 2. Thinking 草稿剥离守卫
对于 MiniMax 等模型的推理过程泄漏，VMR 在透传流中加入了一条极轻量的无分配扫描器。
当且仅当响应开头完全命中 `<think>` 块且后接合法正文时，VMR 会安全剥离思考草稿，将干净的文本提供给 Agent；而一旦检测到该结构形状存疑（可能是模型真的在写带有 `<think>` 字符串的代码教程），守卫会安静退避，**绝对不误杀用户的真实代码**。

## 3. 运维收益：从审计报表中看清合规风险

除了实时 Failover，VMR 还会将每次识别到的软屏蔽打上 `soft_block_detected` 标记，记录在本地审计 JSONL 中。

通过运行 `vmr report`，你可以获得一份包含合规风险分布的月度报表：

```markdown
### 3. 可靠性与故障审计

| 供应商 Endpoint | 总请求数 | 软屏蔽 (Soft-Block) 拦截 | 拦截率 | 应对策略 |
|---|---|---|---|---|
| `provider-a/qwen` | 1,200 | 42 次 | 3.5% | 已通过审计标记捕获，计划在下个版本支持自动 Failover |
| `provider-b/deepseek`| 850 | 2 次 | 0.2% | 表现极优 |

💡 提示：`provider-a` 在夜间 01:00-03:00 的合规拦截率明显上升，建议调整配置，在该时段将 `provider-b` 设为第一优先级。
```

## 4. 总结

做 Agent 接入，不能只看 Demo 跑得顺不顺，更要看生产环境里的“坑”多不多。

中国大模型生态有其独特的合规要求与接口行为。作为一个诞生于中国开发者真实使用场景中的辅助工具，VMR 用极其克制的技术手段包揽了这些脏活累活。
