# Agent 跑了一夜花了多少钱？别只看账单总数，教你挖出隐形 Token 浪费

> **TL;DR**：你以为你的 AI Agent（如 OpenClaw、Pi Agent）跑一晚上只花了 10 块钱？当你打开 API 账单发现扣了 150 块时，往往只能对着一个孤零零的消费总额发呆。本文将带你拆解 Agent 极其隐蔽的 4 大 Token 浪费陷阱：**定时任务默默刷屏、工具 Schema 白吃 Token、Prompt Cache 命中失败、以及失败尝试拖垮墙钟时间**，并用 VMR（Virtual Model Router）生成的报表进行精细化治理。

---

## 0. 现象：非线性的 Agent Token 账单

许多开发者在刚开始用 AI Agent 时，都有过类似的错觉：

> “单次 API 请求才 $0.002，跑个 Agent 任务能花几个钱？”

然而，一旦你把 Agent 放在后台跑无人值守的长任务，第二天早晨看到的账单往往会让你倒吸一口凉气。

为什么 Agent 的花费会远超普通 Chat API？**因为 Agent 的 Token 消耗是非线性的！**
普通聊天是“一问一答”；而 Agent 每一轮都会将之前所有轮次的对话历史、工具调用记录、甚至大量的系统 Prompt 重新打包，发给模型。

到了第 30 轮，哪怕你只说了句“好的，继续”，上游模型接收到的上下文可能已经膨胀到了 8 万 Token！

更糟糕的是，传统的供应商账单只给你提供一个汇总数字：
```
DeepSeek-V3 | Total Tokens: 12,450,000 | Cost: $18.67
MiniMax-M2   | Total Tokens: 8,200,000  | Cost: $12.30
```
这种简单的汇总根本无法回答：**钱究竟花在哪了？哪些 Token 花得值，哪些纯粹是在浪费？**

## 1. 拆解 Agent 的 4 大“隐形 Token 泄漏点”

使用 VMR（Virtual Model Router）对多个生产级 Agent 任务进行审计后，我整理出了 Agent 运行中最常见的 4 个隐形浪费点：

### 浪费点 1：定时任务（Heartbeat/Dream）的静默刷屏
许多开放 Agent 框架（如 OpenClaw）内置了 `heartbeat`（心跳探针）或 `dream_diary`（记忆整理）等后台定时任务。即使你一晚上没有和 Agent 说话，后台的定时任务依然会每隔 15 分钟触发一次请求。由于每次请求都携带着初始的 System Prompt，一晚上几百次心跳在不知不觉中就消耗了数百万 Token。

### 浪费点 2：工具 Schema 暴增（Tool Bloat）白吃上下文
为了让 Agent 具备强大的能力，开发者往往为其接入了 50 甚至 60 个 MCP 工具。每个工具的 JSON Schema 参数定义非常详尽。
**然而在实际任务中，Agent 可能只调用了其中 3 个工具。**
这意味着另外 47 个从未被使用的工具 Schema，在整整 50 轮交互中，每一轮都在重复占用数千 Token 的输入预算！

### 浪费点 3：上游 Prompt Cache 频频失效
为了帮用户省钱，Anthropic、DeepSeek、OpenRouter 等厂商推出了 **Prompt Caching（前缀缓存）**——对于重复的前缀上下文，给予高达 90% 的折扣。
但如果你使用的网关路由策略不够聪明（例如简单的轮询 Round-Robin），或者在透传时频繁改写了 Request Header，就会导致第 2 轮请求被打到了供应商 B，上一次在供应商 A 刚预热好的缓存直接失效！

### 浪费点 4：失败尝试（Failed Attempts）拖垮墙钟时间
当某个 Endpoint 抛出 429 或 500 时，常规网关可能会反复尝试重试。虽然某些厂商不对失败请求扣费，但**失败尝试所消耗的几百秒墙钟时间（Wall-clock Time）是实打实的昂贵成本**。

## 2. 实战：用 `vmr report` 挖出隐形浪费

面对上述隐形浪费，VMR 提供了一套离线、高维度的聚合报表命令：

```bash
vmr report ~/.vmr/logs/ -pricing pricing.yaml
```

生成的 Markdown 报表（`vmr-report.md`）包含了 9 大专有章节，帮助我们逐层剥开 Token 账单的真相。

### 维度一：看清 Token 经济构成（§1 章节）

在报表的第一章节，VMR 帮我们算了一笔明细账：

```markdown
### 1. Token 经济与消耗明细

| 指标 | Token 数量 | 占比 | 说明 |
|---|---|---|---|
| 输入 Token (Tokens In) | 4,120,000 | 88.2% | 上下文重发占据绝对大头 |
| ├── 新鲜 Token (Fresh) | 1,210,000 | 25.9% | 实际新增的对话内容 |
| ├── 缓存命中 (Cache Hit) | 2,810,000 | 60.1% | 享受到 90% 折扣的上下文 |
| └── 缓存写入 (Cache Write)| 100,000  | 2.1%  | 首次构建缓存的开销 |
| 输出 Token (Tokens Out)| 550,000   | 11.8% | 模型实际生成的回答文本 |
```
通过这张表，我们可以清晰看到：**输入上下文占到了总消耗的 88.2%**，优化上下文比去省那点输出 Token 划算得多！

---

### 维度二：工具使用效率分析（§7 自动化浪费诊断）

VMR 的报表会扫描每一轮请求里声明的工具集与实际调用工具集的差值：

```markdown
### 7. 自动化效率诊断与改进建议

⚠️ [工具浪费告警 Top-3]:
1. 任务 `sess_openclaw_01`: 声明了 58 个工具 ( Schema 占用 14,200 字节)，实际仅调用 `fs_read`/`fs_write` 2 个工具。
   💡 建议：对代码重构类任务，使用精简版的 Tool Profile，预计单轮可节省 68% 的输入 Token。
2. 定时任务 `cron_heartbeat`: 过去的 8 小时内触发了 32 次心跳，累计消耗 450,000 Tokens (无有效产出)。
   💡 建议：夜间闲置时段可关闭心跳或调大心跳间隔至 1 小时。
```

### 维度三：Sticky Model 缓存有效性验证（§6.5 章节）

粘性路由（Sticky Model）的唯一目的就是保持上游 Prompt Cache 处于“热状态”。VMR 绝不空谈功能，而是直接按**连续性结果**度量：

```markdown
### 6.5 Sticky Model 缓存有效性度量

| 虚拟模型 | 请求组 | 样本数 | 平均 Cache 命中率 | 平均 TTFT 延迟 |
|---|---|---|---|---|
| `coding` | 连续落在上一端点 (Sticky 生效) | 142 次 | **84.2%** | **420ms** |
| `coding` | 发生了端点切换 (切换端点)   | 18 次  | **12.5%** | **1850ms** |

📌 结论：对 `coding` 模型开启 Sticky 机制后，缓存命中率提升了 71.7%，首字延迟降低了 77.3%。
```

---

### 维度四：端点性价比与失败成本（§6.6 章节）

VMR 拒绝编造失败请求的金额，而是将**时间成本**与**真实产出成本**并列：

```markdown
### 6.6 端点性价比排行榜

| Endpoint | 成功请求 | 失败尝试数 | 失败累计墙钟耗时 | 成本 / 1M 输出 Token |
|---|---|---|---|---|
| `deepseek/chat` | 185 | 2 | 2.4s | **$2.10** |
| `minimax/m2` | 42 | 8 | **64.2s** ⚠️ | **$3.85** |

📌 发现：`minimax/m2` 发生 8 次失败尝试，导致系统额外等待了 64.2 秒。在夜间无人值守时应降低其优先级。
```

## 3. 总结：治理 Agent 成本的黄金法则

要让你的 AI Agent 既高效又省钱，只需遵循三条法则：
1. **砍掉不必要的工具 Schema**：针对特定任务配置最小化的工具集，不要把 60 个工具全部塞给 Agent；
2. **开启 Sticky Model 粘性路由**：锁住上游 Prompt Cache，享受 90% 的上下文折扣；
3. **定期用 `vmr report` 审计**：及时发现偷跑 Token 的后台定时任务。

VMR 的报表功能完全离线运行，不依赖任何第三方云服务，帮你把每一分钱都用在刀刃上。
