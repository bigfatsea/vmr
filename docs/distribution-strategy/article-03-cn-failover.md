# Claude Code 半夜挂了怎么办——按错误类分级的自动故障切换

---

如果你让 Claude Code 跑一个长任务——重构模块、生成测试、批量处理文件——半夜去睡觉，第二天早上看到的可能是：

- `Connection timeout`——供应商挂了
- `429 Too Many Requests`——被限流了
- `Insufficient balance`——欠费了
- 或者更糟：什么都没报错，但任务跑到一半停了

不管哪个结果，你都得手动重跑。如果任务跑了三个小时才挂的，那三小时的 context 和进度就全没了。

这就是 VMR 解决的第一个问题。但它的做法和你想的可能不太一样。

---

## 为什么简单重试不够

大多数 HTTP 客户端的重试逻辑是：失败 → 等一秒 → 再试 → 还是同一个 URL。对 Agent 场景，有三个问题：

**问题一：不是所有错误都应该重试同一个端点。**

- 429（Rate Limit）→ 重试同一个端点可能有用，也可能换个 key 更好
- 401 因为 Key 过期 → 重试 100 次还是 401
- 5xx 因为供应商挂了 → 换一家供应商
- 400 因为内容审核 → 换一家供应商，**但不要惩罚被拦截的端点**——它没病，只是不接你这个请求

**问题二：不应该因为一个请求的内容问题惩罚整个端点。**

如果有人发了一个带敏感词的请求，被供应商内容策略拦截了，你不应该因此把整个端点标记为"挂了"。那个端点对其他人、对其他请求还是健康的——只是这个特定请求被拒绝了。

**问题三：恢复时不应该让真实流量当小白鼠。**

一个端点冷却 30 秒后，你怎么知道它恢复了？最简单的做法是让下一个真实请求去试——但这意味着那个不幸的请求要被拖慢，而且在并发场景下，所有在等这个端点的请求都会被堵在那一个"探测请求"的耗时里。

---

## VMR 的解法：按错误类分级的健康状态机

VMR 把上游返回的错误分成六类，每类有不同的策略：

| 错误类别 | 触发条件 | 行为 | 是否惩罚端点 |
|---|---|---|---|
| **Rate Limit**（限流） | 429 | 服从 `Retry-After` 头，无头时指数退避，换端点 | 是 |
| **Auth / Bad Key**（认证问题） | 401 | 长冷却，换端点 | 是 |
| **Endpoint Issue**（端点不可用） | 402（欠费）/ 404（模型不存在）/ 未知模型名 | 长冷却，换端点 | 是 |
| **Transient**（临时故障） | 5xx / 408 / 连接超时 | 短冷却，指数退避（1s→2s→4s…max 30s），换端点 | 是 |
| **Content Policy**（内容审核） | 400 + 审核相关措辞，或 403 + 审核标记 | 换端点 | **否**——端点健康，只是不接这个内容 |
| **Client Error**（请求本身有问题） | 400（非审核、非 context 相关） | **不换端点**，直接返回客户端 | 否——每个端点都会拒绝 |

**关键设计**：Content Policy 和 Client Error 的区分。前者是"这个请求触发了这个端点的内容策略，换个端点也许能过"——所以换端点但不惩罚。后者是"这个请求本身就是坏的，哪个端点都会拒绝"——所以不换，直接报错。

**恢复探测走独立通道（active 模式，默认）**：冷却到期后，VMR 不会让下一个真实请求去冒险。它发一个极小的 echo-nonce 请求（`{"messages":[{"role":"user","content":"ping"}]}`）去探测端点是否恢复。探测的耗时不影响任何真实请求。探测成功 → 端点恢复健康 → 下一条真实请求正常走。探测失败 → 继续冷却。真实流量完全不需要等待或被"探测请求"拖慢。

## 一个真实例子

假设你的 `coding` 虚拟模型配了三个端点：

```
1. minimax/MiniMax-M3     (便宜，但 context 上限低)
2. deepseek/deepseek-v4-pro  (context 大，中等价位)
3. openrouter/z-ai/glm-5.2    (备用)
```

**场景**：凌晨 3 点，一个长对话 Agent（已经积了 100 轮 context）发请求。

1. **MiniMax** → 返回 400。VMR 的 `DefaultClassify` 检查 body 关键词，没有命中 content policy 或 endpoint 的关键词，归类为 `ErrClient`（请求本身有问题）。不换端点，直接返回客户端。**但目前 VMR 还不会识别"context 超限"这个特定子类**——这是下一版要加的（P1），届时会把 context 超限从 `ErrClient` 里分出来，触发 failover 换到 context 更大的端点。

2. 假设 Agent 缩短了请求后重试。**MiniMax** → 成功返回。后续请求因为 Sticky Model 继续留在 MiniMax（prompt cache 已预热——换端点反而更贵）。

3. 半小时后 MiniMax 突然返回 503 → VMR 归类为 `ErrTransient`，标记冷却，换到 **DeepSeek**。

4. 一分钟后 MiniMax 冷却到期 → VMR 发 echo-nonce 探测 → MiniMax 回应正常 → 恢复健康，下一个请求可继续用。

整个过程 Agent 完全不知道发生了什么。它只是在跑，VMR 在底下默默切换。

## 和直接配多个 API Key 有什么区别？

Claude Code 本身不知道"什么时候该换 key、换哪个 key、换了之后对前一个 key 什么态度"。它是一个客户端，不是一个路由器。它的重试逻辑是为同一个 key 的临时网络波动设计的，不是为"这个 key 欠费了 / 这个供应商挂了"设计的。

VMR 做的事情刚好是 Claude Code 不应该做的——在客户端和供应商之间做智能路由，让客户端保持简单。

---

## 除了 failover，还有会话粘性

有一个容易被忽略的细节：**换端点虽然能救活请求，但会丢掉上游的 prompt cache。**

多轮对话的 Agent 会话，上游供应商会把前面的 context 缓存起来，后续请求只需要传增量。如果你中途换了一个端点，新端点没有这个缓存，下一次请求就要重传全部 context——这直接等于多花钱。

VMR 的 Sticky Model 机制就是解决这个问题的：一个多轮对话尽量钉在同一个端点上，除非那个端点真的挂了。**"更聪明的路由"不会因为频繁切换反而推高成本。**
