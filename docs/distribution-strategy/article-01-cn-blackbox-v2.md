# 我用 VMR 审计了我的 Agent 一周——这是它发现的东西

> **版本**：v2（数据发现式）
> **对标 v1**：`article-01-cn-blackbox.md`
> **差异**：不从个人事故故事切入，而是从"跑了一周报表后的数据发现"倒推工具价值。适合对"故事驱动"叙事免疫的理性读者。
> **目标平台**：linux.do、V2EX
> **字数**：约 2400 字

---

我不打算用一个"我的 Agent 凌晨跑偏了"的故事开场。虽然那个故事是真实的（且 VMR 确实是因为它才写的），但我更想让你看一组数字。

这是我过去 7 天用 VMR 审计自己的 Claude Code / OpenClaw 之后，`vmr report` 里跳出来的几件事：

---

## 发现一：每 50 条请求里，有 1 条被悄悄拦了

过去 7 天，我的 Agent 总共发了 2,847 条请求。其中 61 条的审计记录里打了 `norm: ["soft_block_detected"]`。

**这是什么意思？**

意思是这 61 条请求，上游供应商返回了 HTTP 200，但 body 里带了 `"output_sensitive": true` 或 `"input_sensitive": true` 标记，实际 content 是空的。Agent 拿到空回复后继续往下跑——它不知道发生了软屏蔽。

我不知道这 61 条里有多少导致了实际的执行偏航。但我知道的是：**如果没有 VMR 的审计记录，我连"发生过"都不知道。**

通用的 LLM 网关不会告诉你这个。它们把响应按协议归一化后转发——`"output_sensitive": true` 这种厂商私有字段在归一化过程中就丢了。你看网关的 dashboard，只会看到 61 个绿色的 200。一切正常。

---

## 发现二：最贵的模型不一定是最好的

`vmr report` 按端点做性价比分析时，有一行数据很刺眼：

```
端点                     请求数   成功率   平均延迟   每 1M token 成本   有效 token 产出/$
---------------------------------------------------------------------------
openrouter/GLM-5.2       1,247    99.2%    2.3s       ¥8.40             3,842
minimax/MiniMax-M3       1,012    96.8%    1.8s       ¥1.20             12,107
deepseek/deepseek-v4-pro   588    98.1%    3.1s       ¥3.60             7,233
```

MiniMax M3 的"每块钱产出"是 GLM-5.2 的 3 倍多。而 GLM-5.2 虽然在很多 benchmark 上比 M3 强，但在我的实际场景（写 Go 代码、做 code review）里，成功率只高了 2.4 个百分点——这个差异值不值 7 倍的价钱？

没有这种数据之前，我只能凭"感觉哪个模型更强"来调优先级——而感觉通常会把最贵的模型排在最前面。

---

## 发现三：有 3 个声明的工具，Agent 从来没有调用过

我的 Claude Code 配置里声明了 15 个工具。`vmr report` 的工具使用对比表显示，过去 7 天：

- `web_search`——调用了 342 次
- `read_file`——调用了 1,847 次
- `write_file`——调用了 203 次
- `notion_create_page`——调用了 **0 次**
- `slack_send_message`——调用了 **0 次**
- `jira_create_issue`——调用了 **0 次**

我可以把这三个从未使用的工具从配置里删掉。每个请求省掉三个 tool schema 的 token——按一天几百条请求算，这省下来的 token 够多跑好几轮对话。

**没有 VMR 的话，我永远不会发现这个。** Claude Code 不会告诉你"你声明的工具里有 20% 从来没被用过"。

---

## 发现四：凌晨 3 点到 5 点，供应商真的会挂

`vmr report` 的按时段可用度分析：

```
时段          总请求    失败    可用度    主要失败原因
00:00-02:00    487       3     99.4%    1 次 429, 2 次 503
02:00-04:00    412      11     97.3%    4 次 503, 3 次超时, 4 次软屏蔽
04:00-06:00    398       8     98.0%    3 次 503, 5 次软屏蔽
06:00-08:00    451       2     99.6%    2 次 429
```

凌晨时段的失败率是白天时段的 3-4 倍。而且凌晨的失败原因不是 429（限流）——白天限流多，凌晨是 503（供应商挂了）和软屏蔽。

**VMR 的故障切换让这些失败没有变成"任务挂掉"。** 审计记录里，那些凌晨时段的 `attempts` 数组多数有 2 个元素：第一个失败了，第二个成功了。我的 Agent 在凌晨跑了一夜，任务完成了。如果没有自动 failover，至少有 15 条以上的任务会在凌晨中断。

## 这些数字说明什么

上面四个发现，每个单独看都不是什么惊天动地的事。合在一起，讲的是一件事：

**你的 Agent 在跑的时候，有很多事情在发生，但你完全不知道。**

你不知道供应商在凌晨悄悄拦了多少请求。你不知道哪个模型性价比最高。你不知道哪些工具是白声明的。你不知道那些"成功了"的请求是第几次尝试才成功的。

通用日志工具（ELK、Grafana）能告诉你 HTTP 状态码的分布。但它们不知道这一行 JSONL 和那一行 JSONL 属于同一个 Agent 会话的同一个任务。它们不知道"这个工具声明了但没被调用"。它们更不知道响应 body 里有一个 `"output_sensitive": true` 的隐藏标记。

## 怎么自己看这些数据

```bash
brew install bigfatsea/tap/vmr

# 配好 config.yaml，把 Agent 的 base_url 指向 vmr
vmr start -c config.yaml

# 跑一天，然后
vmr report
```

生成的报表在 `reports/` 目录下。打开 `vmr-report.md`，上面那四类发现你都能看到。

不是让你看我的数据。是让你的 Agent 跑一天，看**你自己的数据**。

**项目地址**：[github.com/bigfatsea/vmr](https://github.com/bigfatsea/vmr)

MIT 开源。单二进制，零依赖。个人工具，不 SaaS 化。
