# 国产模型返回 200 但内容是空的——聊聊软屏蔽和 thinking 泄漏

> **目标平台**：linux.do（首发）
> **叙事策略**：现象描述 → 为什么危险 → 两种模式的技术分析 → 工具怎么解决 → 引申
> **字数**：约 2200 字
> **前置条件**：D1 完成

---

如果你在国内用国产模型跑 Claude Code 或其他 Agent，你大概率遇到过这种情况：

- 发了一条请求，HTTP 状态码是 200
- 但响应内容不是你问的东西——可能是一个空 `content`，也可能带了一个奇怪的内部标记
- Agent 不报错，因为 200 就是成功——它拿着这个"回复"继续往下跑

这种现象有个名字：**软屏蔽（Soft Block）**。它和 429（Rate Limit）、503（Service Unavailable）不一样——那些好歹是明确的错误状态，Agent 和网关都能识别。软屏蔽是**伪装成成功响应的拒绝**。

我最近在写 VMR（一个给 Agent 用的 LLM 路由器）的过程中，花了大量时间专门处理国产模型生态里的这些独特行为。这篇文章想分享一下我发现的两种主要模式，以及为什么它们对 Agent 比对人危险得多。

---

## 模式一：软屏蔽——2xx 但带内容标记

**实际触发特征**（基于 MiniMax 生产环境的实测，非推测）：

国产模型的内容审核系统在拦截请求时，不一定会返回 4xx 错误。有时它会返回正常的 HTTP 200，但在响应体的 JSON 里嵌入一个标记字段，比如：

```json
{
  "choices": [{
    "message": {
      "content": "",
      "input_sensitive": true
    }
  }]
}
```

或者：

```json
{
  "choices": [{
    "message": {
      "content": "",
      "output_sensitive": true
    }
  }]
}
```

**为什么这对 Agent 是致命的**：

人在看到空 `content` 时会立刻意识到出问题了。但 Agent 不做这个判断——它的下一个 API 调用是把整个 `messages` 历史塞进新的请求里，然后问模型"基于以上对话，下一步做什么"。

模型拿到一个包含空回复的对话历史，它的反应是不可预测的：
- 可能忽略空回复，继续正常推理（最好情况）
- 可能把空回复理解为"上一轮任务被拒绝了"，改变执行策略（中等危害）
- 可能基于空回复发展出一整条错误的推理链——因为它必须"说点什么"（最坏情况）

在无人值守的深夜长任务里，第三种情况足以让一个跑了两小时的任务静默偏航。

## 模式二：thinking 泄漏

**触发特征**（MiniMax M3 在 thinking=medium 模式下）：

国产模型（尤其是 MiniMax）在某些配置下会把内部推理链暴露在输出里。有两种形式：

**形式 A：` thinking` XML 标签包裹**

模型返回的流式 SSE 事件中，最先到达的不是正常的 `content`，而是一段包裹在 ` thinking... response` 标签里的推理草稿：

```
data: {"choices":[{"delta":{"content":" thinking"}}]}
data: {"choices":[{"delta":{"content":"我需要分析用户的请求..."}}]}
data: {"choices":[{"delta":{"content":" response"}}]}
data: {"choices":[{"delta":{"content":"这是最终回复..."}}]}
```

**形式 B：纯文本 "Thinking Process:" 草稿**

模型返回的第一个 `content` 值以 `"Thinking Process:"` 开头，后面跟着编号的推理步骤、一个"Final Polish"草稿区、以及一个 `"Looks good. Proceed"` 的自确认标记。标记之后才是真正的回复。

**为什么这对 Agent 危险**：

这些 thinking 内容**不是给客户端看的**。它们是模型内部的推理草稿——可能包含：
- 被模型自己推翻的推理路径
- 对用户指令的重新解读（有时是误读）
- 模型对自己能力边界的自我评估

如果 thinking 泄漏到对话历史里，下一轮 Agent 会把这段内容当成正常的对话历史吃进去。**而这段内容可能包含已经被模型自己否定了的判断。**

## 我怎么在 VMR 里处理这两个问题

先说清楚：**这些是上游厂商的行为，VMR 不能阻止它发生。** VMR 做的事是在网关侧**检测**和**修复**。

### 软屏蔽检测（当前：观测 → 未来：自动 failover）

VMR 在解析响应时，对已知的软屏蔽标记做内容检测。具体来说，它检查响应 body 里是否包含 `"input_sensitive":true` 或 `"output_sensitive":true` 这两个已知的 MiniMax 字段。

如果命中，会在审计记录的 `norm` 数组里追加 `"soft_block_detected"` 标记。这样你事后跑 `vmr report` 时，软屏蔽的发生次数和比例一目了然。

**当前状态**：仅观测打标，不自动 failover。Agent 仍然会拿到那个空回复。之所以先做观测不做 failover，有两个原因：一是流式路径下检测到软屏蔽时，前面的字节可能已经转发给客户端了，**技术上做不到撤回**；二是先积累一期真实数据，确认没有误判，再做自动 failover 才安全。

**后续计划**（P1）：非流式（buffered）路径下，把软屏蔽升级为自动 failover——VMR 检测到软屏蔽后，自动切换到下一个候选端点，Agent 完全不知道发生过什么。流式路径保持观测模式不变（技术上做不到 failover）。

### thinking 剥离（自动修复，有守卫）

对 MiniMax 的 thinking 泄漏，VMR 做了两套独立守卫：

**守卫一：XML 标签剥离**

检测 ` thinking` 标签的开启和闭合，在转发给客户端之前剥掉中间的内容。只触发当响应的第一个 content/text 值以 ` thinking` 开头——这是 MiniMax M3 thinking 模式的特有形状。正常回复中引用 ` thinking` 字样不会被误伤。

**守卫二：草稿段剥离**

检测 "Thinking Process:" 开头的草稿段落，定位到 "Looks good. Proceed" 自确认标记，把标记之前的所有内容都剥掉，从标记之后开始转发真正的回复。

**守卫失效时的保险**：如果上游某天改了 thinking 的格式，导致现有守卫匹配不上，VMR 会自动打一个 `thinking_process_pattern_detected` 观测标记，提示"有个 thinking 模式看起来像但 VMR 没拦截，该检查了"。其余内容原样通过——宁愿漏剥，不误剥。

## 为什么别的工具做不到这件事

翻译型网关（LiteLLM、claude-code-router 等）在处理响应时只关心一件事：**把响应从供应商的格式翻译成客户端期望的格式**。它检查 JSON 结构、字段映射、HTTP 状态码——**不检查 `content` 字段里的文本内容是不是模型真正的输出，更不检查有没有隐藏的敏感标记。**

要做到 VMR 这种级别的检测，需要两个前提：

1. **不翻译响应**——如果响应被翻译型网关重新序列化过，`input_sensitive` 这类字段可能在规范化过程中被丢弃或重排，软屏蔽标记就丢了
2. **两层完整记录**——你需要同时看到"上游实际返回了什么"和"客户端收到了什么"，才能在审计里标出差异

这两个前提都与翻译型网关的架构直接冲突。不是他们"没想到要检测"——是**他们的架构决定了他们看的是"翻译后的格式"，而不是"上游实际返回的原始字节"**。

## 最后说一句

这篇文章不是为了让你觉得"国产模型不行"——不是的。MiniMax / DeepSeek / GLM / Kimi 这些国产模型的性价比和中文理解能力是真的强，很多场景下比海外正价接口更合适。

问题是**这些模型生态里有一些独特的边缘行为**，而现有的工具链（无论是官方 SDK 还是第三方网关）基本没有针对它们做过适配。因为大多数工具是英文社区写的，开发者自己不用国产模型。

VMR 是我自己在用国产模型跑 Agent 的过程中长出来的。thinking 剥离和软屏蔽检测是**真的踩过坑然后修的**，不是看了文档猜出来的。如果你也在用国产模型跑 Agent，可以试试——如果遇到新的 quirk，提个 Issue，我会认真看。
