# 国产 LLM API 的隐藏成本——不是价格，是没人告诉你的那些边缘行为

> **版本**：v3（行业生态分析 / 评论式）
> **对标 v1**：`article-02-cn-softblock.md`
> **差异**：不从技术细节切入，而是拉高视角讨论国产模型 API 生态中的系统性缺口——软屏蔽、thinking 泄漏、私有字段——以及为什么现有工具链没有覆盖这些。VMR 只在最后三分之一出现，作为"有人在填这个缺口"的证据。
> **目标平台**：掘金、少数派
> **字数**：约 2000 字

---

如果你在用国产大模型跑 Agent——不管是 Claude Code 接 DeepSeek，还是 Cursor 配 MiniMax——你已经享受到了一件事：**价格。**

DeepSeek-V4 的 API 价格大概是 Claude Opus 4 的 1/30。MiniMax M3 更便宜。在 token 成本这个维度上，国产模型已经赢了。

但这篇文章想聊的不是价格。是那些**不体现在价格表上的成本。**

---

## 成本一：2xx 不等于成功

绝大多数 LLM 应用的监控逻辑是：HTTP 状态码 2xx = 成功，4xx = 客户端错误，5xx = 服务端错误。日志、告警、dashboard 都按这个分的。

国产模型打破了这个假设。

MiniMax 的内容审核系统在拦截请求时，返回的不是 400 或 403——而是 200，带一个 `"output_sensitive": true` 或 `"input_sensitive": true` 的内部标记。Body 里的 content 是空的。

对监控系统来说，这是一次成功的请求。对 Agent 来说，这是一次没有被感知到的失败——它拿到了一个空回复，把它当成了模型正常的输出，继续往下跑。

更隐蔽的是：这个行为**不是 bug，是设计如此。** 从厂商的角度，内容审核合规是比"让 Agent 跑对任务"更高优先级的需求。从 Agent 的角度——Agent 不在厂商的设计考虑范围内。

这种"成功状态码 + 实际拒绝"的模式，我称之为**软屏蔽**。它不是偶发的，是持续存在的。按我的实测数据，特定时段（凌晨 2-6 点）的软屏蔽率可以达到 1-2%。对于一天跑几千条请求的重度用户来说，这意味着每天有几十次"Agent 拿着空回复继续跑"的情况。

**现有工具链为什么没覆盖**：因为绝大多数 LLM 网关和 SDK 是英文社区写的——OpenAI、Anthropic、Google 没有"返回 200 但实际上拒绝了"这种行为。工具开发者没见过，自然不会去检测。

## 成本二：thinking 泄漏——模型的草稿纸混进了你的对话

MiniMax M3 在 thinking 模式下，会把内部推理链暴露在输出里——` thinking... response` XML 标签包裹的推理步骤，或者 "Thinking Process:" 开头的草稿段落。

这些内容包含：
- 模型对用户意图的重新解读（有时是误读）
- 模型推翻了自己的推理路径
- 模型对自身能力边界的评估（"这个问题我可能答不好"）

如果这些内容进入了对话历史，下一轮 Agent 会把它当成正常的上下文吃进去。模型再基于一个包含"我可能答不好"的对话继续推理——这是在给一个已经在自我怀疑的模型叠加压力。

**这不是翻译错误，是供应商行为。** 英文模型基本没有 thinking 泄漏问题（它们要么不暴露 thinking，要么通过专用的 reasoning_content 字段干净地隔离）。国产模型的 thinking 泄漏是中文开发者特有的问题——而英文社区的开发者不会为这个写修复。

---

## 成本三：私有字段——你的工具链在静默丢弃信息

`input_sensitive`、`output_sensitive`——这是 MiniMax 的私有字段。DeepSeek 有它自己的一套。千问有千问的。火山引擎有火山引擎的。

通用的 LLM 网关不认识这些字段。它们的工作方式是把请求和响应翻译成内部统一格式——这个过程里，不认识的字段被丢弃是常态。

这意味着什么？意味着你的网关看到的"成功响应"，和上游实际返回的"成功响应"，是两份不同的 JSON。上游那份里有一个 `output_sensitive: true` 的警告，网关这份里已经被规范化掉了。

**你用网关是为了增加可观测性，但网关本身在让你更瞎。**

---

## 这些成本的共同根源

这三个问题——软屏蔽、thinking 泄漏、私有字段丢失——有一个共同的根源：

**面向中国模型生态的中间件是缺失的。**

市面上所有主流的 LLM 网关和路由工具，设计目标都是"支持尽可能多的供应商"。要做到这一点，就必须有一个统一的内部格式。有了内部格式，就会丢失厂商特有的信号。

这不是某一个工具的缺陷——是整个生态的架构选择。翻译型网关选择了"广泛兼容"，代价是"深度感知"。

---

## VMR 做了什么不同的选择

我在写 VMR 的时候做了一个在别人看来可能很"蠢"的选择：**不翻译。**

VMR 没有内部格式。请求怎么进来的，就怎么转发给上游——只改一个 model 名字。响应怎么回来的，就怎么转发给客户端——只剥掉已知的 thinking 标签。

这个选择的代价是：VMR 不能"一个 API 打通 1000+ 模型"。它只能在相同的协议族内路由——OpenAI 协议的请求只能路由到 OpenAI 协议的供应商，Anthropic 同此。

**但这个选择换来的是**：

- 可以看到响应 body 里有没有 `output_sensitive: true`——因为它没有被规范化掉
- 可以剥掉 ` thinking... response` 标签——因为它在看原始字节
- 可以在审计记录里同时保留"客户端发了什么"和"上游收到了什么"两层——因为两者只差了 model 名字

这不是"VMR 做得更好"。这是"只有不翻译，才能看到这些东西。"

---

## 一个不成熟的想法

国产模型 API 的生态还在很早期。两年前大家还在讨论"能不能用"，现在已经在讨论"怎么稳定地用""怎么无人值守地用"。

当需求从"能不能通"进化到"能不能信任"时，工具链需要跟着进化。VMR 是朝这个方向走的一小步——一个专门面向 Agent 场景、对国产模型行为有深度感知的路由器。

它不是最快的，不是支持模型最多的，不是 star 最多的。但它是唯一一个在认真处理"国产模型返回 200 但内容是空的"这个问题的。
