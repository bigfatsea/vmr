# 给 Claude Code 装个黑匣子——那次凌晨失败，我能翻出上游收发的原始字节，还能原样重放

> **目标平台**：linux.do（首发）、V2EX（同日或次日）
> **叙事策略**：场景故事 → 问题 → 工具怎么解决 → 为什么别的工具做不到 → 安装
> **字数**：约 2800 字
> **前置条件**：D1 完成（预编译二进制 + vmr version）

---

上上周四凌晨三点，我的 Claude Code 挂了一次。不是那种"啪一下就报错停掉"的挂法，是那种更让人头大的：它对着一个空回复继续往下跑了。

我是第二天早上跑 `vmr report` 才知道的。那条审计记录里，`norm` 字段里有一个标记：`"soft_block_detected"`。某家国产模型供应商在凌晨时段悄悄把请求拦了——返回了一个 HTTP 200，但 body 里什么实质内容都没有，只带了一个 `"output_sensitive": true` 的内部标记。不是 429，不是 503，就是 200。

Claude Code 拿到了这个"空回复"，当成了模型的正常输出，基于它继续做下一步决策。整个任务在一条幻觉路径上跑偏了，跑了三个小时的任务前功尽弃。

这不是供应商的 bug——从他们的角度看，这是内容策略。但**从 Agent 的角度看，这比直接返回 5xx 更危险**。5xx 至少能触发重试或 failover，200 但内容被悄悄替换的"软屏蔽"，Agent 完全感知不到。

---

## 为什么会这样

Agent 的运行方式和人不一样。你看到模型输出了一句莫名其妙的话，会立刻意识到出问题了；Agent 只会把它当下一轮 context 吃进去，继续往前跑。**在无人值守的长任务里，一次软屏蔽足以让跑了几个小时的会话静默偏航。**

而大多数人——包括我——在配 Agent 的时候做的事很简单：把 `ANTHROPIC_BASE_URL` 指向某个中转/代理/路由器，填上国产模型的 API Key。完事。

问题出在中转那一层。市面上几乎所有的 LLM 网关都是"翻译型"的——它们把你的请求先翻译成内部格式，再翻译回目标供应商的格式。这个过程里，它们关心的只有一件事：**把请求正确翻译过去**。至于响应的 body 内容是不是模型真正的输出？不在设计范围内。

---

## 所以我给 Claude Code 装了个黑匣子

三周前我开始写 VMR（Virtual Model Router），一个专门为 Agent 场景设计的透明 LLM 路由器。它做的事说起来简单——挡在你的 Agent 和 LLM 供应商之间，记录每一层收发的原始字节——但这恰好是翻译型网关结构性做不到的事。

核心设计选择就一个：**永远不做翻译。**

- 不把 OpenAI 协议翻译成 Anthropic 协议
- 不把请求"规范化"成内部格式再还原
- 你的客户端发出的每一个字节——包括那些刚上线还没人有空适配的新参数——原样转发给上游
- 上游返回的每一个字节——包括那些文档里没写的行为——原样记录

只有两个例外：把虚拟模型名（你配置的 `coding`、`claude`）替换成真实的上游模型名；以及针对已知的厂商怪癖做守卫式修复。比如 MiniMax 的 M3 模型在 thinking 模式下会在输出前面塞一段 ` thinking... response` 的 XML 标签，VMR 会把它剥掉。**仅此而已。**

其余 99.9% 的字节，原样通过。

## 翻出那次凌晨三点的失败

回到那次软屏蔽。在 VMR 的审计日志里，那条请求记录的 `attempts` 数组长这样（简化）：

```json
{
  "ts": "2026-07-24T03:14:22+08:00",
  "model": "coding",
  "outcome": "ok",
  "attempts": [
    {
      "endpoint": "openai:minimax:MiniMax-M3",
      "status": 200,
      "norm": ["soft_block_detected"],
      "error_class": "",
      "response": {
        "body": {
          "choices": [{"message": {"content": ""}}]
        }
      }
    }
  ]
}
```

注意 `"norm": ["soft_block_detected"]` 这一行。VMR 在转发响应时，检测到了国产模型特有的软屏蔽标记（`"output_sensitive": true` 这类 JSON 字段），在审计记录里打了标。目前是观测模式——让你能从日志里翻出来——后续版本会把它升级为自动 failover（非流式路径），让 Agent 根本不拿到那个空回复。

**但最关键的还不是这个标记，是两层记录。** 审计里同时存了：
- `client.request.body`——客户端发给 VMR 的原始请求（除了 model 名改写，其余完全一致）
- `attempts[0].request.body`——VMR 发给上游的请求（只有 model 名被替换了）
- `attempts[0].response.body`——上游实际返回的响应（被记录了软屏蔽标记）
- `client.response.body`——VMR 转发给客户端的响应（和上游返回的完全一致，不翻译）

翻译型网关做不到这一点。因为它们把请求翻译了一遍再还原——存下来的要么是翻译前的版本，要么是翻译后的版本，不可能是"两个都原样存"。而 VMR 因为不翻译，两层记录天然就是完整的、可对比的。

**既然记录的是真实字节，就可以回放。** `vmr replay -ts "2026-07-24T03:14:22+08:00"` 能把那一次请求原样重发，看上游此刻返回什么。这对于排查"这个供应商是不是在某个时段悄悄改了行为"非常有用。

## 不只是查错：`vmr report` 读得懂 Agent

单条记录的两层对比是"黑匣子"的基础能力。但 VMR 不只是存原始数据——它还做了一层 Agent 特有的分析。

`vmr report` 把审计日志变成报表时，不是按时间排成一张大表，而是按**会话 → 任务 → 轮次**把请求分组：

```
Session 2026-07-24
  ├── chat_id=abc123 (1h22m, 💬22, 🛠️14, ⚡15.2s avg)
  │   ├── Turn 1     → 🆕 初始任务描述 → 模型输出 + 2 次工具调用
  │   ├── Turn 2     → 🆕 工具结果 + 模型继续 → 1 次工具调用
  │   └── ...
```

🆕 前缀标记的是**这一轮新增的请求内容**。你不用从头翻整个 conversation history，一眼就能看出 Agent 这一轮给了模型什么新信息。

还有一张**工具声明与实际调用对比表**：你的 Agent 配置里声明了 15 个工具，但过去 7 天有 3 个从来没被调用过。这意味着你也许可以把它们删掉，省 token。

通用日志分析工具（ELK / Grafana）能给你按 HTTP 状态码做饼图，但它不知道"这一行 JSONL 和那一行 JSONL 属于同一个多轮对话的同一个任务"。VMR 知道。

## 和 claude-code-router 比一下

我知道你在想什么："claude-code-router 36k star，你这个 2 star，凭什么让我换？"

实话实说：**CCR 是很好的工具，它在它的设计哲学里做到了最好。** 但它和 VMR 在根本设计上不同，而不是在同一维度上"谁更好"：

| | VMR | claude-code-router |
|---|---|---|
| 请求处理 | 字节级透传，不做翻译 | Transformer 插件改写请求 |
| 新参数 | 上游上线当天即可用，零改动 | 需插件适配 |
| failover | ✓ | ✓ |
| 请求日志 | ✓（两层完整字节） | ✓（元数据：provider/model/status/latency） |
| 成本估算 | ✓ | ✓ |
| **能翻出上游收发的原始字节吗？** | **能** | 不能——只记元数据 |
| **能把那次失败原样重放吗？** | **能** | 没有等价能力 |
| **能按 Agent 会话/任务/轮次分组吗？** | **能** | 按请求平铺 |
| 国产模型 quirk 修复 | 有（thinking 剥离、软屏蔽检测） | 无 |
| 安装 | 一个 Go 二进制文件 | npm（Node.js + dashboard） |

如果你关心的是"我的 Agent 昨晚跑了什么、花了多少钱、失败了几次"——CCR 能回答。如果你关心的是"**那次失败到底是上游收到了什么、返回了什么，我能不能复现那一刻**"——**只有 VMR 能回答。**

这两类问题需要的是深度不同的记录：一个是统计，一个是取证。前者很多工具能做，后者需要"不翻译"这个架构前提——而这个前提，所有翻译型网关都不会接受，因为它与"一个 API 打通 1000+ 模型"的产品承诺直接冲突。

## 装起来试试

```bash
# macOS
brew install bigfatsea/tap/vmr

# 或直接下载二进制（macOS / Linux × amd64 / arm64）
# https://github.com/bigfatsea/vmr/releases/latest

# 从配置样例开始
curl -o config.yaml https://raw.githubusercontent.com/bigfatsea/vmr/main/config.example.yaml
# 编辑 config.yaml，填上你的 API Key（支持 ${ENV} 语法）

# 校验配置 + 打印路由表
vmr check -c config.yaml

# 跑起来
vmr start -c config.yaml

# 把 Claude Code 的 base_url 指向 vmr
export ANTHROPIC_BASE_URL=http://127.0.0.1:8800
```

然后 Agent 该怎么跑怎么跑。VMR 在背后静静地记所有东西。过一天跑 `vmr report`，你会对"自己的 Agent 到底在做什么"有一个全新的理解。

**项目地址**：[github.com/bigfatsea/vmr](https://github.com/bigfatsea/vmr)

MIT 开源。单二进制，零数据库，零运行依赖。不 SaaS 化，不卖企业版。就是一个我自己每天在用的工具——觉得可能对你们也有用，所以发出来。
