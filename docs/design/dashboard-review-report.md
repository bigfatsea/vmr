# VMR Console 统一化 Demo — Dashboard 专项深度 Review

**评审对象**：`docs/design/console-unification.md`（评审时为草案 v3，现已随本报告定稿至 v5）与 `docs/design/demo/` 四页静态 Demo。
**评审视角**：系统运维人员 / 模型管理员 / 接入方开发者三类真实使用者的视线流、认知负荷与操作闭环。
**评审边界**：只动方案文档与 Demo HTML，不触碰 `internal/server/*.html`、`/status`、`/stats` 的任何实现。
**产出**：第一轮直接修改 27 项 + 10 项决策（已于 2026-09-10 全部拍板，见 §4.3）+ 第二轮复审 8 项（§5.2）+ 第三轮补充 4 项（Stage 6，其中两项推翻了评审自己的误判）。全部改动已落地到 Demo 与方案文档；系统代码未触碰。

业务前提（读完 LiveStats 设计文档后的心智模型，本报告全篇据此判断"什么重要"）：

- 路由半区的一次请求有**两层事实**——请求面（`vmodel/protocol/caller/outcome`，永远可观测）
  与服务面（`provider/key_label/model`、token、TTFT，仅转发成功时存在）。控制台的每一处
  聚合都必须让人看得出自己在看哪一层。
- 观测面也有两条：**完成时账本**（rollup + ring，回答"发生过什么"）与 **in-flight 注册表**
  （回答"现在正在发生什么"）。两者数字不重叠。Live 表是后者的唯一出口，一旦它失效，
  "现在"这一层就整个消失了。
- `client_key_tag`（谁发来的）与 `key_label`（打到了哪个账号的哪把 key）是两个**故意不统一**
  的概念，页面上必须并列、不得互相替代。
- `est_out` 在压缩响应体上**估不出来**，设计文档明写"展示为未知"；`ttft_ms=0` 是"未测量"
  不是"零延迟"。这类"未知 vs 零"的区分是数据模型的一等公民，UI 不许抹平。

### 1.2 评估维度与判据

| 维度 | 判据（不合格的具体形态） |
| --- | --- |
| **信息架构与逻辑流** | 首屏是否回答"忙不忙 / 量多大 / 烧多少 / 快不快 / 有没有坏"；长页是否有导航；同一问题是否被拆散在两处；不同问题是否被塞进同一列 |
| **数据密度与布局** | 是否有逐字重复的两块；高注意力区（Header 右、首屏、表首列）是否被静态或低价值信息占据；控件是否重复出现 |
| **可读性与可视化** | 数字是否自带窗口与单位；颜色是否只表达一种语义；图表选型是否匹配问题；未知与零是否可区分；长文本是否可控 |
| **微交互与状态** | 空/降级/未知态是否有设计；控件是否一控一义；hover 是否有反馈；浮层开合是否同手感；数据新鲜度是否可见 |

### 1.3 处置边界

- **直接修改**：事实清晰、方案确定、无业务争议——语义错误、颜色语义冲突、重复冗余、
  缺失的空/未知态、口径未标注、控件多义、文案过期、样式类缺失。
- **保留决策**：改变数据契约、改变行数量级、改变刷新架构、推翻已拍板的取舍、需要新采集点。

## Stage 3 — 全局汇总与查漏补缺

### 3.1 模块间是否割裂

**割裂点一：Quota / 拓扑 / Performance 三张表说的是同一批账号，却互不引用。**
`openrouter : backup` 在 Quota 表里是 98% 的 gate，在 Fallback 表里是 cooldown 端点，在
Performance 表里可能是错误率最高的一行——三处都在描述同一件事的不同侧面，但页面上没有
任何一条线把它们连起来。已用告警铃的措辞做了最低限度的因果串联（F22），完整的双向互指
需要读侧 join（**[D3]**）。

**割裂点二：完成时账本与 in-flight 之间有一段盲区。**
Live 表回答"正在发生"，Performance/Traffic 回答"这一小时/这一天的总量"。中间那个最常
被问的问题——"刚刚那条为什么失败"——在控制台上**无处可查**，只能去翻 `vmr analyze` 或
原始日志。这是本次评审发现的最大功能缺口（**[D5]**）。

**割裂点三：视觉层级争抢已修复。** 原 Demo 里 `Fallback Endpoints`（拓扑的子表）与
`Usage by Key Label`（顶级区块）用同一个内联 `fs-lg`，层级信息为零。现在 `.section-head`
与 `.sub-head` 两级明确，`.sub-head` 只给真正的子表。

### 3.2 核心监控心智在首屏是否有足够抓手

改动前，首屏（不滚动）能回答的问题只有：并发多少、请求总量、token 总量、进程占了多少内存。
"快不快"和"有没有坏"——监控台被打开的两个最常见理由——**一个都答不了**。

改动后五段 vitals 覆盖：忙不忙 / 量多大 / 烧多少 / 快不快 / 有没有坏。加上告警铃的可操作
计数与区块导轨的 Live 在飞数，首屏已构成一个完整的"是否需要深入"的判断面。

仍缺的一格是**趋势**：所有 vitals 都是标量，没有任何"比一小时前更糟了吗"的暗示。补迷你
sparkline 是可行的（`hourly[]` 已有数据），但会显著增加指标带高度，未单方面加入；如需，
建议与 [D1] 一并考虑。

### 3.3 高压排障场景推演

设想一个真实场景：**用户反馈"Claude Code 卡住了"**。

| 步骤 | 改动前 | 改动后 |
| --- | --- | --- |
| 1. 打开控制台，判断是否普遍问题 | 首屏无延迟无健康，需滚到中部 | 首屏 TTFT + Endpoints 直接判断 |
| 2. 看告警 | 铃铛常年非零（滚动指标），信噪比低 | 铃铛只有可操作项，第一条就是 cooldown 端点 |
| 3. 定位"是哪一条卡住" | 滚到 Live 表 → 诊断列在第 7、8 位 → 5 分钟前的快照，多半已经不是那条 | 列序对齐诊断路径；stall 与排队积压都有明确形态。**但刷新节奏仍是致命短板**（[D1]） |
| 4. 判断"从什么时候开始的" | 唯一的时间序列不画错误，看不出来 | 图上红点标出含错误的桶，tooltip 给错误率 |
| 5. 判断"是哪个账号/上游" | Performance 表可看，但 basis 切换会让计数一起变，容易误判 | 计数与分位分离，err 着色 |
| 6. 判断"刚刚那条具体报了什么" | 无处可查 | **仍然无处可查**（[D5]） |

结论：六步里第 3 步与第 6 步仍是断点，且都需要主理人拍板——它们是本次评审留下的两个
最重要的开放项，其余四步已在本轮闭环。

## Stage 4 — 最终审批意见与整改汇总

### 4.1 宏观定性与核心系统性问题

现有设计的**骨架、视觉语言与技术取舍都是对的**：暗色科技感克制而专业，零依赖纯 SVG 图表、
单文件自包含、令牌化设计系统的方向没有问题。真正的问题不在"不好看"，而在四条系统性的裂缝：

1. **UI 语义与数据模型脱节。** LiveStats 设计文档花了大量篇幅区分"未知 vs 零"、"累计 vs 环形
   窗口"、"字节 vs token"、"请求面 vs 服务面"，而 UI 层把这些区分统统抹平了：`est_out` 未知
   渲染成 `0`，窗口口径切换时整表数字跳变却一字未提，`first_byte_at` 被叫做 "First Tok"。
   **一个把数据模型的核心区分抹掉的 dashboard，会让人做出错误判断**——这是本次评审中最
   严重的一类问题，也是直接修改项里占比最高的一类。

2. **颜色通道被复用，健康语义被稀释。** 红/黄/绿在这套 UI 里同时承担了健康度、限额角色、
   优先级层级三种含义。最刺眼的表现是一个 13% 用量、headroom 2.33 的健康账号顶着红徽章。
   监控台的颜色只有一个正当用途：告诉人"要不要动手"。

3. **高注意力区被低价值信息占据。** Header 右侧最显眼的位置给了永不改变的版本号与 pid；
   首屏五分之一的指标位给了下一行马上要重复一遍的 heap；Live 表的第二列给了纯内部引用号；
   区块标题给了只在读到某两列时才需要的公式。**每一处都不算错，但加在一起，用户要穿过
   一层静态噪声才能摸到会变的东西。**

4. **"实时"是名义上的。** in-flight 注册表在实现上做了逐块盖章、刻意不节流的设计，理由是
   "卡死检测全靠末块与当前时刻的差值"。而 UI 层用 5 分钟一帧去消费它——这个刷新节奏让
   底层最讲究的那部分设计**完全无法兑现**。这不是 UI 细节，是产品定位问题，因此列为
   第一优先级决策项而非直接修改。

## Stage 6 — 第三轮补充（2026-09-10 收尾）

三条补充意见推翻了此前两处判断，都是评审侧读错了产品意图，纠正如下。

### 6.1 P1 — 吞吐指标：删的是重复，不是能力

**评审的错误**：把 S4 理解成"删掉所有吞吐口径"，于是连 vitals 的 `tps` 也一并去掉，
得出"控制台不再有任何吞吐指标"的结论。**真实意图是 TPS 与 Tok/s 两列重复，只删 TPS。**

**已改**：`Tok/s p50 / p90` 回到 Performance 表，vitals 的 TTFT 段副行同步恢复 `tok/s p50`。
留下 Tok/s 而非 TPS 的理由写进方案：名字自解释，口径也更完整（四分量总和 ÷ 整请求时长，
含输入摊销）；TPS 那种"流式剔除首块等待"的细分，价值已由旁边的 `TTFT` 列单独承担。
§5.3 里那条"建议做成 TTFT 列的悬停行"随之作废——不需要折中了。

### 6.2 P3 — Performance 的 Req 本就是窗口内计数

**评审的错误**：读 `by_provider_model[]` 的"累计"字样，判定第一轮 Demo 的"切 basis 计数
跟着变"是语义错误，并把它改成了固定累计量（F42/A2）。**真实意图是整表就该跟着窗口走**：
`Req` 显示窗口内的实际请求数，正因为**它常常不满 100**——那个数字本身就是窗口填充度的
信号；而 ok/err 的分布要看的是"最近一段时间的状态"，不是被时间稀释过的历史存量。

**已改**：整表统一到所选窗口——计数、token 求和、TTFT 与 Tok/s 分位全部同源同窗，
行内不再混两个时间基。控件标签从 `percentile basis` 改回 `window`，区块副标题写明
"Req also shows how full it is"。P3 那条"两个窗口混用"的问题随之自然消失。

**这带来一处必须登记的数据模型影响**（已写进方案的实施清单）：ring 条目要从
`(ts, dur_ms, ttft_ms, tokens.out)` 拓宽为
`(ts, dur_ms, ttft_ms, outcome, tokens{in,out,cache_read,cache_write})`，并且
**ring 必须接纳 error 样本**——没有 `outcome` 就算不出窗口内的 ok/err 分布，没有四分量
就既算不出 Tok/s 也算不出窗口内的 token 求和。分位数计算仍只用 ok 样本。
代价是每键 100 条 × 4 个额外 int64，量级可忽略。**这条与 LiveStats 现行的"ring 只收
`outcome=ok` 且已转发的样本"直接冲突，实施轮必须同时更新那份文档**——只改代码会让
下一个读设计文档的人把它当成 bug 重新提一遍。

### 6.3 传输方式：图标换回文字列

**问题**：第一轮把 stream/json 做成了闪电与文档两个 SVG 图标，理由是"值得一个标记但不
值得一列"。实际效果是读者必须先学一遍图例才能读表——而这是一个只有两种取值的分类维度，
省下的那点宽度换来了永久的解码成本。

**已改**：Performance 表加**独立 `Mode` 列**，文字标签 `stream`（青）/ `json`（灰）。
Live 与 Recent Failures 的 Model 单元格里也一并换成同样的文字标签——同一个概念在三处
用同一套词，不因为"那两处不是分组键"就换一种表达。

### 6.4 P5 — `First / Last Byte`

列名跟随底层字段 `first_byte_at` / `last_byte_at`。理由回到最初那条：同一张表里
`Tok in` / `Tok out` 装的是真 token 计数，两个词必须各归各的。方案的决策记录表同步改写。

### 7.1 Performance 表：Requests 只有一个数

| `traffic.tokens.total` 是**五分量**（含 `reasoning`），页面按四分量理解会对不上 | 对照表里点名，页面须写死总量与 cache 分母的口径 |
| `modelStatus.protocol`、`capabilities`、`max_context_tokens` **现网早就有了**，前几轮的实施清单在重复要求 | 从清单里删掉，避免实施时白做一遍 |

### 7.3 一处需要回看的：Quota 的 `estimated_pct`

第二轮按指令删掉了 Quota 的 `est +2.10% in flight`，理由是"简化计算"。对账时发现
**这个理由不成立，而且当时对该字段的描述是错的**：

`/status` 的 quota 行早就有 `estimated_pct`，它的语义不是"在飞请求的预估增量"，而是
**这一周期的消耗里有多少来自降级的字节数估算、而非上游真实上报的 usage**——也就是
"`Used` 这个数你能信几分"。它已经算好了，取用零成本，删掉省不下任何计算。

按指令保持删除状态，但登记在这里：如果要回补，正确的形态是挂在 `Used` 上的一个数据
质量标记（仅在非零时出现），而不是第二轮那个被误标成"in flight"的百分比。
