# VMR 审计日志压缩与保留策略 — 分析报告

> 任务性质：分析与方案设计，不含实现。
> 输入：`internal/audit/audit.go`、`internal/report/*`、设计文档 §9，以及本机 `logs/` 目录下的真实审计数据（27~30 条记录/文件，实测而非模拟）。

---

## 一、Debrief

**表面诉求**：审计日志单行记录（一次 Agent 请求）体积大（用户描述约 2MB/行，实测环境约 30 万~230 万字节/行），单日文件可达 1~2GB，希望分层压缩：① 单条记录编码压缩（用户提议 base64 / zip+base64）；② 历史文件整体再压缩；③ 超过保留期（如 30 天）自动清理，且不want要"反复扫描磁盘"。

**背后的真实诉求**（我的理解，供校验）：不是单纯"把字节数变小"，而是**磁盘占用长期可控 + 零运维负担 + 不破坏审计契约**。三个约束缺一不可：

1. 不能牺牲设计文档 §9.2 已经立下的契约——审计日志是 `vmr report` 的唯一数据源，且明确设计为"可直接用 jq 查询"（如 `.client.response.body.usage`）。压缩手段如果让当前正在写入的文件变得不可读/不可查，等于破坏了这条契约。
2. 不能影响请求服务热路径——§9.1 已明确"写盘失败仅打日志，绝不影响请求服务"，压缩同理：只能在**不写入中**的历史文件上做，不能挂在每次请求的写路径上。
3. 自动化机制要"廉价且不新增运维实体"——不引入外部 cron/logrotate 依赖（vmr 定位是单二进制自包含工具），也不做全盘扫描；理想是复用已有的每日轮转边界作为触发点。

结论先说：**用户提议的"第一层"（单条记录 base64/zip 压缩）经实测验证是收益最低、代价最高的一层，建议不做**；真正的大头在"第二层"（历史文件整体压缩），且效果远超直觉——下面用本机真实数据说明原因。

---

## 二、实测：现状与根因

### 2.1 现有实现（`internal/audit/audit.go`）

- 每天一个明文 JSONL 文件（`vmr-audit-YYYY-MM-DD.jsonl`），`Logger.Write` 在检测到日期变化时切文件，此前无任何压缩/清理动作。
- 每条 Record 内，`client.request.body`、`client.response.body` 与**每个 attempt 各自的 `request.body`**都是完整 JSON 原样内嵌（§9.2 约定 1：仅成功尝试的 *response* body 去重，*request* body 不去重）。对无 failover 的请求（多数情况），这意味着"整段对话历史"在同一行里至少完整出现两次（client 层 + 唯一 attempt 层），只是 `model` 字段被重写——这是记录本身偏大的第一个放大因子，与压缩无关，是数据模型层面的冗余（见 §5 的"额外发现"）。
- 真正的体积主因：Agent 场景下，每一轮请求都会把**完整对话历史**（含之前所有 tool_use/tool_result、系统提示词、工具 schema）重新发一遍——这是 LLM 无状态 API 的固有特征，不是 vmr 的问题，但意味着**同一个会话里，相邻甚至相隔很远的日志行之间存在海量逐字节重复**。

### 2.2 本机真实数据

```
logs/vmr-audit-2026-07-07-1.jsonl   27 行   8,503,497  字节   均值 314,944 字节/行
logs/vmr-audit-2026-07-07-2.jsonl   30 行  11,628,663  字节   均值 387,622 字节/行
logs/vmr-audit-2026-07-08.jsonl     20 行   8,004,005  字节   均值 400,200 字节/行
全部 77 行合并分布：min 689B　p50 289,869B　p90 714,952B　max 2,319,660B
```

单行最大值 231 万字节，已经摸到用户描述的"2MB/行"；这批是本机测试数据，量级比生产环境小，但分布形态足够代表问题。

**排除了一个假设**：抓取全部日志搜了 `data:image` / `"type":"base64"` 图片 source 特征，**未命中**；`base64` 字样命中的 1380 处逐一抽样后确认是 Agent 对话内容本身在讨论"如何用 base64 编码 model 字符串"（业务文本），不是内联图片。也就是说，**这批数据里体积大的原因是纯文本的对话历史累积，不是二进制图片膨胀**。这排除了"图片是主因"的猜测，但因为设计文档 §7 明确 vmr 支持内联图片请求（vision），生产环境如果大量使用视觉能力，base64 图片仍可能是另一个独立的体积因子——文本压缩对已压缩的 JPEG/PNG 字节基本无效（详见 §5）。这一点无法用当前样本验证，建议后续用 `grep -c '"type":"base64"'` 或按 `media_type` 字段在生产日志上抽样确认。

### 2.3 关键实验：压缩粒度决定压缩比，差距不是线性的

用真实文件做了四组对照（`vmr-audit-2026-07-08.jsonl`，8,004,005 字节）：

| 压缩方式 | 结果字节数 | 压缩比 | 说明 |
| --- | --- | --- | --- |
| **逐行独立 gzip -9**（模拟"第一层"：每条记录单独编码） | 2,390,217 | **3.35×** | 每行只能利用行内重复，看不到跨行重复 |
| 整文件 gzip -9（32KB 滑动窗口） | 2,378,491 | **3.37×** | 窗口太小，看不到相隔较远的重复段——几乎等于逐行压缩，白白浪费了"整文件"这个机会 |
| 整文件 zstd -19（默认窗口） | 107,044 | **74.8×** | 默认窗口已经覆盖了本文件里绝大多数的跨行重复 |
| 整文件 zstd -19 --long=27（128MB 长距匹配） | 106,912 | **74.9×** | 与默认窗口几乎无差，说明本文件重复距离已在默认窗口内；生产环境单日文件更大（1~2GB）时 `--long` 会成为必需项 |
| 整文件 xz -9（对照组，非候选） | 101,572 | 78.8× | 比 zstd -19 略高一点点，但压缩耗时明显更长（下方有耗时对比），且 Go 没有成熟的纯 Go 实现 |

另外两个文件同口径下分别是 **36.3×**（07-07-1）和 **21.3×**（07-07-2，压缩比最低的一份，说明其内部请求间差异更大，仍远超 gzip）。

**这组数据是本报告最核心的结论**：压缩比的天花板不取决于算法本身，而取决于**压缩窗口是否覆盖了重复内容的间距**。gzip 的 32KB 窗口在"单条记录动辄 30 万~200 万字节"的场景下，跨记录重复根本看不见——不管是逐行压缩还是把整个文件丢给 gzip，效果几乎一样（3.3× vs 3.4×）。而 zstd 默认窗口就已经是几 MB～上百 MB 量级，天然覆盖了这种"每轮对话重发一遍历史"的重复模式，压缩比直接跳到两位数甚至更高。

**推论**：用户提议的"第一层"（单条记录 base64 或 zip+base64）无论算法多好，天花板就是 3.3× 左右（因为它的可见范围被"一条记录"这个边界锁死了），而且：

- base64 本身不是压缩，是编码——**单独使用体积会增大 33%**，这是用户提案里需要先澄清的认知偏差。
- zip（DEFLATE）+ base64：先压缩后编码，净效果约 (1/3.3)×1.33 ≈ 40% 的体积，即约 2.5× 的"净压缩比"，仍然远低于整文件 zstd 的 20~75×。
- 额外代价：破坏了 §9.2 "合法 JSON 原样嵌入，可直接 jq 查询"的设计契约（`.client.response.body.usage` 这类查询会失效，得先解压才能查）；且压缩发生在写路径上（每次请求都要压缩一次），需要评估对延迟的影响——即便异步也增加了实现复杂度。

**结论：不建议做用户提议的"第一层"**，收益（相对已有裸文本）有限，代价（可查询性、写路径复杂度）不小。真正高杠杆的动作是"第二层"：对**已经轮转完毕、不再写入**的历史文件做整体长窗口压缩。

### 2.4 耗时验证（确认后台压缩不是负担）

对 11.6MB 文件（当前最大样本）计时：

| zstd 级别 | 耗时 | 压缩后大小 | 压缩比 |
| --- | --- | --- | --- |
| -3（快速） | 0.013s | 709,393 | 16.4× |
| -9（默认附近） | 0.026s | 624,940 | 18.6× |
| -19（最高，含 long） | 0.589s | 546,472 | 21.3× |

线性外推到用户描述的 1~2GB/日文件，`-19` 级别一次性压缩耗时约 **90~180 秒**，且是**后台、每天一次、不在请求路径上**的任务——对一个 ≤3 人团队的自用/小规模部署完全可以接受。即便追求更保守的 CPU 占用，`-9` 级别 180 分之一的耗时也仍能拿到接近的压缩比（18.6× vs 21.3×），是一个合理的兜底选项。

## 三、方案设计（对齐用户提出的三层，逐层给出建议）

### Layer 0（额外发现，未在用户诉求中，但同源且低成本）：记录内部去重

当前一条记录里，`client.request.body` 与该请求唯一一次 attempt 的 `attempts[0].request.body` 几乎是同一份大文本（只有 `model` 字段被 Adapter 重写）。这是数据模型层面的冗余，与"压缩算法"无关，属于"少写一份"而不是"压缩已写的"。

- **建议**：仅在"单 attempt 且 body 与 client 层字节相同（模去掉 model 字段重写）"时，attempts 层不重复存 request body，只记一个引用/差异标记（类似现有"成功尝试的 response body 不存"的既有约定，§9.2 约定 1）。多 attempt（failover）场景各自 body 可能不同（不同 endpoint 的 quirk 改写），仍需各自保留。
- **影响面**：改审计 schema（`Attempt.Request` 变为可选 + 一个 `same_as_client: true` 标记），设计文档明确"改 §9.2 必须同步改 `internal/report`"——这是一个比压缩本身更小但仍需谨慎的改动，且是**唯一需要动审计写入格式**的部分。
- **定位**：可选加分项，不是本轮必须；如果做，收益是"源头减少约 40~50% 的原始体积"（无 failover 时两份大体几乎变一份），与下面的 Layer 2 压缩是乘数关系（源头减半 + 压缩 20~70×，联合收益更大）。

### Layer 1（用户提议的"单条记录压缩"）：**不建议做**

理由已在 §2.3 用实测数据说清楚：天花板低（~2.5-3.4×）、破坏 jq 可查询契约、增加写路径复杂度。如果未来确有"单条记录也要能独立解压查看"的强需求（比如要对接某个只能读单行的外部系统），可以再单独评估，但不是当前问题的高杠杆解法。

### Layer 2（历史文件整体压缩）：**建议做，是本方案的核心**

**触发时机**：复用 `Logger.Write` 里已有的"日期变化即轮转"判断（`internal/audit/audit.go:184-195`）——发现 `date != l.date` 时，除了开新文件，额外对**刚刚关闭的旧文件**（不是当前正在写的）起一个后台 goroutine 做压缩。零新增定时器/轮询基础设施，天然与现有轮转边界对齐，符合用户"不要反复扫描磁盘"的要求（本来就只在日期变化那一刻触发一次，不是周期性扫描）。

**算法选型**：zstd，级别 19（或退而求其次用 9，见 §2.4 耗时权衡）。

- Go 标准库只有 `compress/gzip`（DEFLATE，32KB 窗口），从 §2.3 数据看直接淘汰——用它压缩整文件跟逐行压缩没有本质区别。
- 需要引入 `github.com/klauspost/compress/zstd`：纯 Go 实现、无 cgo、社区广泛使用（Docker、Prometheus 等项目depend），支持长距离匹配（`--long` 对应的 `WithWindowSize`/`WithEncoderConcurrency` 等选项）。这是**唯一需要新增的第三方依赖**。
- 对照设计文档 §11 的既有取舍（"不用 Provider SDK"是针对厂商 SDK 的膨胀与版本纠缠，不针对通用编解码库；项目已经引入 `golang.org/x/image` 处理 WEBP/BMP 解码，属于同类"必要功能 stdlib 没有，选一个成熟无 cgo 库"的先例）。klauspost/compress 不是官方 x/ 包，是社区库，这点如实告知——如果团队对"新依赖"有更高门槛，这是需要用户确认的点（见 §六）。
- **不选 xz/lzma**：压缩比只比 zstd -19 高约 5%（§2.3），但 Go 没有成熟无 cgo 的实现，压缩/解压都明显更慢，性价比不如 zstd。
- **不 shell out 到系统 `zstd`/`gzip` 二进制**：会破坏 vmr"单二进制自包含"的定位（§1），且用户环境不一定装了这些工具。

**工程细节（下一轮实现时需要覆盖）**：

1. **原子性**：压缩到临时文件（`.zst.tmp`）→ fsync → rename 覆盖最终名 → 确认 rename 成功后再删除原始 `.jsonl`。任何一步失败都保留原文件，仅打 stderr 日志——与现有"审计写失败不影响服务"的容错哲学一致。
2. **不碰当前文件**：只处理文件名日期严格早于"今天"的 `.jsonl`（且尚未有对应 `.zst`）——不会跟正在写入的 Logger 竞争。
3. **`vmr report` 透明读取**：`internal/report/report.go` 的 `Build` 目前用 `os.Open` + `bufio.Scanner` 直接读文件；需要按扩展名（`.zst`）分支，用 `zstd.NewReader` 包一层再喂给 Scanner。这样历史压缩文件和当天明文文件可以混在同一次 `vmr report 'vmr-audit-*.jsonl*'` 调用里，用户不需要手动解压。这是让 Layer 2"落地可用"的必要配套，不是可选项。
4. **CPU 优先级**：后台 goroutine，不设置特殊调度优先级即可（§2.4 已证明耗时在分钟级以内，且一天只发生一次）；如果部署在资源紧张的小机器上，可以把级别配置为可调（复用 §四 提到的新配置项思路）。

### Layer 3（保留期自动清理）：**建议做，与 Layer 2 共用同一个触发点**

**核心洞察**（回应用户"不希望反复扫描磁盘"的顾虑）：审计文件名自带日期（`vmr-audit-YYYY-MM-DD(.jsonl|.jsonl.zst)`），清理逻辑不需要 `stat` 每个文件、不需要遍历内容，只需要**列一次目录**（`os.ReadDir`，单次 O(保留天数内的文件个数)，不是 O(磁盘全量) ）、从文件名解析日期、和"今天 - 保留天数"比较。这跟"扫描磁盘"是两回事——用户担心的是周期性、开销随磁盘增长的扫描；这里是**一次性、开销只随"保留天数"增长**的目录列举，哪怕保留 90 天也就是 90 个文件的 `Stat` 级别开销，微秒级。

**触发时机**：与 Layer 2 同一个钩子——`Logger.Write` 检测到日期变化时，顺带跑一次清理（列目录 → 找出超过保留期的文件名 → 删除）。不需要独立的 `time.Ticker`，不需要新的 goroutine 生命周期管理，天然每天恰好执行一次。

**配置**：新增 `audit_retention_days`（int，缺省 **0 = 不清理**）。**默认关闭**是刻意的产品判断：审计日志是 `vmr report` 成本核算的唯一数据源，静默按 30 天删除对没有仔细看文档的用户是数据丢失风险（对照操作准则里"hard-to-reverse operations 默认要确认"的精神）；由用户显式设置天数后才启用，比"预设一个看似合理的默认值"更安全。这一点会在 §六 向用户确认。

**安全细节**：只删除严格早于阈值、且文件名能被正确解析为日期的文件（解析失败的文件名一律跳过，不误删非审计文件）；删除前记 stderr 日志（文件名 + 释放的字节数），保持"控制台可核对"的既有原则（呼应设计文档里"启动摘要"一节的可观测性偏好）。

## 四、行业最佳实践对照

用户提议的三层结构，与几个成熟系统的日志生命周期管理几乎一一对应，说明这个直觉是对的，不是重新发明轮子：

| 系统/工具 | 对应层次 | 做法 |
| --- | --- | --- |
| `logrotate`（Linux 经典方案） | Layer 2 + 3 | 按天/按大小轮转，`compress`（默认 gzip，可换 zstd）延迟一个周期再压缩（`delaycompress`，避免压正在写的文件），`maxage N` 按文件名/mtime 清理 |
| `systemd-journald` | Layer 2 + 3 | 内建 LZ4/zstd 压缩（journal 文件级，非逐条），`MaxRetentionSec`/`SystemMaxUse` 控制总量与期限 |
| Elasticsearch/OpenSearch ILM、Grafana Loki | Layer 2 + 3（更精细：多级） | Hot（可写，不压缩）→ Warm（只读，压缩）→ Cold（更高压缩比，慢存储）→ Delete（过期删除）；本质是"新鲜数据保持易查，老数据牺牲部分访问速度换空间"的同一套哲学 |
| Nginx/Apache access log | Layer 2 + 3 | 同 logrotate，行业标配 |

**共性结论，也是本报告方案的依据**：几乎没有系统在"单条日志记录"粒度做压缩（对应用户的 Layer 1）——都是在"文件完成写入、进入只读阶段"这个边界上做整体压缩，原因与 §2.3 的实测完全一致：日志的可压缩性主要来自跨记录冗余，只有文件级压缩窗口能吃到。这进一步印证了"跳过 Layer 1，把工程精力放在 Layer 2/3"的判断。

## 五、方案之外的两个提醒

1. **图片 payload 是独立变量，文本压缩救不了它**：如果生产环境大量使用 vision 能力（§7 图片降采样功能的存在说明这是真实场景），内联的 base64 图片本身是"已压缩二进制的文本表示"——通用文本压缩算法（gzip/zstd/xz 皆然）对它几乎无效（JPEG/PNG 本身熵已经很高），甚至因为 base64 打乱了字节对齐，压缩比可能比对纯文本更差。**这是一个和"文本冗余压缩"完全不同性质的问题**，如果生产日志证实图片是体积大户，需要的是独立的杠杆（例如审计层可选择性截断/摘要图片 body，只留哈希+尺寸，牺牲"事后能看到图片原图"换空间），而不是指望换个压缩算法解决。建议先在生产日志上用 `grep -c '"type":"base64"'` 或统计 `media_type` 字段确认占比，再决定要不要做。
2. **保留期设置要覆盖账期**：Layer 3 的清理是不可逆操作，一旦触发没有恢复路径。设默认值前建议先想清楚"多久做一次成本核算/对账"，保留期至少要覆盖这个周期（比如按月对账就至少保留 35~40 天），避免清理跑在对账之前。

## 六、待确认事项（下一轮实现前需要用户拍板）

1. **是否接受引入 `github.com/klauspost/compress`（zstd）这个新依赖？** 这是 Layer 2 唯一绕不开的技术选择——stdlib 的 gzip 经实测不可用（§2.3），不引入压缩库就做不了长窗口压缩。
2. **`audit_retention_days` 默认值**：建议缺省 0（不清理，需用户显式设置），是否同意？如果同意，生产环境希望设成多少天（需覆盖你的对账周期）？
3. **是否需要 Layer 0（记录内部去重，client body 与单 attempt body 合并存储）？** 这是唯一会改动审计 *写入* schema 的部分，收益是源头减少约 40~50% 原始体积，代价是要同步改 `internal/report` 的读取逻辑（设计文档 §9.4 的强耦合约定）。可以作为独立任务单独排期，不阻塞 Layer 2/3。
4. **压缩级别**：zstd -19（更优比例，单日耗时约 1.5~3 分钟量级）还是 -9（耗时降到几秒，压缩比略降约 10~15%）？建议默认 -19（后台任务，时间不敏感），但如果部署机器 CPU 资源紧张可以做成可配置项。

以上四点里，1、2、4 若不特别指出偏好，我倾向按报告里的建议（引入 klauspost/compress；retention 默认 0；级别 19 可调）直接推进；3（Layer 0）因为改动审计 schema、影响面更大，建议单独讨论是否要做、什么时候做。
