## 1. 问题定义与优化目标

### 1.1 目标函数
在多订阅与混合采购场景下，团队通常持有若干按周期计费的套餐账号（Token-Plan / Coding-Plan），外加低优先级的按量计费端点。套餐额度**周期性作废、不结转**。调度优化的目标是：

$$\text{最小化浪费} = \sum (\text{周期结束时未用完的套餐额度}) + \sum (\text{套餐用尽后溢出到按量计费的花费})$$

**核心命题是“配速（Pacing）”，而非“负载均衡”**：
负载均衡试图在时间轴上均分请求压力；而配速是在“各套餐周期到期前，恰好平滑将其烧完”。由于各账号购买时间不同、重置日天然错开，传统的存量指标 $\frac{\text{remaining}}{\text{total}}$ 会产生系统性反向调度（将流量大量分给刚重置但周期充裕的账号，而饿死数天后即将过期作废的账号）。

### 1.2 核心现实特征
1. **双重物理计量单位**：请求次数（`requests`）与 Token 消耗（`tokens`）。
2. **多层限额窗口并存**：单一账号可同时受短期速率限制（如 5h、1min）与长期账单周期（如月度总量）约束。
3. **非均一折算规则**：不同模型的扣费倍率各异，输入、输出及缓存读写四分量的折算比例差异显著。

## 2. 额度模型与计费规则

额度模型抽象为自包含的 **Limit 规则实体**：

```yaml
# 单条 Limit 规则语义
metric: requests | tokens     # 计量单位：请求次数 或 Token 总量
every: 1mo                  # 周期长度（如 1min, 5h, 1w, 1mo）
since: "2026-01-01"         # 周期锚点（可选，缺省自动对齐日历边界）
amount: 1000000               # 窗口内上限（基于网关可观测口径）
models: [claude-3-5-sonnet]   # 适用模型（缺省共享，["*"] 为各模型独立池）
token_weights:                # 四分量折算权重（仅 tokens 有效，缺省全 1.0）
  in_fresh: 1.0
  cache_read: 0.1
  cache_write: 1.25
  out: 5.0
model_multipliers:            # 模型倍率字典（支持 "*" 兜底，缺省 1.0）
  claude-3-5-sonnet: 2.0
```

### 2.1 单次扣减公式
单条 Limit 的扣减量为：
$$\text{charge}(L) = \text{base}(L.\text{Metric}, L.\text{TokenWeights}) \times L.\text{ModelMultipliers}[\text{model}]$$

其中：
* 当 $\text{Metric} = \text{requests}$ 时：$\text{base} = 1$；
* 当 $\text{Metric} = \text{tokens}$ 时：$\text{base} = \sum_{c} \text{tokens}_c \times \text{TokenWeights}[c]$，分量遍历净输入（$\text{in\_fresh} = \text{in} - \text{cache\_read} - \text{cache\_write}$）、缓存读取、缓存写入与输出。

### 2.2 扣减边界与口径
* **触发点**：仅在响应转发成功（HTTP 状态码 `< 400`）时扣减一次；传输途中流式截断（已有字节交付）亦计入扣减。
* **零扣减场景**：上游全部失败的请求不扣减任何账号；Failover 链中仅最终成功的端点计费。
* **精度**：计数器全链路采用 `float64` 累计，避免整型离散化累加阶梯偏差。
* **存储语义与折算时机**：`Counters` 只存原始计数与四分量，`token_weights` 均在**读取侧动态套用**（热重载修改权重不会使已累计历史失效）；而 `model_multipliers` 则是唯一的例外，在**计费那一刻预乘**进计数器（因账本按 Provider 聚合，计费后模型维度信息丢失）。因此，配置了模型倍率的账号，其计数器存储的已是加权后的“等价单位”。

### 2.3 价格与控制面解耦
路由核心**不感知、不消费任何货币价格（Price/Cost）数据**。
金额或 Credits 制套餐统一通过单价换算为固定 Token 额度。价格解析完全下沉至离线分析半区，杜绝实时路由决策链随动态价目表漂移。

## 3. 核心算法：Headroom（配速评分）

### 3.1 无量纲余量比
对每条 Limit 规则计算瞬时配速分数：

$$\text{used\_frac} = \min\left(1, \frac{\text{used}}{\text{amount}}\right)$$
$$\text{time\_left\_frac} = \frac{\text{time\_left}}{\text{duration}}$$
$$\text{raw} = \frac{1 - \text{used\_frac}}{\max(\text{time\_left\_frac}, \epsilon)}$$

**物理含义**：
* $\text{raw} = 1$：严格按线性进度消耗；
* $\text{raw} > 1$：欠用（消耗落后于时间流逝），应主动优先调度以防过期浪费；
* $\text{raw} < 1$：超前（消耗快于时间流逝），应降低调度优先级；
* $\text{raw} = 0$：额度已耗尽。

**核心性质**：
* **跨量纲归一**：次数制与 Token 制账号可直接在同一坐标系内比较。
* **自稳定比例控制**：分子分母随消耗与时间同比例缩小，稳态值恒为 1，无需人工整定控制参数。
* **重置日错位免疫**：自动向临近过期且余量充沛的账号倾斜最高权重。

### 3.2 桶（Bucket）与闸（Gate）双角色体系
多 Limit 并存时，系统按其经济学本质划分角色并合成最终评分：

| 角色 | 判定标准 | 职能与调度行为 |
| --- | --- | --- |
| **桶（Bucket）** | 周期最长的固定对齐（Tumbling）规则 | **计费目标**。遵循过期作废原则；欠用（$\text{raw} > 1$）时主动抬高权重倾斜流量。 |
| **闸（Gate）** | 短周期限制（如 5h、1min 速率限制） | **速率约束**。二值保险丝：未用满前不干涉评分（不抬分），一旦达到上限立即熔断跳闸（评分归零沉底）。 |

**综合评分合成规则**：
$$\text{score}(\text{provider}) = \begin{cases} \text{clamp}(\text{raw}(\text{桶}), 0, \text{HeadroomCap}) & \text{当且仅当所有闸规则均未达到上限} \\ 0 & \text{任一闸规则达到上限（跳闸）} \end{cases}$$

若账号下无有效桶规则（例如全为短周期速率闸），则退化为二值可用性门锁。

**关键裁决与数学不变量**：
* **破平决胜规则（`score.go:preferBucket`）**：当多条 Tumbling Limit 名义周期长度完全相同时（如配置两条同周期的不同 Limit），系统按稳定确定性规则决胜：**全模型共享池优先于按模型独立池**；若同属一类则 **Amount 较大者优先**；完全平手则保留配置书写顺序作为最终保底，杜绝迭代顺序不确定性。
* **滚动窗口（Rolling）绝不作为桶**：滚动窗口额度持续再生、不随周期作废，use-it-or-lose-it 前提不成立；其 $time\_left\_frac \equiv 1$ 导致 $raw \le 1$，若作为桶会退化为无法提供抢跑抬分信号的畸形闸。
* **闸的二值保险丝语义**：闸活着（$used < amount$）不参与评分、不抬分也不压分，未达到上限前不掺入效用函数；一旦达到上限立即熔断归零沉底，避免短周期速率闸的中间余量误压长期月度桶的抢跑信号。

## 4. 调度集成与决策管线

### 4.1 管线阶段与不可逾越的次序
额度感知路由挂载在调度管线的固定位置：

```
健康过滤 ──► 条件准入过滤 ──► 策略多键排序 (strategy.Sort)
                                       │
                                       ▼
                             额度感知重排 (梯队内软重排)
                                       │
                                       ▼
                             会话亲和置顶 (Sticky Pin, 最高优先级)
                                       │
                                       ▼
                                 Failover 循环
```

**三条架构硬约束**：
1. **不逾越优先级阶梯**：额度重排发生在 `strategy.Sort` 之后，严格限定在同一优先级梯队内部调整顺序，绝不跨越既有维度（如不能把压在低优先级的按量兜底端点排到高优先级套餐前）。
2. **会话亲和压倒一切**：Sticky Pin 命中时强行将粘性端点移至队首。打断 Prompt Cache 重建的成本远高于短时配额溢出，绝不为省额度破坏长上下文缓存。
3. **只重排、永不剔除**：额度耗尽的端点仅降序排至梯队末尾，保留在候选序列中。若更高优先级端点全军覆没，仍会尝试该端点，依靠上游真实响应触发 Failover。

### 4.2 梯队内占位重排机制
为避免局部配置产生隔空副作用，系统采用**占位重排（In-Tier Placeholder Reorder）**：
1. 在同一优先级梯队内，仅提取配置了 `quota` 的端点计算 `score`；
2. 对这些候选按 `score` 降序执行稳定排序；
3. 将排序结果写回其原有的槽位索引上，未配置配额的端点位置纹丝不动。

### 4.3 调度策略：无状态贪心
系统在新会话调度时选取评分最高的端点：
* **确定性与无状态**：不引入平滑加权轮询（SWRR）的复杂持久化累加器，依赖用量计费后分数的自发下降实现轮转；
* **保护缓存局部性**：使新会话在短时间内保持端点集中，避免流量随机离散破坏 Prefix Cache。

## 5. 计量体系与降级保护

### 5.1 数据源与双层采集
```
首选：上游真实响应 Usage (权威) ──► 响应归一化层单点提取并盖章
备选：本地字符线性估算 (降级)   ──► tokenutil 线性估算 (无缓存保守假设)
```

* **降级兜底**：当上游使用私有压缩、未返回 Usage 或流式中断时，自动切换为本地估算。
* **保守估算原则**：估算时将输入全额视为净输入（`in_fresh`）、输出全额视为 `out`（假设零缓存命中），对防超额采取安全高估。
* **可信度透传**：系统在状态快照中如实暴露 `estimated_pct`（估算用量占比）。计算时分子为未加权的原始估算 Token 数，分母必须为**原始四分量之和**（而非已加权的 `used`），避免因输出分量大权重导致占比计算严重失真。公式由 `internal/quota.EstimatedPct` 单点提供。

### 5.2 状态持久化与生命周期
* **文件存储**：`<log_dir>/vmr-quota.json`，权限 `0600`，通过写临时文件 + 原子重命名（Rename）确保落盘安全。
* **键命名空间**：以 **Provider 名称**为主键，刻意不包含 API Key 哈希，确保在同一套餐内轮换密钥时不丢失历史累计。
* **异步刷盘与优雅退出**：运行期间每 5 秒异步批量刷盘，收到终止信号时执行强制 Flush；非正常退出最坏损失 5 秒统计，对长期配额无实质影响。
* **惰性重置（Lazy Reset）**：周期起点基于锚点 `since` 与周期 `every` 数学推导。读写时比对当前时间，跨周期自动归零复位，无需常驻后台时钟任务。日历月推进自动执行月末截断（如 1 月 31 日购入，2 月自动截断至 2 月 28/29 日）。

## 7. 架构决策与设计边界

### 7.1 核心架构决策汇总

| 决策点 | 采纳方案 | 放弃方案与核心权衡 |
| --- | --- | --- |
| **计量范围** | 仅支持 `requests` 与 `tokens` | 价格随时间波动，将货币引入控制面会导致调度行为漂移。货币预算经除法折算为 Token 即可无损表达。 |
| **分配机制** | 梯队内按 Headroom 贪心排序 | 相比平滑加权轮询（SWRR），无状态贪心天然保持 Prefix Cache 局部性，且无需多节点持久累加器。 |
| **折算层级** | 挂在 Limit 层级（`token_weights` / `model_multipliers`） | 账号级装不下“短窗速率闸按全量次数、月度账单桶按 Credits 加权”的真实分化需求；按 Limit 声明赋予准确表达力。 |
| **Scope 判定** | `models:` 单字段表达三态（空/`*`/具体列表） | 避免引入独立的 `mode: shared\|per_model` 字段产生与 models 列表矛盾的配置组合。 |
| **多窗归并** | 桶为效用目标，闸为二值熔断 | 速率闸的松弛度不代表真实经济价值，闸活着不参与抬分，烧断立即沉底，避免短窗余量反向压制长期目标。 |
| **超额处理** | 软重排沉底，不做本地 429 熔断 | 本地统计包含估算误差，基于估算执行不可逆硬拦截等同于“自制故障”。真正耗尽依赖上游 402/429 触发健康冷却。 |
| **预扣机制** | 不做运行时预扣（Reservation） | 并发超冲上限仅为万分级噪音（约 0.5%），避免引入“预扣-对账-回滚”三段复杂分布式状态机与泄露隐患。 |
| **热重载对齐** | 缺省锚点 `DefaultSince` 对齐到固定日历边界 | 若取原始加载时间，每次热重载都会改变周期起点导致累计额度清零；日历对齐保证自然日内多次热重载计数安全存活。 |
| **密钥轮换** | 注册表以 Provider 名称为 Key | 轮换 API Key 属于凭据维护，绝不能意外清零当期额度导致透支超扣。 |
| **两半区一致性** | 差分测试锁死扣减逻辑 | 路由扣减与离线报表重算共享公式实现，并在组合根编写严格差分测试，防止统计口径分裂。 |

### 7.2 已评估并否决的改进提案（防重复论证）

| 提案 | 裁决 | 深入理据 |
| --- | --- | --- |
| **score 平手时引入轮转因子或随机打散** | **否决** | 贪心重排是每新会话重算的，首个请求计费后 score 立即下降，自发实现平滑轮转；强行轮转会废除确定性与 Prefix Cache 局部性。 |
| **引入精确滑动窗口（Rolling Window）** | **否决** | 需要存储每条请求时间戳，内存与持久化成本高一个数量级；环形分桶误差 $\le 1/K$（如 12 桶即 $\le 8.3\%$），对宏观配速足够精确。 |
| **在 Quota 评分中扣减 in-flight 并发计数** | **否决** | 并发打平时挤爆队首是通用路由排序问题（priority 平手时同样存在），塞入 Quota 会引入无依据的调节魔数 $\alpha$，应在候选调度通用层统一解耦处理。 |
| **Month 推进直接调用 `time.AddDate(0, 1, 0)`** | **否决（已修正）** | Go 的 `AddDate` 会在月末溢出（如 1月31日 + 1mo 变为 3月3日）；必须在日历周期计算中包含显式的月末截断（Truncate to month-end）。 |
| **上游未返回 Usage 时中断计费** | **否决** | 必须执行本地保守线性估算降级（假设零缓存命中），宁可保守高估扣除配额，绝不因缺少 usage 产生配额穿透漏洞。 |
