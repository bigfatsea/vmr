# VMR 项目复盘：一个纯 Vibe Coding 项目的 27 天

**复盘对象**：vmr（Virtual Model Router），2026-07-07 至 2026-08-02，106 个 commit
**项目性质**：全部代码、测试、脚本、文档由 Code Agent 产出；人只做需求、设计、方案、决策
**复盘目的**：提炼可迁移到新项目、新技术领域的方法；同时诚实记录代价与教训

**局限，必须先说清楚**：

3. **大量中间文档被主动删除。** 至少 20 份评审/分析文档创建后在几天内被删。它们的内容读不到了，但**创建与删除的时间点本身**是可读的，而且这个"用完即删"的模式恰恰是本项目最重要的工作方法之一（见 3.5）。

## 2. 编年史：六个阶段

### 阶段 0 — 一页纸（D1 凌晨，人独立完成）

第一个 commit `f494ae0` 里有两份文档：`VirtualModelRouter.md`（172 行）和 `VirtualModelRouter_v2_Fable5.md`（305 行）。20 秒后的第二个 commit 把前者删掉了。

**前者是人自己写的。** 它是整个项目唯一一份没有 agent 参与的产物，也是最重要的一份。它的结构值得逐条看：

- **定位**（一句话 + 一个类比："定位类似于 nginx、caddy、frp、rclone"）
- **问题定义**（为什么现有方案不行）
- **核心抽象**（恰好 4 个：Virtual Model / Endpoint / Strategy / Health）
- **功能边界**（做什么的清单 + **明确排除清单**：Dashboard、Database、User Management、Billing、Analytics Platform、Prompt Management、Workflow、Plugin System、MCP Framework、企业级 AI Gateway，"一律不做"）
- **架构原则**（4 条长期不变的）
- **技术选型**（Go，并写明"原因不是追求极致性能，而是追求部署体验和长期维护成本"）
- **开发策略**（MVP，第一阶段只做什么）
- **完成标准**（一段可验收的描述）

零行代码，零个函数名，零个数据结构。

**这份文档里有两条后来被证明是错的**：

> "Provider 协议适配应优先复用官方 SDK 或成熟 Adapter"
> "Router 内部应定义一套稳定的 Canonical Request / Response，对外部协议变化保持隔离"

这两条是标准的、听起来很专业的架构建议。它们在 D2 被彻底推翻——最终方案是**零 SDK、零中间表示、字节级透传**。这个事实非常重要，3.6 节会单独讲。

### 阶段 2 — 第一次范式反转："直接等价"（D2）

D2 是全项目 commit 最密集的一天（16 个）。核心是 `de0fe34` "Direct-equivalence overhaul"。

它推翻的东西：

- **中间表示（Canonical Request/Response）** → 协议原生格式，永不翻译
- **官方 SDK** → 零 SDK
- **响应处理的第三版实现**

第三条尤其有价值，因为设计文档把三代方案的失败原因逐条记了下来：

> v1 的「200 字节 carry + 字节级状态机」换了 4 个版本都有 corner case（carry 装不下 3000+ 字节 think 块、IN_THINK 时 input 字节丢失、flushTail 重入吐残留）；v2 的「全量缓冲 + 单遍 regex」正确但假流式——TTFB=完整生成时长，逼近 OpenAI SDK 的 `X-Stainless-Timeout: 120` 预算（实测 97K prompt 的请求生成 59s）；v3（现行）以**完整 SSE 事件**为处理单位……**状态机的复杂度病灶在「字节级切分」，不在「模式切换」**。

一个功能，六个版本（状态机 4 版 + 全缓冲 + 事件粒度），失败原因全部留在文档里。

从这天起，"字节忠实透传"成为整个项目的单一核心洞察。后来评审报告的结论是："这是一个有单一核心洞察并围绕它一致执行的项目。这比'功能很多'稀有得多。"

## 3. 这套方法里真正管用的东西

以下 8 条按"可迁移性"排序，第 1 条最通用。

### 3.1 人写"定位与边界"，agent 写一切实现

那份 172 行的 v1 文档是整个项目的地基。它的关键不在于写了什么，而在于**明确排除清单**——一份"绝不做"的名单。

**为什么这是最高杠杆的一件事**：Code Agent 的默认倾向是**增加**。你说"要个报表"，它会给你分组、给你趋势、给你导出、给你配置项。没有排除清单，一个 MVP 会在两周内长成一个平台。vmr 27 天里始终是单二进制、零数据库、零 Web UI、4 个依赖——不是因为 agent 克制，是因为第一天就有一张写死的排除清单。

**给技术背景不强的人的具体做法**：你不需要懂 Go 或 HTTP。你需要能回答五个问题：

1. 一句话说清这是什么（最好带一个类比："像 nginx"）
2. 现在的痛点是什么，为什么现有工具不行
3. 这个系统里最少有哪几个概念（3–5 个，不能更多）
4. **有哪些看起来相关但坚决不做**（这份最长，也最有价值）
5. 做完之后，用户执行哪一条命令、看到什么，才算成功

这五个问题不涉及任何技术知识，但它们决定了项目 80% 的走向。

### 3.2 设计文档是主干，代码是产物

设计文档的完整血缘：

```
VirtualModelRouter.md          172 行  人写          D1  （20 秒后删除）
VirtualModelRouter_v2_Fable5   305 行  Fable 5 扩写  D1
   ↓ 持续增长 305 → 741 行（21 天）
System_Design_v3               861 行  重写合并      D18 （合并 3 份专题文档）
   ↓ 861 → 898 行
Design_v4_Core                 894 行  拆分          D23
Design_v4_Analytics            376 行  拆分          D23
```

**三个可复制的做法**：

1. **文档与代码在同一个 commit 里更新。** 查 `git log --follow` 可以看到，几乎每个特性 commit 都同时改了设计文档。文档不是事后补的。
2. **文档会被重写，不只是追加。** D18 的 v3 是一次真正的重写（把三份专题文档合并进主文档）；D23 的 v4 是一次拆分。**只追加不重写的文档，两个月后没人读。**
3. **文档有版本头**（`<!-- Ver 2026-08-02 10:54, by Sonnet 5 -->`），标明谁在什么时候改的。

### 3.3 "决策与取舍表" + "决定不修表" — 这套方法的核心发明

设计文档里有两张表，我认为它们是这个项目能跨 27 天、跨至少 5 个不同模型保持一致性的**主要原因**。

**决策与取舍表**：三列——决策 / 备选 / 取舍逻辑。样例：

| 决策 | 备选 | 取舍逻辑 |
| --- | --- | --- |
| Canonical 格式 = 协议原生格式，透传不翻译 | 自研中间表示（IR） | IR 意味着永远追各家新字段，是 LiteLLM 复杂度失控的根源；透传对新参数天然前向兼容 |
| 错误分类含 body 嗅探 | 严格按 HTTP status 映射 | 实测各家 status 习惯不一（400 当 404 用等）；**漏判 = 永不 failover，误判只是一次无害切换** |
| 内容合规错误：切换但零惩罚 | 当普通 4xx 处理 | 该错误按请求不按端点：不切换会中断长程任务，惩罚健康会让一条敏感请求打掉整个端点 |

**决定不修表**：三列——项 / 现状 / **不动的理由**。开头一句话说明它为什么存在：

> 已识别、但判定"动它的收益低于扰动成本"的项。每项都不是 bug，改与不改行为一致；**列在这里是为了下次有人盯着它们犹豫时不必重新论证。**

**为什么这两张表对 vibe coding 特别关键**：agent 没有跨 session 记忆。没有这两张表，每一个新 session 都会：

- 重新论证已经定过的决策（浪费）
- 或者更糟——**"修复"一个故意的设计**（破坏）

CLAUDE.md 里因此有一条硬约定：

> Before treating something as a bug: check the "decided-not-to-fix" tables — some odd-looking behavior is a documented, deliberate non-fix.

这两张表回答的是"**为什么不这么做**"。这类信息在代码里读不出来，也是 agent 最容易丢失的信息。

### 3.4 把架构约定变成会失败的测试

`internal/archtest` 是全项目最值得抄的一个包。它做两件事：

- **import 边界**：`internal/report` 不得依赖 `router`/`server`/`config`；`ctxgraph` 不得依赖 `report`/`story`
- **文件行数预算**：`router.go` ≤ 700、`aggregate.go` ≤ 1000、`config.go` ≤ 750

**为什么这对非技术背景的人是关键杠杆**：你审不了 25,000 行 Go 代码。但你可以在 agent 说出一条规则时，立刻回一句：**"把这条规则写成一个会失败的测试。"**

从此这条规则不再依赖任何人的记忆或自觉。router.go 长回 948 行的那天，`go test` 会红。

这个模式适用于任何领域，不限于代码架构。规则一旦能被机械检查，它就从"我们说好的"变成了"改不了的"。

### 3.5 评审是消耗品，结论必须落进永久载体

D11–D24 期间至少 20 份评审/分析文档被创建又删除，其中 07-17 一天内出现四份来自不同模型的独立审计。

**这个模式的完整形态是三步**：

1. 让**另一个模型**（不是写代码的那个）做独立评审，明确要求"不以现有文档为准绳，读代码得出结论，再回头看文档是否一致"
2. 逐条处理评审结论
3. **把结论沉淀进三个永久载体之一，然后删掉评审文档**：
   - 设计文档的决策表（"我们考虑过，选了 A，因为……"）
   - 决定不修表（"我们知道，故意不改，因为……"）
   - 一个会失败的测试（"以后不许再犯"）

**落不进这三个地方的评审结论，等于没做完。**

今天（D28）刚产出的《vmr 全面评审报告》就是这个模式的最新一轮。它的方法声明写得很清楚：

> 刻意不以设计文档为准绳去核对代码，而是反过来：读代码得出结论，再回头看文档是否与之一致。**这一步产出了本报告价值最高的一批发现。**

这句话是整套方法的精髓——**让评审者去质疑文档，而不是拿文档当标准答案**。因为在 vibe coding 项目里，文档和代码是同一批 agent 写的，它们会一起错。

### 3.6 敢于推翻自己的设计——而且是在用过之后

至少 7 次实质性反转：

| 原方案 | 反转后 | 间隔 |
| --- | --- | --- |
| 复用官方 Provider SDK（v1 文档明确建议） | 零 SDK | 1 天 |
| Canonical Request/Response 中间表示（v1 文档明确建议） | 字节透传，永不翻译 | 1 天 |
| 字节级状态机（4 个版本） | 全量缓冲 | 1 天 |
| 全量缓冲（正确但假流式） | SSE 事件粒度 | 1 天 |
| providers 按协议分两层 map | 扁平多协议列表 | 23 天 |
| base_url 路径重叠自动消除 | 删掉，要求 base_url 自带版本 | 3 天 |
| `internal/report2`（新包并行开发） | 合并回 `internal/report` | 1 天 |
| 主动 + 被动双探测模式 | 只留后台探测 | 14 天 |

**最重要的观察**：v1 文档里两条最"专业"、最像正确架构建议的条款——用 SDK、定义 IR——**全是错的**。而它们只有在写完代码、真的跑起来之后才被证伪。

这是 MVP-first 的实际含义，也是 vibe coding 相对传统开发的真正优势所在：**当实现的成本降到一天，"先建后拆"就从奢侈变成了默认策略。** 你不需要在纸上把架构想对，你需要的是快速造出来、用一下、然后有勇气推翻。

`report2` 那次尤其典型：新建一个并行包重写报表（`aceb681`），第二天确认新版可用，立刻合并回原包并删掉旧实现（`a709fac` "Merge internal/report2 into internal/report — one package, not two"）。**并行分支只活了一天。**

### 3.7 测试是 agent 的记忆，不是质量保证

测试/生产比从 D1 的 0.66 一路到 0.94，**全程没有一次"欠测试后补"的阶段**。

对传统开发，测试是防回归的。对 vibe coding，它的作用不一样：

**它是唯一能跨 session、跨模型阻止 agent 破坏既有行为的机制。** 你看不懂代码没关系——测试跑不过就是跑不过。设计文档会被误读，注释会被忽略，CLAUDE.md 可能没被加载，但 `go test ./...` 是红的就是红的。

这个项目里的测试形态特别丰富，值得逐类列出（每一类都对应一种"我担心 agent 以后会破坏什么"）：

| 测试类型 | 守的是什么 |
| --- | --- |
| 单元测试（750 个） | 常规行为 |
| Fuzz（2 个） | 手写扫描器在不受信输入下不 panic |
| Golden 文件 | 报表/叙事输出的完整形状（含中英双语） |
| 不变量测试 | tool_call/tool_result 配对必须 100% |
| 一致性测试（4 个） | `report` 的会话分组必须与 `ctxgraph` 一致——**防的是两处实现悄悄分叉** |
| 确定性测试 | 报表在多次运行/平局场景下必须字节一致 |
| 架构测试 | import 边界 + 文件行数预算 |
| e2e | 双语走通完整报表生成 |
| `-race` | 并发正确性 |

### 3.8 给启发式规则配"失效自检信号"

这条最微妙，但对 agent 写的代码特别重要。

vmr 里有一批基于内容特征的启发式规则（识别 MiniMax 的 thinking 泄漏、识别软封禁标记、识别 SSE 换行格式）。它们都可能因为供应商改措辞而**静默失效**。

处理方式不是"写得更全面"，而是：**当字面守卫没触发、但内容形状仍然可疑时，往审计日志打一个标记**（`crlf_framing_suspected`、`thinking_leak_suspected`）。

于是规则失效时，运维侧**会看到信号**，而不是静默降级。

**为什么这对 vibe coding 是刚需**：agent 极擅长写"看起来处理了所有情况"的代码。它会给你一个覆盖 12 种情况的匹配函数，语气笃定。给这类代码配一个"我可能错了"的信号通道，是把 agent 的过度自信转成可观测事实的唯一办法。

同一思路的另一个体现，是设计文档里对没校准过的阈值的诚实标注，以及 Analytics 文档专门有一节叫**"盲区（诚实声明，避免'没记录'被误读成'没发生'）"**。

## 4. 代价与教训：这套方法的账单

以下全部有证据，不是假设的风险。多数来自 2026-08-03 那份独立评审。**7 项里 6 项已解决、1 项解决了一部分**，状态标在各小节标题里——这份账单本身也在验证 3.5 节的说法：评审结论不落地就等于没做完，而这次落地速度很快，多数在评审当天或复盘写完当天就处理掉了。

### 4.1 引用腐化 — vibe coding 的特有债务 — ✅ 已解决

评审报告称之为"本次评审最重要的发现"：

| 引用形式 | 出现次数 | 状态 |
| --- | --- | --- |
| `§x` / `§x.y` | 约 340 处 | 部分有效，大量失效 |
| `Appendix X.Y` | 约 55 处 | **几乎全部失效** |
| `F<n>` | 约 70 处 | 仅 2 个有效 |
| `T<n>.<n>` | 约 55 处 | **全部失效** |

约 520 处编号引用，过半悬空。另有 11 处引用 `_tmp/plan_sonnet-5.md`——一个 gitignore 且已删除的文件，**其中一处印在用户可见的 CLI 帮助文本里**。

**根因是两个好习惯的交叉**：

- agent 天然爱写精确的交叉引用（"见 §6.5"），这看起来很专业
- 工作文档用完即删（3.5 节说的那个好做法）

两者相乘，就是一批指向虚空的指针。而且**它的累积速度与开发速度成正比**——开发越快，产生的悬空引用越多。评审报告注意到，`internal/story`（最新的模块）也是这个问题最严重的模块。

CLAUDE.md 当时加了一条规则禁止编号引用，但明确说"存量不做一次性清扫"——规则的制定者已经知道存量问题存在，只是选择了不处理。**这份复盘写完当天，存量清扫就被排上了日程**：全项目 ~520 处引用逐一核对，死引用（`Appendix`/`T<n>.<n>`/`F<n>`，F9/F10 除外）清除，裸编号改写成事实性描述，CLAUDE.md 那条规则里"存量不做清扫"的说明也相应去掉了。

**教训**：

1. 禁止编号交叉引用，要在写第一行注释之前就定好。写章节名或一句话描述，不写 `§6.5`。
2. **删除任何工作文档之前，先 grep 代码里对它的引用。**
3. 这类债不影响运行，所以不会有人被迫处理它——它需要被主动排期，而"主动排期"本身可以做到很快：从复盘指出问题到清扫完成，间隔不到一天。

### 4.2 给 agent 看的文档本身会漂移 — ✅ 已解决

评审把 CLAUDE.md 声明的 13 条不变量逐条对照代码，当时查出 **4 条有偏差**（"No Makefile, no CI config in-repo"其实已有两个 workflow；模块表漏了 D27 加的 `internal/i18n`；字节忠实透传的例外只写了两类，漏了图片降采样这第三类；`archtest` 的边界覆盖和行数预算都不完整），已按建议逐条修复。

**但这条教训自己又验证了一次自己**：4 条偏差刚修完没几天，CLAUDE.md 又悄悄漂移出新的一批——开篇仍写"两个入口协议"，但协议已经加到三个（`openai-responses`）；模块表仍没有 `adapter/openairesponses` 这一行；CI 描述仍停在"只跑 ubuntu"，矩阵早就加了 macOS，还多了 gofmt/shellcheck 两个 job。这轮已经一并修正。**CLAUDE.md 不是修一次就完事的文档，它需要跟功能开发同频核对，而不是等下一次外部评审才发现。**

**为什么这比普通文档过时更严重**：CLAUDE.md 是每个新 session 的**第一入口**。一条错误陈述会被无条件继承，并在后续所有工作中传播。普通文档过时了，人会怀疑；给 agent 的简报过时了，agent 不会怀疑。

**教训**：CLAUDE.md 需要定期核对，而且**必须由另一个模型逐条对照代码核**，不能由写代码的那个模型自查。它是配置，不是文档。

**关于它的诞生时机**（D20，第 20 天）：我认为晚了，但没有晚很多。前两周项目形状还在剧烈变化，早写就是写废话。**真正的判据不是天数，是这个信号：当你发现自己在第三个新 session 的开头重复解释同一件事时，就该写了。** 这个项目大概在第 8–10 天就出现了这个信号。

### 4.3 产能太高会让项目悄悄换重心 — ✅ 已解决

分析层（report/story/ctxgraph/chatmsg/i18n）约 12,000 行生产代码，**已超过**路由核心的约 9,000 行。

但 CLAUDE.md 的第一句当时仍是 "Local-run, single-binary, config-driven LLM router"，把分析工具描述成 "Beyond routing, two offline tools"（"除了路由之外，两个离线工具"）——**现已改写成"两个 co-equal halves"**，与 README 在 D25 就已采用的 "flight recorder" 定位对齐。

评审的判断是准确的：这不是失控（分析层是离线只读消费者，有 archtest 强制的边界，再大也不拖累路由），**但它必须被文档诚实承认，否则新贡献者会对这个仓库的重心产生误判。**

人在 D25 重写 README 时其实已经承认了这次漂移（改成 "flight recorder"），但 CLAUDE.md 和设计文档直到这份复盘写完才同步回来——**承认漂移和同步文档是两个动作，中间可以隔很多天，不会自动发生。**

**教训**：vibe coding 的产能高到你会在没注意的时候做出一个不同的东西。**定期回看第一天那份定位文档，问一句：我现在做的还是当初那个东西吗？** 答案是"不是"完全可以接受——但要明确改写定位，而不是让文档和现实各说各话。

### 4.4 跨 session 的接缝无人负责 — ✅ 已解决

评审找到的唯一一个能造成真实生产故障的问题：

> 热重载会接受一份 `api_key` 为空（`${VAR}` 拼错或未导出）的配置，静默把所有流量打成 401，日志无任何提示。

代码里**有** `config.Check()` 这个函数，它正是为检测这类"语法合法但操作上损坏"的配置而写的。但它在 `vmr start` 和热重载这两条自动路径上**从未被调用**——评审当天就补上了这两处调用，热重载和启动路径现在都会把 `Check()` 的每条 `Issue` 打成一行 `WARN`。

**这是跨 session 协作的典型失效模式**：一个 session 写了 `Check()`，另一个 session 加了热重载，每个 session 的产物单独看都正确，**接缝处没有任何人负责**。

同类的还有 4.5 节的资源上界问题。

**教训**：agent 在一个 session 内的局部质量很高，跨 session 的整体性很差。**"最近新增的能力有没有接到已有的调用路径上"是人必须定期做的检查**，agent 不会主动做。

### 4.5 局部正确相乘等于全局错误 — ✅ 已解决

三个缓冲上限，分别定义在三个包，写下这条时的取值：

| 常量 | 位置 | 值 | 各自的理由 |
| --- | --- | --- | --- |
| `MaxRequestBodyMB` | `config` | 8MB | 防超大请求 |
| `bufferedCap` | `router/response.go` | 32MB | 防失控上游撑爆归一化缓冲 |
| `recorderBodyCap` | `server/recorder.go` | 64MB | 防超大响应让审计副本无界增长 |

单请求最坏驻留约 **104MB**，而 `max_concurrency` **默认无限**。每个常量的局部决策都正确。没有任何一处文档、测试或断言把这三个数字合起来看过。

**分两步解决**。第一步（文档层）：UserGuide 补了一段"单请求内存预算"，把三个数字乘起来讲清楚，并建议共享实例设置 `max_concurrency`——这一步先把"没人知道"变成"写在文档里"。第二步（数值层，人指出了一个更好的推导锚点之后才做）：1M-token 上下文窗口对应约 3-4MB 字节量,`MaxRequestBodyMB` 的 8MB 本身就是这个量级 + 一倍余量的产物,但 `bufferedCap`/`recorderBodyCap` 从没按同一套逻辑推导过,只是各自拍了一个"看起来够大"的整数。改用同一套锚点重新推导：`bufferedCap` 32MB→8MB（这个 cap 只是失控上游的安全阀，超限直接降级为无损透传，可以设得激进）、`recorderBodyCap` 64MB→16MB（比 `bufferedCap` 多留一倍余量，因为它的截断丢的是审计信息本身）。单请求最坏驻留从 104MB 降到约 32MB。

**教训**：**agent 极擅长做局部正确的决策，极不擅长发现"三个局部正确加起来是错的"，甚至发现了也未必知道"合理的值应该是多少"——它能算出三个数字的乘积，但不会主动去问"这个乘积该以什么为参照"。** 这类跨模块乘积效应本身要靠人发现；而"改到多少算合理"这一步，往往还需要人带一个具体的外部锚点(这里是"当下模型的上下文窗口量级")进来，agent 才有的算。

### 4.6 agent 只测它认为是"代码"的东西 — ⚠️ 部分已解决

覆盖率的结构性缺口，逐项现状：

- **685 行 shell（`vmr.sh` + `vmr-loadtest.sh`）零行为测试** —— 依然如此。CI 加了 `shellcheck`，但那是静态检查，不是行为测试；launchd/systemd 的 plist/unit 渲染到底能不能被真实接受，它照样测不出来
- `i18n` 覆盖率 17.3% —— 依然如此，数字分毫未变
- ✅ **CI 只跑 ubuntu** —— 已解决，矩阵加了 macOS（`vmr.sh` 的 launchd 专属分支这下才第一次真的被跑到）
- ✅ **`RewriteRoles` 唯一没有 fuzz** —— 已解决，`FuzzRewriteRoles`/`FuzzRewriteInputRoles` 已补上；fuzz 跑起来 30 秒内就在共享扫描器里挖出一个真实的无限循环（畸形请求体能挂死处理它的 goroutine），不只是补了覆盖率数字

**教训**：agent 会认真测它写的 Go 代码，不会主动去测 shell、配置示例、CI 脚本这些"周边"——这类盲区要显式点名要求，而且**点名之后修起来往往比想象中快**（CI 矩阵、fuzz 补齐都是当天的事），真正难啃的是"给 shell 脚本补行为测试"这类没有现成工具链的缺口，静态检查能顶一阵但不能替代它。

### 4.7 一些小的、但说明问题的地方

- **`docs/` 混进市场/分发文档**（知乎回答、Reddit 回复、Twitter 卡片、文章草稿）—— ✅ 已解决。这条写下的时候是 27 份，写完这份复盘的过程中又多冒出 2 篇知乎稿件、变成 29 份——**问题在被记录的同一时刻还在变严重**，是"agent 产出太便宜，导致不加区分地留下"最直接的实证。后来这批内容被整体移到仓库根的 `archived/`（gitignore 排除，不再随 `docs/` 混着看），工程文档和 GTM 内容第一次真正分开。
- **一个 commit message 是一整张终端渲染的表格**（`7b1932a`，把 agent 的输出直接粘进去了，含 box-drawing 字符和断行）。小事，但它标记了一个人在 review 环节偷懒的瞬间。
- **31 个 commit 的 message 短于 14 字符**（"update"、"udpate"（拼错）、"cleanup"、"minior changes"）。与之对照的是 agent 起草的那些结构化多行 message。两种质量并存。

## 5. 迁移到新项目：最小可行流程

面向"换一个技术领域"或"技术背景不强但想做真实软件项目"的场景。

### 5.1 人不可外包的四个动作

其余一切都可以交给 agent。这四件不行：

1. **定边界** —— 尤其是那份"绝不做"的清单。agent 的默认方向是加，只有你能说不。
2. **拍反转** —— 用过之后推翻自己早先的设计。agent 会倾向于在既有方案上打补丁，不会主动说"这个方向从根上就错了"。
3. **审接缝** —— 跨模块、跨 session 的整体性。局部正确 × 局部正确 ≠ 全局正确。
4. **承认漂移** —— 定期比对"我在做的"和"我说要做的"，然后**改写定位**，而不是假装没变。

### 5.2 逐日流程

**Day 0（人独立完成，不用 agent）**

写一页纸，回答 3.1 节那五个问题。不写任何实现细节。这份文档你要能一口气读完。

**Day 0.5**

让 agent 把它扩写成完整设计方案。**你逐条读**——你读的不是技术，是**理由**。每一条"为什么选 A 不选 B"，如果你读不懂，那就是它没写清楚，让它重写到你懂为止。这一步筛掉的是 agent 的"看起来很专业但没想清楚"。

**Day 1**

MVP。硬性要求两条：

- 测试与代码同步产出，不接受"先跑通再补测试"
- 用真实数据/真实依赖做一次端到端验证，把结果写下来（vmr 的 `DEV_PLAN.md` 里每条验收都带实测数字）

**Day 2 起，每个特性**

代码 + 测试 + 设计文档，**同一个 commit**。

**每周一次**

换一个模型做独立评审。评审提示词里必须包含："不要以现有文档为准绳，从代码读出结论，再回头看文档是否一致。"

评审结论逐条处理，然后落进三个载体之一，落完删掉评审文档：

- 设计文档的**决策与取舍表**
- **决定不修表**
- 一个**会失败的测试**

**触发式，不按时间**

- 当你第三次向新 session 解释同一件事 → 写 CLAUDE.md（或等价的项目简报）
- 当 agent 说出一条规则（"这个文件不该超过 500 行"、"A 不能依赖 B"）→ 立刻说："把它写成一个会失败的测试"
- 当设计文档超过 800 行 → 考虑重写或拆分，不要继续追加

### 5.3 三份必须存在的文档

| 文档 | 谁写 | 回答什么 | 何时更新 |
| --- | --- | --- | --- |
| 定位文档（一页） | 人 | 做什么 / **不做什么** | 重心真的变了的时候（并且要明确改写） |
| 设计方案（含两张决策表） | agent，人审 | 怎么做 / **为什么不那么做** | 每个特性 |
| 项目简报（CLAUDE.md） | agent，另一个模型核 | 新 session 的最短上手路径 | 每次结构变化；定期交叉核对 |

**两张表比文档正文更重要**：决策与取舍表（为什么选 A 不选 B）、决定不修表（知道它奇怪，故意不改，理由如下）。

### 5.4 适用边界 — 这套方法在什么条件下成立

必须诚实地说：vmr 的几个特性极大地降低了 vibe coding 的风险，换个项目不一定成立。

**vmr 具备的有利条件**：

- **行为可逐字节验证**——"经 vmr 收到的字节 == 直连收到的字节"是一个可以机械检验的命题。这让正确性有了客观裁判。
- 单用户本地工具，**无用户数据、无数据库迁移、无多人协作、无合规要求**
- **零 UI**——没有设计、交互、可访问性这些难以自动验证的维度
- 4 个依赖，无框架、无生态版本纠缠
- 作者本人就是唯一用户，反馈闭环以小时计

**换成下列情况，同样的方法需要额外护栏**：

| 情况 | 需要补什么 |
| --- | --- |
| 有数据库/数据迁移 | 迁移的可逆性和演练必须是人的职责，不能交给 agent 自证 |
| 有 UI | 需要视觉回归、真人试用；agent 无法自验"好不好用" |
| 多人协作 | CLAUDE.md 类文档从"给 agent 看"变成"给人和 agent 共同看"，准确性要求更高 |
| 有真实用户数据 | 审计日志这类"全量记录"的设计要先过隐私关（vmr 自己也把"提供关闭 body 记录的选项"列为待办） |
| 目标不可机械验证 | 优先补一个能自动判定的验收信号，没有它，测试就只是在锁定当前行为而不是锁定正确行为 |

**核心判据**：如果这个项目有一个**能自动判定对错的信号**，vibe coding 的规模上限会很高；如果没有，人必须在每一步都在场，产能优势会大幅缩水。

## 6. 一句话总结

这个项目的成功不来自任何一次聪明的 prompt，而来自一套**把知识往仓库里沉淀的纪律**：

一页人写的边界文档定住了范围；两张决策表让 27 天里至少 5 个不同模型不必重新论证已经定过的事；23,959 行测试和一个 archtest 包让"我们说好的"变成了"改不了的"；每周一轮换模型的独立评审，结论落进永久载体后即刻删掉评审本身。

而它的账单同样清晰：520 处悬空的交叉引用、一份自己有 4 条陈述与代码不符的 AI 简报、一次未被文档承认的重心漂移、一个跨 session 接缝里的静默 401 故障、三个各自合理相乘等于 104MB 的缓冲常量。**这份账单里,五项已经还清,还剩 shell 零测试和 i18n 低覆盖率这一项没动**——付账的速度跟欠账的速度一样快,这本身也是"把知识往仓库里沉淀"这套纪律的一部分:问题一旦被写进永久载体,就变成了一件会被排期处理的事,而不是一段只存在于对话历史里、随时可能被遗忘的抱怨。

**这些代价有一个共同形状：它们全部发生在"局部"与"整体"的接缝上。** agent 在局部的质量已经超过多数人类项目的平均水平；整体性——跨模块、跨 session、跨时间的一致性——仍然是人必须在场的地方。

这大概就是当前阶段 vibe coding 最准确的分工线。

## 附录：可直接复用的清单

**项目启动时**

- [ ] 一页定位文档，含明确排除清单，人自己写
- [ ] 让 agent 扩写成设计方案，逐条读"理由"部分
- [ ] MVP 要求测试同步产出 + 真实端到端验证并记录数字

**每个特性**

- [ ] 代码 + 测试 + 设计文档同一个 commit
- [ ] 新决策进"决策与取舍表"（决策 / 备选 / 取舍逻辑）
- [ ] 决定不改的怪异行为进"决定不修表"（项 / 现状 / 不动的理由）

**每周**

- [ ] 换模型做独立评审，要求"从代码读结论，再核对文档"
- [ ] 评审结论落进：设计文档决策表 / 决定不修表 / 一个会失败的测试
- [ ] 落完删掉评审文档，**删之前先 grep 代码里对它的引用**

**触发式**

- [ ] 第三次重复解释同一件事 → 写项目简报
- [ ] agent 说出一条规则 → "把它写成一个会失败的测试"
- [ ] 设计文档 > 800 行 → 重写或拆分
- [ ] 加了新的检查函数 → 确认它被接到了自动路径上

**定期人工检查（agent 不会做）**

- [ ] 所有资源上界列成一张表，相乘看一遍
- [ ] 项目简报的每条声明逐条对照代码（让另一个模型做）
- [ ] 各层代码量对比 vs 定位文档说的重心
- [ ] shell 脚本、配置示例、CI 这些"非代码"部分有没有守护

**从一开始就定死的约定**

- [ ] 注释和文档之间**不用编号交叉引用**，写章节名或一句话描述
- [ ] 启发式规则必须配"失效自检信号"
- [ ] 注释记录"被替换掉的旧方案错在哪"，而不只是"现在这个方案是什么"
