## 一、底层元原则 (Meta-Principles)

### 1. 神合形不合：求本质契约，反机械八股
- **反对形式主义对称**：不同任务（宏观分析、架构审计、代码整洁清理、微观性能穿透等）的业务语境、技术重心与交付载体截然不同。严禁生硬套用一模一样的小节标题。
- **追求内在逻辑统一**：所有 Prompt 及其产出报告统一的是**思维闭环与价值诉求**——
  1. **明确目标与计划**：交代清楚这次任务做了什么、核心要点是什么、打算怎么做；
  2. **按计划展开实质要点**：结合具体计划逐项推进，深入提炼关键发现，而不是走过场；
  3. **全局综合评估**：执行结束后跳出单点，汇总全链路要点，给出顶层总结与全局健康度评估；
  4. **分级与 ROI 决策**：对发现与建议按优先级合理分批，详略得当，关键事项深入根因与方案。
- **实事求是**：章节命名和组织结构必须深度适配当前任务的专业语言。

### 2. 成果价值导向：过程进工作区，结论进交付物
- **严禁流水账**：最终交付物绝不是操作日记，不要记录“第一步我调用了某工具，第二步我读了某文件”这类低信息密度的过程复述。
- **职责二分法**：
  - **过程产物 (Scratch / Working state)**：任务推进中的原始日志、搜索记录、临时台账与草稿笔记，一律落在隔离的临时工作区（如 `_tmp/`），任务结束即刻销毁；
  - **最终交付物 (Deliverable)**：必须是高度提炼、自包含、具有独立决策参考价值的严肃成果。正文中的要点是从过程文件中精炼提纯出来的核心洞见。
- **框架支撑与自由留白 (Scaffolding & Serendipity)**：预设框架是确保任务下限的脚手架，但绝不能成为束缚认知的牢笼。执行者在深入一线代码与数据时，极易捕获超纲但极有价值的意外发现（Serendipitous Findings）。Prompt 必须在交付物中为其设立显式的开放通道（如“其他补充事项”），允许且鼓励记录一切有价值的超纲洞见。

### 3. 第一性原理与权威查重（批判但不盲目）
- **立足代码与用户现状**：审阅与评估以用户真实诉求、系统运行现状与代码事实为最高基准，敢于挑战历史设计中的失效假设。
- **查重先行，推翻带新证据**：项目既有的决策和取舍（如 `KNOWN_ISSUES`、`ROADMAP`、设计文档中的 `decided-not-to-fix`）往往凝聚了历史深层权衡。新 Prompt 必须要求执行者开工前先对齐既有权威文档；重合事项注明索引，推翻已有决策必须先引用、再举出新证据，绝不允许假装没看见而重复立项。

### 4. 最小认知打扰与非阻塞心流
- **非阻塞 Debrief**：开工前必须输出对任务要求、范围边界、计划策略的理解（Debrief）。**Debrief 默认为陈述性输出**，若无必须等待用户确认的阻塞性事项，立即启动下一阶段，严禁客套等待确认而中断执行。
- **升级留档优先于中断打扰**：执行过程中遇到两难、高风险或需负责人拍板的权衡，**一律不动手、不中断发问**，登记到报告的“待决策建议清单”，留待最终统一裁决。

### 5. 环境防线与零污染
- **基线先行**：任何涉及代码变动的任务，必须以只读命令跑通安全基线（构建、测试、race、vet、archtest），作为后续等价性评估的锚点。
- **边界清晰**：统一以基础设施配置（如 `.gitignore`）为边界，被忽略内容一律视作不存在，不查不改；若存在必要的数据源（如 `logs/`）或生成的交付物（如 `reports/`），必须设立显式的“例外条款”。

## 二、Prompt 标准解剖结构 (Standard Anatomy)

一份成熟、严谨的生产级 Prompt 应由以下逻辑模块有机组合而成：

```
┌────────────────────────────────────────────────────────┐
│ 1. 角色定义与核心目标 (Role & Prime Objectives)        │
│    - 专业身份、审查视角、核心主线、成功标准           │
├────────────────────────────────────────────────────────┤
│ 2. 核心原则与底层约束 (Guiding Principles & Guards)    │
│    - 第一性原理、查重先行、行为保持、忽略边界          │
├────────────────────────────────────────────────────────┤
│ 3. 协作机制与过程产物管理 (Workspace & Artifacts)      │
│    - 临时工作区生命周期、过程文件命名倾向、Subagent 协同│
├────────────────────────────────────────────────────────┤
│ 4. 统一优先级与分级体系 (Issue Classification)         │
│    - T1 / T2 / T3 梯队综合定义、统一元数据字段        │
├────────────────────────────────────────────────────────┤
│ 5. 分阶段执行步骤 (Phased Workflows)                   │
│    - 阶段一: 调研、对齐、初始化与 Debrief (非阻塞)     │
│    - 阶段二: 专项攻坚 / 数据生成 / 核心切片            │
│    - 阶段三: 分领域/分视图下钻审查 (产出过程文件)      │
│    - 阶段四: 验证推演 / 交叉核验 (只读验证)            │
│    - 阶段五: 撰写自包含交付报告 (提炼要点、分级编排)   │
├────────────────────────────────────────────────────────┤
│ 6. 交付与启动协议 (Delivery & Boot Protocol)           │
│    - 报告落盘路径、对话最终摘要、Debrief 触发规范      │
└────────────────────────────────────────────────────────┘
```

## 三、核心机制设计规范

### 3.1 过程产物与工作区生命周期

1. **工作区目录命名规整**：
   - 格式：`_tmp/<task>-<model-slug>-<timestamp>/`
   - 说明：`<task>` 为当前任务简短标识；`<model-slug>` 与 `<timestamp>` 确保并发隔离与可追溯性。
2. **过程文件命名惯例**：
   - **核心标准文件**：`progress.md`（记录执行进度、基线与检查清单）+ `findings.md`（记录各阶段实质发现与原始要点）。凡意涵相同，统一使用此命名。
   - **语义化特化增补**：允许根据具体业务场景增补特定文件（例如清理任务的 `candidates.md` 清理台账与 `notes-for-lead.md` 决策记录），但不得随意命名、散落存储。
3. **销毁铁律**：
   - 任务完成并生成最终交付文件后，**必须彻底删除整个临时工作区**，保持仓库工作区绝对干净。

### 3.2 最终交付物设计哲学（反八股、反流水账、开放留白）

最终报告必须是一个**独立、完整、自包含、详略得当且留有开放空间的交付物**。其内在逻辑应体现为五层递进，但各章节名称需结合具体任务自然呈现：

1. **背景、目标与打算怎么做 (Context & Plan)**：
   - 清晰阐述本次任务审阅/盘点的范围、技术基准、核心约束；
   - 交代具体的执行计划（如何划分领域/视图、抽样策略、验证手段）。
2. **计划执行记录与核心要点 (Execution & Core Findings)**：
   - 按照前述计划逐项展开，呈现真实的落地要点；
   - 必须是从过程文件（`findings.md` 等）中**提炼出的高价值事实与洞见**，严禁记录“执行了某个工具”的流水账。
3. **全过程综合评估 (Holistic Assessment)**：
   - 跳出单点，汇总所有环节的要点；
   - 给出系统层面的成熟度评级、整体健康度评估、或收益与代码净变化预估。
4. **分级建议与落地规划 (Prioritized Recommendations & Roadmap)**：
   - 按照 T1/T2/T3 合理分批组织，每条事项均须提供明确的描述与 ROI 评估；
   - **详略得当原则**：不重要或次要的瑕疵简单交代；重要问题详细描述；关键与系统性缺陷深入展开根因剖析、给出建议方案与验证依据。
   - 针对不同任务承载专属附录（如 Mermaid 架构拓扑/时序/甘特图、组件存废矩阵、分批落地命令等）。
5. **其他补充事项 / 开放性发现 (Other Observations & Everything Else)**：
   - **为未预料的高价值发现预留专用通道**：在实际审查或执行过程中，Reviewer 或 Agent 极有可能凭借敏锐洞察发掘出**超出原定框架、初始计划或领域白名单之外的新点与意外收获**（例如：开发体验与工具链暗坑、潜在的系统安全/合规盲区、意外发掘的产品形态构想、依赖库版本风险等）。
   - **只要有价值，皆可入此章**：严禁因为“不在初始清单内”而舍弃宝贵发现。本章负责承接所有无法归入前述章节但具备实际技术或业务价值的“Everything Else”，为一线 Agent 留出充分的发挥空间。

### 3.3 优先级综合分级体系 (T1/T2/T3)

分级是资源分配的决策依据，不能理解为机械的死板标签：

- **T1（综合评估后建议优先/尽快处理）**：
  - *通用特征*：证据充分、简单易修、ROI 高、风险低、复杂度可控。
  - *场景自适应*：
    - 体验审查中：指严重影响决策但修复直接的口径矛盾、高价值指标缺失；
    - 架构审计中：指改动边界清晰、有把握快速修正的架构坏味道或并发小漏洞；
    - 代码清理中：可进一步细化为 T1-A（零风险直接修）、T1-B（机械等价清理）、T1-C（单点结构性简化）；
    - 网关/热路径中：要求**必须提供可直接落地的修复建议与验证命令**。
- **T2（建议排期/待办）**：
  - *通用特征*：收益成立，但存在设计权衡、依赖外部模块、需要较大改动成本或轻微破坏性风险。
- **T3（暂缓/不改/刻意取舍）**：
  - *通用特征*：收益不抵风险，或经评估确认当前现状属于合理的刻意取舍（Deliberate non-fix），陈述充分理由后维持现状。

**统一元数据字段要求**：
每一条记录在报告中的问题/建议，均需覆盖以下字段：
`编号`、`梯队/分类`、`标题`、`证据锚点 (文件与符号/视图名)`、`影响/价值`、`建议方案`、`成本与风险`、`依赖`。

### 3.4 执行协议与自主决策机制

1. **启动阶段：非阻塞 Debrief**
   - 在正式执行前，Prompt 要求输出简短 Debrief，陈述对范围、重点与计划的理解；
   - **协议铁律**：Debrief 属于告知性输出。只要不存在必须用户确认的阻断性事项，直接推进到下一阶段，不等待用户回复。
2. **执行阶段：自主推进与留档升级**
   - **可自决事项**：事实清楚、证据确凿、风险可控的操作与记录，自行决策执行；
   - **升级留档事项**：对于方案各有优劣、涉及业务战略取舍或潜在破坏性改动的疑难点，一律不动手、不向用户临时提问，规范化登记入报告中的“待用户决策清单”。
3. **对话交付：双层交付协议**
   - **盘上成果**：完整的深度分析、评估矩阵、图表与分级方案写入仓库根目录的 Markdown 报告文件；
   - **对话输出**：对话界面仅提供极简总结（报告路径 + 核心要点提炼），不刷屏输出全文，保持上下文清爽。

### 3.5 多 Agent / Subagent 协同边界

若 Prompt 支持或要求使用 Subagent（例如结合 `run-subagent` 体系）：
1. **任务自包含**：每个子任务必须拥有明确的上下文与输入输出契约。
2. **只读任务范围正交**：纯审查任务中，各 Worker 的审查白名单必须精确到文件或目录路径，严禁两路 Worker 范围重叠产生冗余。
3. **写任务严格隔离**：涉及代码修改的任务，派发 Subagent 必须通过 Git worktree 等机制实现物理隔离，禁止多会话在同一工作区并发写。
4. **谁派发谁验收**：主控负责汇总去重，子任务的过程发现沉淀到工作区 `findings.md`，由主控综合提炼，不为并发而并发。

## 四、Prompt 编写与审查 Checklist

在设计新的 Prompt 或评审既有 Prompt 时，请对照以下清单逐项检验：

- [ ] **定位清晰度**：是否明确了执行者的专业角色、审阅视角的最高基准（第一性原理/用户诉求/架构纯洁性）？
- [ ] **查重与尊重历史**：是否前置要求通读既有权威文档（如 `KNOWN_ISSUES`），避免把已有权衡当新发现？
- [ ] **反八股检验**：最终报告的章节划分是否根据当前任务的业务与技术特性实事求是地设计？是否存在生硬套用统一标题的八股现象？
- [ ] **反流水账检验**：是否明确禁绝了工具调用和操作步骤的流水账描述？是否要求正文从过程文件中提炼实质要点？
- [ ] **详略得当与 ROI**：是否强调了对次要问题简述、重要与关键问题深入展开根因剖析与建议方案？
- [ ] **开放性留白空间**：报告结构是否预留了“其他补充事项 (Other Observations / Everything Else)”章节，为超出初始计划但极具价值的偶发洞见留出表达空间？
- [ ] **T1 定义的场景适配**：T1 是否基于综合分析（高 ROI、低风险、易修、证据充分）进行了恰当的场景细化？
- [ ] **目录边界与例外**：是否简化采用 `.gitignore` 作为统一忽略边界？若有数据输入源或产物保留，是否有清晰的例外说明？
- [ ] **过程文件生命周期**：过程产物是否严格限制在 `_tmp/<task>-<model-slug>-<timestamp>/` 内？是否约定任务结束即刻删除？
- [ ] **自主与交互流畅度**：Debrief 是否为非阻塞协议？是否明确禁止执行中途向用户频繁发问，改为问题升级留档？
- [ ] **多 Prompt 对称性**：涉及姊妹文件共用的小节（范围约束、协作机制、产物命名、问题分级、交付协议），其核心契约与底层原则是否保持同步一致？
