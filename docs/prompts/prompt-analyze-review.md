# 角色与目标
你将扮演系统分析与体验评估专家。请先查阅项目文档与 CLI 帮助信息，确认全量分析报告（包含 Markdown 与 HTML 等格式）的生成规范；随后利用 `logs/` 目录下的已有日志生成全套分析产物，并以**最终使用者（User）视角**对生成的报告进行全面深入的 Review，最终沉淀一份包含执行过程与改进建议的完整评估文档。

---

## 范围与环境约束
1. **第一性原理与独立判断（从用户真实诉求出发）**：
   - 审阅时请以**第一性原理与最终用户的真实业务/决策诉求**为最高基准，不受系统当前实现限制，也不要被历史设计文档或注释中的既有定论所束缚。
   - 只要有理有据，应敢于挑战现有报告的布局、指标定义与呈现形式，客观指出关键信息缺失或体验断层。
2. **聚焦生产与分析产物**：审阅聚焦在生成的分析报告、相关业务代码、配置文件及分析设计文档，默认忽略测试代码（如 `*_test.go`），避免无关干扰并显著节约 Token。
3. **忽略目录**：严禁读取或修改 `_tmp/` 和 `archived/` 目录下的任何文件，视其不存在。
4. **资源与耗时**：本任务为长耗时分析任务，可按需持续占用计算资源直至所有流程执行完毕。
5. **Token 与效率控制**：
   - 所有的思考过程（Thinking）与回复输出（Response）保持紧凑精炼、逻辑明确，不冗余客套。
   - 工具调用尽量批量化合并处理，减少来回往返频次，在保证分析深度的前提下最大化节约 Token。

---

## 协作机制与过程产物管理

1. **过程产物与进度跟踪**：
   - 为避免长周期审查中的上下文丢失，请建立**轻量级进度跟踪机制**（如使用进度表文件标记生成与阅读阶段）。
   - 过程记录重在状态跟踪与关键点备忘，详实的审阅成果与改进建议直接归集到主报告中，避免双重维护的冗余开销。
2. **合理启用 Subagent**：
   - 在适合的场景下（例如：并行抽样审阅不同维度的报告/HTML/Journey 叙事、深挖特定复杂报表结构等），**积极利用 Subagent 进行分工协作**。
   - 借助 Subagent 保持主会话上下文整洁，并提炼关键发现沉淀至主报告。

## 执行步骤

### 阶段一：文档调研与执行计划制定
1. 查阅相关设计文档及命令行帮助（`--help`），理清所有可生成的报告类型、维度及参数组合。
2. 在项目根目录（或指定目录）创建主 Markdown 文档（如 `ANALYZE_REVIEW_REPORT_<MODEL>_<DATE>.md`）作为统一的**执行与评估主文档**，并初始化进度跟踪。
3. 在该文档中列出完整的待生成报告清单与初始执行计划。

### 阶段二：全量生成示例报告
- 基于 `logs/` 目录下的现有日志数据，执行完整命令生成全套报告（覆盖所有 HTML、Markdown 及细分视图）。

### 阶段三：制定结构化 Review 计划
1. 扫描报告输出目录的完整层级，提取全量文件清单并记录在主文档中。
2. 制定分阶段的 Review 路线与抽样策略：
   - 按报告类型/功能模块分批次阅读。
   - **代表性抽样**：对于同类型、结构重复的 Markdown/HTML，选取具有代表性的若干份进行深入审阅即可，避免无意义的同质复读。

### 阶段四：从用户视角开展多维度 Review
在主文档中分批记录审阅发现，重点聚焦以下维度：
1. **信息价值与完整性**：
   - 报告提供的信息是否具备实际业务/决策价值？
   - 相关专业术语与指标定义是否清晰易懂？
   - 是否存在用户强烈需要但当前报告缺失的关键信息（纯从用户诉求出发，无需受限于当前系统后端能力）。
2. **布局与可视化合理性**：
   - 对比分析（Compare）是否做到直观的双栏/多维对照？
   - 多分支、深层级的调用链路或树状结构，是否采用了合理的树形可视化、展开/折叠等易读交互？
   - 整体信息流与排版是否符合直觉、清晰易读。
3. **逻辑一致性与错误排查**：
   - 检查是否存在事实错误、逻辑矛盾、数据口径不一致、表达瑕疵或排版错乱。

### 阶段五：全景总结与综合改进建议
在主文档末尾完成全景总结，内容必须包含：
1. **整体价值与用户体验评估**（核心优势与当前体验痛点）。
2. **关键信息缺口与问题清单（Gap Analysis）**（建议采用表格，明确问题/缺口编号、涉及视图、缺口描述、用户影响与优先级）。
3. **结构、布局与可视化优化建议**（鼓励结合 **Mermaid 流程图/布局示意图** 说明期望的对比布局、交互流或数据展示原型）。

## 交付与启动协议
- **主文档结构**：必须包含 1. 执行计划与文件清单 -> 2. 生成过程记录 -> 3. 分批 Review 详细记录 -> 4. 用户视角价值与缺口总结 -> 5. 综合改进建议（含 Mermaid 优化示意）。
- **文件命名规范**：所有新建文档，文件名中建议带上 LLM 模型名称和当前日期作为后缀（如 `ANALYZE_REVIEW_REPORT_<MODEL>_<DATE>.md`）。
- **任务Debrief**：在正式开始前，请先输出简短的 Debrief（确认你对任务目标、约束、执行步骤、Subagent 协同与代表性抽样策略的理解，并说明是否有任何疑问）。
