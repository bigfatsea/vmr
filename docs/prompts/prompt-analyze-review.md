# 角色与目标
你将扮演系统分析与体验评估专家。请先查阅项目文档与 CLI 帮助信息,确认全量分析报告(包含 Markdown 与 HTML 等格式)的生成规范;随后利用 `logs/` 目录下的已有日志生成全套分析产物(默认全量套件,以及 `-journey`/`-compare`/`-benchmark` 各聚焦视图),并以**最终使用者(User)视角**对生成的报告进行全面深入的 Review,最终把发现分流沉淀进项目既有的权威文档体系(见执行步骤·阶段五)。

---

## 范围与环境约束
1. **第一性原理与独立判断(从用户真实诉求出发)**:
   - 审阅时请以**第一性原理与最终用户的真实业务/决策诉求**为最高基准,不受系统当前实现限制,也不要被历史设计文档或注释中的既有定论所束缚。
   - 只要有理有据,应敢于挑战现有报告的布局、指标定义与呈现形式,客观指出关键信息缺失或体验断层——但推翻 `KNOWN_ISSUES` 中已有的刻意取舍前,必须先引用它、给出新证据。
2. **开工前对齐既有权威文档**:通读 `KNOWN_ISSUES`(已知问题与刻意取舍)与 `ROADMAP`(分析半区尚未建成的功能清单)。本次发现如果是"现有报告有缺陷/不一致",先查 `KNOWN_ISSUES` 是否已追踪;如果是"用户想要但还没有的能力",先查 `ROADMAP` 是否已登记——避免把已追踪的问题当新发现重新论证。
3. **聚焦生产与分析产物**:审阅聚焦在生成的分析报告、相关业务代码、配置文件及分析设计文档,默认忽略测试代码(如 `*_test.go`),避免无关干扰并显著节约 Token。
4. **忽略目录**:严禁读取或修改 `_tmp/` 和 `archived/` 目录下的任何文件,视其不存在(本任务自身写入 `_tmp/` 的过程文件除外)。
5. **资源与耗时**:本任务为长耗时分析任务,可按需持续占用计算资源直至所有流程执行完毕。
6. **Token 与效率控制**:
   - 所有的思考过程(Thinking)与回复输出(Response)保持紧凑精炼、逻辑明确,不冗余客套。
   - 工具调用尽量批量化合并处理,减少来回往返频次,在保证分析深度的前提下最大化节约 Token。

## 协作机制与过程产物管理

1. **过程产物只进 `_tmp/`,任务完成即删**:建立轻量级进度跟踪文件 `_tmp/review_progress_analyze_<model>_<date>.md`(`_tmp/` 已被 `.gitignore` 排除),标记生成与阅读阶段、待读清单、阶段性发现暂存;任务完成后删除。
2. **合理启用 Subagent**:
   - 在适合的场景下(例如:并行抽样审阅不同维度的报告/HTML/Journey 叙事、深挖特定复杂报表结构等),**积极利用 Subagent 进行分工协作**。
   - 借助 Subagent 保持主会话上下文整洁,并提炼关键发现沉淀至过程文件。

## 执行步骤

### 阶段一:文档调研与执行计划制定
1. 查阅相关设计文档、`KNOWN_ISSUES`、`ROADMAP` 及命令行帮助(`--help`),理清所有可生成的报告类型、维度及参数组合(默认全量套件,以及 `-journey`/`-compare`/`-benchmark` 各聚焦视图)。
2. 初始化 `_tmp/` 过程跟踪文件,列出完整的待生成报告清单与初始执行计划。
3. **输出任务 Debrief**:向用户简要说明你对任务目标、约束、执行步骤、Subagent 协同与代表性抽样策略的理解,并说明是否有任何疑问,确认后进入下一阶段。

### 阶段二:全量生成示例报告
1. 基于 `logs/` 目录下的现有日志数据,分别执行默认全量命令与 `-journey`/`-compare`/`-benchmark` 各聚焦命令,生成全套报告(覆盖所有 HTML、Markdown 及细分视图)。
2. **如实记录,不臆造**:若 `logs/` 现有数据不足以驱动某类报告或视图(如缺少可比较的多任务样本),如实记录跳过原因,不得为凑齐清单而构造数据或假设结果。

### 阶段三:制定结构化 Review 计划
1. 扫描报告输出目录的完整层级,提取全量文件清单并记录在过程文件中。
2. 制定分阶段的 Review 路线与抽样策略:
   - 按报告类型/功能模块分批次阅读。
   - **代表性抽样**:对于同类型、结构重复的 Markdown/HTML,选取具有代表性的若干份进行深入审阅即可,避免无意义的同质复读。
   - **双语覆盖**:分析半区的输出是 EN/ZH 双语(`internal/i18n`),抽样时至少各挑一份同类报告的中英文版本对照检查,而不是只读默认语言。

### 阶段四:从用户视角开展多维度 Review
在过程文件中分批记录审阅发现,重点聚焦以下维度:
1. **信息价值与完整性**:
   - 报告提供的信息是否具备实际业务/决策价值?
   - 相关专业术语与指标定义是否清晰易懂?
   - 是否存在用户强烈需要但当前报告缺失的关键信息(纯从用户诉求出发,无需受限于当前系统后端能力)。
2. **布局与可视化合理性**:
   - 对比分析(Compare)是否做到直观的双栏/多维对照?
   - 多分支、深层级的调用链路或树状结构,是否采用了合理的树形可视化、展开/折叠等易读交互?
   - 整体信息流与排版是否符合直觉、清晰易读;中英文两版是否表意一致、排版对齐。
3. **逻辑一致性与错误排查**:
   - 检查是否存在事实错误、逻辑矛盾、数据口径不一致、表达瑕疵或排版错乱。

### 阶段五:结论沉淀(不新开报告,直接落进既有权威文档)
本阶段不产出新的仓库常驻报告文件,而是按发现性质分流:

1. **功能缺口 → `ROADMAP`**:用户真实需要、但当前系统尚不具备的能力(新视图/新指标/新导出),按其现有分类(新视图/新信号/新导出格式)追加条目,写明现状、可能方案与触发条件;追加前检索是否已有相近条目。
2. **现有产物的缺陷与不一致 → `KNOWN_ISSUES`**:已生成报告中的事实错误、逻辑矛盾、口径不一致、体验断层(布局、可视化、双语不一致等),按其 §1/§2 既有惯例登记为刻意取舍或待定问题。两类性质不同,不要混进同一张清单——`ROADMAP` 自身的维护原则强调"混进同一张清单会让技术债读起来比实际长"。
3. **对话最终交付**:整体价值与体验评估、Gap Analysis 全景(问题/缺口编号、涉及视图、缺口描述、用户影响与优先级)、结构/布局/可视化优化建议(含 Mermaid 示意图),作为本次任务的最终回复呈现(必要时发布为 Artifact),不落盘为仓库文件。
