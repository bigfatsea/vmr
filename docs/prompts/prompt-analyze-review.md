# 角色与目标
你将扮演系统分析与体验评估专家。请先查阅项目文档与 CLI 帮助信息,确认全量分析报告(包含 Markdown 与 HTML 等格式)的生成规范;随后利用 `logs/` 目录下的已有日志生成全套分析产物(默认全量套件,以及 `-journey`/`-compare`/`-benchmark` 各聚焦视图),并以**最终使用者(User)视角**对生成的报告进行全面深入的 Review,最终把发现整理进统一的交付报告(见执行步骤·阶段五)。

---

## 自主决策与问题升级(主控与 Subagent 共同遵守)
任务全程**严禁中断进程向用户提问或请求确认**,决策规则如下:
1. **可自行决策**:对事实清楚、证据确凿、风险可控的事项(抽样范围调整、分析维度权衡、报表缺陷定性、文档/文案纰漏等),依据第一性原理与用户诉求**自行决策并形成分析结论**,决策依据记录到工作区过程文件即可。
2. **必须升级留档**:高风险、涉及深层业务定位取舍或需负责人裁决的宏观争议(T2/T3),**一律不中断发问**,统一登记到交付报告中的"待用户决策清单/建议"(含事项描述、各方案权衡与倾向性建议),留待任务结束后由用户统一裁决。
3. **登记优先于询问**:任何时刻遇到两难,先登记留档、继续推进其余可独立开展的审阅工作,绝不为等待答复而阻塞流水线。
4. **对 Subagent 同样生效**:Worker 级别的无把握事项写入工作区 `findings.md` 交主控裁决;主控亦无把握的,按第 2 条升级留档——任何一级 Agent 都不得向用户直接发问。

## 范围与环境约束
1. **第一性原理与独立判断(从用户真实诉求出发)**:
   - 审阅时请以**第一性原理与最终用户的真实业务/决策诉求**为最高基准,不受系统当前实现限制,也不要被历史设计文档或注释中的既有定论所束缚。
   - 只要有理有据,应敢于挑战现有报告的布局、指标定义与呈现形式,客观指出关键信息缺失或体验断层——但推翻 `KNOWN_ISSUES` 中已有的刻意取舍前,必须先引用它、给出新证据。
2. **开工前对齐既有权威文档**:通读 `KNOWN_ISSUES`(已知问题与刻意取舍)与 `ROADMAP`(分析半区尚未建成的功能清单),避免把已追踪的问题当新发现重新论证;本任务全程只读,不修改已有文档与代码,它们仅作查重与背景参考。
3. **聚焦分析产物本身**:审阅对象以生成的分析报告(HTML/Markdown/JSON 产物)与 `internal/i18n` 双语文案为主;业务代码与配置文件仅在需要核实报告数字口径、追溯呈现逻辑时**按需查阅**,不对其做代码质量审查(那属于 prompt-full-review / prompt-routing-review 的职责),默认忽略测试代码(如 `*_test.go`)。
4. **忽略目录**:所有被仓库 `.gitignore` 忽略的内容(含 `_tmp/`、`archived/`、`logs/`、`reports/` 等生成物目录及仓库根的构建产物如 `vmr` 二进制)一律视为不存在,不读取、不审阅、不修改(本任务自身写入工作区 `_tmp/` 的过程文件除外)。**例外条款(本任务特有)**:`logs/` 下的审计日志是本任务的数据输入源,必须读取;`vmr analyze` 生成的 `reports/` 报告产物是本任务的审阅对象,且为交付给用户的成果——**保留在 `reports/` 供用户查看,任务不负责清理**。
5. **资源与耗时**:本任务为长耗时分析任务,可按需持续占用计算资源直至所有流程执行完毕。
6. **Token 与效率控制**:
   - 所有的思考过程(Thinking)与回复输出(Response)保持紧凑精炼、逻辑明确,不冗余客套。
   - 工具调用尽量批量化合并处理,减少来回往返频次,在保证分析深度的前提下最大化节约 Token。

## 协作机制与多 Agent 分工

1. **过程产物只进 `_tmp/`,任务完成即删**:按《产物命名与存储规范》建立任务工作区,进度(`progress.md`)与阶段性发现(`findings.md`)都落在工作区内(`_tmp/` 已被 `.gitignore` 排除);任务完成后删除整个工作区。阶段二生成在 `reports/` 下的报告产物不属于过程产物,保留在 `reports/` 供用户查看。
2. **合理启用 Subagent**:
   - 在适合的场景下(例如:并行抽样审阅不同维度的报告/HTML/Journey 叙事、深挖特定复杂报表结构等),**积极利用 Subagent 进行分工协作**。
   - **分工正交性建议**:按分析视图类型划分互不重叠的审查范围(例如:Worker A 审阅 Macro 宏观指标与口径、Worker B 审阅 Task/Journey 链路叙事与树形调用结构、Worker C 审阅 Compare 与 Benchmark 对比基准、Worker D 审阅双语对照与文案排版质量)。
   - **编排方式**:若当前环境已装配 `run-subagent` Skill(项目 `.pi/skills/run-subagent/SKILL.md`),按其方法论执行派发与回收(触发三问、验收四查);未装配时按常规 Subagent 方式运作。底线一致:派发任务自包含、只读任务无需 worktree 隔离、谁派发谁验收、不为并行而并行。
   - 借助 Subagent 保持主会话上下文整洁,并提炼关键发现沉淀至工作区 `findings.md`。

## 产物命名与存储规范(全局统一)
所有提示词共用以下命名规则,避免中间产物散落与随意命名:
- **任务工作区**:`_tmp/<task>-<model-slug>-<timestamp>/`,本任务 `<task>` 固定为 `analyze-review`。工作区目录名统一承载模型名与时间戳,目录内文件使用固定语义名,不再重复后缀。
- **`<model-slug>`**:当前 LLM 模型名清洗为文件名安全形式(转小写,`/`、`: `、空格等替换为 `-`)。
- **`<timestamp>`**:任务开始时刻,格式 `YYYYMMDD-HHMMSS`,全程固定不变。
- **过程文件管理**:过程文件一律放在任务工作区内,严禁散落在 `_tmp/` 根目录或仓库其他位置。标准过程文件为 `progress.md`(进度与执行状态)与 `findings.md`(阶段性发现与要点),各任务意涵、用途相同的文件尽量统一使用同一名字;任务有额外需求时可增补语义化的任务特有文件,名字允许不同,但意涵、用途相同者优先统一。
- **只读原则**:本任务全程只读——不修改任何已有文档(包括 `KNOWN_ISSUES`、`ROADMAP`、`CHANGELOG.md` 及设计文档等)和任何代码;唯一的写操作是 `_tmp/` 工作区内的过程文件、最终交付报告以及阶段二执行 `vmr analyze` 输出到 `reports/` 的审阅对象产物。
- **收尾**:任务完成后删除整个工作区;交付报告在删除前已按阶段五撰写并保留在仓库根目录。
- **最终交付报告**:任务完成后在仓库根目录新建 `ANALYZE_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`,承载阶段五的全部结论与完整评估叙事。最终交付报告定位为内容自包含、深度严谨的独立报告,拒绝流水账式的操作过程复述;其内在逻辑为:开头清晰阐明任务目标、要点与具体计划,正文围绕具体计划展开并提炼过程文件中的实质要点,随后对全过程做综合总结与评估,最终按合理逻辑给出分级清单与 ROI 评估(详略得当,重要与关键事项做深度根因剖析与建议方案);各任务根据自身技术与业务特性因地制宜设计章节,不搞机械教条的八股结构。
- **对话最终交付**:对话中仅给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准。

## 问题列表统一分级(T1/T2/T3)
最终交付的问题列表必须按处理优先级分梯队,同一梯队内按"收益/成本"降序:
- **T1 强烈建议**:经综合分析后建议尽快处理的事项。T1 不是单一硬指标,通常表现为:证据充分、简单易修、ROI 高、风险低、复杂度可控;不同任务可按自身特点酌情收严或细化(见各提示词的具体约定)。本任务中重点表现为:严重影响管理与运维决策的指标口径自相矛盾、高价值指标或核心链路信息缺失、图表与关键交互断层、易修且收益显著的体验硬伤;
- **T2 建议排期**:收益成立,但存在权衡、依赖或可观成本,登记为待办;
- **T3 暂缓/不建议**:低 ROI、高风险,或与既有刻意取舍一致——写明理由后不动。
每条统一字段:**编号(如 T1-1)、梯队、标题、证据锚点(文件与符号,或报告视图名)、影响/用户价值、建议方案、成本与风险、依赖**。

## 执行步骤

### 阶段一:文档调研与执行计划制定
1. 查阅相关设计文档、`KNOWN_ISSUES`、`ROADMAP` 及命令行帮助(`--help`),理清所有可生成的报告类型、维度及参数组合(默认全量套件,以及 `-journey`/`-compare`/`-benchmark` 各聚焦视图);核实当前仓库 `./vmr` 二进制可用性,必要时先运行只读命令 `go build -o vmr ./cmd/vmr` 确保与当前代码对齐。
2. 按《产物命名与存储规范》初始化任务工作区(`progress.md`、`findings.md`),列出完整的待生成报告清单与初始执行计划。
3. **输出任务 Debrief**:向用户简要说明你对任务目标、约束、执行步骤、Subagent 协同与代表性抽样策略的理解。若无必须等待用户确认的重要事项,直接进入下一阶段;仅当存在重要事项需要用户确认,且必须等待用户确认后才能执行后续步骤时,才停下来等待确认。

### 阶段二:全量生成示例报告
1. 基于 `logs/` 目录下的现有日志数据,分别执行默认全量命令与 `-journey`/`-compare`/`-benchmark` 各聚焦命令,生成全套报告(覆盖所有 HTML、Markdown 及细分视图)。
2. **如实记录,不臆造**:若 `logs/` 现有数据不足以驱动某类报告或视图(如缺少可比较的多任务样本),如实记录跳过原因,不得为凑齐清单而构造数据或假设结果。

### 阶段三:制定结构化 Review 计划
1. 扫描报告输出目录的完整层级,提取全量文件清单并记录在工作区 `progress.md` 中。
2. 制定分阶段的 Review 路线与抽样策略:
   - 按报告类型/功能模块分批次阅读。
   - **代表性抽样**:对于同类型、结构重复的 Markdown/HTML,选取具有代表性的若干份进行深入审阅即可,避免无意义的同质复读。
   - **双语覆盖**:分析半区的输出是 EN/ZH 双语(`internal/i18n`),抽样时至少各挑一份同类报告的中英文版本对照检查,而不是只读默认语言。

### 阶段四:从用户视角开展多维度 Review
在工作区 `findings.md` 中分批记录审阅发现,重点聚焦以下维度:
1. **信息价值与完整性**:
   - 报告提供的信息是否具备实际业务/决策价值?
   - 相关专业术语与指标定义是否清晰易懂?
   - 是否存在用户强烈需要但当前报告缺失的关键信息(纯从用户诉求出发,无需受限于当前系统后端能力)。
2. **布局与可视化合理性**:
   - 对比分析(Compare)是否做到直观的双栏/多维对照?
   - 多分支、深层级的调用链路或树状结构,是否采用了合理的树形可视化、展开/折叠等易读交互?
   - 整体信息流与排版是否符合直觉、清晰易读;中英文两版是否表意一致、排版对齐。
3. **逻辑一致性与错误排查**:
   - 检查是否存在事实错误、逻辑矛盾、数据口径不一致、表达瑕疵或排版错乱。

### 阶段五:撰写交付报告(不修改任何已有文档与代码)
本阶段不修改 `KNOWN_ISSUES`/`ROADMAP`/`CHANGELOG.md` 等任何已有文档,也不修改任何代码;全部结论统一整理进新建的交付报告:

1. **撰写交付报告**:按《产物命名与存储规范》在仓库根目录新建 `ANALYZE_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`。报告必须是一份自包含、专业深入的独立评估报告,**严禁流水账式的工具调用与操作过程复述**。报告紧扣用户体验与决策诉求,推荐按以下专业章节展开:
   - **审阅范围与评估计划 (Review Scope & Evaluation Plan)**:清晰交代本次任务目标(用户视角审阅分析体系全景)、输入数据源规模、覆盖的命令与产物清单(默认全量套件及各聚焦视图)、具体审阅计划(多维抽样策略、双语对照方案与 Subagent 协同分工);
   - **各分析视图审阅要点 (Detailed View-by-View Findings)**:按具体报表类型展开,从过程文件(`findings.md`)中提炼关键要点——Macro 宏观指标的决策价值与口径一致性、Journey 链路叙事与树形调用可读性、Compare/Benchmark 视图的多维对比效果、双语表达与排版渲染质量;
   - **分析套件整体体验综合评估 (Holistic UX Assessment)**:对整个审阅过程进行提炼总结,汇总各环节要点,从用户真实决策场景出发客观评定现有报表体系的整体成熟度、关键断层与信息盲区;
   - **优化建议与分级清单 (Prioritized Recommendations)**:按 T1/T2/T3 梯队编排,每项均给出明确描述与 ROI 评估——简单或次要问题简述,重要体验硬伤详述,关键缺陷给出根因剖析与改进方案;与 `KNOWN_ISSUES`/`ROADMAP` 既有条目重合的标注索引;
   - **布局与可视化重构提案 (Layout & Visualization Proposals)**:针对复杂调用树、双栏对比等痛点提出具体的可视化交互改善构想(附带 Mermaid 示意图);
   - **其他补充事项 (Other Observations & Everything Else)**:为 Reviewer 与执行 Agent 预留的开放空间,记录过程中发掘的超出上述预设框架或维度的额外有价值发现(如 CLI 工具易用性、日志采样建议、端到端测试体验等)。只要有实际价值,均可在此畅所欲言。
2. **对话最终交付**:任务完成后在对话中给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准,不落盘为其他仓库文件。
3. 删除任务工作区。

## 交付与启动协议
- **交付形态**:仓库根目录新建的 `ANALYZE_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`(承载阶段五的完整评估叙事、各视图要点剖析与分级优化建议)+ 对话中的精炼总结;全程只读,不修改任何已有文档与代码。生成的 `reports/` 报告产物保留供用户查看。
- **过程产物**:统一落在任务工作区 `_tmp/analyze-review-<model-slug>-<timestamp>/`,过程文件均在其中,任务完成后删除工作区(见《产物命名与存储规范》)。
- **任务 Debrief**:见阶段一第 3 步;若无重要事项需要用户确认,直接进入下一步;仅当有重要事项必须确认后才能执行时才停下来等待确认。
