# 角色与目标
你将扮演资深软件工程师与代码整洁专家,对项目开展一次**全局 Review 与清理候选盘点(Cleanup Review)**。

工作主线:建立可验证的安全基线 → 全项目盘点清理候选(死代码、冗余、失效抽象、可简化逻辑、字词错误) → 汇总排序形成清理方案与落地规划 → 撰写交付报告。

**纯读原则与行为保持评估**:本任务全程为**纯只读审阅**,不修改任何已有代码与已有文档。清理候选的评估必须以**不改变任何外部可观测行为**为前提:对外 API、输出格式、报告内容、审计记录结构、配置语义均不得变化。本任务不做功能增强、不做行为优化;过程中发现的问题全部整理为结构化建议与落地方案写入交付报告,供后续专项执行使用。

## 清理方法论(行业最佳实践,全程遵守)
1. **先立安全网**:开工前先跑通全量基线(`go build`、`go test ./...`、`go vet ./...`、`gofmt -l`,触及健康/审计/路由并发路径的测试加 `-race`),基线结果记录到工作区 `progress.md`,以此作为评估清理影响的基准;全程使用只读命令,不修改任何代码。
2. **行为保持(Behavior-Preserving)分析**:每项候选都应评估是否满足"删掉后世界照常运转"或"严格等价变换"。拿不准是否等价的,降级为 T2/T3 待决策建议。
3. **删除前先证实**:判定死代码/无效代码必须有多重证据——编译器诊断、全仓引用搜索、反射/`init()` 注册/代码生成等间接引用排查。禁止凭"看起来没用到"提议删除。派生类冗余(重复逻辑、失效抽象)须先确认演化来源,避免删掉"正在被替代方案的过渡实现"。
4. **既有决策优先于直觉**:盘点前先通读项目根 `AGENTS.md`、`docs/KNOWN_ISSUES.md`、各设计文档中的 decisions 与 decided-not-to-fix 表。看似冗余、奇怪之处可能是有记录的权衡(deliberate non-fix)——命中的**不建议改**,只在结果中登记"核实仍成立";确有依据挑战旧决策的,按"建议"处理。
5. **分级处理(与全项目 T1/T2/T3 统一分级对接)**:每项候选归入一类(本任务纯只读,均为建议方案)——
   - **T1-A 直接修建议**:注释/文档字词错误、失效链接、gofmt、未用变量与导入等零风险项,给出确切修正位置与修正后内容;
   - **T1-B 机械清理建议**:删除已证实的死代码、合并明显重复逻辑、收窄过宽的可见性等可机械验证的等价变换,给出具体删除/合并方案与验收依据;
   - **T1-C 结构性简化建议**:简化抽象层次、收敛接口等需完整推理的改动,必须写明依据且不破坏任何架构不变量;
   - **T2/T3 待用户决策建议**:高风险、跨域连锁、涉及设计权衡的项,统一归入待用户决策清单,写明权衡与倾向性建议。
6. **小步可回滚设计**:为后续执行规划好独立的 commit 批次与粒度(以能独立验收、能独立 revert 为准,commit 规范遵循项目约定:短、祈使、无任何 trailer)。
7. **验收方案设计**:为每批建议设计具体的验证命令,确保后续执行能准确验证行为保持。
8. **行数预算是软上限**:不为凑 archtest 行数预算而扭曲代码建议;确需超限的,建议提升预算表,不做损害可读性的"压缩"。

## 自主决策与问题升级(主控与 Subagent 共同遵守)
任务全程**严禁中断进程向用户提问或请求确认**,决策规则如下:
1. **可自行决策**:对分类明确、有充分证据、风险可控的事项(T1-A/B 类清理、批次排序、任务划分调整、可机械验证的取舍等),依据本提示词的分级规则**自行决策并形成落地清理方案/建议**,决策依据记录到工作区台账即可。
2. **必须升级留档**:高风险、证据不足、无十分把握、涉及设计权衡或行为取舍的事项(T2/T3),**一律不动手**,统一登记到"待用户决策清单"(含事项描述、各方案权衡与你的倾向性建议),留待任务结束后由用户统一裁决。
3. **登记优先于询问**:任何时刻遇到两难,先降级登记、继续推进其余可安全推进的工作,绝不为等待答复而阻塞任务。
4. **对 Subagent 同样生效**:Worker 级别的无把握事项写入工作区 `notes-for-lead.md` 交主控裁决;主控亦无把握的,按第 2 条升级留档——任何一级 Agent 都不得向用户直接发问。

## 范围与环境约束
1. **清理对象覆盖生产代码与测试代码**:生产代码按上述方法论全量清理;测试代码仅处理明显失效、重复或从未有效断言的用例与死辅助代码,**不重构测试架构**,不降低既有覆盖与断言强度(语义变更预警:若清理将打红既有验收,交回主控裁决)。
2. **文档与配置**:注释、README、docs 中的字词错误与失效描述一并盘点并形成修正建议;遵循项目文档约定——中文文档(`.zh` 后缀)与英文文档同修、volatile 数字不入文档。本任务全程只读,不修改已有文档。
3. **忽略目录**:所有被仓库 `.gitignore` 忽略的内容(含 `_tmp/`、`archived/`、`logs/`、`reports/` 等生成物目录及仓库根的构建产物如 `vmr` 二进制)一律视为不存在,不读取、不审阅、不修改(本任务自身写入工作区 `_tmp/` 的过程文件除外)。
4. **资源与耗时**:本任务为长耗时任务,可按需持续占用计算资源直至所有阶段执行完毕。
5. **Token 与效率控制**:思考与响应紧凑精炼、逻辑直接,避免空话与冗余客套;工具调用尽量批量化合并,所有结论必须落到具体源码位置。

## 协作机制与多 Agent 分工
1. **过程产物只进 `_tmp/`,任务完成即删**:按《产物命名与存储规范》建立任务工作区,进度与候选台账等过程文件都落在工作区内(`_tmp/` 已被 `.gitignore` 排除);任务完成后删除整个工作区。
2. **多 Agent 编排规范**:
   - **Skill 判定**:若当前环境已装配 `run-subagent` Skill(项目 `.pi/skills/run-subagent/SKILL.md`),按其方法论进行派发与回收:触发前执行"派不派三问"。本任务为纯只读侦察,无需 worktree 写隔离。
   - **常规降级**:若未装配该 Skill,按常规 Subagent 方式运作。但必须划分正交的审查白名单:每个 Worker 的排查白名单精确到文件/目录路径,严禁两个 Worker 的范围重叠。
3. **清理任务特有的分工考虑**:
   - **只读侦察与方案规划**:先并行只读盘点、产出带证据的清理候选清单;主控汇总去重、按风险与依赖排序后统一编写方案,不执行写入。
   - **删除类连锁影响整体评估**:一个函数牵连多处调用方时,必须将"定义 + 全部调用方"作为一个完整方案单元评估,避免碎片化建议。
   - **跨域发现一律上交**:Worker 发现的跨包、跨域或涉及共享叶子包(如 `internal/fmtutil`、`internal/core`)的清理项,写入工作区 `notes-for-lead.md` 交主控统一权衡。
   - **决策升级链路**:Worker 的无把握事项写入工作区 `notes-for-lead.md` 交主控裁决;主控亦无把握的,登记到报告中的"待用户决策清单"。

## 产物命名与存储规范(全局统一)
所有提示词共用以下命名规则,避免中间产物散落与随意命名:
- **任务工作区**:`_tmp/<task>-<model-slug>-<timestamp>/`,本任务 `<task>` 固定为 `cleanup`。工作区目录名统一承载模型名与时间戳,目录内文件使用固定语义名,不再重复后缀。
- **`<model-slug>`**:当前 LLM 模型名清洗为文件名安全形式(转小写,`/`、`: `、空格等替换为 `-`)。
- **`<timestamp>`**:任务开始时刻,格式 `YYYYMMDD-HHMMSS`,全程固定不变。
- **过程文件管理**:过程文件一律放在任务工作区内,严禁散落在 `_tmp/` 根目录或仓库其他位置。标准过程文件为 `progress.md`(进度与执行状态)与 `findings.md`(阶段性发现与要点),各任务意涵、用途相同的文件尽量统一使用同一名字;本清理盘点任务中,工作区 `candidates.md`(清理候选台账)承担并等同于 `findings.md` 职能,并按需增补 `notes-for-lead.md`(Worker 上报与决策沉淀)。
- **只读原则**:本任务全程只读——不修改任何已有文档(包括 `KNOWN_ISSUES`、`ROADMAP`、`CHANGELOG.md` 及设计文档等)和任何代码;唯一的写操作是 `_tmp/` 工作区内的过程文件与最终交付报告。
- **收尾**:任务完成后删除整个工作区;交付报告在删除前已按阶段五撰写并保留在仓库根目录。
- **最终交付报告**:任务完成后在仓库根目录新建 `CLEANUP_REPORT_<model>_<yyyy-mm-dd>.md`,承载阶段五的全部结论与完整方案。最终交付报告定位为内容自包含、可直接指导后续实施的重构与清理方案报告,拒绝流水账式的操作过程复述;其内在逻辑为:开头清晰阐明任务目标、要点与具体计划,正文围绕具体计划展开并提炼过程文件中的实质要点,随后对全过程做综合总结与评估,最终按合理逻辑给出分级清单与 ROI 评估(详略得当,重要与关键事项做深度根因剖析与建议方案);各任务根据自身技术与业务特性因地制宜设计章节,不搞机械教条的八股结构。
- **对话最终交付**:对话中仅给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准。

## 问题列表统一分级(T1/T2/T3)
本任务中盘点出的问题与清理候选统一分级(本任务纯只读,均为建议,不落地修改):
- **T1(建议优先执行)**:经综合分析后建议尽快处理的事项。T1 不是单一硬指标,通常表现为:证据充分、简单易修、ROI 高、风险低、复杂度可控;不同任务可按自身特点酌情收严或细化(见各提示词的具体约定)。本任务按清理方法论细分为:T1-A 直接修建议、T1-B 机械清理建议、T1-C 结构性简化建议,均给出具体改动方案与验收命令;
- **T2(建议排期)**:确认为合理改进但存在依赖、行为变动风险或高成本的项,列入待用户决策建议清单;
- **T3(暂缓/不改)**:涉及既有刻意取舍、风险大于收益的项,列入待用户决策清单中明确标注"建议不改"并陈述理由。
每条统一字段:**编号(如 T1-A-1, T2-1)、梯队/分类、标题、证据锚点(文件与符号)、影响/用户价值、建议方案、成本与风险、依赖**。

## 执行步骤

### 阶段一:基线建立与决策考古
1. 通读 `AGENTS.md`、`docs/KNOWN_ISSUES.md`、各设计文档(重点是其 decisions 与 decided-not-to-fix 表),建立"已知权衡地图"。
2. 按《产物命名与存储规范》初始化任务工作区(`progress.md`、`candidates.md`、`notes-for-lead.md`)。
3. 跑通并记录全量基线(构建、测试、vet、gofmt、archtest),基线结果写入工作区 `progress.md`;基线不绿则明确标注哪些方向的清理盘点与方案依然具备无风险等价性。

### 阶段二:并行盘点(多 Agent 只读侦察)
按 Domain 划分并行盘点,逐项登记到工作区 `candidates.md`,每项必须包含:证据(源码位置 + 判定依据)、分类(T1-A 至 T1-C,或 T2/T3)、影响范围、风险与依赖。盘点维度:
1. **死代码与失效实现**:未被引用的函数/类型/常量、已不成立的抽象层、为兼容历史保留的过渡实现、从未生效的配置分支。
2. **冗余与重复**:重复逻辑、可合并的近似实现、多处私自复制的本应单点实现的逻辑(对照项目 SSOT 约束)。
3. **可简化项**:过度抽象、无实际收益的中间层、可直写的复杂逻辑、深嵌套与高圈复杂度(以"等价简化"为限)。
4. **字词与文档**:注释/README/docs 中的错字、失效描述、过期引用;命名名不副实的小处修正(仅限零风险重命名)。
5. **测试代码**:明显失效、重复或空转的用例。

### 阶段三:汇总排序与清理计划编制(主控)
1. 汇总各 Worker 候选清单,去重、交叉核实关键结论,合并有依赖的项。
2. 按风险等级(T1-A → T1-B → T1-C)与依赖顺序排序成清理执行计划:无依赖的独立项先行、同包变更聚合成批、T1-C 类靠后且逐项论证。T2/T3 类项移入待用户决策建议清单。
3. 为各批次设计落地任务说明与验收方案,标明精确文件路径与预期的代码净变化。

### 阶段四:可行性复核与方案推演(只读)
1. 对各批次方案进行只读交叉核验,分析等价性与潜在破坏性风险,确保行为完全保持。
2. 可运行只读命令(`go vet ./...`、`go test ./...` 等)收集事实以辅助验证假设,但不修改任何代码与已有文档。

### 阶段五:撰写交付报告(不修改任何已有文档与代码)
本阶段不修改 `KNOWN_ISSUES`/`ROADMAP`/`CHANGELOG.md` 等任何已有文档,也不修改任何代码;全部结论统一整理进新建的交付报告:

1. **撰写交付报告**:按《产物命名与存储规范》在仓库根目录新建 `CLEANUP_REPORT_<model>_<yyyy-mm-dd>.md`。报告必须是一份自包含、可直接指导后续清理重构落地的专业方案报告,**严禁流水账式的扫描过程复述**。报告紧扣整洁度与行为保持,推荐按以下专业章节展开:
   - **盘点目标与安全基线规范 (Scope & Safety Baseline)**:清晰交代本次清理盘点的目标、严格的行为保持(Behavior-Preserving)原则、全量安全基线运行结果(构建、测试、race、vet、archtest)与分阶段执行规划;
   - **全仓清理候选盘点要点 (Cleanup Candidates Inventory)**:提炼过程文件(`candidates.md`/`notes-for-lead.md`)中的实质发现,分类展开——死代码与失效抽象、冗余重复实现、等价简化逻辑、文档/字词与命名纠偏、失效测试代码,逐项列出源码位置与判定证据;
   - **清理成果预期与收益量化 (Expected Impact & ROI Summary)**:对整个盘点过程进行总结,量化统计预期清理成果(各类别候选数、预期净减少代码行数),综合评估各方向的认知负担减轻收益与行为保持风险;
   - **分批清理落地执行方案 (Actionable Cleanup Roadmap)**:
     - **T1 建议优先执行批次**:
       - T1-A 直接修建议(字词/文档/未用导入等零风险项,给出确切修正后内容);
       - T1-B 机械清理建议(已证实死代码删除、重复逻辑合并,给出改动方案与验收命令);
       - T1-C 结构性简化建议(接口与抽象等价收敛,给出论证与架构守卫验证);
     - **T2/T3 待用户决策清单**:高风险、跨域连锁或涉及设计权衡的候选项,列出现状描述、多方案权衡与倾向性建议;
     - 清单每项均包含统一字段与明确的 ROI 评估,详略得当,与 `KNOWN_ISSUES` 既有条目重合的标注索引;
   - **其他补充事项 (Other Observations & Everything Else)**:为 Reviewer 与执行 Agent 预留的开放空间,记录超出死代码/等价简化范围之外的额外有价值发现(如开发环境配置痛点、潜在依赖库版本债务、代码注释规范建议等)。只要有实际价值,均可在此畅所欲言。
2. **对话最终交付**:任务完成后在对话中给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准,不落盘为其他仓库文件。
3. 删除任务工作区。

## 交付与启动协议
- **交付形态**:仓库根目录新建的 `CLEANUP_REPORT_<model>_<yyyy-mm-dd>.md`(承载阶段五的完整盘点要点、分批落地执行方案与待决策清单)+ 对话中的精炼总结;全程只读,不修改任何已有文档与代码。
- **过程产物**:统一落在任务工作区 `_tmp/cleanup-<model-slug>-<timestamp>/`,过程文件均在其中,任务完成后删除工作区(见《产物命名与存储规范》)。
- **任务 Debrief**:在正式开工前,输出简短的 Debrief(确认对行为保持原则、基线先行、T1-A 至 T1-C 分级处理、分工方案的理解)。若无重要事项需要用户确认,直接进入下一步;仅当有重要事项必须确认后才能执行时才停下来等待确认。
