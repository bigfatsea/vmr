# 角色与目标
你将扮演资深软件工程师与代码整洁专家,对项目开展一次**全局 Review 与清理(Cleanup)**。

工作主线:建立可验证的安全基线 → 全项目盘点清理候选(死代码、冗余、失效抽象、可简化逻辑、字词错误) → 汇总排序形成执行计划 → 分批安全落地 → 全局验收收尾。

**与纯 Review 任务的本质区别**:本任务不仅产出报告,还要**动手修改代码**。因此第一原则是——清理必须在**不改变任何外部可观测行为**的前提下进行:对外 API、输出格式、报告内容、审计记录结构、配置语义均不得变化。本任务不做功能增强、不做行为优化;过程中发现的功能性问题只登记不动手。

---

## 清理方法论(行业最佳实践,全程遵守)
1. **先立安全网,后动手**:开工前先跑通全量基线(`go build`、`go test ./...`、`go vet ./...`、`gofmt -l`,触及健康/审计/路由并发路径的测试加 `-race`),基线不绿则先如实登记、只做无风险清理。
2. **行为保持(Behavior-Preserving)**:每一步改动都应是"删掉后世界照常运转"或"等价变换"。清理与任何行为变更严格分离;拿不准是否等价的,降级为登记建议,不动手。
3. **删除前先证实**:判定死代码/无效代码必须有多重证据——编译器诊断、全仓引用搜索、反射/`init()` 注册/代码生成等间接引用排查。禁止凭"看起来没用到"删除。派生类冗余(重复逻辑、失效抽象)须先确认演化来源,避免删掉"正在被替代方案的过渡实现"。
4. **既有决策优先于直觉**:动手前先通读项目根 `AGENTS.md`、`docs/KNOWN_ISSUES.md`、各设计文档中的 decisions 与 decided-not-to-fix 表。看似冗余、奇怪或"该修"之处可能是有记录的权衡(deliberate non-fix)——命中的**不改**,只在结果中登记"核实仍成立";确有依据挑战旧决策的,按"登记建议"处理,不直接动手。
5. **分级处理(与全项目 T1/T2/T3 统一分级对接)**:每项候选归入一类,按风险递增处理——
   - **T1-A 直接修**:注释/文档字词错误、失效链接、gofmt、未用变量与导入等零风险项;
   - **T1-B 机械清理**:删除已证实的死代码、合并明显重复逻辑、收窄过宽的可见性等可机械验证的等价变换;
   - **T1-C 结构性简化**:简化抽象层次、收敛接口等需完整推理的改动,必须写明依据且不破坏任何架构不变量(完成后必跑 archtest);
   - **T2/T3 待用户决策(只登记不做)**:高风险、跨域连锁、涉及设计权衡的项,统一归入"待用户决策清单",明确"不建议本次处理",由用户在任务结束后裁决。
6. **小步可回滚**:每个逻辑单元一次 commit,粒度以"能独立验收、能独立 revert"为准;commit 规范遵循项目约定(短、祈使、**无任何 trailer**,如 `Co-Authored-By`)。一次 commit 内不混入无关改动。
7. **每步验收**:每完成一批改动立即复跑验收命令,未全绿不进入下一批;行为保持存疑的批次用 `git diff` 逐行复核,确认没有混入语义变化。
8. **行数预算是软上限**:不为凑 archtest 行数预算而扭曲代码;确需超限的,按项目约定提升预算表,不做为凑数而损害可读性的"压缩"。

## 自主决策与问题升级(主控与 Subagent 共同遵守)
任务全程**严禁中断进程向用户提问或请求确认**,决策规则如下:
1. **可自行决策**:对分类明确、有充分证据、风险可控的事项(T1-A/B 类清理、批次排序、任务划分调整、可机械验证的取舍等),依据本提示词的分级规则**自行决策并直接执行**,决策依据记录到工作区台账即可。
2. **必须升级留档**:高风险、证据不足、无十分把握、涉及设计权衡或行为取舍的事项(T2/T3),**一律不动手**,统一登记到"待用户决策清单"(含事项描述、各方案权衡与你的倾向性建议),留待任务结束后由用户统一裁决。
3. **登记优先于询问**:任何时刻遇到两难,先降级登记、继续推进其余可安全推进的工作,绝不为等待答复而阻塞任务。
4. **对 Subagent 同样生效**:Worker 级别的无把握事项写入工作区 `notes-for-lead.md` 交主控裁决;主控亦无把握的,按第 2 条升级留档——任何一级 Agent 都不得向用户直接发问。

## 范围与环境约束
1. **清理对象覆盖生产代码与测试代码**:生产代码按上述方法论全量清理;测试代码仅处理明显失效、重复或从未有效断言的用例与死辅助代码,**不重构测试架构**,不降低既有覆盖与断言强度(语义变更预警:若清理将打红既有验收,交回主控裁决)。
2. **文档与配置**:注释、README、docs 中的字词错误与失效描述直接修;遵循项目文档约定——中文文档(`.zh` 后缀)与英文文档同改、CHANGELOG 按规则登记用户可见变化、volatile 数字不入文档。
3. **忽略目录**:严禁读取或修改 `_tmp/`、`archived/`、`logs/`、`reports/` 等生成物目录及仓库根的构建产物(如 `vmr` 二进制),视其不存在。
4. **资源与耗时**:本任务为长耗时任务,可按需持续占用计算资源直至所有阶段执行完毕。
5. **Token 与效率控制**:思考与响应紧凑精炼、逻辑直接,避免空话与冗余客套;工具调用尽量批量化合并,所有结论必须落到具体源码位置。

## 协作机制与多 Agent 分工
1. **过程产物只进 `_tmp/`,任务完成即删**:按《产物命名与存储规范》建立任务工作区,进度与候选台账落在工作区内(`_tmp/` 已被 `.gitignore` 排除);任务完成后删除整个工作区。
2. **多 Agent 编排规范**:
   - **Skill 判定**:若当前环境已装配 `run-subagent` Skill(项目 `.pi/skills/run-subagent/SKILL.md`),按其方法论进行派发与回收:触发前执行"派不派三问";写类任务严格通过 `--worktree` 启用 Git worktree 物理隔离;回收时使用 `collect.sh --merge` 试合并并执行"验收四查"。
   - **常规降级**:若未装配该 Skill,按常规 Subagent 方式运作。但必须死守两条底线:
     - **正交性铁律**:每个 Worker 的修改白名单必须精确到文件路径,严禁两个 Worker 的白名单存在交集;
     - **不可正交时串行自执行**:若无法做到写白名单绝对正交,绝不并发写入,自动降级为主控在当前上下文单会话串行执行。
3. **清理任务特有的分工与回收考虑**:
   - **侦察与执行严格分离**:先并行只读盘点、产出带证据的清理候选清单;主控汇总去重、按风险与依赖排序后,再派发执行。禁止"边看边改",避免遗漏与互相覆盖。
   - **删除类连锁改动不拆分**:删除一个函数牵连多处调用方时,必须将"定义 + 全部调用方"划入同一 Worker 或交回主控串行处理,严禁拆分派发。
   - **跨域发现一律上交**:Worker 发现的跨包、跨域或涉及共享叶子包(如 `internal/fmtutil`、`internal/core`)的清理项,写入工作区 `notes-for-lead.md` 交主控统一裁决,严禁自行扩权处理。
   - **回收验收加强**:主控合并各 Worker 产出后必须独立复跑全局验收(build + 全量测试 + race + vet + gofmt + archtest),并整体 `git diff` 复核是否混入行为变更——"Worker 说全绿"和"主控看到全绿"是两件事,对删除类改动尤其如此。
   - **决策升级链路**:Worker 的无把握事项写入工作区 `notes-for-lead.md` 交主控裁决;主控亦无把握的,登记到"待用户决策清单"——全程不向用户发问(详见"自主决策与问题升级"一节)。

## 产物命名与存储规范(全局统一)
所有提示词共用以下命名规则,避免中间产物散落与随意命名:
- **任务工作区**:`_tmp/vmr-<task>-<model-slug>-<timestamp>/`,本任务 `<task>` 固定为 `cleanup`。工作区目录名统一承载模型名与时间戳,目录内文件使用固定语义名,不再重复后缀。
- **`<model-slug>`**:当前 LLM 模型名清洗为文件名安全形式(转小写,`/`、`: `、空格等替换为 `-`)。
- **`<timestamp>`**:任务开始时刻,格式 `YYYYMMDD-HHMMSS`,全程固定不变。
- **工作区内固定文件名**:`progress.md`(执行阶段与批次状态)、`candidates.md`(清理候选清单台账与排序计划)、`notes-for-lead.md`(Worker 上报与决策沉淀)。其余任何中间产物一律写入本工作区,严禁散落在 `_tmp/` 根目录或仓库其他位置。
- **收尾**:任务完成后整个工作区删除;需保留的结论在删除前已按阶段五沉淀进权威文档。
- **仓库常驻文件**:不新建任何常驻报告文件(如根目录 `CLEANUP_REPORT*.md` 已被废弃,结论由权威文档编辑与对话最终交付承载)。
- **对话最终交付**以统一标题起头:`vmr cleanup report — <model> <YYYY-MM-DD HH:MM>`。

## 问题列表统一分级(T1/T2/T3)
本任务中盘点出的问题与清理候选统一分级:
- **T1(本轮执行)**:T1-A 直接修、T1-B 机械清理、T1-C 结构性简化;
- **T2(待办/排期)**:确认为合理改进但存在依赖、行为变动风险或高成本的项,登记进 `KNOWN_ISSUES` "待定与待解决问题"清单或列入待用户决策清单;
- **T3(暂缓/不改)**:涉及既有刻意取舍、风险大于收益的项,列入待用户决策清单中明确标注"建议不改"并陈述理由。
每条统一字段:**编号(如 T1-A-1, T2-1)、梯队/分类、标题、证据锚点(文件与符号)、影响/用户价值、建议方案、成本与风险、依赖**。

## 执行步骤

### 阶段一:基线建立与决策考古
1. 通读 `AGENTS.md`、`docs/KNOWN_ISSUES.md`、各设计文档(重点是其 decisions 与 decided-not-to-fix 表),建立"已知权衡地图"。
2. 按《产物命名与存储规范》初始化任务工作区(`progress.md`、`candidates.md`、`notes-for-lead.md`)。
3. 跑通并记录全量基线(构建、测试、vet、gofmt、archtest),基线结果写入工作区 `progress.md`;基线不绿则明确标注哪些清理动作仍可安全进行。

### 阶段二:并行盘点(多 Agent 只读侦察)
按 Domain 划分并行盘点,逐项登记到工作区 `candidates.md`,每项必须包含:证据(源码位置 + 判定依据)、分类(T1-A 至 T1-C,或 T2/T3)、影响范围、风险与依赖。盘点维度:
1. **死代码与失效实现**:未被引用的函数/类型/常量、已不成立的抽象层、为兼容历史保留的过渡实现、从未生效的配置分支。
2. **冗余与重复**:重复逻辑、可合并的近似实现、多处私自复制的本应单点实现的逻辑(对照项目 SSOT 约束)。
3. **可简化项**:过度抽象、无实际收益的中间层、可直写的复杂逻辑、深嵌套与高圈复杂度(以"等价简化"为限)。
4. **字词与文档**:注释/README/docs 中的错字、失效描述、过期引用;命名名不副实的小处修正(仅限零风险重命名)。
5. **测试代码**:明显失效、重复或空转的用例。

### 阶段三:汇总排序与执行计划(主控)
1. 汇总各 Worker 候选清单,去重、交叉核实关键结论,合并有依赖的项。
2. 按风险等级(T1-A → T1-B → T1-C)与依赖顺序排序成执行计划:无依赖的独立项先行、同包变更聚合成批、T1-C 类靠后且逐项论证。T2/T3 类项移入"待用户决策清单",明确本次不做。
3. 生成各批次的任务说明(若使用 `run-subagent` Skill 则填写其 task-description brief),写类任务的白名单精确到文件路径,并显式声明禁改清单。

### 阶段四:分批执行(写入与小步验证)
1. 按批次派发执行(优先 worktree 隔离;无法隔离时串行执行),遵循小步提交纪律,每批自验通过后提交交付。
2. 主控逐批回收、合并、验收(见"回收验收加强"),未绿的批次退回或回滚,不带入下一批。

### 阶段五:全局验收与收尾
1. 全局复跑全部验收命令(含 `-race` 与 archtest),整体 `git diff` 复核无行为变更混入。
2. 按项目规则收尾:用户可见变化登记 CHANGELOG(`[Unreleased]`,分组 Added/Changed/Fixed)、中英文文档同改确认、commit 规范自查。
3. 在对话交付中完成总结:
   - **清理成果统计**(T1-A/B/C 各处理了多少项、代码量净变化、commit 列表);
   - **待用户决策清单**(T2/T3 梯队:自主决策规则下升级留档的全部事项,含现状描述、方案权衡与倾向性建议,每条字段按《问题列表统一分级》);
   - **执行过程摘要**。
4. 删除任务工作区。

## 交付与启动协议
- **交付形态**:已通过全量测试与验证的代码修改 + `CHANGELOG.md` 增量编辑(若有用户可见变化)+ 对话中的完整交付叙事(成果统计 + 待用户决策清单),不新建 `CLEANUP_REPORT*.md` 一类的仓库常驻报告文件——项目约定明确"one-off comprehensive review reports are no longer produced"。
- **过程产物**:统一落在任务工作区 `_tmp/vmr-cleanup-<model-slug>-<timestamp>/`,任务完成后删除(见《产物命名与存储规范》)。
- **任务 Debrief**:在正式开工前,输出简短的 Debrief(确认对行为保持原则、基线先行、T1-A 至 T1-C 分级处理、自主决策与升级规则、分工与回收方案的理解)。**Debrief 为陈述性输出,不阻塞等待用户答复**,输出后立即进入阶段一。
