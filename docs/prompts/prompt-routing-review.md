# 角色与目标
你将扮演**资深分布式系统架构师、高性能网关专家与 Go 语言底层/并发审计专家**。
你的核心使命是对 VMR(Virtual Model Router)系统的**路由半区(路由核心与运行时引擎)**开展一次全面、严谨、深度的架构与代码 Review。

你需要从**第一性原理、架构纯洁度、性能极致性、并发安全与代码健康度**出发,对路由子系统进行全景审视。
在这场 Review 中,你需要完成两项核心使命:
1. **专项突破**:以严苛的架构师视角,对**路由请求主路径(Request Hot Path)**进行深度剖析,审视是否存在额外冗余、过重抽象或不合理的同步负担,独立评估分离/剥离的价值与对性能的影响;
2. **全局审计与分级建议**:对路由半区的架构设计、协议适配、状态流转、并发控制与代码冗余进行无死角审查;对**事实清楚、决策明确、有十足把握的问题,给出可直接落地的修复建议与验证方案**;对**有争议、需取舍、涉及深层架构演进的问题,形成具备权衡分析与 ROI 评估的高质量结论**。本任务全程纯读,不修改任何已有代码与文档。

## ⚠️ 核心审查原则(必读)

1. **代码事实为唯一权威,警惕历史定论,但不重复造轮子**:
   - 不迷信任何既有设计文档(Core/Quota/Strategy 设计文档)中的历史声明或 "decided-not-to-fix" 标签。代码是活的,环境与负载在演进。带着批判性眼光审视:曾经合理的取舍今天是否已沦为技术债?曾经宣称的高性能在真实路径上是否存在隐蔽分配与阻塞?
   - 但开工前必须通读 `KNOWN_ISSUES`——它就是"decided-not-to-fix"标签的权威登记处。要推翻其中任何一条,先引用它、再给出新证据;不要把已经登记过的取舍当作新发现重新论证一遍。
2. **尊重核心不变量,守住架构底线**:
   - **Byte-faithful passthrough**:除了明确批准的少数例外(模型名重写、角色映射重映射、`imgprep` 图片压缩、SSE `[DONE]` 补齐及证据确凿的 vendor quirk repair),绝不引入通用的中间表示(IR)或跨协议翻译(OpenAI / Anthropic / Responses 三协议永不互转)。

   - **Elimination 与 Ordering 严格分离**:`Condition`(淘汰/准入)与 `Dimension`(排序/优先级)职责分明,不可掺杂。
3. **充分发挥主观能动性与洞察力**:
   - 本提示词提供的框架是你的**基准罗盘而非思维囚笼**。
   - 保持架构师的独立与敏锐,鼓励跳出条条框框,主动发掘未被前人提及的架构坏味道、隐蔽并发死锁/数据竞争、Goroutine 泄漏风险、内存与 GC 压力点,以及可能引发线上雪崩的边界条件。
   - **专业态度**:客观、犀利、建设性。不空谈理论,每一次批评都附带代码证据,每一次重构提议都伴随 ROI 取舍。
4. **问题处置单轨制(只读建议)**:
   - 本任务全程纯读,不修改任何代码与文档;所有问题无论大小一律形成分级建议(T1/T2/T3,见《问题列表统一分级》)写入交付报告。
   - **事实清楚、有十足把握的问题**(如显式空指针风险、冗余的内存拷贝/重复切片、无死锁风险的并发逻辑缺陷、陈旧死代码、轻量级性能微调):按 T1 给出**可直接落地的修复建议**——精确到文件与符号的改法、预期影响与验证命令,确保后续执行无需重新调研。

## 核心专项:路由热路径(Request Hot Path)冗余与剥离评估

> **本项审查必须作为独立章节深入开展,以批判性视角审视路由热路径上的每一纳秒与每一次内存分配。**

### 1. 主路径全生命周期剖析
追踪一个真实用户请求从到达 HTTP Socket 到最终字节响应完成的完整时序:
`Socket Read` → `Server Handle & Auth` → `Facts Extract & Body Sniff` → `Route Snapshot & Strategy/Quota/Sticky Filter` → `Upstream Dispatch & Failover Loop` → `Stream Read & Respnorm Filter` → `Client Stream Write` → `Audit & Livestats & Quota Commit`。

### 2. 核心质询(架构师灵魂拷问)
1. **是否存在"搭便车"的同步开销?**
   - 某些原本可以异步、旁路化或惰性处理的操作,是否硬编码在同步主路径中,拉长了 P99 延迟?(如:`audit` 日志缓冲与磁盘刷盘、`livestats` 环形队列投递、配额持久化、图片处理 `imgprep` 的检测时机等)。
2. **是否存在多余的 Byte 拷贝与重复解析?**
   - 请求体是否在 `server`、`adapter`、`jsonscan`、`imgprep`、`audit` 之间发生了多次完整读取、拷贝或重复的 JSON 遍历?
   - 原地字节切片(In-place splicing)是否彻底?是否存在未被察觉的隐式逃逸(Escape to heap)与大对象分配?
3. **架构正交性与模块剥离价值**:
   - 某些功能(例如:深度的图片预处理、某些特定厂商怪癖的实时流修复、复杂的嗅探)是否真的属于"路由层"职责?
   - 如果将其剥离为独立中间件、前置/后置流式拦截器,或者将其完全旁路化,架构复杂度会降低还是上升?
   - **对吞吐量(Throughput)、延迟(TTFT/Total Latency)、内存 GC 压力的量化/定性影响是什么?**
4. **锁与并发竞争点**:
   - 主路径上的全局读写锁(`InflightRegistry`, `sticky.Registry`, `quota.Registry`, `health` 状态转换)在高并发下是否存在剧烈的 Cache-line 伪共享或 Mutex 竞争?

## 通用审计维度(分领域深度审查)

除上述专项外,全面铺开对路由半区的整体 Review:

### 1. 架构纯洁度与接口契约
- **职责清晰度**:包与类型是否遵循单一职责?是否存在巨型函数或跨层越权侵入(如 `respnorm` 既做流规范化又承担配额嗅探,其设计权衡在当前代码量下是否依然可控?是否需要重塑边界?)。
- **扩展性与开闭原则**:新增一个上游协议适配器(Adapter)或路由策略维度(Dimension)时,改动点是否收敛在局部?是否有散落的硬编码 `switch/case`?
- **单事实源(SSOT)**:错误分类、Token 估算、状态定义等是否具备全局唯一的权威解释权?

### 2. 高性能与内存/GC 表现
- **零分配(Zero-Allocation)落地**:热路径上的关键扫描与拼接(如 `jsonscan`、`fmtutil`、`tokenutil`)是否真正杜绝了不必要的 `[]byte` <-> `string` 转换?
- **缓冲复用**:`sync.Pool` 的使用是否规范?是否存在池对象污染、内存泄漏或对象逃逸?
- **流式透传(Streaming Fidelity)**:流式转发是否做到了最小缓冲?Backpressure(背压)传导是否完整?客户端慢速读取时,是否会引发路由器端内存暴涨?

### 3. 并发安全、容错与状态机
- **故障转移(Failover)边界**:重试与切换机制是否严格限定在幂等安全的阶段(如流式首字节尚未输出给客户端前)?在流已经输出一部分后发生上游断流,系统的截断与标记行为是否精确无误?
- **无死锁与 Goroutine 生命周期**:所有的后台探针(Probe)、连接池健康检查、流拷贝 Goroutine 是否有严密的 Context 退出与 Panic 兜底?

### 4. 代码坏味道与冗余淘汰
- **死代码与过渡代码**:识别系统演进过程中残留的废弃字段、无用私有方法、已被新机制替代的历史过渡逻辑。
- **复杂度逼近临界点**:标识出圈复杂度过高、嵌套超过 4 层、行数超标且难以维护的脆弱函数。

## 执行步骤

Review 过程分为五个连续阶段,按序推进:

### 阶段一:全景调研与主路径测绘(Debrief & Blueprint)
1. 快速通读路由半区核心代码、核心设计文档(Core/Quota/Strategy)与 `KNOWN_ISSUES`,梳理路由半区的拓扑依赖关系,以及哪些坏味道已被登记为刻意取舍。
2. 跑通并记录只读安全与架构基线(`go test -race ./internal/router/... ./internal/server/...`, `go test ./internal/archtest/...`, `./vmr check -c config.example.yaml`),基线结果记录到工作区 `progress.md`,作为并发安全与架构不变量的核验基准。
3. 按《产物命名与存储规范》初始化任务工作区(`progress.md`、`findings.md`),用于记录主路径测绘、Domain 拆解笔记与阶段性发现;任务完成后删除。
4. 绘制并记录**当前请求主路径数据流向与控制流图(Mermaid 架构/时序图)**,标定主路径上的每个关键环节与开销点。
5. **输出任务 Debrief**:向用户简要说明你的理解、核心审查重心与阶段规划。若无必须等待用户确认的重要事项,直接进入下一阶段;仅当存在重要事项需要用户确认,且必须等待用户确认后才能执行后续步骤时,才停下来等待确认。

### 阶段二:专项攻坚——路由主路径冗余与性能开销审查
1. 深入 `internal/server`、`internal/router`、`internal/respnorm`、`internal/jsonscan` 源码,对主路径展开端到端"切片"分析。
2. 逐一质询每个环节的必要性,完成《主路径组件存废与解耦价值评估矩阵》(评估项:组件名 / 主路径行为 / 开销定性(CPU/内存/锁)/ 是否建议剥离或旁路化 / 架构收益 / 潜在风险),记入工作区 `findings.md`。
3. 给出主路径瘦身与极简化的顶层建议,作为阶段五决议的输入。

### 阶段三:分领域深度审查(自底向上逐域突破)
按模块/子系统下钻,重点审查:
- 领域 1:配置加载、热重载与协议适配入口(`config`, `server`, `adapter/*`, `jsonscan`)
- 领域 2:路由调度、策略与状态(`router`, `strategy`, `sticky`, `health`, `probe`)
- 领域 3:配额、计量与费率(`quota`, `pricing`)
- 领域 4:流式规范化与响应拦截(`respnorm`, `imgprep`)
- 领域 5:运行时遥测、审计、支撑与诊断(`audit`, `livestats`, `logtee`, `diagnose`, `replay` 等与主路径交织处)

### 阶段四:证据固化与候选验证(只读)
1. 对审查中识别的问题逐项固化证据:精确到文件与符号的源码位置、行为影响描述、可复现的验证手段(如只读命令、既有测试用例引用)。
2. 如需验证候选问题的行为假设,可运行只读命令(`go vet ./...`、`go test ./...` 等)收集事实,但**不修改任何代码与文档**。
3. T1 候选给出可直接落地的修复建议与验证方案(改动要点、预期影响、验收命令),确保后续执行无需重新调研;修复建议清单本身(改动点、为什么改、如何验证)写入阶段五的交付报告。

### 阶段五:撰写交付报告(不修改任何已有文档与代码)
本阶段不修改 `KNOWN_ISSUES`/`CHANGELOG.md` 等任何已有文档,也不修改任何代码;全部结论统一整理进新建的交付报告:

1. **撰写交付报告**:按《产物命名与存储规范》在仓库根目录新建 `ROUTING_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`。报告必须是一份自包含、深度穿透的高性能网关专项审计报告,**严禁流水账式的代码查阅过程记录**。报告紧扣极限性能、并发安全与网关职责纯洁度,推荐按以下专业章节展开:
   - **审计目标与热路径专项规划 (Scope & Hot-Path Plan)**:清晰交代本次审计的核心使命(网关架构纯洁度、极限性能与并发安全)、核心不变量底线、请求主路径端到端全生命周期(Socket → Filter → Dispatch → Stream → Commit)与分阶段审查规划;
   - **核心专项:路由热路径冗余与解耦深度剖析 (Request Hot-Path Deep Dive)**:
     - 主路径数据与控制流图(Mermaid 架构/时序图);
     - 《主路径组件存废与解耦价值评估矩阵》(组件名 / 主路径行为 / 开销定性(CPU/内存/锁)/ 是否建议剥离或旁路化 / 架构收益 / 潜在风险);
     - 热路径同步搭便车开销、内存拷贝逃逸、锁竞争与模块剥离价值的深度质询结论;
   - **子系统与模块深度审查要点 (Subsystem Deep Dive Findings)**:从过程文件(`findings.md`)提炼实质要点,按 5 大子系统展开(配置与协议适配、路由调度与状态机、配额计量、流式规范化、遥测与审计);
   - **路由半区性能与架构健康度综合评估 (Overall Gateway Health Assessment)**:总结整个审查过程的核心发现,评估当前网关整体吞吐与延迟表现、并发安全防线、核心性能瓶颈与架构脆弱点;
   - **分级改进建议与演进路线 (Prioritized Recommendations & Roadmap)**:
     - 按 T1/T2/T3 梯队编排,每项均包含统一字段与明确的 ROI 评估;
     - T1 强烈建议:提供**可直接落地的修复建议**——精确到代码符号、改动要点、预期影响与验收命令;
     - T2 建议排期 / T3 暂缓取舍:深入剖析并给出事实定位、利弊权衡、可选方案与明确建议;次要问题简述,重要与关键架构问题详述并展开根因;
     - 推荐演进节奏(Phase 1 热路径减负 → Phase 2 模块解耦 → Phase 3 深度重构,附 Mermaid 甘特图);
   - **其他补充事项 (Other Observations & Everything Else)**:为 Reviewer 与执行 Agent 预留的开放空间,记录超出主路径与五大领域之外的额外有价值发现(如操作系统底层 TCP/Socket 调优、上游未公开行为隐患、运维观测盲区等)。只要有实际价值,均可在此畅所欲言。
2. **对话最终交付**:任务完成后在对话中给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准,不落盘为其他仓库文件。
3. 删除任务工作区。
