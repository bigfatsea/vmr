## ⚠️ 核心审查原则(必读)

1. **代码事实为唯一权威,警惕历史定论,但不重复造轮子**:
   - 不迷信任何既有设计文档(Core/Quota/Strategy 设计文档)中的历史声明或 "decided-not-to-fix" 标签。代码是活的,环境与负载在演进。带着批判性眼光审视:曾经合理的取舍今天是否已沦为技术债?曾经宣称的高性能在真实路径上是否存在隐蔽分配与阻塞?
   - 但开工前必须通读 `KNOWN_ISSUES`——它就是"decided-not-to-fix"标签的权威登记处。要推翻其中任何一条,先引用它、再给出新证据;不要把已经登记过的取舍当作新发现重新论证一遍。
2. **尊重核心不变量,守住架构底线**:
   - **Byte-faithful passthrough**:除了明确批准的少数例外(模型名重写、角色映射重映射、`imgprep` 图片压缩、SSE `[DONE]` 补齐及证据确凿的 vendor quirk repair),绝不引入通用的中间表示(IR)或跨协议翻译(OpenAI / Anthropic / Responses 三协议永不互转)。
   - **两半区隔离**:路由核心严禁反向依赖离线分析层(`internal/report`, `journey`, `taskseg` 等);JSONL 审计日志是唯一的单向解耦桥梁。
   - **Leaf 包纯洁性**:`core`, `fmtutil`, `tokenutil`, `digest`, `jsonscan`, `livestats` 等必须保持零内部依赖(`archtest` 强制约束)。
   - **Elimination 与 Ordering 严格分离**:`Condition`(淘汰/准入)与 `Dimension`(排序/优先级)职责分明,不可掺杂。
3. **充分发挥主观能动性与洞察力**:
   - 本提示词提供的框架是你的**基准罗盘而非思维囚笼**。
   - 保持架构师的独立与敏锐,鼓励跳出条条框框,主动发掘未被前人提及的架构坏味道、隐蔽并发死锁/数据竞争、Goroutine 泄漏风险、内存与 GC 压力点,以及可能引发线上雪崩的边界条件。
4. **问题处置双轨制(务实自驱)**:
   - **级别 A(就地修复,直接搞定)**:事实清楚、无设计争议、改动边界可控且有把握一次性修好(如显式空指针风险、冗余的内存拷贝/重复切片、无死锁风险的并发逻辑修补、陈旧死代码清理、轻量级性能微调)。**直接修改代码并补齐/通过测试,绝不把举手之劳推诿给后续报告**。
   - **级别 B(深度剖析,决策上报)**:涉及主干接口契约调整、对并发模型有破坏性重构、有多种权衡方案且各有利弊、或需要与项目负责人研讨拍板的架构重构。**留待阶段五深入分析,给出清晰的事实定位、利弊权衡、可选方案与明确的建议**。

## 二、核心专项任务:路由主路径(Request Hot Path)冗余与剥离评估

> **本项审查必须作为独立章节深入开展,以批判性视角审视路由热路径上的每一纳秒与每一次内存分配。**

### 1. 主路径全生命周期剖析
追踪一个真实用户请求从到达 HTTP Socket 到最终字节响应完成的完整时序:
`Socket Read` → `Server Handle & Auth` → `Facts Extract & Body Sniff` → `Route Snapshot & Strategy/Quota/Sticky Filter` → `Upstream Dispatch & Failover Loop` → `Stream Read & Respnorm Filter` → `Client Stream Write` → `Audit & Livestats & Quota Commit`。

### 2. 核心质询(架构师灵魂拷问)
1. **是否存在"搭便车"的同步开销?**
   - 某些原本可以异步、旁路化或惰性处理的操作,是否硬编码在同步主路径中,拉长了 P99 延迟?(如:`audit` 日志缓冲与磁盘刷盘、`livestats` 环形队列投递、配额持久化、图片处理 `imgprep` 的检测时机等)。
2. **是否存在多余的 Byte 拷贝与重复解析?**
   - 请求体是否在 `server`、`adapter`、`jsonscan`、`imgprep`、`audit` 之间发生了多次完整读取、拷贝或重复的 JSON 遍历?
   - 原地字节切片(In-place splicing)是否彻底?是否存在未被察觉的隐式逃逸(Escape to heap)与大对象分配?
3. **架构正交性与模块剥离价值**:
   - 某些功能(例如:深度的图片预处理、某些特定厂商怪癖的实时流修复、复杂的嗅探)是否真的属于"路由层"职责?
   - 如果将其剥离为独立中间件、前置/后置流式拦截器,或者将其完全旁路化,架构复杂度会降低还是上升?
   - **对吞吐量(Throughput)、延迟(TTFT/Total Latency)、内存 GC 压力的量化/定性影响是什么?**
4. **锁与并发竞争点**:
   - 主路径上的全局读写锁(`InflightRegistry`, `sticky.Registry`, `quota.Registry`, `health` 状态转换)在高并发下是否存在剧烈的 Cache-line 伪共享或 Mutex 竞争?

## 三、通用审计维度(分领域深度深挖)

除上述专项外,全面铺开对路由半区的整体 Review:

### 1. 架构纯洁度与接口契约
- **职责清晰度**:包与类型是否遵循单一职责?是否存在巨型函数或跨层越权侵入(如 `respnorm` 既做流规范化又承担配额嗅探,其设计权衡在当前代码量下是否依然可控?是否需要重塑边界?)。
- **扩展性与开闭原则**:新增一个上游协议适配器(Adapter)或路由策略维度(Dimension)时,改动点是否收敛在局部?是否有散落的硬编码 `switch/case`?
- **单事实源(SSOT)**:错误分类、Token 估算、状态定义等是否具备全局唯一的权威解释权?

### 2. 高性能与内存/GC 表现
- **零分配(Zero-Allocation)落地**:热路径上的关键扫描与拼接(如 `jsonscan`、`fmtutil`、`tokenutil`)是否真正杜绝了不必要的 `[]byte` <-> `string` 转换?
- **缓冲复用**:`sync.Pool` 的使用是否规范?是否存在池对象污染、内存泄漏或对象逃逸?
- **流式透传(Streaming Fidelity)**:流式转发是否做到了最小缓冲?Backpressure(背压)传导是否完整?客户端慢速读取时,是否会引发路由器端内存暴涨?

### 3. 并发安全、容错与状态机
- **故障转移(Failover)边界**:重试与切换机制是否严格限定在幂等安全的阶段(如流式首字节尚未输出给客户端前)?在流已经输出一部分后发生上游断流,系统的截断与标记行为是否精确无误?
- **无死锁与 Goroutine 生命周期**:所有的后台探针(Probe)、连接池健康检查、流拷贝 Goroutine 是否有严密的 Context 退出与 Panic 兜底?

### 4. 代码坏味道与冗余淘汰
- **死代码与过渡代码**:识别系统演进过程中残留的废弃字段、无用私有方法、已被新机制替代的历史过渡逻辑。
- **复杂度逼近临界点**:标识出圈复杂度过高、嵌套超过 4 层、行数超标且难以维护的脆弱函数。

## 四、执行步骤与工作流程

Review 过程分为五个连续阶段,按序推进:

### 阶段一:全景调研与主路径测绘(Debrief & Blueprint)
1. 快速通读路由半区核心代码、核心设计文档(Core/Quota/Strategy)与 `KNOWN_ISSUES`,梳理路由半区的拓扑依赖关系,以及哪些坏味道已被登记为刻意取舍。
2. 建立轻量级过程文件 `_tmp/review_progress_routing_<model>_<date>.md`(`_tmp/` 已被 `.gitignore` 排除),用于记录主路径测绘、Domain 拆解笔记与阶段性发现;任务完成后删除。
3. 绘制并记录**当前请求主路径数据流向与控制流图(Mermaid 架构/时序图)**,标定主路径上的每个关键环节与开销点。
4. **输出任务 Debrief**:向用户简要说明你的理解、核心审查重心与阶段规划,确认后进入下一阶段。

### 阶段二:专项攻坚——路由主路径冗余与性能开销审查
1. 深入 `internal/server`、`internal/router`、`internal/respnorm`、`internal/jsonscan` 源码,对主路径展开端到端"切片"分析。
2. 逐一质询每个环节的必要性,完成《主路径组件存废与解耦价值评估矩阵》(评估项:组件名 / 主路径行为 / 开销定性(CPU/内存/锁)/ 是否建议剥离或旁路化 / 架构收益 / 潜在风险),记入过程文件。
3. 给出主路径瘦身与极简化的顶层建议,作为阶段五决议的输入。

### 阶段三:分领域深度审查(自底向上逐域突破)
按模块/子系统下钻,重点审查:
- 领域 1:协议适配与入口层(`server`, `adapter/*`, `jsonscan`)
- 领域 2:路由调度、策略与状态(`router`, `strategy`, `sticky`, `health`)
- 领域 3:配额、计量与费率(`quota`, `pricing`)
- 领域 4:流式规范化与响应拦截(`respnorm`, `imgprep`)
- 领域 5:运行时遥测、审计与支撑(`audit`, `livestats`, `logtee` 等与主路径交织处)

### 阶段四:实战处置——"就地修复"(级别 A)与自动化验证
1. 在审查过程中随时识别**级别 A(事实清楚、低风险、有把握直接搞定)**的问题。
2. 动手实施代码修复(如优化热路径上的无效逻辑、修正并发小漏洞、删除死代码、补齐防御性校验)。
3. 运行项目全量测试与架构约束检查,确保系统行为不被破坏:
   ```bash
   go test ./...
   go test -race ./...
   go test ./internal/archtest/...
   ./vmr check -c config.example.yaml
   ```
4. **每一项就地修复,在 `CHANGELOG.md` 的 `[Unreleased]` 下补一条 `Fixed` 条目**(用户/开发者可见的行为变化,遵循该文件既有格式)。修复清单本身(改了什么、为什么、如何验证)作为阶段五对话交付的一部分呈现,不再另建报告文件——`KNOWN_ISSUES` 自身的原则是"已修复的问题不进这里,代码本身就是证明"。

### 阶段五:结论沉淀(级别 B 决议,不新开报告)
1. **路由半区整体健康度**:若有变化,更新 `KNOWN_ISSUES` 的"当前状态"小节(§0),替换过时表述,不叠加演进记录。
2. **级别 B 结论 → `KNOWN_ISSUES`**:对每个级别 B 问题,仍按"现象与代码锚点 → 根因与冲突分析 → 方案对比 → ROI 取舍"的顺序分析清楚(完整分析呈现在对话交付里,见第 4 点);落进 `KNOWN_ISSUES` 的只是分析后的结论,按其既有惯例挑位置——
   - 结论是"确实是刻意取舍、不必改"→ §1,陈述当前结论与理由;
   - 结论是"待办、值得排期"→ §2,按现有分组与"组内 ROI 排序"惯例插入,标注方案要点与 ROI 取舍(收益:性能/延迟/维护性/正交性;成本:改动量/协议风险/破坏性)。
   追加前检索是否已有相近条目,避免重复登记。
3. **跨阶段实施节奏 → `KNOWN_ISSUES` §3**(跨组排期结论):给出推荐的演进节奏(如 Phase 1 热路径减负 → Phase 2 模块解耦 → Phase 3 深度重构),可用 Mermaid 甘特图辅助说明,图本身放进对话交付。
4. **对话最终交付**:主路径存废评估矩阵全貌、每条级别 B 结论的深入分析(事实定位、方案对比、权衡过程)、架构拓扑与时序 Mermaid 图,作为本次任务的最终回复呈现(必要时发布为 Artifact),不落盘为仓库文件。
