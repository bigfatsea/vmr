# 角色与目标
你将扮演资深软件架构师与代码审计专家,对项目开展一次全面、严谨、深度的系统级 Review。

工作主线:梳理项目全貌并划分**领域(Domain Decomposition)** → 逐域深度审阅并沉淀记录 → 横向拉通跨域业务链路并源码核实 → 站在**顶层架构与系统演进的高度**全景审视整体设计、模块解耦、边界清晰度与技术债务,最终把结论整理进统一的交付报告(见执行步骤·阶段五)。

---

## 自主决策与问题升级(主控与 Subagent 共同遵守)
任务全程**严禁中断进程向用户提问或请求确认**,决策规则如下:
1. **可自行决策**:对事实清楚、证据确凿、风险可控的事项(领域边界划分调整、链路穿透深度、模块坏味道定性、架构问题评级等),依据第一性原理与架构纯洁度**自行决策并形成分析结论**,决策依据记录到工作区过程文件即可。
2. **必须升级留档**:高风险、涉及主干架构分歧、业务战略取舍或需负责人拍板的宏观重构(T2/T3),**一律不中断发问**,统一登记到交付报告中的"待用户决策清单/建议"(含事项描述、各方案权衡与倾向性建议),留待任务结束后由用户统一裁决。
3. **登记优先于询问**:任何时刻遇到两难,先登记留档、继续推进其余可独立开展的审计工作,绝不为等待答复而阻塞流水线。
4. **对 Subagent 同样生效**:Worker 级别的无把握事项写入工作区 `findings.md` 交主控裁决;主控亦无把握的,按第 2 条升级留档——任何一级 Agent 都不得向用户直接发问。

## 范围与环境约束
1. **聚焦业务代码**:审计重点为**核心生产与业务代码**(架构分层、接口定义、核心算法、状态机、数据流与错误处理),**默认忽略测试代码**(`*_test.go`、测试套件、Mock 等)。
2. **第一性原理与独立判断,但不重复造轮子**:不盲从设计文档与代码注释中的历史定论(decisions、decided-not-to-fix 等声明),回归第一性原理立足代码现状批判性审视,敢于挑战因系统演进而已失效的旧有假设,指出新瓶颈与坏味道——但历史结论也不是默认错误的:开工前先通读 `KNOWN_ISSUES`(已知问题与刻意取舍的唯一权威清单)与 `ROADMAP`(分析半区未建功能清单),与已有条目重合的发现先判断是否已被覆盖;要推翻其中任何一条,先引用它、再给出新证据,而不是假装没看过、独立发现一遍。
3. **查重先行与只读原则**:审计时通读 `KNOWN_ISSUES` 与 `ROADMAP`,与已有条目重合的发现标注"已被既有条目覆盖"并给出条目索引即可;本任务全程只读,不修改任何已有文档(`KNOWN_ISSUES`/`ROADMAP`/`CHANGELOG.md` 等)与代码。路由半区的产品级新能力想法在报告中单列一节,由用户裁决。
4. **忽略目录**:所有被仓库 `.gitignore` 忽略的内容(含 `_tmp/`、`archived/`、`logs/`、`reports/` 等生成物目录及仓库根的构建产物如 `vmr` 二进制)一律视为不存在,不读取、不审阅、不修改(本任务自身写入工作区 `_tmp/` 的过程文件除外,见下文)。
5. **资源与耗时**:本任务为长耗时审计,可按需持续占用计算资源直至所有阶段执行完毕。
6. **Token 与效率控制**:
    - 思考(Thinking)与响应(Response)保持紧凑精炼、逻辑直接,避免空话与冗余客套。
    - 工具调用尽量批量化合并处理;所有结论必须有具体的源码位置作为事实支撑。

## 协作机制与多 Agent 分工

1. **过程产物只进 `_tmp/`,任务完成即删**:按《产物命名与存储规范》建立任务工作区,进度(`progress.md`)与阶段性发现(`findings.md`)等过程文件都落在工作区内(`_tmp/` 已被 `.gitignore` 排除,不会污染仓库)。这是全局约定"非 trivial 任务先建过程文件"惯例的具体落地;任务完成后删除整个工作区;交付报告在删除前已按阶段五撰写并保留在仓库根目录。
2. **合理启用 Subagent**:在适合的场景(独立 Domain 并行审查、复杂子模块代码下钻、大范围特征初筛等)积极分工协作,以保持主会话上下文整洁。**编排方式**:若当前环境已装配 `run-subagent` Skill(项目 `.pi/skills/run-subagent/SKILL.md`),按其方法论执行派发与回收(触发三问、验收四查);未装配时按常规 Subagent 方式运作。底线一致:派发任务自包含、只读任务无需 worktree 隔离、谁派发谁验收、不为并行而并行。其阶段性结论归集到工作区 `findings.md`。

## 产物命名与存储规范(全局统一)
所有提示词共用以下命名规则,避免中间产物散落与随意命名:
- **任务工作区**:`_tmp/<task>-<model-slug>-<timestamp>/`,本任务 `<task>` 固定为 `full-review`。工作区目录名统一承载模型名与时间戳,目录内文件使用固定语义名,不再重复后缀。
- **`<model-slug>`**:当前 LLM 模型名清洗为文件名安全形式(转小写,`/`、`: `、空格等替换为 `-`)。
- **`<timestamp>`**:任务开始时刻,格式 `YYYYMMDD-HHMMSS`,全程固定不变。
- **过程文件管理**:过程文件一律放在任务工作区内,严禁散落在 `_tmp/` 根目录或仓库其他位置。标准过程文件为 `progress.md`(进度与执行状态)与 `findings.md`(阶段性发现与要点),各任务意涵、用途相同的文件尽量统一使用同一名字;任务有额外需求时可增补语义化的任务特有文件,名字允许不同,但意涵、用途相同者优先统一。
- **只读原则**:本任务全程只读——不修改任何已有文档(包括 `KNOWN_ISSUES`、`ROADMAP`、`CHANGELOG.md` 及设计文档等)和任何代码;唯一的写操作是 `_tmp/` 工作区内的过程文件与最终交付报告。
- **收尾**:任务完成后删除整个工作区;交付报告在删除前已按阶段五撰写并保留在仓库根目录。
- **最终交付报告**:任务完成后在仓库根目录新建 `FULL_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`,承载阶段五的全部结论与完整评估叙事。最终交付报告定位为内容自包含、深度严谨的独立报告,拒绝流水账式的操作过程复述;其内在逻辑为:开头清晰阐明任务目标、要点与具体计划,正文围绕具体计划展开并提炼过程文件中的实质要点,随后对全过程做综合总结与评估,最终按合理逻辑给出分级清单与 ROI 评估(详略得当,重要与关键事项做深度根因剖析与建议方案);各任务根据自身技术与业务特性因地制宜设计章节,不搞机械教条的八股结构。
- **对话最终交付**:对话中仅给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准。

## 问题列表统一分级(T1/T2/T3)
最终交付的问题列表必须按处理优先级分梯队,同一梯队内按"收益/成本"降序:
- **T1 强烈建议**:经综合分析后建议尽快处理的事项。T1 不是单一硬指标,通常表现为:证据充分、简单易修、ROI 高、风险低、复杂度可控;不同任务可按自身特点酌情收严或细化(见各提示词的具体约定)。本任务中重点表现为:改动边界清晰、有把握快速修正的架构坏味道或局部坏设计、无争议并发边界漏洞、明显失效死逻辑或接口过度暴露;
- **T2 建议排期**:收益成立,但存在权衡、依赖或可观成本,登记为待办;
- **T3 暂缓/不建议**:低 ROI、高风险,或与既有刻意取舍一致——写明理由后不动。
每条统一字段:**编号(如 T1-1)、梯队、标题、证据锚点(文件与符号)、影响/用户价值、建议方案、成本与风险、依赖**。

## 执行步骤

### 阶段一:全景调研与领域(Domain)划分
1. 快速通读项目核心设计文档(含 `KNOWN_ISSUES`、`ROADMAP`)与顶层代码架构,理清系统的职责全貌与核心设计哲学。
2. 按《产物命名与存储规范》初始化任务工作区(`progress.md`、`findings.md`)。
3. **制定领域划分方案**:将系统业务代码按架构职责划分为若干边界清晰的 Domain(如:路由与协议适配、状态与配额、数据分析与报表、存储与审计、CLI 与基础设施等),明确各 Domain 的范围、核心业务包与审查焦点。鼓励使用清晰的 **Mermaid 架构拓扑图** 表达各领域关系。
4. **输出任务 Debrief**:向用户简要说明你对审查范围、聚焦业务代码策略、Domain 初始划分构想、Subagent 协同方案及执行步骤的理解。若无必须等待用户确认的重要事项,直接进入下一阶段;仅当存在重要事项需要用户确认,且必须等待用户确认后才能执行后续步骤时,才停下来等待确认。

### 阶段二:分 Domain 深度 Review(自底向上逐域击破)
按计划推进各领域审查,成果归集到工作区 `findings.md`,重点关注:
1. **职责与边界**:该领域是否满足单一职责?模块内聚性如何?是否存在对外的不合理泄漏或越权依赖?
2. **核心业务实现质量**:核心业务逻辑、状态机、数据流转、错误处理与并发安全的实现是否严谨健壮?
3. **代码健康度与坏味道**:抽样核心业务源文件,排查过大文件/函数、重复逻辑、硬编码及不合理的设计模式。
4. **领域级问题与改进建议**:记录该领域内部发现的具体缺陷与优化空间,标注是否与 `KNOWN_ISSUES` 现有条目相关。

### 阶段三:跨 Domain 链路串联与源码核实(横向拉通)
1. 选取贯穿系统的核心业务主链路(如:请求全生命周期链路、数据生产与消费离线链路、状态同步与持久化链路等),横向串联各 Domain(鼓励辅以清晰直观的 **Mermaid 流程/时序图**)。
2. **源码级交叉核实**:针对跨域交互、契约协议(Interface/Schema)、边界转换等关键节点,深入定位并查阅业务源码,验证:
    - 各 Domain 间的协同是否符合架构契约?是否存在隐式耦合、协议不一致或重复解析?
    - 是否存在循环依赖、边界穿透或跨层破坏架构不变量的情况?

### 阶段四:顶层架构全景审视(更高 Level 自顶向下)
跳出单一模块和具体实现细节,站在系统架构演进与全局设计哲学的最高层级,以**简单、优雅、健壮**为目标,重点审视以下维度——其判定结论与事实证据必须追加沉淀至工作区 `findings.md`,作为阶段五综合报告的核心输入:

1. **架构模型、分层解耦与组织一致性**:评估当前分层体系(如整洁架构、单向依赖流向)是否彻底,子系统之间是否维持**最小且不可变的交互契约**、是否存在跨层隐式渗透;同时审视模块、文件、标识符的命名是否准确表达职责与架构意图,项目结构是否与职责边界对齐,是否存在名不副实的组织错位。
2. **极简、简化与复杂度控制(避免过度设计)**:核心数据流是否**高保真、零无谓转换**,是否存在无实际收益的中间抽象层、复杂 IR 或性能冗余;能否以更简方案达成目的——必要时允许在功能或指标上让步(如 Token 估算牺牲精度换取简单、避免引入复杂算法);过大文件/函数、深嵌套、高圈复杂度是否逼近认知负担临界点。
3. **单事实源(SSOT)与逻辑权威性**:关键业务逻辑(如报文解析、哈希计算、状态判定等)是否在全系统具备**唯一的权威实现**,杜绝多处私自分裂。
4. **显式严谨与防御性健壮性**:评估类型系统是否清晰区分未定义与零值(如 unknown vs free),配置是否具备严格的 Fail-fast 校验,并发与异步状态机是否具备严密的边界与 Panic 兜底。
5. **冗余与失效代码**:识别重复的模块、函数、逻辑与抽象(并判断其演化来源),以及未被引用的代码、已不成立的抽象层、为兼容历史而保留的过渡实现——失效的抽象比没有抽象更具误导性。
6. **可演进性与改动成本**:评估一次需求变更所牵动的修改范围与跨越的包数,识别阻碍演进的强耦合与脆弱点,判断历史设计权衡在当前及未来负载下是否仍然适用,为重构优先级提供依据。

### 阶段五:撰写交付报告(不修改任何已有文档与代码)
本阶段不修改 `KNOWN_ISSUES`/`ROADMAP`/`CHANGELOG.md` 等任何已有文档,也不修改任何代码;全部结论统一整理进新建的交付报告:

1. **撰写交付报告**:按《产物命名与存储规范》在仓库根目录新建 `FULL_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`。报告必须是一份自包含、立足系统演进的架构审计报告,**严禁流水账式的审查过程记录**。报告紧扣顶层架构与代码实现,推荐按以下专业章节展开:
   - **审计目标与领域划分方案 (Scope & Domain Plan)**:清晰交代本次审计的核心目标、审查范围与第一性原理基准,给出系统业务领域划分方案(Domain Decomposition)、各域审查焦点与具体执行路线(配 Mermaid 系统架构拓扑图);
   - **逐领域架构审计要点 (Domain Audit Findings)**:按领域展开,提炼过程文件(`findings.md`)中的技术要点——各 Domain 的职责边界与内聚性、核心业务实现健壮性、代码健康度与模块坏味道;
   - **跨域主链路穿透与顶层设计审视 (Cross-Cutting Flows & Top-Level Architecture)**:主业务链路穿透核实记录(配 Mermaid 时序/流程图);自顶向下审视系统分层解耦、极简与复杂度控制、单事实源(SSOT)以及阻碍演进的结构脆弱点;
   - **系统整体健康度综合评估 (Overall Architectural Health)**:全面总结执行过程中的核心结论,给出系统当前的架构成熟度评级、核心架构优势与关键技术债务全景;
   - **架构问题分级与排期规划 (Prioritized Findings & Roadmap)**:按 T1/T2/T3 梯队组织问题清单,每项均包含统一字段与明确的 ROI 评估——不重要或零星瑕疵简要说明,重要架构风险详细描述,关键系统性缺陷按"代码锚点 → 根因分析 → 建议方案 → ROI 评估"四段式深入论证;给出跨领域实施排期建议(附 Mermaid 甘特图);
   - **其他补充事项 (Other Observations & Everything Else)**:为 Reviewer 与执行 Agent 预留的开放空间,记录超出预设 Domain 与主链路之外的额外有价值发现(如工程构建与发布工具链、文档与命名全局体感、未来演化预判等)。只要有实际价值,均可在此畅所欲言。
2. **对话最终交付**:任务完成后在对话中给出精炼总结(报告文件路径 + 关键结论摘要),完整内容以报告文件为准,不落盘为其他仓库文件。
3. 删除任务工作区。

## 交付与启动协议
- **交付形态**:仓库根目录新建的 `FULL_REVIEW_REPORT_<model>_<yyyy-mm-dd>.md`(承载阶段五的完整架构评估叙事、逐域审计要点与分级演进规划)+ 对话中的精炼总结;全程只读,不修改任何已有文档与代码。
- **过程产物**:统一落在任务工作区 `_tmp/full-review-<model-slug>-<timestamp>/`,过程文件均在其中,任务完成后删除工作区(见《产物命名与存储规范》)。
- **任务 Debrief**:见阶段一第 4 步;若无重要事项需要用户确认,直接进入下一步;仅当有重要事项必须确认后才能执行时才停下来等待确认。
