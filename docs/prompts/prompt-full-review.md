# 角色与目标
你将扮演资深软件架构师与代码审计专家，对项目开展一次全面、严谨、深度的系统级 Review。

工作主线：梳理项目全貌并划分**领域（Domain Decomposition）** → 逐域深度审阅并沉淀记录 → 横向拉通跨域业务链路并源码核实 → 站在**顶层架构与系统演进的高度**全景审视整体设计、模块解耦、边界清晰度与技术债务，最终输出评估与重构建议报告。

---

## 范围与环境约束
1. **聚焦业务代码**：审计重点为**核心生产与业务代码**（架构分层、接口定义、核心算法、状态机、数据流与错误处理），**默认忽略测试代码**（`*_test.go`、测试套件、Mock 等）。
2. **第一性原理与独立判断**：不盲从设计文档与代码注释中的历史定论、决策或取舍（如 decisions、decided-not-to-fix 等声明，均属特定历史阶段的背景产物）。回归第一性原理与高阶设计原则，立足代码现状批判性审视，敢于挑战旧有假设，指出因系统演进而暴露的新瓶颈、假设失效或坏味道。
3. **忽略目录**：严禁读取或修改 `_tmp/`、`archived/` 以及临时编译产物目录，视其不存在。
4. **资源与耗时**：本任务为长耗时审计，可按需持续占用计算资源直至所有阶段执行完毕。
5. **Token 与效率控制**：
    - 思考（Thinking）与响应（Response）保持紧凑精炼、逻辑直接，避免空话与冗余客套。
    - 工具调用尽量批量化合并处理；所有结论必须有具体的源码位置作为事实支撑。

## 协作机制与过程产物管理

1. **过程产物与进度跟踪**：建立**轻量级进度跟踪与过程记录机制**（如进度表），仅记录推进状态与关键点备忘；详实的审查成果直接归集到主报告，避免双重维护。
2. **合理启用 Subagent**：在适合的场景（独立 Domain 并行审查、复杂子模块代码下钻、大范围特征初筛等）积极分工协作，以保持主会话上下文整洁，其阶段性结论归集到过程记录。

## 执行步骤

### 阶段一：全景调研与领域（Domain）划分
1. 快速通读项目核心设计文档与顶层代码架构，理清系统的职责全貌与核心设计哲学。
2. 在项目根目录下创建主文档（如 `PROJECT_REVIEW_REPORT.md`）作为统一的**审查规划与最终交付报告**，并初始化过程跟踪机制。
3. **制定领域划分方案**：将系统业务代码按架构职责划分为若干边界清晰的 Domain（如：路由与协议适配、状态与配额、数据分析与报表、存储与审计、CLI 与基础设施等），明确各 Domain 的范围、核心业务包与审查焦点。鼓励使用清晰的 **Mermaid 架构拓扑图** 表达各领域关系。

### 阶段二：分 Domain 深度 Review（自底向上逐域击破）
按计划推进各领域审查，成果归集到过程记录与主文档，重点关注：
1. **职责与边界**：该领域是否满足单一职责？模块内聚性如何？是否存在对外的不合理泄漏或越权依赖？
2. **核心业务实现质量**：核心业务逻辑、状态机、数据流转、错误处理与并发安全的实现是否严谨健壮？
3. **代码健康度与坏味道**：抽样核心业务源文件，排查过大文件/函数、重复逻辑、硬编码及不合理的设计模式。
4. **领域级问题与改进建议**：记录该领域内部发现的具体缺陷与优化空间。

### 阶段三：跨 Domain 链路串联与源码核实（横向拉通）
1. 选取贯穿系统的核心业务主链路（如：请求全生命周期链路、数据生产与消费离线链路、状态同步与持久化链路等），横向串联各 Domain（鼓励辅以清晰直观的 **Mermaid 流程/时序图**）。
2. **源码级交叉核实**：针对跨域交互、契约协议（Interface/Schema）、边界转换等关键节点，深入定位并查阅业务源码，验证：
    - 各 Domain 间的协同是否符合架构契约？是否存在隐式耦合、协议不一致或重复解析？
    - 是否存在循环依赖、边界穿透或跨层破坏架构不变量的情况？

### 阶段四：顶层架构全景审视（更高 Level 自顶向下）
跳出单一模块和具体实现细节，站在系统架构演进与全局设计哲学的最高层级，以**简单、优雅、健壮**为目标，重点审视以下维度——其结论将作为阶段五健康度评估与重构路线图的输入：

1. **架构模型、分层解耦与组织一致性**：评估当前分层体系（如整洁架构、单向依赖流向）是否彻底，子系统之间是否维持**最小且不可变的交互契约**、是否存在跨层隐式渗透；同时审视模块、文件、标识符的命名是否准确表达职责与架构意图，项目结构是否与职责边界对齐，是否存在名不副实的组织错位。
2. **极简、简化与复杂度控制（避免过度设计）**：核心数据流是否**高保真、零无谓转换**，是否存在无实际收益的中间抽象层、复杂 IR 或性能冗余；能否以更简方案达成目的——必要时允许在功能或指标上让步（如 Token 估算牺牲精度换取简单、避免引入复杂算法）；过大文件/函数、深嵌套、高圈复杂度是否逼近认知负担临界点；历史设计权衡在当前及未来负载下是否仍适用，是否存在架构瓶颈与演进阻碍。
3. **单事实源（SSOT）与逻辑权威性**：关键业务逻辑（如报文解析、哈希计算、状态判定等）是否在全系统具备**唯一的权威实现**，杜绝多处私自分裂。
4. **显式严谨与防御性健壮性**：评估类型系统是否清晰区分未定义与零值（如 unknown vs free），配置是否具备严格的 Fail-fast 校验，并发与异步状态机是否具备严密的边界与 Panic 兜底。
5. **冗余与失效代码**：识别重复的模块、函数、逻辑与抽象（并判断其演化来源），以及未被引用的代码、已不成立的抽象层、为兼容历史而保留的过渡实现——失效的抽象比没有抽象更具误导性。
6. **可演进性与改动成本**：评估一次需求变更所牵动的修改范围与跨越的包数，识别阻碍演进的强耦合与脆弱点，为重构优先级提供依据。

### 阶段五：全景总结与架构演进路线图
在主文档末尾完成全篇综合总结，内容必须包含：

1. **系统整体架构健康度评估**：优势亮点、核心不变量坚守度与当前薄弱点。

2. **系统性问题清单与改进建议**：每项问题/建议统一采用四段式结构——
   - **问题描述**：具体现象、代码锚点与影响范围；
   - **根因分析**：成因与演化路径；
   - **建议方案**：可落地的修复或重构步骤；
   - **ROI 评估**：分别从 Return 与 Investment 各取最贴切的角度权衡——Return 可选用户价值、问题严重性、性能与稳定性、架构简洁优雅程度、易维护性等，Investment 可选修改工作量、复杂度提升、维护成本增加、潜在风险等——只选与该项最相关的角度，给出明确取舍结论。
   清单最终**按 ROI 排序、按 Domain 分组**呈现，形成"哪些值得先做、哪些收益有限甚至不值得做"的全局决策视图。

3. **中长期架构演进与重构建议路线图**：以第 2 点的 ROI 排序与 Domain 分组为输入，结合 **Mermaid 甘特图或路线图** 分阶段安排行动项与重构优先级——高 ROI（回报高、投入低、风险小）项前置，低 ROI 或高风险项延后，或明确给出"不建议做"的结论。
