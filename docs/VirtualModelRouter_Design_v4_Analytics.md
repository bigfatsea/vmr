# Virtual Model Router (vmr) — 设计方案 · Part 2：报表与叙事（Analytics）

本文档描述 vmr 审计日志的离线消费方——统一分析入口 `vmr analyze` 的两大半区：**宏观聚合报表**（横向用量、成本、可靠性与效率分析）与 **Agent 任务叙事重建**（纵向会话生命周期、决策流与执行差异诊断）。

配套文档：
- `docs/VirtualModelRouter_Design_v4_Core.md`（Part 1）—— 路由核心。定义系统唯一的输入契约（`audit.Record`）。
- `docs/VirtualModelRouter_Design_v4_Quota.md` —— 额度模型专篇。定义配额账本与额度对照口径。
- `docs/VirtualModelRouter_Design_v4_LiveStats.md` —— 实时遥测专篇。
- `docs/VirtualModelRouter_Design_v4_Strategy.md` —— 战略定位与竞品分析。

**核心架构边界**：分析半区为纯离线、只读消费者，通过只读扫描审计日志（JSONL / zstd）运行。分析半区不参与任何在线路由决策，且绝不反向被路由核心依赖（由 `internal/archtest` 严格守卫）。

## 1. 第一性原理与两级变焦视图

### 1.1 第一性原理：审计日志作为时间轴快照
在现代多轮 Agent 工作流中，客户端每一轮都会将累积的完整历史重新发送给模型。因此，审计记录不是孤立离散的日志行，而是**同一份对话状态在时间轴上的不可变快照序列**。

这天然构成了类似 Git 的内容寻址模型：
* **消息即 Blob**：消息内容不可变，具有确定的规范化内容哈希；
* **轮次即 Manifest（Tree）**：单次请求的上下文为有序消息哈希向量；
* **演进即 Edit（Commit）**：相邻请求之间的上下文变化表现为结构性编辑操作；
* **任务与会话即 Lineage（Branch）**：一系列非破坏性编辑连成的连续执行流。

会话聚合、任务切分、上下文压缩（Compaction）与信息损失评估，全部抽象为该上下文图上的结构化查询，而非零散的启发式规则。

### 1.2 两级连续变焦架构
* **宏观报表半区（Macro Report）**：横向聚合全局请求，回答“资源花在哪、哪条链路在失败、整体 Prompt Cache 命中率如何”。
* **任务叙事半区（Journey Narrative）**：纵向还原单任务执行轨迹，回答“Agent 具体是如何执行该任务的、哪一步开始出现偏离或死循环”。
* **逐请求详单（Request Details）**：两者共同的微观下钻终点，提供单请求单轮增量差分与证据溯源。

## 2. 宏观报表半区（Macro Report）

宏观报表半区负责从全量审计数据中提取全局性统计事实。

### 2.1 聚合流水线
1. **拓扑与边界识别**：基于 `internal/ctxgraph` 构建消息哈希图，切分独立会话链（Lineage）并识别任务轮次边界。
2. **多维指标投影**：流式归集模型、日期、客户端凭据、上游端点等维度的指标分桶（请求数、延迟、TTFT、Token 四分量及缓存效率）。
3. **领域切片物化**：将内存聚合数据投影为标准化的切片文件（`macro/*.json`），并通过单一渲染管线输出人读 Markdown 报告。

### 2.2 领域切片体系与单体 JSON 的剔除
系统放弃脆弱的单体大 JSON，按消费关注点拆分为独立领域切片：
* `macro/summary.json`：全景核心指标、系统效率与首屏亮点；
* `macro/finance.json`：模型与客户端成本、账户额度对照与定价覆盖情况；
* `macro/reliability.json`：端点可用性、错误分布与会话粘性有效性；
* `macro/workloads.json`：时序分布、请求流式占比与客户端上游归属；
* `macro/context-efficiency.json`：会话拓扑、历史压缩损失与工具集形态。

以上五份是原子写入的核心切片集（缺一即视为产物损坏）。`macro/guard.json`（Agent Guard 的离线双向取证审计，设计见 Part 1 的 Agent Guard 一节）是独立于这五份之外的**可选**追加切片——数据源是新产生的审计字段 `audit.Record.Guard`（在线护栏盖章时的权威路径）或对 `Client.Request`/`Client.Response.Body` 的离线现场补扫（Fallback Path，覆盖未盖章时期的历史记录，双路设计见 Part 1），而非对既有五份数据的再切分，因此不受"新增维度需理由"红线约束（Agent Guard 的立项边界决定了它是新数据源而非既有数据的再切分，见 Part 1）；补扫无论在线护栏是否配置都会运行，只有当一个记录连请求体都为空时才会真正跳过；不影响五份核心切片的原子性判定。

### 2.3 准入令牌：`manifest.json`
为保证整套产物的原子性与强一致性，系统在全部领域切片落盘后，原子写入 `manifest.json`：
1. **一致性校验**：记录切片清单及其 SHA-256 校验和。读取方先验令牌，任何指纹不符即视为产物无效。
2. **数据溯源**：记录输入日志列表、时间跨度、时区与生成配置。
3. **数值解耦**：令牌仅负责元数据准入与溯源，绝不承载具体业务指标数值。

### 2.4 单一渲染路径与表现层
报表 Markdown 渲染严格遵循单一流向：
$$\text{内存聚合} \longrightarrow \text{落盘领域切片 JSON} \longrightarrow \text{ViewModel 构建器} \longrightarrow \text{固定序列化器} \longrightarrow \text{Markdown 报表}$$

* **禁止双重路径**：实时渲染与纯渲染模式（`-render-only`）共用从切片读取并构建 ViewModel 的后半段路径，由构造保证数据绝对一致。
* **ViewModel 与固定序列化**：构建器负责完成业务格式化与本地化（i18n），产出扁平排版结构；序列化器仅负责确定性组装，不引入动态模板引擎。

### 2.5 成本核算口径
* **按量等价口径（Pay-as-you-go Equivalent）**：所有成本反映“按公开列表价或覆盖单价逐 Token 计费所需金额”，用于衡量套餐价值与溢出代价，非财务实付对账。
* **分级降级披露**：对于缺乏价格数据的端点标为“未定价”，上游未返回标准 Usage 时标注“降级估算占比”，缺分量费率时标明下界提示，严禁将未知费率伪装为免费（`$0.00`）。

### 2.6 额度对照与差分一致性纪律
宏观报表中的“额度与消耗对照”子表（`macro/finance.json`）并排展示“本报表窗口消耗”与来自 `<log_dir>/vmr-quota.json` 的“本周期实时已用”：
* **权威基准**：`requests` 口径重算严格读取 `audit.Attempt.Forwarded`（路由半区 `forwardSuccess` 唯一置位点），而非反推状态码。软拦截（2xx + `error_class=content`）未转发配额零扣，截断流仍扣配额且标记为已转发。
* **差分测试守护**：由于分析半区禁止依赖路由半区，两者对同一批记录的配额计算一致性由组合根的 `cmd/vmr/quota_parity_test.go` 跨半区差分测试死锁保护，严禁各自私自改动公式造成分裂。

## 3. 上下文图与叙事半区（Context Graph & Journey）

### 3.1 `internal/ctxgraph`：内容寻址上下文图
上下文图负责将扁平的审计记录转换为高阶语义图结构：
* **Manifest 建模**：对每条请求的消息列表进行规范化哈希计算，生成哈希向量。
* **五类编辑分类（Edit Classification）**：
  相邻 Manifest 之间的结构转换精确归为五类：
  * **`Append`**：内容严格前缀递增，代表任务正常推进；
  * **`ReplaceTail`**：前缀一致但尾部更替，代表重试或临时提示词微调；
  * **`Splice`**：中段被替换但保留首尾，代表原地上下文压缩；
  * **`Contract`**：长度剧烈收缩，代表历史发生截断，触发 Lineage 切分；
  * **`Fork`**：重叠率显著偏低，代表开启全新对话，触发 Lineage 切分。
* **结构化缝合（Stitching）**：通过消息精确哈希倒排索引，跨文件与跨会话检索前驱。
  * **确定性决胜排序**：由于 Go `map` 迭代顺序具有随机性，当多个候选前驱重叠率打平时，严格执行三级稳定排序（**覆盖率高者胜出 ──► 间隔时间短者胜出 ──► Lineage 索引小者胜出**），杜绝因遍历随机性导致同一语料多次重跑得到不同的 Journey ID。
  * **断裂守门**：遵循“宁可断开，绝不误连”原则，置信度不足时保留断裂标记供人工复核。

### 3.2 上下文压缩（Compaction）三形态与信息损失

现代 Agent 框架在长程任务中会主动压缩历史以控制上下文开销。系统通过上下文图的 Edit 转换精准捕获 Compaction 的三类形态：
* **原地替换（Splice）**：保留系统提示词与末尾活动消息，中段历史被精简为一个或多个摘要块；
* **尾部截断（Contract / Truncation）**：单轮上下文长度急剧收缩（当前长度 < 前轮长度 × 0.6），触发 Lineage 分裂；
* **重构更替（ReplaceTail）**：前缀一致但尾部分岔，多见于临时重试或提示词微调。

**信息损失评估**：系统在检测到 Compaction 时，自动差分对比压缩前后的消息集合，提取被丢弃轮次中曾提及的文件路径、工具输出及关键实体。若后续 Step 出现因上下文遗失导致的盲目重试或事实性偏离，系统生成相应的 Finding 预警，精确定位长任务退化根因。

### 3.3 数据分层模型
任务叙事半区按三层拓扑组织：
```
Journey (连续叙事链，由一个或多个缝合的 Lineage 构成)
  └── Task (由用户真实新指令驱动的连续工作单元)
        └── Step (单次上游请求/响应轮次)
```

* **因果配对不变量**：在单请求内部，工具调用与工具结果遵循严格因果闭环配对，不采用猜想启发式。
* **去重事件流**：消息按在 Journey 中的首次出现时间全局去重，避免重复展示累积历史。

### 3.4 决策脊柱（Decision Spine）与排障展示
叙事半区通过“决策脊柱”提炼核心排障脉络：
* **概览卡**：呈现任务关键节点、总耗时、模型切换次数与成本估算；
* **Step 角色标注**：按优先级标定轮次属性（压缩 🧹 > 错误 ⚠️ > 重试 🔄 > 执行 🔧 > 规划 📋 > 汇报 💬 > 观察 👀）；
* **决策动因行**：提炼模型输出简评或思考摘要（Reasoning），紧跟工具调用核心参数；
* **缓存断裂归因**：Prompt Cache 命中率骤降时，自动归因至系统提示词变更、工具集调整、换端点或上游缓存逐出；
* **产物追踪（Touched Artifacts）**：汇总整个执行流程触碰过的文件与执行命令；
* **工具调用时序图**：以直观字符图展现各工具的调用频次、重试与失败分布。

### 3.5 异常行为检测器（Findings）
系统内置规则化检测器，捕获 Agent 典型失效模式：
* **行为与重试类**：密集重复调用（`exact_repeat_tool_call`）、报错未调整盲目重试（`error_retry_unadapted`）、无动作纯叙事（`narration_without_action`）；
* **决策与推理类**：推理决策与实际动作脱节（`reasoning_action_mismatch`）、规划与执行偏离（`plan_execution_misalignment`）；
* **工具与证据类**：报错后未经检验宣称成功（`error_then_unverified_success`）、工具返回结果未被引用（`unused_tool_result`）、未经验证的实体引用（`unverified_entity_reference`）；
* **压缩与约束类**：上下文压缩丢弃核心约束（`constraint_text_dropped_at_compaction`）。

**契约分离**：每条 Finding 拥有稳定的机器标识 `FindingCode`（如 `exact_repeat_tool_call`），程序化分析依赖 Code 判定，展示文案跟随输出语言。

### 3.6 双 Journey 对比（`-compare`）与差异下钻
支持对两次运行进行横向比对：
* **规则指标差分**：对比耗时、Token 构成、工具复用度、缓存效率等标量，标记显著变化（`Notable`）；
* **结构分叉点检测（Divergence Point）**：对齐两次运行的工具执行签名，精确定位双方首次产生决策分歧的 Step 位置；
* **最终交付物比对**：逆序提取文件写入类工具调用参数，对比两者的最终成果差异；
* **请求级微观比对（`vmr diff`）**：针对具体坐标的单请求执行 Header、System Prompt、工具定义与消息序列的纯结构差分。

### 3.7 诚实声明与分析盲区（避免“未记录”误读为“未发生”）
* **客户端私有未上报行为**：vmr 仅记录到达网关的网络流量，客户端在本地被截断或丢弃的历史对网关不可见；
* **外部真实副作用**：因果闭环记录工具参数与输出，但工具在宿主机磁盘或远端产生的实际物理副作用仅能通过工具返回值溯源；
* **未执行分支不可推测**：Prompt 中的条件分支与未选中的决策路径，在审计日志中不留痕迹。

## 4. 辅助设施与多语言体系（i18n）

### 4.1 本地化架构（`internal/i18n`）
* **类型化文本**：为零依赖叶子包，按业务章节组织。输出结构体使用强类型字段，字段命名错误在编译期拦截。
* **语序自由度**：对于需要插值的复杂语句，使用函数值字段（`func(...) string`）提供独立格式化实现，杜绝不同语言共享占位符顺序带来的脆弱性。
* **机器标识与展示文本解耦**：JSON 切片与 Markdown 均支持多语言切换，但机器枚举标识（`FindingCode`、`MetricCode`）与原文证据锚点（`EvidenceAnchor`）恒定不变。

### 4.2 独立分析配置：`report.yaml`
分析命令的设计受众通常为日志离线审计人员，可能脱离路由部署环境运行：
* **配置解耦**：分析专用参数（语言、默认输出目录、LLM 解读配置等）维护于轻量级 `report.yaml`，不依赖路由生产配置 `config.yaml`。
* **优先级次序**：命令行旗标 > `report.yaml` > 内建默认值。
* **自指流量自动剔除**：若分析过程中使用了 LLM 解读且请求打回 VMR 自身，系统自动基于密钥指纹识别并剔除此部分自指流量，防止污染审计指标。

## 5. 架构决策与不变量

| 决策点 | 采纳方案 | 核心权衡理由 |
| --- | --- | --- |
| **基准事实层** | 基于消息规范化哈希的内容寻址图（`internal/ctxgraph`） | Agent 每一轮重发全历史，内容寻址是差分计算唯一可靠的数学基座，杜绝私有启发式切分导致的分歧。 |
| **因果关系** | 仅信任协议强约束的工具闭环配对 | 真实网络协议保证了 Tool Call 与 Tool Result 的精确成对，收窄推断范围，拒绝基于启发式臆测执行结果。 |
| **断裂处理** | 宁可断开，绝不误连 | 将不相关任务错误缝合会导致因果倒置并误导复盘；断裂在界面上显式可见，误连则隐蔽破坏分析。 |
| **详单生成** | 默认按需懒物化，单轮差分展示 | 避免批量预生成数百个详单带来的磁盘 IO 暴增；通过增量消息与前驱链接彻底消除 $O(N^2)$ 的全历史重复存储。 |
| **表现层架构** | ViewModel + 固定序列化器，不引模板引擎 | 编译期强类型约束杜绝运行期字段拼写或表格错位；单一渲染路径确保全量运行与从 JSON 渲染结果完全等价。 |
| **解读层边界** | 规则派生指标优先，LLM 解读定位为可选第三层 | 确保分析报告中的每一个基础数值、分位与比率绝对客观可复现，LLM 仅用于高阶语义总结与发散归因。 |
| **经验阈值校准** | 关键切分参数由真实生产语料校验沉淀 | `contractLenRatio=0.6`、`forkCoverage=0.5` 等硬编码常量经过数千真实调用语料验证，避免随意调参破坏稳定性。 |
| **成本核算口径** | 按量等价口径（Pay-as-you-go Equivalent） | 评估模型选用价值与套餐溢出代价，非实收对账；缺失价格时显式降级提示，严禁将未知费率伪装为 `$0.00`。 |
| **统一跨命令坐标** | 发布标准化 `req` 坐标（`basename:line`） | 为 `vmr diff` 与 `vmr replay` 提供一致定位符，排障时无需人工核对日志行号。 |
| **产物安全隔离** | 分析产物统一维持 `0600` / 目录 `0700` | 报表与详单承载与审计日志等价的完整对话明文，严禁放宽权限造成信息泄漏。 |

## 6. 已知限制与暂不处理事项

判定“动它的收益低于扰动成本，或当前数据不足以支撑调整”的项。沉淀在此避免后续重复论证（对齐 AGENTS.md 约束）：

| 项 | 现状 | 不动与保留现状的理由 |
| --- | --- | --- |
| **`stitch.go` 缝合两档分数阈值** | `stitchCompactionScore`（0.5）与 `stitchHeadPruneScore`（0.15）为初始校准值 | 该阈值已在生产语料上验证产生合理分布；在未接入形态截然不同的新 Agent 框架前，不随意修改硬编码参数。 |
| **`Metrics.ErrorRecoveryCount` 在 OpenAI 协议下偏低** | 仅识别 Anthropic 原生的 `is_error` 内容块，OpenAI 协议无标准对应字段 | 坚守“宁可粗糙也不猜语义”的纪律，拒绝基于响应文本正则猜测错误；待上游形成标准化错误信号后再接入。 |
