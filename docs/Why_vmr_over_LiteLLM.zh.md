# 为什么选 vmr，而不是 LiteLLM（或 Portkey，或其他任何"翻译型"网关）

[English](Why_vmr_over_LiteLLM.md) | 简体中文

**万能转换插头只改变插头的形状，好让它插进不同的插座——电流本身原封不动地通过。变压器改变的是电流本身。LiteLLM 是变压器，vmr 是转换插头。**

## 一句话版本

LiteLLM（以及大多数所谓"万能 LLM 网关"）的工作方式是：把每个请求先翻译成自己的内部统一格式，再翻译回你选定的那家供应商的格式。vmr 从不做任何翻译——它只看你的客户端说的是哪种协议（OpenAI 还是 Anthropic），挑一个说同一种协议的上游，然后把你的字节几乎原样转发过去。一种做法是为"支持所有供应商，哪怕形状完全不一样"做优化；另一种做法是为"永远不要成为你的 agent 请求变得面目全非的那个原因"做优化。

如果你跑的是一个真正的 AI agent——无人值守地调 API、自己重试、没法在结果不对的时候问一句"这个响应看着对吗"——第二种特性的分量,比听上去要重得多。

## 翻译型网关真正会出问题的地方

假设某家供应商明天上线一个新参数——`reasoning_effort`、一种新的 `cache_control` 结构、一种新的 `tool_choice` 模式，随便什么。翻译型网关必须先显式学会这个字段才能转发它：解析进自己的内部 schema，再在发往供应商的路上映射回去。在有人给网关打补丁之前，这个字段要么被静默丢掉，要么整个请求直接失败。

vmr 没有一个"你的请求要在里面幸存下来"的内部 schema。它只对一个字段做字节级替换（`model`，把你的虚拟名换成真实的上游名），其余每一个字节——键的顺序、空白、未知参数——都按你客户端发出时的原样转发。供应商刚上线的新参数，第一天就能透过 vmr 正常工作，vmr 代码一行都不用改——因为它压根没对"应该有哪些字段"这件事持有任何意见。

这不是假设。这个代码库本身就只针对 MiniMax 做了两处范围极窄、明确限定触发条件的修复（剥掉一个会污染对话历史的 `<think>` 标签，剥掉 MiniMax 在某些模式下输出的一段纯文本"思考"内容）——**仅此而已**。这就是在真实生产环境接了好几家供应商之后，跟直连相比全部的字节级差异。除此之外——不管是 OpenAI/Anthropic 已知的字段，还是还没被发明出来的字段——全部原样通过。

## 放在一起比

| | vmr | LiteLLM |
|---|---|---|
| 请求处理 | 字节级透传——没有内部 schema | 把每个请求翻译成统一的内部格式 |
| 供应商新参数（比如 `reasoning_effort`） | 第一天就能用，vmr 不用改代码 | 得先加上显式支持才能转发 |
| 响应流式 | 真透传——SSE 事件到达就转发 | 经统一格式重新序列化 |
| 部署形态 | 单个 Go 二进制，4 个直接依赖，零数据库 | Python；功能齐全通常需要 Postgres + Web 管理后台 |
| 配置 | 一份 YAML | 配置文件 + 可选的数据库驱动管理界面 |
| 供应商覆盖面 | 任何 OpenAI/Anthropic **协议兼容**的端点 | 100+ 家供应商，包含原生协议完全不同的那些 |
| Agent 会话感知 | 内置：请求自动分组为会话 → 任务 → 轮次，能标出声明了但从没被调用的工具，追踪每轮增量 | 不是设计重点 |
| 审计留痕 | 每个请求、每次 failover 尝试、每一条实际生效的字节级归一化——一行 JSONL，可回放 | 有日志，但不是按 agent 会话语义组织的 |
| 最适合 | 一个（或几个）你信任、无人值守运行的 agent，字节保真度比供应商数量更重要 | 服务多个供应商/多个用户的集中式团队网关，需要开箱即用的费用管理和权限控制 |

简单不只是设计上的偏好，实际跑起来也便宜：压测至 150 req/s，vmr 自己的路由开销在 12 个测试场景中有 9 个的 p95 都在个位数毫秒以内（[`loadtest/`](../loadtest/)）。

## 什么时候真的该用 LiteLLM

实话实说：vmr 不是万能替代品。

- **你需要的供应商协议真的不一样**——不只是换个 base_url，而是请求/响应结构从根本上不同，LiteLLM 已经为它写好了翻译器（一些只做 embeddings 的 API、一些用自定义格式的本地模型服务）。透传只能在协议兼容的端点之间生效——这是"从不碰你字节"必须付出的代价。
- **你需要一个托管的多租户网关**，自带费用统计、按团队分预算、管理后台，服务多个互不共享配置文件的下游用户。这是 LiteLLM 已经做好的产品；vmr 刻意不做 Web UI，也不做数据库。
- **你想要一个被广泛采用、维护力量雄厚的翻译层作为安全网**，即使它偶尔会比供应商最新字段慢半拍。如果供应商覆盖面对你来说比字节级保真更重要，这是合理的选择。

如果以上都不是你的情况——如果你实际拥有的是一个 agent（或一小群你信任的 agent），打的是几家 OpenAI/Anthropic 兼容的供应商，你想要的是"客户端的请求原封不动地到达供应商，出问题时能精确看到到底发生了什么"——那正是 vmr 唯一在做、也只做这一件事的工作。
