# VMR 前置敏感词过滤 — 分析与系统设计报告

> 任务性质：分析、研究与系统设计，不含实现。
> 输入：`houbb/sensitive-word` 项目源码（亲自核验）、`GO_PORTING_ANALYSIS.md`（仅作参考）、VMR 现有设计与真实审计数据。

---

## 一、Debrief

**要解决的问题**：OpenClaw 等 Agent 系统的长程任务中，请求内容不可控，时常触发上游 LLM 的内容合规拦截。VMR 现有策略是事后处理——`ErrContent` 分类后 failover 到下一家且不惩罚被拦端点，解决约 80% 的问题。剩余场景考虑加一层**事前关键词过滤**：请求发往上游前检测并替换敏感词，让请求"出门前就干净"。

**明确的约束**：只用关键词匹配（不引入小模型），性能开销必须对延迟几乎无影响，实现难度要低——追求低成本高收益的极简做法。

**用户的预判**（待本报告检验）：改写只涉及个别字词，不影响整段语义；触发本来就低频；综合可感知影响概率很低。

**本报告要回答的问题**：sensitive-word 是个什么东西；VMR 加这层是否合理、是否必要、有什么负面影响、值不值得做；若做，怎么集成、怎么实现、能从 sensitive-word 借鉴什么。

---

## 二、sensitive-word 项目简析（基于源码亲自核验）

`houbb/sensitive-word` 是一个 Java 敏感词库，主代码 121 个 Java 文件，词库（v0.27.0 起拆分到独立仓库 `sensitive-word-data`）约 6.5 万词（本仓库测试资源 `dict_20231117.txt` 实测 65,338 行）。

### 2.1 核心数据结构与算法

**自称 DFA，实为标准前缀树（Trie）+ 多起点扫描**，不是带失配指针的 Aho-Corasick 自动机。这一点移植分析的判断正确，源码核验属实：

- `WordDataTreeNode`：每节点一个 `HashMap<Character, Node>` + `end` 结束标记。
- `WordDataTree.doContains`：从根逐字符下沉，返回三态 `NOT_FOUND / CONTAINS_PREFIX / CONTAINS_END`——三态是它做"最长匹配"的关键（PREFIX 表示"还可能更长，继续喂字符"）。
- 主循环（`SensitiveWord.innerSensitiveWords`）：对文本每个位置 i 调 `sensitiveCheck(i)`，在该起点同时对**黑名单树和白名单树**求最长命中（`WordCheckWord.getActualLength`：逐字符 append，两棵树同时查，直到双双 NOT_FOUND）；仅当 `白名单命中长度 < 黑名单命中长度` 才记为敏感词，然后 `i += denyLen - 1` 跳过已命中段。
- 复杂度：最坏 O(n × L)（L 为起点可延伸的最长深度），命中跳跃使实际表现尚可（README 称纯匹配约 14 万 QPS）；长文本大词库且大量前缀部分匹配时存在重复扫描，弱于真 AC 自动机的 O(n)。

### 2.2 分层架构

几乎每个能力点都是"接口 + 默认实现 + 组合器"：

| 层 | 职责 | 要点 |
| --- | --- | --- |
| `support/data` | Trie 本体 | 动态增删词（`synchronized`），全量重建后原子换根 |
| `support/format` | 文本归一化链 | 大小写、全半角、异形数字（①⑴壹→1）、异形英文、繁简（依赖 opencc4j）；先全文构建 `Map<Character,Character>` 映射，匹配时查表 |
| `support/check` | 检测器 | 词匹配 + num/email/url/ipv4 独立检测器，可组合 |
| `support/allow`/`deny` | 黑白名单 | 各一棵树，运行时并行比长度 |
| `support/replace` | 替换策略 | 缺省按字符替换为 `*`，可自定义 |
| `support/resultcondition` | 命中后二次条件 | 如英文全词匹配（`av` 不命中 `have`） |
| `bs/` | fluent-api 引导 | 配置组装入口 |

### 2.3 对本任务最有价值的三个认知

1. **它的复杂度大半来自"对抗性场景"**：归一化链（全半角/异形字/繁简/重复字忽略）防的是**恶意用户变形绕过**（如 "F*u*c*k"、"①⑧禁"）。这与 VMR 的场景根本不同——详见 §3.4。
2. **词库是最大资产，也是最大风险源**：6.5 万词覆盖广，但直接全量启用意味着巨大的假阳性面（词表里含大量日常语境可正常出现的词）。
3. **白名单机制不是锦上添花**：黑白名单并行比长度的设计说明作者深知误杀是常态，必须有恢复通道。任何词面过滤系统都需要这个部件。

## 三、VMR 加前置过滤：合理性、必要性与负面影响

### 3.1 事实基础

先把能核实的事实摆出来：

1. **现有审计数据中，内容拦截发生率为零**。全部可用审计日志共 97 个请求（2026-07-07/08 两天），`error=content` 的尝试为 0。当前数据窗口太短（两天、单一使用者、以 MiniMax 为主力），**不足以证实也不足以证伪"时常出现"**——你的经验判断来自更长的 OpenClaw 使用史，这里如实并列：经验说常见，数据尚未捕捉到。
2. **VMR 已有的事后机制**（设计文档 §5）：`ErrContent` 靠 403/451 + 中英文词表嗅探识别，切换不惩罚端点；全部候选都被拦时客户端原样收到最后一次内容错误。这就是"80% 方案"的实现。
3. **一个 failover 覆盖不了的确定性盲区**：设计文档 §5 已知边界明确记录——MiniMax 会在 **HTTP 200 内嵌合规标记**（`input_sensitive` 等字段）并返回空/替换内容。透传路径不查 2xx body，这种"软拦截"对 VMR 不可见、不触发 failover、原样到达客户端。**对软拦截，事前过滤是唯一防线**——这是前置过滤最硬的必要性论据。
4. **架构缝已预留**：设计文档 §12.1 早已规划此功能，接入点定在 `chatHandler` body 缓冲后、`router.Serve` 前；imgprep（图片降采样）已用同一接入点、同一改写模式（`map[string]json.RawMessage` 局部改写 + fail-open + `recover` 兜底）实证可行。集成不需要新架构。
5. **审计天然支持取证**：`client.request.body` 记原文、`attempts[].request.body` 记出站内容——改写前后两个版本在现有审计结构下**零改动即自动分层留档**。

### 3.2 合理性：事前 vs 事后的本质差别

failover 的语义是"这家拦，换家试"，它有三个结构性短板，前置过滤恰好各补一个：

- **全军覆没无解**：一条足够敏感的请求会被所有厂商拦下，failover 走完全链后原样报错，长程任务中断——这正是你要消灭的场景。
- **软拦截不可见**（§3.1 第 3 条）：failover 根本不知道发生了拦截。
- **失败往返有成本**：每次被拦是一次完整的上游往返（连接 + 请求体上传 + 等待判定），长 prompt 下是秒级浪费；事前过滤是微秒级。

所以从机制上讲，前置过滤与 failover 是**互补的两道防线**（出门前消毒 + 出门后换路），不是替代关系。合理性成立。

### 3.3 必要性与效果的最大不确定性：词表 ≠ 厂商审查模型

必须实事求是地指出：**"关键词能解决 80% 以上问题"目前没有实证支撑**，且有一个结构性怀疑理由——

厂商的内容审查（尤其国内厂商）如今普遍是**模型审查**而非词表审查。拦截分两类：

- **词面触发**：请求里存在具体敏感词 → 词过滤有效；
- **语境触发**：整段话题、意图、组合语义敏感，但拆开没有一个词在任何词表里 → 词过滤无效，且我们无法事先知道两类的比例。

我们的词表与厂商审查模型的重合度是未知的。好消息是这个不确定性**可以低成本地被消除**：每次 content 拦截的完整请求体都在审计日志里，积累若干真实拦截样本后，人工回看即可判断"这条如果做了词过滤能不能救"——用事实回答 80% 还是 30%。这直接导出本报告的核心建议（§4）。

### 3.4 一个关键洞察：我们没有对手

sensitive-word 的设计场景是 UGC 平台防**恶意用户**变形绕过审查，所以需要全半角/异形字/繁简/重复字忽略这一整条归一化链。VMR 的场景是**自己人的 agent 无意间触雷**——没有人在变形绕过，敏感词以词面原形出现。这意味着：

> **归一化链、反绕过能力、6.5 万全量词库，在 VMR 场景下都是不必要的复杂度。词面精确匹配 + 小词表就是完整解。**

这一条把"极简做法"的下限拉得非常低（§5）。

### 3.5 负面影响（按严重程度排序）

1. **Agent 请求不是纯文本——改写可能污染代码与数据（最重要的反方论点）**。你的预判"改个别字词不影响语义"在**对话文本**里成立；但 OpenClaw 的 messages 里大量内容是 `tool_result`（文件内容、命令输出、代码）、工具定义、tool_calls 参数。敏感词若恰好出现在**代码字符串、文件路径、配置值、要写回磁盘的文件内容**里，替换成 `***` 后模型基于污染内容操作 → 把 `***` 写回文件 → **数据损坏**。长程 agent 的这条故障路径比"输出质量略降"严重一个量级。缓解办法存在（限定改写范围，见 §5.3），但代价是覆盖率下降——tool_result 里的敏感内容恰恰可能是触发拦截的主力（如浏览网页抓回的文本）。这是本方案最核心的权衡。
2. **破坏直连等价原则的第三个例外**。VMR 刚刚完成"除 model 名与可关闭的图片压缩外字节级透传"的整肃，这层过滤是第四处主动改写。可控性靠三点维持：默认关闭、开关即词表路径（与 `image_downscale` 同构）、审计双层留档使每处差异可解释。原则没有被推翻，但例外清单变长了，每加一个例外都在消耗"透传"承诺的纯度。
3. **假阳性代价不对称**。聊天里错杀一个词是小事；agent 场景一次误杀可能让模型误解指令或数据。词表必须从小、从严、从实际事故中生长，而不是从 6.5 万词库开始。
4. **词表维护是长期负债**。厂商审查标准漂移、新话题出现，词表要跟着改；词表文件本身是敏感物料，不能入 git（需 gitignore + 文档说明）。
5. **性能**：可忽略，你的判断正确。小词表 Trie 扫描是微秒级，比 imgprep 的图片解码便宜几个量级，相对 LLM 秒级响应无感。此项不构成反对理由。

### 3.6 值不值得做——结论

**替换式过滤本身：值得做，但不是现在做，更不是从全量词库开始做。** 论证链：

- 问题的**真实频率未经量化**（现有数据 0/97），效果的**上限未经验证**（词面触发占比未知）。在这两个数字出来之前实现替换逻辑，是在猜测上盖房子。
- 但两个数字都可以用**近乎零成本的观测**获得，且观测本身就有独立价值（见下）。
- 一旦数据证实"频率不低 + 词面触发占比高"，极简实现（§5）在 VMR 现有架构上是一天级的工作量——**晚做没有惩罚，早做要付维护费和数据污染风险**。典型的"期权比现货便宜"。

**因此推荐两阶段路线：**

**第一阶段（建议立即做，纯观测零风险）：把问题变成可量化的。**
1. **软拦截检测**：在响应归一化器（已有 2xx body 缓冲/扫描能力）加对 MiniMax `input_sensitive`/`output_sensitive` 类标记的嗅探，命中只做两件事——审计 `norm` 记 `soft_block_detected`、可选触发 failover（软拦截语义上等同 ErrContent）。这补上 failover 的盲区，本身就是独立正收益，且不改任何字节。
2. **拦截样本积累**：`vmr report` 的 error_classes 已单列 content 桶；审计里每次拦截的完整原文都在。跑几周 OpenClaw，回看全部 content/soft_block 样本，回答两个问题：月频多少次？其中词面可救的占比多少？
3. 数据说话后再决定第二阶段是否启动。

**第二阶段（数据证实后）：按 §5 的极简方案实现替换式过滤。**

## 四、（若做）集成方案与系统设计

以下设计以"第二阶段启动"为前提，原则：复用既有缝、不引入新概念、默认关闭、fail-open。

### 4.1 总体形态

```
配置:  word_filter: words.txt        # 开关即词表路径，缺省关闭（与 image_downscale 同构）

数据流: chatHandler
        缓冲 body → 审计记录原文 → 并发闸
        → imgprep.Downscale(可选)
        → wordfilter.Scrub(可选)      ← 新增，同一接入点、同一模式
        → probe 解析 → router.Serve   （failover 重放自然使用改写后内容）
```

- **新包 `internal/wordfilter`**，与 imgprep 平级对称：直接函数调用，不建插件注册表（§12.1 的"不预留接口"决策继续有效——这已是具体功能，不是框架）。
- **fail-open 铁律**：词表加载失败、解析 panic、任何异常 → 原文放行 + stderr 日志。过滤器的 bug 绝不能挡下本可成功的请求。

### 4.2 匹配引擎：第一版用 `strings.Replacer`，够了

- 预期词表规模是**几十到几百词**（事故驱动生长，见 4.4），这个量级下 Go 标准库 `strings.NewReplacer`（内部即 Trie，构建后并发安全只读）就是零依赖、零维护的完整答案。`old1, new1, old2, new2...` 一次构建，原子指针随词表热加载换新。
- 不做归一化链（§3.4 的论证：无对抗方，词面匹配即完整解）。唯一可能保留的是 ASCII 大小写不敏感——把英文词的大小写变体在构建 Replacer 时展开即可，不需要运行时归一化。
- 词表若真长到万级再换 Aho-Corasick（`cloudflare/ahocorasick` 等成熟库），接口不变只换内核——这是预留的升级路径，不是现在的实现。

### 4.3 改写范围：只碰对话文本，不碰工具语义（针对 §3.5 风险 1）

复用 imgprep 的 `map[string]json.RawMessage` 局部改写模式，但字段选择上更保守：

| 位置 | 处理 | 理由 |
| --- | --- | --- |
| `messages[].content`（字符串形态） | 替换 | 对话文本，风险低 |
| `messages[].content[].text`（分块形态，role=user/system/assistant） | 替换 | 同上 |
| `system`（Anthropic 顶层） | 替换 | 同上 |
| `tool_result` 内容、`tool_calls` 参数、工具定义 | **第一版不碰** | 污染代码/数据的高危区；宁可漏拦不可错改 |

代价如实声明：tool_result 里的敏感内容（如网页抓取文本）仍可能触发拦截，此时兜底仍是 failover。若第一阶段的样本显示拦截主力恰恰在 tool_result，再单独评估——那时的选项可能是"tool_result 只检测不替换、命中即本地拒绝或告警"而非盲目替换。

### 4.4 词表策略：事故驱动生长，不用全量词库

- **从空词表开始**，每次真实拦截（content error / soft_block）后，从审计原文里人工提炼触发词加入——这是 VMR 独有的闭环：**审计是词表的自动采集器**。与"事故账本"哲学完全一致，且天然保证词表里每个词都对应真实事故，假阳性面最小。
- sensitive-word 的 6.5 万词库作**参考池**：提炼时可查询某词是否在其词库/属什么标签，辅助判断；绝不整库导入。
- 词表文件格式取其最简：一行一词，`#` 注释；可选 `词 => 替换词` 语法支持定向改写（缺省替换为 `*` 等长串）。
- **词表文件加入 .gitignore**（敏感物料不入库），仓库放 `words.example.txt` 说明格式。
- 热加载走既有 fsnotify 通道（§12.1 预判过这个问题，答案是肯定的）：监听词表文件，变更即重建 Replacer 原子替换，坏词表保留旧版本——与配置热加载同一套语义。

### 4.5 审计与可观测

- 命中改写时在审计记一笔（沿用 norm 的思路，请求侧对应物）：如 `client.request` 层加 `scrubbed: ["词A×2","词B×1"]` 或仅计数——具体字段随实现定，原则是**每处字节差异可解释**（改 §9.2 必同步 report，既有契约）。
- 原文与改写后内容已由双层审计自动分离（client 层原文 / attempts 层出站），取证零成本。
- `vmr report` 增加 scrub 命中统计，与 content error 趋势对照——直接量化"过滤挡了多少、漏了多少"。

### 4.6 上线策略：先 log-only 再 enforce

即使第二阶段启动，也分两步：先以**只记录不改写**模式跑（词表命中写审计，不动字节），观察一段时间的命中分布确认无误杀，再切换 enforce。配置上可用 `word_filter_mode: log | enforce`（或首版直接内置 log-only 先行发布）。

### 4.7 从 sensitive-word 借鉴什么、不借鉴什么

**借鉴**：
1. **三态 Trie 语义**（NOT_FOUND/PREFIX/END）与"命中后跳跃 `i += len`"——若将来自研 Trie/升级 AC 时的正确性参照；
2. **白名单意识**：它的黑白名单并行设计提醒我们误杀是常态。极简版的对应物是词表支持 `!词` 前缀表示豁免（实现上就是从 Replacer 剔除），不需要两棵树；
3. **词库数据资产**作参考池与标签查询；
4. **对拍清单**（GO_PORTING_ANALYSIS.md 第六节）里的语义坑，若走到自研匹配内核那步，是现成的测试用例来源。

**不借鉴**：
- 190 文件级的接口抽象与组合器体系（VMR 场景一个函数够）；
- 归一化链全套（无对抗方，见 §3.4）；
- 标签分类、num/email/url/ipv4 检测器、动态增删 API（热加载全量重建即可）；
- 全量词库默认启用。

## 五、其他事项

1. **软拦截检测独立于本功能的价值**：§3.6 第一阶段的软拦截嗅探即使永远不做第二阶段也应该做——它修复的是 failover 的已知盲区（被拦了但 VMR 以为成功，健康记成功、客户端拿到空响应），属于现有机制的完备性补丁，与"要不要改写请求"是两件事。
2. **与 ErrContent 嗅探词表的关系**：VMR 已有一个小词表（`adapter.contentHint`，用于错误分类）。前置过滤词表与它职责不同（一个改请求、一个分类响应错误），不要合并；但拦截样本分析时两者共享同一数据源（审计）。
3. **`GO_PORTING_ANALYSIS.md` 的评价**：其对 sensitive-word 的架构与算法判断经源码核验基本准确（Trie 非 AC、format 链、黑白名单比长度等）；其推荐的"先移植对拍、再换 AC"路线是针对**做一个通用 Go 敏感词库**的正确路线，但与 VMR 的需求错位——VMR 不需要通用库，需要的是场景化的最小内核。若将来真要做独立的 Go 敏感词库开源项目，那份分析的分阶段路线可采纳。
4. **失败样本的隐私提示**：审计里的被拦原文含 OpenClaw 会话内容，分析提炼词表时注意这些文件的存放与清理（现有 0600 权限 + 不入库已覆盖大半）。
5. **不建议做的延伸**：响应侧过滤（改模型输出）——超出"规避上游拦截"的目标，且直接违背透传原则，收益不明；语义级过滤（嵌入/小模型）——你已明确排除，本报告同意：与 VMR 的零依赖、微秒级定位不符。

## 附：结论一页纸

| 问题 | 答案 |

| 前置词过滤合理吗 | 合理，与 failover 互补（救全军覆没、救软拦截盲区、省失败往返） |
