# Virtual Model Router (vmr) — 设计方案 · 实时请求统计（Live Stats）

**这是 v4 版设计文档里路由半区的一个子系统专篇。** 路由核心本身（虚拟模型、协议透传、Adapter、调度与健康、审计日志格式）见 `docs/VirtualModelRouter_Design_v4_Core.md`（Part 1）；本文描述的实时统计挂在它的请求生命周期与收尾钩子上。系统通过三层数据模型（瞬态 in-flight 请求注册表 + 瞬态 slim 小时级 WAL + 历史 rollup 账本）实现零外部依赖的进程内实时遥测。

配套文档：
- `docs/VirtualModelRouter_Design_v4_Core.md`（Part 1）—— 审计日志格式与 `/status` 契约是本文的邻接面。
- `docs/VirtualModelRouter_Design_v4_Quota.md` —— Token 四分量计数的扣费逻辑与本文盖章值同源。
- `docs/VirtualModelRouter_Design_v4_Analytics.md`（Part 2）—— 离线分析半区，共享审计日志数据契约。
- `docs/VirtualModelRouter_Design_v4_Strategy.md` —— 战略定位与竞品分析。

本文范围严格限定在**内置实时统计**：单进程内存聚合 + In-flight 实时状态跟踪 + 自有轻量落盘文件 + 自带控制台展示，不做任何对外推送集成。

## 1. 问题定义与核心约束

### 1.1 核心需求
路由在多客户端、多端点环境下常态运行时，运营者需要实时了解三个层面的事实：
1. **进行中状态**：当前有几个请求在排队、几个在执行、已耗时多久、卡住的流何时收到最后一个数据块；
2. **短期性能分位**：各模型端点近期的首字延迟（TTFT p50/p90）与输出速率（Tok OUT/s p50/p10）；
3. **分维度用量汇总**：按小时、按日历日、按客户端凭据与上游凭据聚合的请求数及 Token 四分量。

### 1.2 架构硬约束
1. **热路径零阻塞**：完成时记账挂在响应提交之后（脱离主请求路径），执行 O(1) 工作；进行中盖章仅限无锁原子更新或局部快照。
2. **磁盘与内存有界**：不无限累积第二份 per-request 数据；内存仅保留 7 天滚动窗口，读时聚合成本恒定。
3. **零配置与独立性**：开箱即用，无需配置外部时序数据库；统计与审计正文解耦，用户选择关闭审计正文记录时监控仍完整可用。
4. **隐私分级**：遥测流纯粹为定量指标，不包含任何 Prompt 或响应文本正文。

## 2. 架构总览：进行中状态面 + 完成时账本

系统将观测面划分为两个互补且互不重叠的计数体系：

```
[请求进入] (完成鉴权，进入并发门前)
  │
  ├─► In-flight 内存注册表登记 (router 内存, state: queued)
  │     ├─ 向上游发起请求 ──► 盖章 sent_at / attempt / provider / model / key_label (state: running)
  │     └─ 接收响应数据流 ──► 逐块盖章 first_byte_at / last_byte_at / 实时估算输出 Tokens
  │
[请求结束] (任意路径退出)
  │
  ├─► In-flight 注册表整条移除 (内存瞬态清理)
  │
  └─► 完成时账本记账 (收尾钩子, 脱离主请求路径)
        ├─ 内存当前小时累加器 (更新计数与全局性能环形缓冲 Global Ring)
        └─ 追加写入瞬态 WAL (slim 小时文件, ~200B/行)

[小时滚动边界] (跨小时首个请求触发，懒处理)
  └─ 扫描未滚动的 slim 文件 ──► 聚合生成 rollup 行 ──► 追加至永久 rollup 账本 ──► 删除 slim 文件

[读路径: GET /stats & /status.html]
  └─ 动态合并: In-flight 快照 + 内存近 7 天 Rollup 映射 + 当前小时累加器 + 全局性能环分位
```

### 核心原则
* **钩子只记账，不算账**：所有分位数计算与复杂维度折叠推迟至读路径动态按需执行；高频读通过短期缓存兜底。
* **瞬态 WAL + 幂等 Rollup**：slim 流只充当小时级暂存日志，聚合入 Rollup 后即物理删除；崩溃重放具备自然幂等性。
* **In-flight 纯内存存续**：进行中状态回答“现在正在发生什么”，完成时账本回答“过去发生了什么”，两本账互不交叉。

## 3. 数据模型

### 3.1 凭据标识与 Token 盖章契约
为杜绝下游消费侧反解析响应体推导指标，路由在转发成功（Winning Attempt）时对核心事实单点盖章：
* **`tokens`**：四分量原始整型计数（`in` / `out` / `cache_read` / `cache_write`）。其中 `in` 为净输入（Fresh Input，扣除 Cache Read/Write），与配额计量基准一致。
* **`key_label`**：实际生效的上游凭据别名（对应配置中展开的凭据标签，或缺省密钥尾部指纹）。与客户端标识 `client_key_tag` 平行并存，分别回答“谁发来的”与“打到了哪个上游账号”。

### 3.2 瞬态 WAL（slim 小时文件）
* **路径与权限**：`<log_dir>/vmr-stats-YYYYMMDD-HH.jsonl`，权限 `0600`。
* **隔离保护**：子系统持独立的建议性文件锁（`.vmr-stats.lock`），防多进程写冲突。未获锁实例自动降级为纯内存运行。
* **结构特征**：单行约 200 字节，记录单个请求的元数据切片（时间戳、虚拟模型、协议、流式标记、最终结果、客户端标识、上游端点三元组、总耗时、首字延迟、Token 四分量及是否转发成功）。**严禁记录任何正文、请求头或 URL。**

### 3.3 永久汇总账本（Rollup 历史）
* **路径**：`<log_dir>/vmr-stats-rollup.jsonl`，只增追加模式，永久保留。
* **聚合粒度**：按 `(hour × dims)` 空间聚合。`dims` 涵盖虚拟模型、协议、上游提供商、模型名、上游凭据标签、客户端标识及流式特征。
* **数据形态**：
  * 状态计数：`ok` / `error` / `canceled` 请求数；
  * Token 计数：四分量绝对和；
  * 耗时指标：存储 `sum` 与 `n` 结构（供读侧计算算术均值），不存储直方图。
* **Last-Wins 恢复机制**：写入采用标准文件追加。系统启动读取时，同键条目遵循“后者覆盖前者（Last-Wins）”，天然消除进程崩溃重滚产生的重复行。

### 3.4 内存状态拓扑
聚合器在内存中维护三块固定边界的有界状态：
1. **Rollup 内存映射**：仅加载近 7 天日历日窗口内的聚合数据，常数级内存上限（约数 MB）。跨日历日时自动剔除掉出窗口的数据。
2. **当前小时累加器**：保存当前未结账小时的高速聚合分桶。
3. **全局性能采样环（Global Ring）**：在内存中维护跨端点全局最近 300 条成功完成且已测 TTFT 的请求（`recent_requests`），记录时间戳、端点、流式标记、耗时、TTFT 及 Token 消耗元组，供读时计算全局 `overall` 分位数及前端控制台按 10/30/100/300 窗口动态切片。

## 4. 读写路径与归因规则

### 4.1 收尾钩子写路径
* 挂载于请求生命周期收尾点（响应已完全交付客户端之后）。
* 保证单次调用执行 O(1) 内存更新并追加写入 slim WAL。
* **失败与降级**：磁盘写失败仅降级局部统计精度，绝不影响客户端响应，内存计数照常更新。

### 4.2 事实归因三层规则
系统严格分层归因，防止失败调用污染服务质量指标：

| 事实层 | 归属维度 | 规则 |
| --- | --- | --- |
| **请求全貌** | 虚拟模型、协议、客户端标识、状态分类 | 全量请求（含 4xx、5xx、取消）均纳入对应维度的数量统计。 |
| **端点归因** | 上游提供商、模型、上游凭据标签 | 转发成功取生效端点，完全失败取最后一次尝试的端点，用于故障分析。 |
| **服务质量** | 首字延迟（TTFT）、Token 吞吐率、采样环准入 | **仅限成功转发且正常交付的请求**；失败尝试绝不污染性能分位池。 |

### 4.3 读路径性能保护
* 控制台高频轮询通过聚合快照短期缓存（如 3 秒 TTL）兜底，活跃轮询期避免重复全量折叠。
* In-flight 进行中状态与并发闸计数每次实时穿透读取，不经缓存。

## 5. 进行中状态跟踪（In-flight Registry）

### 5.1 职责划分与生命周期
In-flight 注册表归属于路由层核心运行时，独立于完成时账本：
* **注册时机**：请求完成协议预检与鉴权后、进入并发闸之前注册，初始状态为 `queued`（排队中）；
* **出站盖章**：向上游发起具体尝试时，状态转为 `running`，记录发出时间戳与端点目标；遇故障重试时覆盖更新；
* **流式跟踪**：响应数据流到达时，实时盖章首字节到达时刻，并在每个数据块到达时刷新最后活跃时间戳与累计输出 Token；
* **注销销毁**：请求退出主流程（无论成功、失败、取消或中途异常断开）时整条移除，瞬态无残留。

### 5.2 观测指标与反向设计
* **流卡死识别**：流式传输中持续刷新最后到达时间戳，运维端通过当前时间与末块到达差值直接判定上游是否静默挂起。
* **自适应短轮询**：控制台采用自适应轮询（活跃时 ~2s，空闲 15s），放弃易受网络抖动导致状态乱序重绘的 SSE 细粒度推送，依靠全量快照实现天然状态自愈。

## 6. 生命周期：滚动、恢复与清理

### 6.1 边界小时滚动（Lazy Rollover）
滚动采用边界惰性触发（跨小时首个请求驱动），无需常驻定时器：
1. 发现样本时间跨越当前小时边界时触发关账；
2. 顺序读完旧小时 slim 文件，按多维空间聚合生成 Rollup 条目；
3. 原子追加写入 Rollup 历史文件；
4. 确认物理落盘后，安全删除已归档的 slim 文件。

### 6.2 进程重启与故障自愈
进程启动时执行确定性初始化流程：
1. **获取目录锁**：尝试获取 `.vmr-stats.lock`，竞争失败则降级为纯内存运行，杜绝双写损坏；
2. **加载滑动窗口**：仅解析 Rollup 历史中近 7 天窗口内的记录构建内存表，超期历史保留在磁盘但不入内存；
3. **未决补偿滚动**：若存在历史未滚动的残留 slim 文件（如异常断电停机遗留），立即执行补聚合并归入 Rollup；
4. **重建当前状态**：读取当前小时 slim 文件，快速复原当前小时计数器并填充最近性能采样环；
5. **打开新 WAL**：以追加模式就绪当前小时的 slim 文件。

## 7. 遥测 API 契约与分位计算规范

`GET /stats` 在受鉴权保护下提供统一遥测 JSON 视图：

### 7.1 核心字段契约
* `concurrency`：全局并发闸状态（`limit` 上限、`in_flight` 正在执行数、`waiting` 门外排队数）。
* `inflight[]`：当前活跃请求明细列表（排队时长、执行时长、当前重试轮次、目标端点、末块活跃时间、预估 Token）。
* `hourly[]`：近期按小时时序聚合数据（支持通过 `?range=12h|24h|3d|7d` 调节时间跨度）。
* `by_provider_model[]`：按物理模型维度的累计指标（成功/失败/取消计数、Token 消耗、平均耗时与平均首字延迟）。
* `recent_requests[]`：内存中保留的最近 300 条跨端点全局不分组请求样本（记录精确时间戳、端点、流式标记、耗时、TTFT 及 Token 消耗），供控制台 Performance 视图按全局最新 10/30/100/300 条请求切片并聚合呈现。
* `overall`：基于全局 300 条请求计算的全局窗口块（分位数在数学上不可合并，由服务端在读时聚合）。
* `recent_errors[]`：内存中保留的最近 100 条失败/异常请求明细环（记录精确时间戳、端点、HTTP 状态码及错误分类 `core.ErrorClass`，不含正文）。

### 7.2 性能窗口块计算规范
每个窗口块包含：实际有效样本数 `n`、Token 消耗和、首字延迟分位（`ttft_p50` / `ttft_p90`）以及生成速率分位（`toks_p50` / `toks_p10`）。

* **生成速率口径（`toks`）**：
  * **流式请求**：剥除首字等待时间，仅计算实际生成阶段的纯吞吐：
    $$\text{toks} = \frac{\text{tokens.out}}{(\text{dur\_ms} - \text{ttft\_ms}) / 1000}$$
  * **非流式请求**：以整体耗时为分母：
    $$\text{toks} = \frac{\text{tokens.out}}{\text{dur\_ms} / 1000}$$
* **吞吐分位数方向（取 p10 而非 p90）**：
  * TTFT 属于耗时/成本型指标（越小越优），其劣质尾部表现为数值高位，故观测 **p90**；
  * Toks 属于产出/能力型指标（越大越优），其劣质尾部表现为数值低位，故观测 **p10**（保底输出吞吐）；采用 p90 会将极少数瞬时突发吞吐误判为服务基线。
* **物理防噪下限**：流式生成区间低于 50ms 的样本视为突发刷流（不具备统计参考价值），直接排除在吞吐样本池之外，避免亚毫秒极端除法扭曲统计分位。

## 8. 架构决策与不变量

| 决策项 | 设计选择 | 权衡依据 |
| --- | --- | --- |
| **凭据解耦** | `client_key_tag`（调用方）与 `key_label`（上游凭据）严格分列 | 明确区分“谁发起的请求”与“打了哪个上游物理账号”，解决多 Key 聚合分账痛点。 |
| **Token 净输入** | 统一采用 Fresh Input 记账（排除缓存复用） | 消除缓存膨胀带来的输入失真，与配额感知扣费基准严格对齐。 |
| **端点归因与质量解耦** | 端点记终态尝试，质量指标由 `Sample.Forwarded` 门控 | 失败调用需要记录端点用于故障分析，但只有成功交付的请求允许进入性能分位采样环。 |
| **WAL 生命周期** | 瞬态 slim 小时文件在 Rollup 后立即删除 | 确保磁盘使用严格有界，全量明细仍由独立生命周期的审计日志全权承载。 |
| **独立文件锁** | 自带 `.vmr-stats.lock`，竞争失败降级纯内存 | 与 audit 解耦，在 `-audit=false` 下监控仍完整可用；双实例竞争时避免写乱 Rollup 归档。 |
| **滚动驱动模型** | 跨小时首个请求惰性滚动，不设后台常驻 Ticker | 保持单机极简无状态，消除后台定时器带来的线程并发与停机同步开销。 |
| **内存时间窗口** | Rollup 仅在内存加载近 7 天日历日数据 | 控制台展示需求上限为 7 天；内存占用稳定恒定，历史更久分析由离线工具承载。 |
| **时区权威特例** | 日历日分桶采用宿主机 `time.Local` | `livestats` 为零依赖叶子包不可依赖 `fmtutil`；生产态与 `DisplayZone` 恒等，为文档化特例。 |
| **读缓存兜底** | `snapCacheTTL`（3s）缓存聚合段快照 | 吸收前端控制台 ~2s 自适应短轮询，避免活跃期重复全量 fold，In-flight 实时穿透不缓存。 |
| **全局分位聚合** | 服务端读时基于全局最新 300 条样本环计算 `overall` | 分位数在数学上不可加权平均合并，前端拿到分行数据无法自算全局 p50，必须由服务端计算。统一全局采样环兼顾服务端 overall 聚合与控制台多窗口动态分行聚合。 |
| **吞吐防噪下限** | 排除生成跨度低于 50ms（`minToksSpanMS`）的样本 | 尾部突发刷流（几毫秒交付）除法会产生上千 tok/s 的物理不可能数值，直接剔除避免分位失真。 |
| **失败排障空窗** | 内存专设 100 条 `recent_errors[]` 明细环 | 填补实时 in-flight 与小时级统计之间的排障断层，无需调阅底层原始审计日志。 |
| **长连接与轮询** | 控制台采用自适应短轮询，放弃 SSE 推送 | 进行中状态属于易变状态集，细粒度推送遇网络抖动易乱序重绘；全量快照天然幂等自愈。 |
